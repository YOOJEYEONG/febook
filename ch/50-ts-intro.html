50장. TypeScript를 쓰는 이유

이 챕터에서 배우는 것

  • TypeScript가 실제로 막아 주는 버그
  • TS Playground에서 설치 없이 바로 실습하는 법
  • 설치하고 실행하는 법, 그리고 2026년의 도구 지형(TypeScript 7, Node의 타입 제거)
  • tsconfig.json에서 꼭 알아야 할 옵션 4개
  • 타입 추론 — 대부분은 안 써도 됩니다
  • 타입은 실행 시점에 사라진다는 결정적 사실

읽는 데 약 30분 · 사전 지식: JavaScript 함수·객체(27·28장), npm(46장), 번들러(47장)

왜 필요한가

JavaScript는 관대한 언어입니다. 숫자 자리에 문자열을 넣어도, 인자를 하나 빠뜨려도 일단 실행해 보고 어떻게든 결과를 만들어 냅니다. 작은 스크립트에서는 이 관대함이 편하지만, 파일이 수백 개로 늘고 여러 사람이 함께 고치기 시작하면 이야기가 달라집니다. 잘못된 값이 조용히 흘러가다가 엉뚱한 곳에서 터지기 때문입니다. 아래 코드를 보세요.

JavaScript에서 실제로 일어나는 일 
function getDiscount(price, rate) {
  return price * (1 - rate);
}

getDiscount("10000", 0.1);   // "10000" * 0.9 = 9000  (우연히 동작)
getDiscount(10000);          // rate가 undefined → NaN
getDiscount(10000, "10%");   // NaN
// 어느 것도 오류를 내지 않습니다. 화면에 NaN이 뜬 뒤에야 압니다.

세 호출 모두 오류 메시지 하나 없이 지나갑니다. 문제는 결제 화면에 "NaN원"이 찍힌 뒤, 그것도 사용자가 신고한 뒤에야 드러납니다. 같은 함수를 TypeScript로 쓰면 매개변수 뒤에 : number를 붙여 "여기에는 숫자만 와야 한다"고 적어 둘 수 있습니다.

TypeScript 
function getDiscount(price: number, rate: number): number {
  return price * (1 - rate);
}

getDiscount("10000", 0.1);
// ❌ Argument of type 'string' is not assignable to parameter of type 'number'.
//    → 코드를 저장하는 순간, 편집기에서 빨간 줄로 표시됩니다

오류 메시지를 풀어 읽으면 "string 타입의 인자는 number 타입 매개변수에 넣을 수 없다"입니다. 핵심은 언제 알게 되느냐입니다. 사용자가 겪은 뒤가 아니라, 코드를 저장하는 순간 편집기가 알려 줍니다. 비유하자면 TypeScript는 워드 프로세서의 맞춤법 검사기와 같습니다. 글을 인쇄하기 전에 빨간 밑줄로 틀린 곳을 짚어 주지만, 글의 내용이 사실인지까지 확인해 주지는 않습니다. 이 비유는 이 챕터 뒷부분의 "타입은 사라진다"를 이해할 때도 그대로 쓰입니다.

얻는 것설명
실행 전에 오류 발견사용자가 겪기 전에 개발자가 먼저 봅니다
자동 완성객체의 속성 이름을 외울 필요가 없습니다. 이것만으로도 생산성이 크게 오릅니다
안전한 리팩터링속성 이름을 바꾸면 영향받는 모든 곳이 즉시 표시됩니다
문서 역할함수 시그니처만 봐도 무엇을 받고 무엇을 주는지 압니다
협업남이 만든 함수를 코드를 읽지 않고도 올바르게 쓸 수 있습니다

표에서 가장 과소평가되는 항목이 자동 완성입니다. 타입을 알고 있으면 편집기가 user.까지만 쳐도 name, email 같은 후보를 보여 줍니다. 오타로 존재하지 않는 속성을 읽는 실수(user.nmae)가 원천적으로 사라집니다. 처음 TypeScript를 쓰는 사람이 가장 먼저 체감하는 장점도 오류 검사보다 이쪽입니다.

⚠️ 자주 하는 오해 — TypeScript가 해 주지 않는 것

오해 — TypeScript를 쓰면 런타임 오류가 사라진다. 사실 — 타입은 빌드가 끝나면 완전히 사라집니다. 실행되는 것은 평범한 JavaScript입니다.
서버가 예상과 다른 데이터를 보내면? 타입은 아무것도 막지 못합니다. 사용자가 이상한 값을 입력하면? 마찬가지입니다.
TypeScript는 "내가 쓴 코드끼리 앞뒤가 맞는가"를 검사할 뿐, 바깥에서 들어오는 값은 여전히 런타임에 검증해야 합니다(54장).

설치 없이 바로 해 보기 — TS Playground

TypeScript를 배우는 가장 빠른 방법은 직접 틀려 보는 것입니다. 그런데 프로젝트를 만들고 설정 파일을 잡는 것부터 시작하면 정작 타입을 실험하기도 전에 지칩니다. 그래서 이 부(50~56장)의 예제는 모두 공식 온라인 실습장인 TS Playground(https://www.typescriptlang.org/play)에서 바로 돌려 볼 수 있게 안내합니다. 이 책의 실행기는 JavaScript만 실행하므로, TypeScript 예제는 Playground를 쓰세요. 설치도, 로그인도 필요 없습니다.

  1. 주소를 열면 왼쪽에 코드 편집기, 오른쪽에 결과 패널이 나옵니다. 편집기의 기본 코드는 지우고 시작하세요.
  2. 예제를 붙여 넣으면 문제가 있는 곳에 즉시 빨간 물결 밑줄이 생깁니다. 밑줄에 마우스를 올리면 오류 메시지가 보입니다.
  3. 변수 이름 위에 마우스를 올리면 TypeScript가 추론한 타입이 말풍선으로 나옵니다. 이 습관이 가장 좋은 학습법입니다.
  4. 오른쪽 패널의 .JS 탭에서는 타입이 지워진 변환 결과를, Errors 탭에서는 오류 목록을 볼 수 있습니다.
  5. Run 버튼을 누르면 변환된 JavaScript가 실행되고, console.log 결과가 Logs 탭에 찍힙니다.
  6. 상단의 TS Config 메뉴에서 strict 같은 옵션을 켜고 끌 수 있습니다. 기본값은 strict가 켜진 상태입니다.

앞의 getDiscount 예제를 Playground에 붙여 보세요. 빨간 줄을 확인한 다음, "10000"을 10000으로 고치면 밑줄이 사라지는 것을 볼 수 있습니다. 이후 챕터에서 ▶ Playground에 붙여 보세요라는 안내가 나오면 같은 방법으로 실험하면 됩니다. 예제에 일부러 넣어 둔 ❌ 줄은 실제로 오류가 나는 것이 정상입니다.

내 컴퓨터에서 시작하기

Playground로 감을 잡았다면 실제 프로젝트에서는 어떻게 쓰는지 봅시다. 대부분은 직접 설정할 필요가 없습니다. 47장에서 본 Vite가 TypeScript용 템플릿을 제공하기 때문입니다.

# 새 프로젝트라면 도구가 알아서 설정해 줍니다
npm create vite@latest my-app -- --template react-ts

# 기존 프로젝트에 추가
npm install -D typescript
npx tsc --init        # tsconfig.json 생성

# 타입 검사 실행 (파일은 만들지 않고 검사만)
npx tsc --noEmit

tsc는 TypeScript 컴파일러의 명령 이름입니다. --noEmit은 "결과 파일은 만들지 말고 검사만 하라"는 뜻입니다. 검사를 통과하면 아무것도 출력되지 않고, 문제가 있으면 파일 이름과 줄 번호가 담긴 오류 목록이 나옵니다.

🔧 요즘은 tsc가 변환을 하지 않습니다

실무에서는 Vite·esbuild·SWC가 타입을 그냥 떼어내고 JavaScript로 바꿉니다(47장). 훨씬 빠르기 때문입니다. tsc는 타입 검사 전용으로 쓰고, 실제 변환은 번들러가 맡는 구조가 표준입니다. 그래서 npx tsc --noEmit(검사만)을 CI에서 돌립니다.

2026년의 도구 지형

TypeScript 주변 도구는 최근 몇 년 사이 크게 바뀌었습니다. 2026년 11월 기준으로 알아 둘 변화는 두 가지입니다.

  • TypeScript 7 — 컴파일러가 Go로 다시 작성되었습니다. 2026년 7월 8일 정식 출시된 TypeScript 7.0은 컴파일러를 Go 언어로 옮긴 네이티브 버전입니다. 공식 블로그 발표 기준으로 전체 빌드가 대체로 8~12배 빨라졌습니다. 설치 방법은 그대로 npm install -D typescript이고, 명령도 그대로 tsc입니다. 또 2026년 3월의 TypeScript 6.0부터 strict가 기본값으로 켜졌고, 6.0에서 '곧 없어질 옵션'으로 예고된 것들(target: es5, baseUrl 등)은 7.0에서 오류가 됩니다. 다만 아직 프로그래밍용 API가 없어서 Vue·Svelte·Astro·MDX 같은 도구는 당분간 TypeScript 6.0을 함께 쓰도록 안내되어 있습니다.
  • Node.js가 .ts 파일을 바로 실행합니다. Node 22.18·23.6부터 node app.ts가 별도 설정 없이 동작하고, 24.12·25.2에서 안정 기능이 되었습니다. 원리는 타입 표기를 공백으로 지우고 실행하는 것(타입 제거, type stripping)입니다. 그래서 타입 검사는 하지 않으며, 지우기만으로 처리할 수 없는 문법(대표적으로 enum, 51장)은 실행되지 않습니다.

두 변화가 가리키는 방향은 같습니다. "변환은 타입을 지우기만 하는 빠른 도구가, 검사는 tsc가"라는 분업이 굳어지고 있습니다. 아래 tsconfig.json에 새로 들어간 옵션 두 개도 이 흐름에서 나왔습니다.

tsconfig.json — 꼭 알아야 할 옵션 4개

tsconfig.json은 TypeScript에게 "이 프로젝트를 어떤 규칙으로 검사할지" 알려 주는 설정 파일입니다. 옵션이 백 개가 넘지만, 처음에는 대부분 도구가 정해 준 값을 그대로 쓰면 됩니다. 직접 이해하고 있어야 하는 것은 아래 네 개뿐입니다.

{
  "compilerOptions": {
    "strict": true,                 // ① 엄격한 검사 — 가장 중요
    "noEmit": true,                 // ② 검사만, 변환은 번들러가 담당
    "verbatimModuleSyntax": true,   // ③ 타입 import는 import type 으로
    "erasableSyntaxOnly": true      // ④ 지우기만으로 없앨 수 있는 문법만 허용

    // …나머지는 Vite 템플릿이 정해 준 값 그대로 (아래 접은 표 참고)
  },
  "include": ["src"]
}
  1. strict — 여러 엄격한 검사를 한 번에 켭니다. 바로 아래 상자에서 자세히 봅니다. 꺼 두면 TypeScript의 이득 대부분이 사라집니다.
  2. noEmit — tsc가 JavaScript 파일을 만들지 않게 합니다. 변환은 Vite가 하므로 tsc는 검사만 하면 됩니다.
  3. verbatimModuleSyntax(TypeScript 5.0+) — 타입만 가져올 때는 import type { User } from "./types"처럼 type을 명시하게 합니다. 타입을 지우기만 하는 도구는 User가 타입인지 값인지 모르기 때문에, 이렇게 표시해 두어야 실행 시점에 "없는 값을 가져오려 한다"는 오류가 나지 않습니다.
  4. erasableSyntaxOnly(TypeScript 5.8+) — enum처럼 JavaScript 코드를 새로 만들어 내는 TypeScript 문법을 금지합니다. 그런 문법은 Node의 타입 제거나 일부 도구에서 동작하지 않기 때문입니다. 대신 쓸 방법은 51장에서 봅니다.

③·④는 2026년 기준 Vite의 react-ts 템플릿과 Node.js 공식 문서가 모두 권장하는 설정입니다. 템플릿으로 프로젝트를 만들었다면 이미 들어 있습니다.

⭐ "strict": true는 반드시 켜세요

이 옵션 하나가 여러 검사를 한꺼번에 켭니다. 그중 가장 중요한 것은 strictNullChecks입니다. "이 값이 null일 수도 있다"는 가능성을 끝까지 추적하는 검사입니다.

// strict: false — null 검사를 안 해도 통과합니다
function getLength(text: string) {
  return text.length;      // text가 null이면? 런타임 오류
}

// strict: true
function getLength(text: string | null) {
  return text.length;
  // ❌ 'text' is possibly 'null'.
  //    → null 검사를 강제합니다
}

string | null은 "문자열이거나 null"이라는 뜻입니다(51장의 유니온 타입). strict: false로 쓰는 TypeScript는 이득의 절반 이상을 버리는 것입니다. "Cannot read properties of null" — JavaScript에서 가장 흔한 런타임 오류를 막아 주는 것이 바로 이 옵션입니다. TypeScript 6.0부터는 아예 기본값이 되었습니다.

타입 추론 — 대부분은 안 써도 됩니다

"TypeScript를 쓰면 모든 변수에 타입을 붙여야 한다"고 생각하기 쉽지만 그렇지 않습니다. TypeScript는 초기값을 보고 타입을 스스로 알아냅니다. 이것을 타입 추론이라고 합니다. const age = 20을 보면 굳이 말하지 않아도 age가 숫자라는 것을 압니다.

// ❌ 불필요합니다. TypeScript가 이미 압니다
const name: string = "홍길동";
const age: number = 20;
const tags: string[] = ["a", "b"];

// ✅ 추론에 맡기세요
const name = "홍길동";        // string (정확히는 "홍길동" 리터럴 타입)
const age = 20;                // number
const tags = ["a", "b"];       // string[]

// ✅ 함수의 반환 타입도 대개 추론됩니다
function double(n: number) {
  return n * 2;                // number 로 추론
}

▶ Playground에 붙여 보세요. 위쪽 세 줄과 아래쪽 세 줄은 이름이 겹쳐 오류가 나므로 한쪽씩 붙이면 됩니다. 변수 이름에 마우스를 올리면 추론 결과가 보입니다. string[]은 "문자열의 배열"이라는 뜻입니다. 추론에 맡기면 코드가 짧아질 뿐 아니라, 초기값을 바꿀 때 타입 표기를 함께 고칠 필요도 없습니다.

✍️ 타입을 명시해야 하는 곳

  • 함수의 매개변수 — 추론할 근거가 없습니다. 반드시 써야 합니다.
  • 빈 배열을 객체 속성이나 상태의 초기값으로 둘 때 — 아래 예시처럼 요소 타입을 알 수 없으면 never[]가 됩니다.
  • 공개 API의 반환 타입 — 의도를 문서화하고, 실수로 반환 타입이 바뀌는 것을 막습니다.
  • 추론 결과가 너무 넓거나 좁을 때
빈 배열이 never[]가 되는 경우 
const cart = { items: [] };        // items: never[]
cart.items.push("사과");
// ❌ Argument of type 'string' is not assignable to parameter of type 'never'.

// ✅ 요소 타입을 알려 줍니다
const cart2: { items: string[] } = { items: [] };
cart2.items.push("사과");          // ✅

// 참고: 단독 변수는 다릅니다
const list = [];                   // strict에서는 '진화하는 배열'로 취급
list.push("사과");                 // 이후 list는 string[] 로 추적됩니다

never는 "어떤 값도 들어갈 수 없는 타입"입니다. 그래서 never[]는 무엇도 넣을 수 없는 배열입니다. 객체 속성 안의 빈 배열은 TypeScript가 요소 타입을 짐작할 단서가 없어서 이렇게 됩니다. React의 useState([])도 같은 이유로 never[]가 됩니다(56장). 반면 const list = []처럼 단독 변수는 이후의 push를 따라가며 타입을 넓혀 주지만, 의도를 분명히 하려면 이때도 const list: string[] = []로 적는 편이 읽기 좋습니다.

🤔 자주 하는 오해 — 타입을 많이 적을수록 안전하다

오해 — 모든 변수에 타입을 직접 적어야 TypeScript를 제대로 쓰는 것이다. 사실 — 추론된 타입과 직접 적은 타입은 안전성이 똑같습니다. 오히려 불필요한 표기는 초기값이 바뀔 때 함께 고쳐야 할 곳만 늘립니다. 매개변수처럼 추론할 근거가 없는 곳에만 적는 것이 실무의 기본입니다.

타입은 사라집니다

앞에서 TypeScript를 맞춤법 검사기에 비유했습니다. 맞춤법 검사기의 빨간 밑줄은 인쇄물에 찍히지 않습니다. TypeScript의 타입도 마찬가지로 빌드가 끝나면 흔적 없이 지워집니다. 브라우저가 실제로 받는 것은 타입 표기가 빠진 평범한 JavaScript입니다. Playground의 .JS 탭에서 직접 확인할 수 있습니다.

변환 전후 
// TypeScript
interface User { id: number; name: string; }
function greet(user: User): string {
  return `안녕하세요, ${user.name}님`;
}

// ↓ 빌드 결과 (JavaScript)
function greet(user) {
  return `안녕하세요, ${user.name}님`;
}
// interface는 흔적도 없이 사라집니다

interface는 객체의 모양(어떤 속성이 어떤 타입인지)에 이름을 붙이는 문법입니다(52장에서 자세히). 이 사실에서 중요한 결론이 하나 나옵니다. 실행 중에는 타입이 존재하지 않으므로, "이 값이 정말 User인가?"를 타입으로 물어볼 방법이 없습니다.

👻 그래서 이런 것이 불가능합니다

// ❌ 실행 시점에 타입은 존재하지 않습니다
if (value instanceof User) { }        // interface는 값이 아닙니다
if (typeof value === "User") { }      // typeof는 JS 타입만 알려 줍니다

// ✅ 실행 시점 검사는 직접 만들어야 합니다 (54장)
function isUser(value: unknown): value is User {
  return typeof value === "object" && value !== null && "id" in value;
}

마지막 함수의 반환 타입 자리에 있는 value is User는 처음 보는 문법입니다. "이 함수가 true를 돌려주면 그 뒤로는 value를 User로 봐도 된다"는 약속으로, 타입 가드라고 부릅니다. 지금은 "실행 중 검사는 평범한 JavaScript 조건문으로 직접 한다"는 것만 기억하고, 자세한 내용은 54장에서 봅니다.

서버 응답처럼 믿을 수 없는 데이터는 Zod 같은 검증 라이브러리로 런타임에 확인하는 것이 실무 표준입니다. "타입을 선언했으니 안전하다"는 착각이 실제 사고로 이어집니다.

any는 탈출구입니다

TypeScript에는 "이 값은 검사하지 마"라고 선언하는 특별한 타입 any가 있습니다. 급할 때는 편리하지만, 안전벨트를 풀고 운전하는 것과 같습니다. 평소에는 차이를 못 느끼다가 사고가 날 때 차이가 드러납니다.

let value: any = "문자열";
value.toFixed(2);        // 오류 없음. 실행하면 터집니다
value.아무거나.해도.됩니다;  // 전부 통과

// any를 쓰는 순간 그 값에 대한 모든 검사가 꺼집니다

더 큰 문제는 any가 퍼진다는 점입니다. any 값에서 꺼낸 속성도, 그것을 넘겨받은 변수도 any가 되어 검사가 꺼진 영역이 코드 곳곳으로 번집니다. 그래서 "타입을 모르겠다"는 상황에는 any 대신 unknown을 씁니다. unknown은 "무엇인지 모른다. 그러니 확인하기 전에는 쓰지 마라"는 뜻입니다.

anyunknown
아무 값이나 담기가능가능
바로 사용하기가능 (위험)불가 — 먼저 타입을 확인해야 함
권장피하세요이쪽을 쓰세요
 
function handle(value: unknown) {
  // value.length;          ❌ 확인 전에는 아무것도 못 합니다
  if (typeof value === "string") {
    value.length;           // ✅ 여기서는 string 임이 확실합니다
  }
}

▶ Playground에 붙여 보세요. 주석 처리된 value.length의 주석을 풀면 오류가 나고, if 안쪽에서는 같은 코드가 통과합니다. 조건문을 통과하는 순간 타입이 좁아지는 이 동작이 54장의 주제입니다.

🛠️ 현장 노트 — TypeScript 도입 순서

  1. 새 파일부터 적용합니다. 기존 코드를 한 번에 바꾸려 하지 마세요.
  2. strict: true로 시작하세요. 나중에 켜면 오류가 수천 개 나옵니다.
  3. 막힐 때 any를 쓰되 // TODO: 타입 정리 주석을 남기세요.
  4. 편집기에서 타입 위에 마우스를 올려 추론 결과를 확인하는 습관을 들이세요. 가장 좋은 학습법입니다.

처음에는 답답합니다. "그냥 되는데 왜 오류가 나지" 싶은 순간이 계속 옵니다. 하지만 그 오류들은 대부분 실제로 위험한 코드입니다. 2~3주만 버티면 타입 없는 코드가 불안해집니다.

📌 요약

  • TypeScript는 실행 전에 타입 오류를 잡고, 자동 완성과 안전한 리팩터링을 제공한다.
  • 실습은 TS Playground에서 한다. 마우스를 올려 추론 결과를 확인하는 습관이 핵심이다.
  • 타입은 빌드 후 완전히 사라진다. 런타임 오류를 없애 주지 않는다.
  • 외부에서 들어오는 데이터는 런타임 검증이 따로 필요하다.
  • "strict": true는 필수. 특히 strictNullChecks가 핵심 가치다. TypeScript 6.0부터는 기본값이다.
  • 실무에서는 tsc는 검사, 변환은 번들러가 담당한다. verbatimModuleSyntax·erasableSyntaxOnly가 이 분업을 돕는다.
  • 대부분은 추론에 맡긴다. 매개변수와, 단서가 없는 빈 배열은 명시한다.
  • any 대신 unknown을 쓴다.
