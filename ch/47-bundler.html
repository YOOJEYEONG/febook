번들러가 푸는 문제

문제번들러가 하는 일
파일이 너무 많다수백 개의 모듈을 몇 개의 파일로 묶습니다
브라우저가 node_modules를 모른다import "react"를 실제 경로로 바꿔 줍니다
최신 문법을 못 쓴다구형 브라우저용 문법으로 변환합니다
JS가 아닌 것도 import 하고 싶다CSS·이미지·SVG를 다룰 수 있게 합니다
안 쓰는 코드가 들어간다제거합니다 (트리 셰이킹)
파일이 크다공백·주석 제거, 이름 축약 (압축)

🌐 브라우저는 import "react"를 이해하지 못합니다

import React from "react";              // ❌ 브라우저: 어디 있는 파일인지 모름
import React from "/node_modules/react/index.js";   // ✅ 이렇게 바꿔 줘야 함

34장에서 확장자를 생략할 수 없다고 한 이유가 이것입니다. 번들러가 "react" 같은 패키지 이름(bare specifier)을 실제 경로로 해석해 줍니다.

⚡ Vite가 빠른 이유

  • 개발 중에는 번들하지 않습니다. 브라우저의 네이티브 ES 모듈(34장)을 그대로 씁니다. 파일을 고치면 그 파일 하나만 다시 보내면 됩니다. 프로젝트가 커져도 시작 속도가 거의 그대로입니다.
  • 변환은 Go로 만든 esbuild가 담당해 JavaScript로 만든 도구보다 훨씬 빠릅니다.
  • 배포용 빌드에서만 실제로 번들합니다. (Rollup 계열 엔진 사용)

webpack은 개발 중에도 전체를 번들해서 시작이 느렸습니다. 이것이 체감 차이의 핵심입니다.

트랜스파일과 폴리필 — 다른 것입니다

트랜스파일 (transpile)폴리필 (polyfill)
대상문법기능(API)
예화살표 함수 → function
옵셔널 체이닝 → && 체인		Array.prototype.at
Promise, fetch
방법코드를 다시 씁니다없는 기능을 직접 구현해 채워 넣습니다
용량거의 안 늘어남늘어납니다
트랜스파일 예 
// 원본
const add = (a, b) => a + b;
const name = user?.profile?.name;

// 구형 브라우저용으로 변환된 결과
var add = function (a, b) { return a + b; };
var name = user === null || user === void 0 ? void 0 : ...;

🎯 어디까지 지원할지 정해야 합니다

// package.json 또는 .browserslistrc
{
  "browserslist": [">0.5%", "last 2 versions", "not dead"]
}

지원 범위를 넓게 잡을수록 변환과 폴리필이 늘어 파일이 커지고 느려집니다. 실제 사용자 통계를 보고 정하세요. 아무도 쓰지 않는 브라우저를 위해 모든 사용자에게 무거운 코드를 보내는 것은 손해입니다. Internet Explorer는 2022년에 지원이 종료되었으므로 더 이상 대상이 아닙니다.

최적화 기법

트리 셰이킹

// utils.js — 함수가 50개 있다고 합시다
export function formatDate() { }
export function formatPrice() { }
// … 48개 더

// main.js
import { formatPrice } from "./utils.js";
// → 번들에는 formatPrice 만 포함됩니다. 나머지 49개는 제거

34장에서 말한 "ESM만 트리 셰이킹이 가능한" 이유가 이것입니다. import는 정적으로 분석할 수 있어 번들러가 실행 전에 무엇이 쓰이는지 알 수 있습니다.

🌳 트리 셰이킹이 안 되는 경우

  • CommonJS 패키지 — require는 실행 시점에 결정되어 분석할 수 없습니다.
  • 부수 효과가 있는 모듈 — 불러오기만 해도 무언가 실행되는 코드는 지울 수 없습니다. (package.json의 "sideEffects": false로 "안전하다"고 알릴 수 있습니다.)
  • 전체를 가져오는 import — import * as _ from "lodash"보다 import debounce from "lodash/debounce"가 훨씬 가볍습니다.

코드 분할

// 34장의 동적 import가 분할 지점이 됩니다
const { Chart } = await import("./chart.js");

// React에서
const AdminPage = lazy(() => import("./AdminPage"));

번들러는 이 지점을 인식해 별도 파일로 분리하고, 그 코드가 실제로 필요할 때 내려받습니다. 관리자 페이지 코드를 일반 사용자에게 보내지 않는 것만으로 초기 로딩이 크게 줄어듭니다.

파일 이름 해시

main.a3f19c2b.js
style.7e2d81f0.css

파일 내용이 바뀌면 이름도 바뀝니다. 그러면 브라우저와 CDN이 "새 파일"로 인식해 반드시 새로 받습니다(3장 캐시 문제). 반대로 내용이 그대로면 이름도 그대로라 캐시를 계속 씁니다. "배포했는데 옛 화면이 보여요"를 구조적으로 해결하는 방법입니다.

소스맵

압축된 코드는 사람이 읽을 수 없습니다. 소스맵은 "압축된 코드의 이 위치는 원본의 몇 번째 줄"이라는 대응표입니다. 덕분에 개발자 도구에서 원본 코드로 디버깅할 수 있습니다.

🔍 운영 환경의 소스맵

소스맵을 함께 배포하면 누구나 원본 코드를 볼 수 있습니다. 프론트엔드 코드는 어차피 공개되지만(1장), 주석과 변수명까지 그대로 노출되는 것이 부담일 수 있습니다. 실무에서는 소스맵을 생성하되 공개 배포에는 포함하지 않고, 오류 추적 서비스에만 올리는 방식을 자주 씁니다(79장).

환경 변수

.env — .gitignore에 반드시 추가 
VITE_API_URL=https://api.example.com
VITE_APP_NAME=내 서비스

# 접두사(VITE_)가 없는 것은 클라이언트 코드에 주입되지 않습니다
DATABASE_PASSWORD=secret
// Vite
console.log(import.meta.env.VITE_API_URL);

// Next.js는 NEXT_PUBLIC_ 접두사를 씁니다
console.log(process.env.NEXT_PUBLIC_API_URL);

🔓 프론트엔드 환경 변수는 비밀이 아닙니다

빌드 시점에 값이 코드에 그대로 박힙니다. 번들 파일을 열면 누구나 볼 수 있습니다. 1장의 원칙 그대로입니다.
VITE_·NEXT_PUBLIC_ 같은 접두사 규칙이 있는 이유가 바로 이것입니다. "이 값은 공개된다는 것을 알고 넣는다"는 명시적 선언입니다. 비밀 키는 서버에만 두고, 프론트엔드는 서버를 경유해 호출해야 합니다(37·78장).

번들 분석

npm run build         # 결과 파일과 크기가 출력됩니다
npx vite-bundle-visualizer     # 무엇이 용량을 차지하는지 시각화

🛠️ 현장 노트 — 번들이 클 때 확인 순서

  1. 분석 도구로 먼저 봅니다. 추측하지 마세요. 대개 특정 패키지 하나가 범인입니다.
  2. 전체를 가져오는 import를 찾습니다. 필요한 함수만 가져오세요.
  3. 첫 화면에 필요 없는 것을 동적 import로 분리합니다.
  4. 중복 설치된 패키지를 확인합니다. 같은 라이브러리의 다른 버전이 두 벌 들어가 있는 경우가 있습니다(npm ls).
  5. browserslist를 좁힙니다. 폴리필이 줄어듭니다.

🚀 처음 시작할 때

npm create vite@latest my-app
cd my-app
npm install
npm run dev

설정 파일을 직접 만들 필요가 없습니다. 번들러 설정을 깊이 파는 것은 나중 일이고, 대부분의 프로젝트는 기본값으로 충분합니다.

📌 요약

  • 번들러는 모듈 해석·변환·최적화를 담당한다. 브라우저는 import "react"를 모른다.
  • 트랜스파일은 문법 변환, 폴리필은 없는 기능 채우기. 폴리필은 용량을 늘린다.
  • 트리 셰이킹은 ESM에서만 제대로 동작한다. 전체 import를 피한다.
  • 코드 분할은 동적 import()가 지점이 된다.
  • 파일 이름 해시가 캐시 문제를 구조적으로 해결한다.
  • 소스맵으로 압축 코드를 원본으로 디버깅한다. 공개 배포 여부는 신중히.
  • 프론트엔드 환경 변수는 비밀이 아니다. 빌드 시 코드에 박힌다.
  • Vite는 개발 중 번들하지 않고 네이티브 ESM을 써서 빠르다.
