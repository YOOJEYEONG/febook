Git이 푸는 문제

Git 없이 일하면 
최종.psd
최종_수정.psd
최종_진짜최종.psd
최종_진짜최종_이번엔진짜.psd
최종_v2_김대리수정_0415.psd

Git은 버전 관리 시스템입니다. 이런 일을 해 줍니다.

  • 변경 이력 — 누가, 언제, 무엇을, 왜 바꿨는지 전부 기록
  • 되돌리기 — 어느 시점으로든 복구
  • 동시 작업 — 여러 명이 같은 파일을 각자 고치고 나중에 합치기
  • 실험 — 본 코드를 건드리지 않고 브랜치에서 시도

☁️ Git ≠ GitHub

  • Git — 내 컴퓨터에서 돌아가는 프로그램. 인터넷 없이도 완전히 동작합니다.
  • GitHub — Git 저장소를 인터넷에 올려 공유하는 서비스. GitLab, Bitbucket도 같은 역할입니다.

"Git을 배운다"는 것은 프로그램 사용법을, "GitHub을 쓴다"는 것은 협업 플랫폼을 익히는 일입니다.

3단계 영역 — Git 이해의 핵심

파일이 거치는 세 곳 
┌──────────────┐  git add   ┌──────────────┐ git commit ┌──────────────┐
│  작업 폴더    │ ─────────▶ │  스테이징     │ ─────────▶ │   저장소      │
│ Working Dir  │            │ Staging Area │            │ Repository   │
│ 지금 편집 중  │            │ 다음 커밋에   │            │ 영구 기록     │
│              │            │ 넣을 것들     │            │              │
└──────────────┘            └──────────────┘            └──────┬───────┘
                                                                │ git push
                                                                ▼
                                                        ┌──────────────┐
                                                        │  원격 저장소   │
                                                        │   (GitHub)   │
                                                        └──────────────┘

📦 스테이징은 왜 있나

"바꾼 것 전부"가 아니라 "이번 커밋에 넣을 것만" 고르기 위해서입니다. 로그인 기능과 오타 수정을 같이 작업했다면, 두 개의 커밋으로 나눌 수 있습니다. 나중에 이력을 볼 때 훨씬 깔끔하고, 문제가 생겼을 때 한쪽만 되돌리기도 쉽습니다.
택배 상자에 물건을 넣어 두는 단계(스테이징)와 봉인해서 보내는 단계(커밋)라고 생각하면 됩니다.

기본 흐름

# 최초 1회 설정 (커밋에 기록될 이름과 메일)
git config --global user.name "홍길동"
git config --global user.email "hong@example.com"

# 새 저장소 시작
git init

# 또는 기존 저장소 복제
git clone https://github.com/user/repo.git

# 매일 쓰는 흐름
git status                     # ← 가장 자주 쓰는 명령. 항상 먼저 확인
git add index.html             # 특정 파일만 스테이징
git add .                      # 변경된 것 전부
git commit -m "로그인 폼 추가"
git push                       # 원격으로 올리기
git pull                       # 원격의 변경사항 받아오기

# 이력 보기
git log --oneline --graph      # 한 줄씩, 그래프로
git diff                       # 아직 스테이징 안 한 변경
git diff --staged              # 스테이징된 변경

처음이라면 이 명령들을 읽기만 하고, 실제로 따라 하는 것은 아래 첫 저장소를 GitHub에 올리기 실습에서 하세요. Git 설치와 GitHub 계정이 먼저 필요합니다.

👀 git status를 습관처럼 치세요

Git 초보자의 문제 대부분은 "지금 어떤 상태인지 모르는 것"에서 옵니다. git status는 현재 브랜치, 스테이징된 파일, 안 된 파일, 원격과의 차이를 친절한 문장으로 전부 알려 줍니다. 무엇을 하기 전에도, 하고 나서도 확인하세요.

커밋 메시지 쓰기

❌ 나쁜 예
  "수정"
  "asdf"
  "버그 픽스"
  "최종"

✅ 좋은 예
  "로그인 실패 시 에러 메시지 표시"
  "상품 목록 무한 스크롤 구현"
  "결제 금액 계산에서 소수점 오차 수정"

많은 팀이 Conventional Commits라는 규칙을 씁니다.

feat: 장바구니 담기 기능 추가
fix: 모바일에서 헤더가 겹치는 문제 수정
docs: README에 설치 방법 추가
style: 코드 포맷팅 (동작 변화 없음)
refactor: 주문 계산 로직을 별도 모듈로 분리
test: 결제 계산 테스트 추가
chore: 의존성 업데이트

✍️ 좋은 커밋의 기준

  • "무엇을"보다 "왜"를 씁니다. 무엇을 바꿨는지는 코드에 이미 있습니다.
  • 하나의 커밋은 하나의 논리적 변경. 나중에 되돌릴 때 결정적입니다.
  • 메시지는 "이 커밋을 적용하면 ~하게 된다"는 형태로 쓰면 자연스럽습니다.

실습 — 첫 저장소를 GitHub에 올리기

6장에서 만든 my-first-site 폴더를 GitHub에 올려 봅시다. 처음부터 끝까지 한 번 해 보면 위의 명령들이 무엇을 하는지 손에 잡힙니다. 명령은 VS Code의 터미널(Ctrl+`, 44장)에 입력합니다.

1단계 — Git 설치

  • Windows — git-scm.com에서 Git for Windows를 받아 설치합니다. (또는 PowerShell에서 winget install --id Git.Git -e --source winget.) 설치 중 질문은 대부분 기본값으로 두되 두 군데만 바꾸면 좋습니다. "Choosing the default editor used by Git"에서 Use Visual Studio Code as Git's default editor, "Adjusting the name of the initial branch"에서 Override the default branch name을 고르고 main. Git Bash(44장)와 로그인 도우미(Git Credential Manager)가 함께 설치됩니다.
  • macOS — 터미널에 git --version을 입력합니다. Git이 없으면 "명령어 라인 개발자 도구를 설치하겠습니까?" 창이 뜨는데, 설치를 누르면 Apple의 Xcode Command Line Tools와 함께 Git이 설치됩니다. (창이 안 뜨면 xcode-select --install.) 몇 분 걸립니다.

✅ 체크포인트 — 터미널(Windows는 설치 후 새로 연 터미널)에서 git --version을 입력하면 git version 2.xx.x처럼 버전이 나옵니다.

2단계 — 최초 1회 설정

git config --global user.name "홍길동"
git config --global user.email "hong@example.com"   # GitHub 가입 메일과 같게
git config --global init.defaultBranch main          # 새 저장소의 기본 브랜치 이름
git config --global core.editor "code --wait"        # 커밋 메시지를 VS Code로 쓰기

git config --global --list                           # 확인

core.editor 설정은 터미널에서 code 명령이 동작할 때만 의미가 있습니다. Windows는 VS Code 설치 때 자동으로 됩니다. macOS는 VS Code에서 Cmd+Shift+P → Shell Command: Install 'code' command in PATH를 한 번 실행하세요.

🪤 -m 없이 git commit을 쳤더니 이상한 화면이 떴다면

메시지를 쓰라고 편집기가 열린 것입니다. 편집기를 따로 설정하지 않았다면 대개 Vim이 열리는데, 글자가 입력되지 않고 빠져나가는 방법도 보이지 않아 많은 사람이 당황합니다.

  1. i를 눌러 입력 모드로 들어가 메시지를 씁니다.
  2. Esc를 누른 뒤 :wq를 치고 Enter — 저장하고 종료(커밋 완료).
  3. 커밋을 취소하고 나가고 싶다면 Esc 후 :q! Enter.

위의 core.editor "code --wait"를 설정하면 VS Code 탭이 열리고, 메시지를 쓰고 저장한 뒤 탭을 닫으면 커밋이 완료됩니다. 충돌 해결 뒤의 git commit(아래)처럼 -m 없이 쓰는 경우가 실무에서 꽤 있습니다.

3단계 — GitHub 가입과 빈 저장소 만들기

  1. github.com/signup에서 메일·비밀번호·사용자 이름(Username)을 정하고 가입합니다. 메일로 온 확인 코드를 입력하면 끝입니다. 사용자 이름은 저장소 주소에 들어가므로 공개되어도 괜찮은 이름으로 짓습니다.
  2. 오른쪽 위 + → New repository를 누릅니다.
  3. Repository name에 my-first-site를 적고, Public 또는 Private을 고릅니다.
  4. "Add a README file", .gitignore, license 항목은 모두 체크하지 않은 채로 Create repository를 누릅니다. 빈 저장소여야 내 컴퓨터의 이력을 그대로 올릴 수 있습니다.

✅ 체크포인트 — "Quick setup"이라는 안내와 함께 https://github.com/사용자이름/my-first-site.git 형태의 주소가 보입니다. 이 주소를 복사해 둡니다.

📧 메일 주소를 공개하고 싶지 않다면

커밋에 적은 메일은 공개 저장소에서 누구나 볼 수 있습니다. GitHub Settings → Emails에서 "Keep my email addresses private"을 켜면 …@users.noreply.github.com 형태의 대체 주소가 표시됩니다. 2단계의 user.email에 그 주소를 쓰면 됩니다.

4단계 — 내 컴퓨터에서 첫 커밋

cd ~/Desktop/my-first-site      # 6장에서 만든 폴더로 (PowerShell도 같은 표기가 통합니다)
git init                         # 이 폴더를 Git 저장소로 만들기
git status                       # index.html 이 빨간색 "Untracked" 로 보임
git add .
git status                       # 이제 초록색 "Changes to be committed"
git commit -m "첫 페이지 추가"
git log --oneline                # 방금 만든 커밋 확인

Windows에서 바탕화면이 OneDrive와 동기화되어 있으면 경로가 ~/OneDrive/Desktop(또는 ~/OneDrive/바탕 화면)일 수 있습니다. 가장 확실한 방법은 VS Code로 그 폴더를 연 상태에서 터미널을 여는 것입니다. 터미널이 이미 그 폴더에서 시작합니다(pwd로 확인).

✅ 체크포인트 — git log --oneline이 a1b2c3d (HEAD -> main) 첫 페이지 추가 같은 한 줄을 보여 줍니다. 괄호 안이 master라면 2단계의 init.defaultBranch 설정 전에 git init을 한 것이니 git branch -M main으로 이름을 바꿉니다. git init을 하면 폴더 안에 숨김 폴더 .git이 생깁니다. 이력 전체가 여기 들어 있으니 지우지 마세요.

5단계 — 원격 저장소 연결하고 push

# 3단계에서 복사한 주소를 "origin"이라는 이름으로 등록
git remote add origin https://github.com/사용자이름/my-first-site.git
git remote -v                    # 등록 확인

# 처음 한 번은 -u 로 "내 main = origin의 main"을 연결
git push -u origin main
# 이후로는 그냥 git push

git clone으로 받은 저장소는 origin이 자동으로 등록되어 있지만, git init으로 만든 저장소는 직접 remote add를 해야 어디로 올릴지 압니다.

6단계 — 로그인(인증): 비밀번호로는 안 됩니다

첫 push 때 GitHub이 "당신이 누구인지" 확인합니다. 이때 GitHub 계정 비밀번호를 넣으면 거절됩니다. GitHub은 2021년부터 Git 명령의 비밀번호 인증을 막았기 때문입니다. 아래 방법 중 하나를 씁니다.

방법어떻게추천 대상
브라우저 로그인Git for Windows에 포함된 Git Credential Manager가 첫 push 때 브라우저 로그인 창을 띄웁니다. 승인하면 끝이고, 다음부터는 묻지 않습니다Windows 기본
GitHub CLIGitHub 공식 터미널 도구 gh를 설치(macOS brew install gh, Windows winget install --id GitHub.cli)한 뒤 gh auth login. 질문에 GitHub.com → HTTPS → "Authenticate Git with your GitHub credentials?"에 Yes → Login with a web browser를 고르고, 화면의 코드를 브라우저에 입력합니다macOS에 가장 쉬움
Personal Access TokenGitHub Settings → Developer settings → Personal access tokens에서 토큰을 만들고, push 때 비밀번호 칸에 토큰을 붙여 넣습니다. Fine-grained token이라면 이 저장소에 Contents: Read and write 권한을 줍니다도구를 더 설치할 수 없을 때
SSH 키내 컴퓨터에서 키 쌍을 만들어 공개 키를 GitHub에 등록합니다. 주소가 git@github.com:… 형태가 됩니다익숙해진 뒤 (GitHub 안내)

🔑 토큰은 비밀번호와 같습니다

터미널에서 비밀번호나 토큰을 붙여 넣을 때는 화면에 아무것도 표시되지 않는 것이 정상입니다. 붙여 넣고 Enter를 누르세요. 토큰은 만들 때 한 번만 보여 주므로 안전한 곳에 보관하고, 코드나 채팅에 붙여 넣지 마세요. 유출되었다면 즉시 GitHub에서 삭제(revoke)합니다.

✅ 체크포인트 — 터미널에 * [new branch] main -> main과 branch 'main' set up to track 'origin/main'이 나오고, GitHub 저장소 페이지를 새로고침하면 index.html이 보입니다. 이제 파일을 고칠 때마다 git add . → git commit -m "…" → git push 세 단계로 GitHub에 반영됩니다.

오류 메시지원인과 해결
Author identity unknown2단계의 user.name·user.email을 설정하지 않았습니다
src refspec main does not match any커밋이 하나도 없거나 브랜치 이름이 master입니다. git log로 커밋을 확인하고 git branch -M main
remote origin already exists이미 등록했습니다. 주소를 바꾸려면 git remote set-url origin 새주소
Support for password authentication was removed비밀번호를 넣었습니다. 위 6단계의 방법 중 하나로 인증합니다
Updates were rejected … (fetch first)GitHub 쪽에 내가 없는 커밋(예: README 체크)이 있습니다. git pull --rebase origin main 후 다시 git push
Repository not found주소의 사용자 이름·저장소 이름 오타이거나, 다른 계정으로 로그인되어 있습니다

브랜치

브랜치는 독립된 작업 공간입니다. 본 코드를 건드리지 않고 새 기능을 만들다가, 완성되면 합칩니다.

git branch                      # 브랜치 목록
git switch -c feature/login     # 새 브랜치를 만들고 이동 (구: git checkout -b)
git switch main                 # 이동 (구: git checkout)

# main으로 돌아와 합치기
git switch main
git merge feature/login
git branch -d feature/login     # 다 쓴 브랜치 삭제
브랜치 이름 관례 
main            운영에 배포되는 안정 버전
develop         개발 통합 (팀에 따라 있기도, 없기도)
feature/login   새 기능
fix/header-bug  버그 수정
hotfix/payment  운영 긴급 수정

🚫 main에 직접 커밋하지 마세요

실무에서는 거의 모든 팀이 브랜치를 만들어 작업하고 PR로 합칩니다. main에 바로 커밋하면 리뷰를 건너뛰게 되고, 문제가 생겼을 때 되돌리기도 어렵습니다. 많은 저장소가 아예 main 직접 푸시를 차단해 두었습니다.

충돌 해결

두 사람이 같은 파일의 같은 줄을 다르게 고치면 Git은 무엇이 맞는지 알 수 없어 충돌(conflict)을 알리고 사람에게 판단을 넘깁니다.

충돌이 난 파일의 모습 
<<<<<<< HEAD
const title = "우리 서비스";        ← 지금 내 브랜치의 내용
=======
const title = "환영합니다";          ← 합치려는 브랜치의 내용
>>>>>>> feature/login
해결 절차 — 3번의 git commit은 -m 없이 쓰면 편집기가 열립니다(위 Vim 상자)

🤝 충돌은 사고가 아닙니다

충돌은 Git이 "두 사람의 의도가 다른데 내가 함부로 정할 수 없다"고 정직하게 알려 주는 것입니다. 오히려 덮어쓰기를 막아 주는 안전장치입니다.
줄이는 방법: 브랜치를 오래 두지 말고 자주 합치기, git pull을 자주 하기, 한 파일을 여러 명이 동시에 크게 고치지 않도록 미리 나누기.

되돌리기

HEAD와 커밋 해시 읽기

되돌리기 명령에는 HEAD~1, a1b2c3d 같은 이름이 나옵니다. 먼저 이것부터 읽을 줄 알아야 합니다.

git log --oneline 의 출력 
e4f5a6b (HEAD -> main, origin/main) 버튼 색 수정     ← HEAD     (지금)
c3d4e5f 상품 목록 추가                               ← HEAD~1   (하나 전)
a1b2c3d 첫 페이지 추가                               ← HEAD~2   (둘 전)
  • 커밋 해시 — 맨 앞의 e4f5a6b는 커밋마다 붙는 고유 번호입니다. 실제로는 40자리지만 앞 7자리 정도만 써도 Git이 알아듣습니다. 복사해서 git show e4f5a6b처럼 씁니다.
  • HEAD — "지금 내가 서 있는 커밋"을 가리키는 표시입니다. 보통은 현재 브랜치의 가장 최근 커밋입니다. HEAD -> main은 "지금 main 브랜치에 있고, 그 끝이 이 커밋"이라는 뜻입니다.
  • HEAD~1 — HEAD에서 한 칸 전 커밋. HEAD~2는 두 칸 전입니다. 해시를 몰라도 상대 위치로 가리킬 수 있습니다.
  • origin/main — 마지막으로 확인했을 때 GitHub의 main이 있던 위치입니다. HEAD와 같은 줄에 있으면 push할 것이 없다는 뜻입니다.
상황명령
수정을 취소하고 싶다 (아직 add 안 함)git restore 파일
스테이징만 취소git restore --staged 파일
방금 커밋 메시지 수정git commit --amend
마지막 커밋을 취소하되 변경은 남기기git reset --soft HEAD~1
마지막 커밋을 변경까지 완전히 버리기git reset --hard HEAD~1 ⚠️
이미 공유한 커밋을 되돌리기git revert 커밋해시
지금 작업을 잠시 치워 두기git stash / 되돌리기 git stash pop

⚠️ reset과 revert의 차이

  • reset — 이력 자체를 없던 일로 만듭니다. 아직 공유하지 않은 커밋에만 쓰세요.
  • revert — "취소하는 새 커밋"을 추가합니다. 이력이 남아 안전합니다.

이미 push한 커밋에 reset을 하고 강제 푸시하면 동료들의 저장소가 깨집니다. 공유된 이력은 revert로 되돌리는 것이 원칙입니다.

🛟 커밋한 것은 웬만하면 잃지 않습니다

git reflog     # 브랜치 이동·리셋을 포함한 모든 이동 기록
git switch -c 복구용 <해시>   # 사라진 것처럼 보이는 커밋으로 되돌아가기

reset --hard로 날린 커밋도 일정 기간은 reflog에 남아 있습니다. "망했다" 싶을 때 가장 먼저 쳐 볼 명령어입니다. 다만 커밋하지 않은 변경은 정말로 사라지니, 애매하면 일단 커밋하세요.

🔐 비밀 키를 커밋하면 지워도 남습니다

Git은 모든 이력을 보존합니다. API 키를 커밋한 뒤 다음 커밋에서 지워도 이전 커밋에는 그대로 남아 있고, 누구나 볼 수 있습니다. 공개 저장소라면 봇이 몇 분 만에 찾아냅니다.
대응: 파일을 지우는 것으로는 부족합니다. 그 키를 즉시 폐기하고 새로 발급받아야 합니다. 예방책은 처음부터 .gitignore에 .env를 넣는 것입니다.

🛠️ 현장 노트 — 신입이 알아 두면 좋은 것

  1. 모든 명령을 외울 필요 없습니다. status, add, commit, push, pull, switch, merge 7개면 시작할 수 있습니다.
  2. GUI 도구를 써도 됩니다. VS Code의 Source Control 패널, GitHub Desktop, Fork 등. 다만 내부에서 무슨 일이 일어나는지는 알아야 문제가 생겼을 때 해결할 수 있습니다.
  3. PR은 작게. 500줄짜리 PR은 아무도 제대로 리뷰하지 못합니다.
  4. 커밋 전에 git diff로 자기 코드를 한 번 읽으세요. 디버깅용 console.log가 딸려 들어가는 것을 여기서 잡습니다.

📌 요약

  • Git은 프로그램, GitHub은 공유 서비스다.
  • git init으로 만든 저장소는 git remote add origin 주소로 연결한 뒤 git push -u origin main.
  • GitHub push에는 비밀번호가 아니라 브라우저 로그인·gh auth login·토큰·SSH 중 하나로 인증한다.
  • HEAD는 지금 있는 커밋, HEAD~1은 하나 전, 해시는 커밋의 고유 번호다.
  • 파일은 작업 폴더 → 스테이징 → 저장소 → 원격 순으로 이동한다.
  • git status를 습관적으로 확인한다.
  • 커밋은 하나의 논리적 변경, 메시지에는 왜를 쓴다.
  • main에 직접 커밋하지 않고 브랜치 + PR로 일한다.
  • 충돌은 사고가 아니라 안전장치다. 표시를 지우고 최종 내용만 남긴 뒤 add·commit.
  • 공유한 커밋은 revert, 공유 전이면 reset.
  • .env는 반드시 .gitignore에. 커밋된 키는 폐기하고 재발급해야 한다.
