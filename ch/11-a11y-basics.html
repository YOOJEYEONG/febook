11장. 웹 접근성 기초

이 챕터에서 배우는 것

  • 접근성이 소수를 위한 배려가 아닌 이유
  • 스크린 리더가 화면을 읽는 방식
  • 키보드만으로 쓸 수 있게 만드는 법
  • 명도 대비 기준과 확인 방법
  • ARIA의 첫 번째 규칙 — ARIA를 쓰지 않는 것

읽는 데 약 18분 · 77장에서 심화합니다

왜 배워야 하나

누구를 위한 것인가

"시각장애인을 위한 것"이라고 생각하기 쉽지만 훨씬 넓습니다.

  • 시각 — 전맹, 저시력, 색각 이상. 한국 남성의 약 5%가 색각 이상입니다.
  • 운동 — 손 떨림, 마비, 한 손만 쓸 수 있는 상황. 마우스 대신 키보드·스위치를 씁니다.
  • 청각 — 영상에 자막이 없으면 내용을 전혀 알 수 없습니다.
  • 인지 — 난독, 주의력 문제. 복잡한 화면, 갑자기 움직이는 요소가 장벽이 됩니다.
  • 일시적·상황적 — 팔을 다친 사람, 밝은 햇빛 아래에서 화면을 보는 사람, 지하철에서 소리를 못 켜는 사람, 한 손에 아이를 안은 사람.

🌐 결국 모두를 위한 것

자막은 청각장애인을 위해 만들어졌지만 지하철에서 영상 보는 모두가 씁니다. 경사로는 휠체어를 위해 만들어졌지만 유아차와 캐리어가 더 많이 씁니다. 접근성 개선은 거의 항상 전체 사용성 개선으로 돌아옵니다. 그리고 마지막으로, 나이가 들면 누구나 시력과 손의 정밀도를 잃습니다.

법적 의무이기도 합니다

한국에서는 「장애인차별금지 및 권리구제 등에 관한 법률」에 따라 웹사이트가 장애인의 접근을 부당하게 제한하지 않도록 정당한 편의를 제공할 의무가 있습니다. 국내 기술 기준으로는 한국형 웹 콘텐츠 접근성 지침(KWCAG)이 국가표준으로 제정되어 있고, 국제 기준은 W3C의 WCAG(Web Content Accessibility Guidelines)입니다. 공공기관 프로젝트에서는 접근성 준수가 계약 조건인 경우가 많습니다.

스크린 리더는 어떻게 읽는가

스크린 리더는 화면을 이미지로 보지 않습니다. DOM과 브라우저가 계산한 접근성 트리를 읽습니다. 각 요소마다 세 가지를 말해 줍니다.

전달 항목예어디서 오는가
역할 (role)"버튼", "링크", "제목 수준 2"태그 종류에서 자동으로
이름 (name)"장바구니 담기"요소의 텍스트, label, alt, aria-label
상태 (state)"선택됨", "비활성", "펼쳐짐"checked, disabled, aria-expanded 등
같은 화면, 다른 소리 
<div class="btn" onclick="addToCart()">🛒</div>
<!-- 읽히는 소리: (아무것도 없음 또는 "쇼핑 카트 이모지")
     역할 없음. 이름 없음. Tab으로 도달조차 못 함. -->

<button onclick="addToCart()">
  <span aria-hidden="true">🛒</span> 장바구니 담기
</button>
<!-- 읽히는 소리: "장바구니 담기, 버튼"
     Tab으로 도달, Enter/Space로 실행. -->

직접 들어 보는 것이 가장 빠릅니다. 별도 설치 없이 지금 켤 수 있습니다.

  • macOS — ⌘ + F5 (VoiceOver)
  • iPhone — 설정 > 손쉬운 사용 > VoiceOver
  • Android — 설정 > 접근성 > TalkBack
  • Windows — Ctrl + Win + Enter (내레이터), 또는 무료 프로그램 NVDA

키보드 접근성

⌨️ 오늘 당장 할 수 있는 가장 좋은 테스트

마우스에서 손을 떼고 Tab 키만으로 여러분의 사이트를 써 보세요. 로그인하고, 메뉴를 열고, 폼을 제출해 보세요. 막히는 지점이 곧 누군가가 그 사이트를 못 쓰는 지점입니다. 5분이면 끝나고, 발견률이 매우 높습니다.

키동작
Tab / Shift+Tab다음 / 이전 조작 가능 요소로 이동
Enter링크 이동, 버튼 실행, 폼 제출
Space버튼 실행, 체크박스 토글, 페이지 스크롤
화살표라디오 그룹·select 안에서 이동
Esc모달·팝업 닫기 (직접 구현해야 합니다)

포커스 표시를 지우지 마세요

가장 흔한 접근성 파괴 코드 
/* ❌ 절대 하면 안 되는 것 */
*:focus { outline: none; }

/* ✅ 마음에 안 들면 지우지 말고 바꾸세요 */
:focus-visible {
  outline: 3px solid #1f5f4f;
  outline-offset: 2px;
  border-radius: 3px;
}

테두리가 보기 싫다고 outline: none을 넣으면, 키보드 사용자는 지금 자기가 어디 있는지 알 수 없게 됩니다. 눈을 감고 마우스를 쓰는 것과 같습니다.

:focus는 마우스로 눌렀을 때도 적용되지만, :focus-visible은 키보드로 이동했을 때만 적용됩니다. "마우스 클릭 시에는 안 보이고 키보드 사용 시에는 보이게" 하려면 이것을 쓰면 됩니다.

순서와 tabindex

  • Tab 순서는 DOM 순서를 따릅니다. CSS로 시각적 위치만 바꾸면 순서가 어긋나 혼란을 줍니다.
  • tabindex="0" — 원래 포커스 못 받는 요소를 순서에 포함시킵니다.
  • tabindex="-1" — Tab 순서에서는 빼되 JavaScript로는 포커스 가능. 모달을 열 때 안으로 포커스를 옮기는 데 씁니다.
  • tabindex="1" 이상의 양수는 쓰지 마세요. 전체 순서를 뒤죽박죽으로 만듭니다.

명도 대비

연한 회색 글씨는 디자인 시안에서는 세련돼 보이지만, 저시력 사용자나 햇빛 아래에서는 아예 읽히지 않습니다. WCAG는 최소 기준을 숫자로 정해 두었습니다.

대상AA (실무 기본 목표)AAA
일반 텍스트4.5 : 1 이상7 : 1
큰 텍스트 (약 24px 이상, 굵은 글씨는 약 19px 이상)3 : 1 이상4.5 : 1
UI 요소 경계·아이콘3 : 1 이상—

확인은 도구로 합니다. 크롬 개발자 도구에서 색상 값을 클릭하면 대비 비율이 바로 표시되고, 기준 미달이면 경고가 뜹니다. Lighthouse 검사에도 포함되어 있습니다(49장).

🎨 색만으로 정보를 전달하지 마세요

"필수 항목은 빨간색", "성공은 초록, 실패는 빨강" 같은 표현은 색각 이상 사용자에게 아무 정보가 아닙니다. 색은 보조 수단으로만 쓰고, 반드시 글자·아이콘·모양을 함께 주세요. "빨간 테두리" 대신 "빨간 테두리 + ⚠ 아이콘 + '이메일 형식이 올바르지 않습니다' 문구"입니다.

ARIA — 마지막에 쓰는 도구

ARIA는 HTML만으로 표현할 수 없는 역할·상태를 보조기술에 알려 주는 속성 모음입니다. 탭 UI, 트리, 콤보박스처럼 HTML에 대응 요소가 없는 것을 만들 때 필요합니다.

📕 ARIA의 첫 번째 규칙

"쓰지 않을 수 있으면 쓰지 마라." — W3C ARIA 저작 실무 가이드 이미 그 역할을 하는 HTML 요소가 있다면 그것을 쓰는 것이 항상 낫습니다. <button>은 역할·키보드 조작·포커스를 전부 기본 제공하지만, <div role="button">은 역할 이름만 붙일 뿐 나머지를 전부 직접 구현해야 합니다. 잘못 쓴 ARIA는 아예 안 쓴 것보다 나쁩니다. 없는 상태를 있다고 말하거나, 실제와 다른 역할을 알려 주기 때문입니다.
속성쓰는 곳
aria-label="닫기"보이는 글자가 없는 요소(아이콘 버튼)에 이름을 준다
aria-labelledby="id"다른 요소의 텍스트를 이름으로 삼는다
aria-describedby="id"추가 설명(도움말·오류 메시지)을 연결
aria-hidden="true"보조기술에서 숨긴다. 장식용 아이콘에 사용. 포커스 가능한 요소에는 절대 쓰지 않는다
aria-expanded펼침·접힘 상태를 알린다 (아코디언, 드롭다운)
aria-live="polite"이 영역이 나중에 바뀌면 읽어 달라. 검색 결과 개수, 저장 완료 알림
role="alert"즉시 읽어야 하는 중요 알림

오늘부터 지킬 8가지

✅ 실무 최소 체크리스트

  1. 누르는 것은 <button>, 이동하는 것은 <a href>
  2. 모든 이미지에 alt (장식은 alt="")
  3. 모든 입력에 연결된 <label>
  4. Tab 키만으로 전체 기능을 쓸 수 있는가
  5. 포커스 표시를 지우지 않기 (:focus-visible로 다듬기)
  6. 명도 대비 4.5:1 이상, 색만으로 정보 전달하지 않기
  7. <html lang="ko">, 제목 계층 지키기
  8. ARIA는 HTML로 안 될 때만

자동 검사 도구도 도움이 됩니다. 크롬 개발자 도구의 Lighthouse, 브라우저 확장 axe DevTools 등이 대표적입니다. 다만 자동 도구가 잡아내는 것은 전체 문제의 일부일 뿐입니다. "alt가 있는가"는 검사할 수 있지만 "alt의 내용이 적절한가"는 사람만 판단할 수 있습니다.

📌 요약

  • 접근성 대상은 장애인만이 아니다. 일시적·상황적 제약까지 포함한다.
  • 한국에서는 법적 의무이며 공공 프로젝트에서는 계약 조건인 경우가 많다.
  • 스크린 리더는 역할·이름·상태를 읽는다. 시맨틱 태그가 이 셋을 공짜로 준다.
  • Tab 키만으로 써 보기가 가장 효율적인 자체 점검이다.
  • outline: none은 금지. :focus-visible로 대체한다.
  • 명도 대비 4.5:1(일반 텍스트), 색만으로 정보를 전달하지 않는다.
  • ARIA의 첫 번째 규칙은 ARIA를 쓰지 않는 것이다. 잘못 쓴 ARIA는 없느니만 못하다.
