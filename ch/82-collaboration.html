🗣️ 개발 전에 물어야 할 것들

1장에서 말했듯 "왜 이렇게 만드는가"를 묻는 능력이 코딩 실력보다 중요합니다. 시안에 없는 상황을 미리 물어보세요.

  • 데이터가 없으면 어떻게 보이나요? (빈 상태)
  • 로딩 중에는요?
  • 실패하면 어떻게 알리나요?
  • 이 목록이 1만 개면요?
  • 글자가 아주 길면요?
  • 모바일에서는 어떻게 보이나요?
  • 권한이 없는 사용자에게는요?

나중에 발견하면 다시 만들어야 합니다. 미리 물으면 5분입니다.

좋은 PR

📏 PR은 작게

500줄짜리 PR은 아무도 제대로 리뷰하지 못합니다. 연구와 경험 모두 큰 PR일수록 리뷰 품질이 급격히 떨어진다는 것을 보여 줍니다. "LGTM"만 달리고 넘어갑니다.
200줄 이하를 목표로 하세요. 기능이 크면 여러 PR로 쪼갭니다. "UI만 먼저", "로직만 먼저"처럼 나누면 됩니다.

PR 설명 템플릿 
## 무엇을
장바구니 수량 변경 기능을 추가했습니다.

## 왜
사용자가 상품을 지웠다가 다시 담아야 하는 불편이 있었습니다. (이슈 #123)

## 어떻게
- 수량 입력에 디바운스를 적용해 API 호출을 줄였습니다
- 낙관적 업데이트로 즉시 반영되게 했습니다

## 확인 방법
1. 장바구니로 이동
2. 수량을 3으로 변경
3. 새로고침 후에도 유지되는지 확인

## 스크린샷
(변경 전/후 또는 화면 녹화)

## 리뷰어에게
- 낙관적 업데이트 실패 시 롤백 처리가 적절한지 봐 주세요
- 디바운스 300ms가 적당할까요?

💬 "리뷰어에게" 항목이 핵심입니다

어디를 봐 달라고 명시하면 리뷰 품질이 크게 올라갑니다. "전부 봐 주세요"보다 "이 부분이 확신이 안 섭니다"가 훨씬 유용한 피드백을 이끌어냅니다. 그리고 스스로 먼저 리뷰하세요. git diff로 자기 코드를 읽으면 디버깅용 console.log, 주석 처리한 코드, 오타를 대부분 잡을 수 있습니다(45장).

리뷰를 하는 쪽

보아야 할 것 (중요도 순)
① 동작이 맞는가 — 요구사항을 충족하는가, 엣지 케이스는
② 버그 가능성 — null 처리, 경쟁 상태, 메모리 누수
③ 보안 — 78장의 항목들
④ 읽기 쉬운가 — 6개월 뒤에 이해되는가
⑤ 설계 — 더 단순한 방법이 있는가
⑥ 서식·스타일 — 도구가 할 일입니다(48장). 사람이 지적하지 마세요

💔 사람이 아니라 코드를 리뷰하세요

❌ "이건 왜 이렇게 하셨어요?"           → 추궁처럼 들립니다
❌ "이건 틀렸습니다"                    → 단정적
❌ "제가 하면 이렇게 할 텐데요"          → 도움이 안 됩니다

✅ "여기서 items가 null이면 오류가 날 것 같은데, 확인해 주실 수 있을까요?"
✅ "map 대신 filter를 쓰면 더 명확할 것 같습니다. 어떻게 생각하세요?"
✅ "저는 이 부분이 잘 이해되지 않는데, 설명을 주석으로 남겨 주실 수 있나요?"
✅ "이 방식 좋네요. 배워 갑니다."       ← 좋은 점도 말하세요

🏷️ 중요도를 표시하면 오해가 줄어듭니다

[must]    반드시 고쳐야 합니다 (버그·보안)
[should]  고치는 것이 좋습니다
[nit]     사소한 취향입니다. 무시하셔도 됩니다
[ask]     궁금해서 묻습니다
[praise]  좋은 부분입니다

이 표시가 없으면 사소한 의견도 수정 요구처럼 읽혀 불필요한 왕복이 생깁니다.

리뷰를 받는 쪽

🧘 코드에 대한 지적은 나에 대한 지적이 아닙니다

머리로는 알아도 처음에는 기분이 나쁩니다. 정상입니다. 경력이 쌓여도 완전히 없어지지는 않습니다. 다만 리뷰가 없는 팀에서 일하는 것이 훨씬 나쁘다는 것을 곧 알게 됩니다.

  • 이해가 안 되면 물어보세요. "왜 그게 문제가 되나요?"는 좋은 질문입니다
  • 동의하지 않으면 근거를 대세요. 무조건 수용하는 것이 좋은 태도는 아닙니다
  • 토론이 길어지면 대화로 옮기세요. 댓글 열 개보다 5분 통화가 빠릅니다
  • 고친 뒤에는 무엇을 어떻게 고쳤는지 답글을 남기세요
  • 고맙다고 말하세요. 리뷰는 시간을 들여 해 주는 일입니다

질문하는 기술

⏰ 신입에게 가장 중요한 능력입니다

혼자 8시간 헤매는 것보다 30분 뒤에 묻는 것이 팀에 훨씬 이득입니다. "물어보면 무능해 보일까"라는 걱정 때문에 시간을 버리는 것이 신입이 가장 많이 하는 실수입니다.
다만 어떻게 묻느냐가 중요합니다.

나쁜 질문 vs 좋은 질문 
❌ "이거 안 돼요"
❌ "에러 나는데 어떻게 해요?"

✅ "장바구니 수량 변경이 저장되지 않습니다.

   시도한 것:
   - Network 탭 확인 → PATCH 요청은 200으로 성공
   - 응답 본문에도 새 수량이 들어 있음
   - 화면 상태만 갱신되지 않음

   추측:
   - 상태를 직접 수정해서 React가 감지 못 하는 것 같은데
     확인해 봐도 push는 안 쓰고 있습니다

   관련 코드: CartItem.tsx 42번째 줄

   30분 정도 봤는데 막혔습니다. 방향만 알려 주실 수 있을까요?"

📋 좋은 질문의 요소

  1. 무엇을 하려는가 (목표)
  2. 무엇이 일어나는가 (실제 결과 — 오류 메시지 그대로)
  3. 무엇을 시도했는가 ← 이게 가장 중요합니다
  4. 어디를 봐야 할지 (파일·줄)

이렇게 정리하다가 스스로 답을 찾는 경우도 많습니다. "고무 오리에게 설명하기"라고 불리는 현상입니다.

함께 일하는 태도

🤝 실무에서 통하는 것들

  1. 모르는 것을 모른다고 말하세요. 아는 척하다 나중에 터지는 것이 훨씬 나쁩니다.
  2. 진행 상황을 미리 공유하세요. 마감 하루 전 "못 할 것 같습니다"가 최악입니다. 막힐 것 같으면 일찍 말하세요.
  3. 추정치는 넉넉하게. 신입은 대부분 절반 이하로 추정합니다. "2일"이라고 생각되면 "4일"이라고 말하는 편이 낫습니다.
  4. 남의 코드를 비난하지 마세요. 그때는 그 나름의 이유가 있었을 수 있습니다. "왜 이렇게 되어 있나요?"라고 물어보세요.
  5. 디자이너·기획자를 존중하세요. "이건 개발이 안 됩니다"보다 "이렇게 하면 3일, 이렇게 하면 하루입니다"가 훨씬 생산적입니다.
  6. 배운 것을 공유하세요. 팀 채널에 짧게 남기는 것만으로도 신뢰가 쌓입니다.

📌 요약

  • 개발 전에 엣지 케이스를 물어보세요. 나중에 물으면 다시 만들어야 합니다.
  • PR은 작게(200줄 이하). 큰 PR은 리뷰가 형식적이 됩니다.
  • PR 설명에 무엇을·왜·확인 방법·리뷰어에게를 씁니다.
  • 리뷰는 사람이 아니라 코드에. 서식은 도구가 잡습니다.
  • 중요도 표시([must]/[nit])로 오해를 줄입니다.
  • 30분 막히면 물어보세요. 단, 시도한 것을 정리해서.
  • 주석은 "왜"를 씁니다.
  • 모른다고 말하고, 일찍 공유하고, 추정치는 넉넉하게.
