Suspense

<Suspense fallback={<Skeleton />}>
  <SlowComponent />
</Suspense>

"이 안쪽이 아직 준비되지 않았으면 대체 화면을 보여줘"라고 선언하는 장치입니다. 각 컴포넌트가 isLoading을 확인해 분기하는 대신, 로딩 처리를 바깥으로 끌어냅니다.

지연 로딩과 함께 (68장) 
const Chart = lazy(() => import("./Chart"));

<Suspense fallback={<ChartSkeleton />}>
  <Chart data={data} />
</Suspense>

📌 데이터 페칭에 쓰려면 지원하는 도구가 필요합니다

아무 fetch나 Suspense가 알아채는 것이 아닙니다. Suspense와 연동되도록 만들어진 라이브러리나 프레임워크가 필요합니다 (TanStack Query의 useSuspenseQuery, Next.js의 서버 컴포넌트 등).
직접 만든 useEffect 페칭은 Suspense가 감지하지 못합니다.

에러 경계

// 에러 경계는 아직 클래스 컴포넌트로만 만들 수 있습니다
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }
  componentDidCatch(error, info) {
    reportToSentry(error, info);      // 79장
  }
  render() {
    if (this.state.hasError) return this.props.fallback;
    return this.props.children;
  }
}

// 실무에서는 라이브러리를 씁니다
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary fallback={<ErrorPage />}>
  <Suspense fallback={<Skeleton />}>
    <UserProfile />
  </Suspense>
</ErrorBoundary>

🕳️ 에러 경계가 잡지 못하는 것

  • 이벤트 핸들러 안의 오류 — try/catch로 직접(33장)
  • 비동기 코드(setTimeout, Promise) 안의 오류
  • 서버 렌더링 중의 오류
  • 에러 경계 자기 자신의 오류

즉 렌더링 중에 던져진 오류만 잡습니다. 그래도 "흰 화면"을 막는 최소한의 안전망이므로 앱 최상단에는 반드시 두세요. 경계가 없으면 오류 하나에 앱 전체가 언마운트됩니다.

🎯 경계를 어디에 둘까

"이 부분이 깨져도 나머지는 살아 있어야 하는" 단위로 나눕니다. 사이드바 위젯이 실패해도 본문은 보여야 하고, 댓글이 실패해도 글은 보여야 합니다. 앱 전체에 하나만 두면 작은 오류에 전체가 죽습니다.

useTransition

function SearchPage() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState([]);
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    setQuery(e.target.value);          // 급한 일: 입력 즉시 반영

    startTransition(() => {
      setResults(search(e.target.value));   // 급하지 않은 일: 밀려도 됨
    });
  }

  return (
    <>
      <input value={query} onChange={handleChange} />
      <div style={{ opacity: isPending ? 0.6 : 1 }}>
        <HeavyResultList results={results} />
      </div>
    </>
  );
}

⚡ 무엇을 푸는가

무거운 목록을 렌더링하는 동안 입력이 버벅이는 문제입니다(35장). React는 렌더링을 중간에 멈출 수 없어서 그동안 입력이 막힙니다.
startTransition으로 감싼 갱신은 "급하지 않다"고 표시되어, 더 급한 갱신(타이핑)이 들어오면 중단하고 그것을 먼저 처리합니다. 결과적으로 입력은 항상 즉각 반응합니다.

useDeferredValue — 더 간단한 방법 
function SearchPage() {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);   // 한 박자 늦게 따라옵니다

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <HeavyResultList query={deferredQuery} />
    </>
  );
}

🆚 디바운스와 다릅니다

디바운스(31장)는 정해진 시간을 기다립니다. 300ms라면 빠른 기기에서도 300ms를 기다립니다.
useDeferredValue는 렌더링 우선순위를 조정합니다. 기기가 빠르면 거의 즉시 반영되고, 느리면 알아서 뒤로 밀립니다.
다만 네트워크 요청 횟수를 줄이는 것은 여전히 디바운스의 몫입니다. 둘은 목적이 다르고, 함께 쓰기도 합니다.

function LikeButton({ post }) {

③ useActionState · useFormStatus — 폼 (62장) 
function SignupForm() {
  const [state, formAction, isPending] = useActionState(signupAction, null);

  return (
    <form action={formAction}>
      <input name="email" />
      <SubmitButton />
      {state?.error && <p role="alert">{state.error}</p>}
    </form>
  );
}

function SubmitButton() {
  const { pending } = useFormStatus();      // 부모 form의 제출 상태를 읽습니다
  return <button disabled={pending}>{pending ? "가입 중…" : "가입"}</button>;
}

서버 컴포넌트

React Server Components(RSC)는 서버에서만 실행되는 컴포넌트입니다. 결과만 클라이언트로 전송되고, 컴포넌트 코드 자체는 브라우저로 가지 않습니다.

// 서버 컴포넌트 (기본값 — Next.js App Router 기준)
async function ProductList() {
  const products = await db.product.findMany();   // ⭐ DB에 직접 접근
  return <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

// 클라이언트 컴포넌트 — 지시어를 명시합니다
"use client";
function AddToCartButton({ id }) {
  const [count, setCount] = useState(0);          // 훅은 여기서만
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
서버 컴포넌트클라이언트 컴포넌트
실행 위치서버에서만서버(초기 HTML) + 브라우저
번들 포함안 됨 — 용량 0포함됨
상태·이벤트·훅불가가능
DB·파일·비밀 키직접 접근 가능불가
async 컴포넌트가능불가

📉 무엇을 얻는가

  • 번들 크기 감소 — 마크다운 변환기 같은 무거운 라이브러리를 서버에서만 쓰면 사용자는 한 바이트도 받지 않습니다
  • 데이터 접근이 직접적 — API 계층 없이 DB를 바로 조회합니다
  • 비밀 키 안전 — 서버 코드는 브라우저로 가지 않습니다(1장)
  • 워터폴 감소 — 브라우저가 "HTML 받고 → JS 받고 → API 호출"하는 대신 서버가 한 번에 준비합니다

🚧 제약과 오해

  • 서버 컴포넌트에서 useState·useEffect·이벤트 핸들러를 쓸 수 없습니다.
  • 서버 → 클라이언트로 넘기는 props는 직렬화 가능해야 합니다. 함수는 넘길 수 없습니다(Server Action 제외).
  • 런타임 CSS-in-JS와 충돌합니다(22장).
  • "서버 컴포넌트 = SSR"이 아닙니다. SSR은 컴포넌트를 서버에서 HTML로 만드는 것이고, RSC는 애초에 클라이언트로 코드를 보내지 않는 것입니다. 개념이 다릅니다(70장).
  • 사용하려면 지원하는 프레임워크가 필요합니다. React만으로는 쓸 수 없습니다.

📌 요약

  • Suspense는 로딩 처리를 바깥으로 끌어내는 선언적 장치다. 지원하는 도구가 필요하다.
  • 에러 경계는 렌더링 중 오류만 잡는다. 이벤트·비동기 오류는 try/catch로.
  • 에러 경계는 "깨져도 나머지는 살아야 하는" 단위로 나눠 배치한다.
  • useTransition은 갱신에 우선순위를 매겨 입력이 막히지 않게 한다.
  • useDeferredValue는 디바운스와 다르다. 요청 횟수를 줄이는 것은 디바운스의 몫이다.
  • React 19: use·useOptimistic·useActionState·useFormStatus, forwardRef 불필요.
  • 서버 컴포넌트는 코드가 브라우저로 가지 않아 번들이 0이고 DB에 직접 접근한다.
  • RSC ≠ SSR. 개념이 다르다.
