좁히기란

51장에서 유니온 타입으로 "문자열이거나 숫자"를 표현했습니다. 그런데 이런 값은 그대로는 쓸 데가 별로 없습니다. 문자열 메서드를 쓰려니 숫자일 수 있고, 숫자 메서드를 쓰려니 문자열일 수 있기 때문입니다. 그래서 실제로 값을 쓰기 전에 "지금은 둘 중 무엇인가"를 확인해야 하고, 그 확인을 통과한 자리에서는 타입이 하나로 줄어듭니다. 이것을 타입 좁히기(narrowing)라고 합니다.

공항 보안 검색대를 떠올려 보세요. 들어오기 전에는 "누구든 될 수 있는 사람"이지만, 검색대를 통과한 사람은 탑승구 구역 안에서 "검사를 마친 승객"으로 취급됩니다. 조건문이 검색대이고, 조건문의 중괄호 안이 탑승구 구역입니다.

function print(value: string | number) {
  // value.toUpperCase();   ❌ number일 수도 있으므로 불가

  if (typeof value === "string") {
    value.toUpperCase();    // ✅ 여기서는 string 임이 확실합니다
  } else {
    value.toFixed(2);       // ✅ 여기서는 number
  }
}

🔬 제어 흐름 분석

TypeScript는 코드의 흐름을 따라가며 각 지점에서 변수의 타입을 다시 계산합니다. if를 통과했으면 그 조건이 참인 상태라는 것을 알고 있습니다. 그래서 특별한 문법 없이 평범한 JavaScript 조건문만으로 타입이 좁혀집니다. 이것이 TypeScript가 다른 타입 언어보다 자연스럽게 느껴지는 이유입니다.

▶ 위 예제를 Playground에 붙여 보세요. if 안, else 안, 그리고 if 바깥에서 각각 value에 마우스를 올리면 string, number, string | number로 타입이 바뀌어 보입니다. 같은 변수인데 코드의 위치에 따라 타입이 다른 것이 좁히기의 핵심입니다.

좁히는 방법들

좁히는 방법은 다섯 가지로 정리됩니다. 모두 원래 JavaScript에 있던 검사이고, TypeScript는 그 검사의 의미를 이해할 뿐입니다. 값의 종류에 따라 알맞은 도구가 다르므로, 각 상자의 제목(무엇을 거를 때 쓰는지)을 먼저 보세요.

① typeof — 원시 타입 
function f(x: string | number | boolean | undefined) {
  if (typeof x === "string") { /* string */ }
  else if (typeof x === "number") { /* number */ }
  else if (typeof x === "boolean") { /* boolean */ }
  else { /* undefined */ }
}

// ⚠️ typeof null === "object" (25장)이므로 null은 이 방법으로 못 거릅니다

typeof는 "string", "number", "boolean", "undefined", "object", "function" 같은 JavaScript의 기본 분류만 알려 줍니다. 그래서 원시 타입끼리 섞인 유니온을 가를 때 가장 잘 맞습니다. 반대로 "어떤 모양의 객체인가"는 typeof로 구분할 수 없고 아래의 in이나 판별 유니온을 써야 합니다. 각 if 갈래 안에 커서를 두고 x에 마우스를 올리면, 앞 갈래에서 걸러진 타입이 하나씩 빠져 나가는 것이 보입니다.

② 진리값 검사 — null·undefined 거르기 
function f(user: User | null) {
  if (!user) return;        // 이른 반환 (26장)
  user.name;                // ✅ 여기서는 User
}

// ⚠️ 주의: 0과 빈 문자열도 falsy 입니다 (25장)
function g(count: number | undefined) {
  if (!count) { /* count가 0일 때도 여기 옵니다 */ }
  if (count === undefined) { /* ✅ 정확합니다 */ }
  if (count != null) { /* ✅ null과 undefined 모두 거릅니다 */ }
}
③ instanceof — 클래스 
function handle(error: unknown) {
  if (error instanceof ValidationError) {
    error.field;            // ✅ (33장의 커스텀 에러)
  } else if (error instanceof Error) {
    error.message;
  } else {
    String(error);
  }
}
// catch 블록의 값은 unknown 입니다 (useUnknownInCatchVariables)
// 그래서 이런 확인이 반드시 필요합니다

catch (error)의 error는 왜 unknown일까요? JavaScript에서는 throw "문자열"처럼 아무 값이나 던질 수 있기 때문입니다(33장). 그래서 error.message를 바로 읽으면 안 되고, instanceof Error로 먼저 확인합니다. 실무 코드에서 가장 자주 쓰는 좁히기 패턴 중 하나입니다.

④ in — 속성 존재 여부 
type Dog = { bark(): void };
type Cat = { meow(): void };

function speak(animal: Dog | Cat) {
  if ("bark" in animal) {
    animal.bark();          // ✅ Dog
  } else {
    animal.meow();          // ✅ Cat
  }
}
⑤ 판별 유니온 — 가장 권장되는 방법 (52장) 
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; size: number }
  | { kind: "rect"; width: number; height: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.size ** 2;
    case "rect":   return shape.width * shape.height;
  }
}

판별 유니온은 52장에서 상태 설계 도구로 보았습니다. 좁히기 관점에서 보면 가장 확실한 방법입니다. kind 값 하나만 확인하면 그 갈래에 어떤 속성이 있는지 정확히 정해지기 때문입니다. in이나 typeof처럼 "아마 이럴 것이다"라고 추측할 여지가 없습니다. ▶ Playground에 붙인 뒤 case "circle": 안에서 shape.를 입력해 보면 radius만 후보로 나옵니다.

✅ never로 빠짐없이 처리했는지 검사하기

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.radius ** 2;
    case "square": return shape.size ** 2;
    // rect를 빠뜨렸다고 합시다
    default: {
      const exhaustive: never = shape;
      // ❌ Type '{ kind: "rect"; … }' is not assignable to type 'never'
      //    → 처리하지 않은 경우가 있다고 알려 줍니다
      throw new Error(`처리되지 않은 종류: ${exhaustive}`);
    }
  }
}

나중에 새로운 종류를 추가하면 이 자리에서 컴파일 오류가 나서 "어디를 고쳐야 하는지" 알려 줍니다. 매우 강력한 패턴입니다.

사용자 정의 타입 가드

앞의 검사들은 한두 줄로 끝났습니다. 하지만 "이 값이 User 모양인가"처럼 검사가 길어지면 같은 조건문을 여러 곳에 복사하게 됩니다. 이때 검사를 함수로 빼내고, 그 함수가 true를 돌려주면 타입이 좁혀지도록 표시할 수 있습니다. 반환 타입 자리의 value is User가 그 표시입니다. 50장에서 잠깐 본 문법을 여기서 제대로 배웁니다. 일반 함수였다면 반환 타입이 그냥 boolean이라 호출한 쪽에서 타입이 좁혀지지 않습니다.

// 반환 타입에 'value is Type' 을 씁니다
function isString(value: unknown): value is string {
  return typeof value === "string";
}

function isUser(value: unknown): value is User {
  return (
    typeof value === "object" &&
    value !== null &&
    "id" in value &&
    "name" in value
  );
}

function handle(value: unknown) {
  if (isUser(value)) {
    value.name;             // ✅ User 로 좁혀집니다
  }
}

// 배열 필터링에서
const items: (User | null)[] = [user1, null, user2];

const clean1 = items.filter(item => item !== null);
//    ↑ TypeScript 5.5부터는 User[] 로 추론됩니다 (타입 가드를 자동으로 추론)
//      그 이전 버전에서는 (User | null)[] 로 남았습니다

function isNotNull<T>(value: T | null): value is T {
  return value !== null;
}
const clean2 = items.filter(isNotNull);    // ✅ User[] — 조건이 복잡해 자동 추론이 안 될 때 이렇게 씁니다

TypeScript 5.5부터는 item => item !== null처럼 단순한 콜백을 보고 타입 가드를 스스로 추론합니다. 그래서 예전 자료에 흔하던 isNotNull 같은 함수가 필요한 경우가 줄었습니다. 그래도 조건이 길어지거나 여러 곳에서 같은 검사를 쓸 때는 직접 만든 타입 가드가 여전히 유용합니다.

⚠️ 타입 가드는 거짓말할 수 있습니다

function isUser(value: unknown): value is User {
  return true;              // 😱 아무것도 검사하지 않아도 통과합니다
}

컴파일러는 여러분의 말을 믿습니다. 그래서 타입 가드 안의 검사 로직이 실제로 정확한지는 사람이 책임져야 합니다. 속성 하나만 확인하고 "이건 User다"라고 선언하면 나중에 터집니다.

타입 단언 — 최후의 수단

좁히기는 "확인했으니 안다"이고, 타입 단언(as)은 "확인은 안 했지만 내 말을 믿어라"입니다. 타입 가드가 신분증을 확인하는 직원이라면, 단언은 신분증 확인 없이 "제가 보증합니다"라고 문을 열어 주는 것입니다. 대부분은 맞겠지만 틀렸을 때 막아 줄 장치가 없습니다.

const input = document.getElementById("email") as HTMLInputElement;
input.value;      // ✅ 컴파일은 통과합니다

// 하지만 그 요소가 없거나 input이 아니면 런타임에 터집니다

🤔 자주 하는 오해 — as는 값을 변환한다

오해 — value as number라고 쓰면 문자열이 숫자로 바뀐다. 다른 언어의 형 변환(캐스팅)과 같다. 사실 — as는 컴파일러가 보는 타입 표기만 바꿉니다. 빌드 후에는 다른 타입 표기처럼 지워지므로 실제 값은 그대로입니다. "42" as unknown as number는 실행해도 여전히 문자열 "42"입니다. 값을 바꾸려면 Number("42")처럼 JavaScript 함수로 변환해야 합니다(25장).

위 표의 value!(느낌표)는 non-null 단언으로, "null이나 undefined가 아니라고 믿어라"는 뜻입니다. as와 똑같이 아무것도 확인하지 않으므로, 틀리면 런타임 오류가 납니다. 단언이 필요한 정당한 상황도 있습니다. 타입 정보가 부족한 오래된 라이브러리를 쓰거나, TypeScript가 알 수 없는 사실(HTML에 그 요소가 반드시 있다)을 개발자가 알 때입니다. 그럴 때도 아래처럼 확인으로 바꿀 수 있는지 먼저 따져 보세요.

표현의미위험도
value as Type"이 타입이라고 믿어라"중간 — 틀리면 런타임 오류
value!"null·undefined가 아니라고 믿어라"중간
value as unknown as Type"관계없는 타입으로 강제 변환"매우 높음 — 거의 항상 잘못된 설계 신호
satisfies검사하되 추론은 유지안전
as 대신 안전하게 
// ❌ 단언
const input = document.getElementById("email") as HTMLInputElement;

// ✅ 확인
const el = document.getElementById("email");
if (el instanceof HTMLInputElement) {
  el.value;
}

// ✅ 또는 옵셔널 체이닝과 함께 (26장)
const value = (document.getElementById("email") as HTMLInputElement | null)?.value;

satisfies — 검사와 추론을 동시에

타입 표기(: Config)에는 부작용이 하나 있습니다. 값이 그 타입에 맞는지 검사해 주는 대신, 값의 타입이 표기한 타입으로 넓어집니다. port가 숫자라는 구체적인 정보가 "문자열 또는 숫자"로 뭉개지는 것입니다. satisfies는 검사만 하고 넓히지는 않는 연산자입니다.

type Config = Record<string, string | number>;

// ❌ 타입을 명시하면 구체적인 정보를 잃습니다
const a: Config = { port: 3000, host: "localhost" };
a.port.toFixed();     // ❌ string일 수도 있다고 판단합니다

// ✅ satisfies — Config를 만족하는지 검사하되, 추론은 구체적으로 유지
const b = { port: 3000, host: "localhost" } satisfies Config;
b.port.toFixed();     // ✅ number 임을 알고 있습니다
b.host.toUpperCase(); // ✅ string
// b.wrong;           ❌ 없는 키는 여전히 오류

▶ Playground에 붙여 보세요. a.port.toFixed()에는 오류가, b.port.toFixed()에는 오류가 없습니다. 설정 객체, 라우트 목록, 색상표처럼 "정해진 규칙은 지키되, 실제로 넣은 값의 구체적인 정보도 살리고 싶은" 상수에 특히 잘 맞습니다.

satisfies는 TypeScript 4.9부터 사용할 수 있습니다. "이 값이 이 타입에 맞는지 검사해 줘. 단, 타입을 넓히지는 마"라는 뜻입니다.

외부 데이터는 런타임에 검증하세요

지금까지의 도구는 모두 내 코드 안에서 타입을 다루는 방법이었습니다. 그런데 프론트엔드가 다루는 값의 상당수는 바깥에서 옵니다. 서버 응답, 사용자 입력, localStorage에 저장된 값은 TypeScript가 빌드할 때 볼 수 없는 값입니다. 50장의 맞춤법 검사기 비유로 돌아가면, 검사기는 내가 쓴 문장만 검사할 뿐 남이 보내온 편지는 검사하지 못합니다.

🚨 이 코드는 거짓말입니다

const user: User = await response.json();
// 서버가 무엇을 보내든 통과합니다. TypeScript는 확인하지 않습니다.
user.name.toUpperCase();   // name이 없으면 런타임 오류
Zod로 검증하기 — 실무 표준 
import { z } from "zod";

const UserSchema = z.object({
  id: z.number(),
  name: z.string(),
  email: z.email(),                  // Zod 4 표기 (예전 표기: z.string().email())
  role: z.enum(["admin", "user"]),
  createdAt: z.iso.datetime()        // ISO 8601 날짜 문자열
});

// 스키마에서 타입을 자동으로 뽑아냅니다 — 중복 정의가 없습니다
type User = z.infer<typeof UserSchema>;

async function getUser(id: number): Promise<User> {
  const response = await fetch(`/api/users/${id}`);
  const raw = await response.json();

  // 실제로 검사합니다. 형태가 다르면 여기서 오류가 납니다
  return UserSchema.parse(raw);
}

스키마는 "데이터가 이런 모양이어야 한다"는 규칙을 실행 중에도 존재하는 값으로 적은 것입니다. 타입은 빌드 후 사라지지만 스키마는 JavaScript 객체라 남아 있으므로, 실제로 들어온 값을 하나하나 비교할 수 있습니다. parse는 모양이 맞으면 값을 그대로 돌려주고, 다르면 "어느 속성이 왜 틀렸는지" 담긴 오류를 던집니다. 그리고 z.infer로 스키마에서 타입을 뽑으므로 타입과 검증 규칙을 한 곳에서 관리할 수 있습니다. 위 코드는 Zod 4(2026년 기준 최신 메이저 버전) 문법입니다.

🛡️ 검증이 필요한 지점

  • API 응답 — 서버가 언제든 바뀔 수 있습니다
  • 사용자 입력 — 폼, 쿼리 문자열
  • localStorage에서 읽은 값 — 옛 버전의 데이터가 남아 있을 수 있습니다(39장)
  • 환경 변수 — 배포 설정 누락을 시작 시점에 잡습니다

내 코드 안은 TypeScript가 지켜 주고, 바깥과의 경계는 런타임 검증이 지킵니다. 둘 다 필요합니다.

🛠️ 현장 노트 — as가 늘어난다면

코드에 as가 많아진다면 타입 설계가 잘못되었다는 신호입니다. 잘 설계된 타입에서는 좁히기만으로 대부분 해결됩니다.

  • 유니온이 너무 넓지 않은지 — 판별 유니온으로 바꿀 수 있는지
  • 함수가 너무 많은 경우를 처리하려 하는지 — 나눌 수 있는지
  • any가 흘러들어와 그것을 as로 수습하고 있는지

as를 쓸 때는 왜 안전한지 주석으로 남기세요. "이 시점에는 반드시 로드되어 있음" 같은 근거가 있어야 다음 사람이 판단할 수 있습니다.

📌 요약

  • TypeScript는 제어 흐름을 분석해 평범한 조건문만으로 타입을 좁힌다.
  • 도구: typeof · 진리값 · instanceof · in · 판별 유니온.
  • 진리값 검사는 0과 빈 문자열도 걸러 버린다. != null이 정확하다.
  • never 검사로 모든 경우를 처리했는지 컴파일러가 확인하게 만든다.
  • 타입 가드(value is T)는 내용의 정확성을 사람이 책임진다.
  • as는 검사하지 않는다. 확인 가능한 상황이면 좁히기를 쓴다.
  • satisfies는 검사하되 추론을 유지한다.
  • 외부 데이터는 Zod 같은 도구로 런타임 검증한다.
