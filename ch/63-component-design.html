상속이 아니라 합성

32장에서 "상속보다 합성"이라고 했습니다. React는 이 원칙을 철저히 따릅니다. React에는 컴포넌트 상속이 없습니다.

// ❌ 다른 언어에서 하던 방식 — React에는 없습니다
class PrimaryButton extends Button { }

// ✅ 합성: 컴포넌트를 조립합니다
function PrimaryButton(props) {
  return <Button variant="primary" {...props} />;
}

// ✅ children으로 감싸기 (58장)
<Card>
  <UserProfile user={user} />
</Card>

여러 자리를 열어 두기

// children이 하나로 부족하면 props로 여러 자리를 받습니다
function Dialog({ title, body, footer }) {
  return (
    <div className="dialog">
      <header>{title}</header>
      <div className="body">{body}</div>
      <footer>{footer}</footer>
    </div>
  );
}

<Dialog
  title={<h2>삭제 확인</h2>}
  body={<p>정말 삭제할까요?</p>}
  footer={<><Button>취소</Button><Button variant="danger">삭제</Button></>}
/>

🧩 JSX도 그냥 값입니다

58장에서 배웠듯 JSX는 값이므로 props로 넘길 수 있습니다. "이 자리에 무엇이 들어갈지 컴포넌트가 정하지 않고 쓰는 쪽이 정하게" 만드는 것이 합성의 핵심입니다. 그래서 컴포넌트가 훨씬 유연해집니다.

props drilling

// ❌ user를 4단계 아래로 전달하기 위해 중간 컴포넌트들이 받기만 합니다
<App user={user}>
  <Layout user={user}>
    <Sidebar user={user}>
      <Profile user={user} />

💡 Context를 꺼내기 전에 — 합성으로 해결되는 경우가 많습니다

// ✅ 완성된 요소를 children으로 내려보냅니다
function App() {
  const user = useUser();
  return (
    <Layout>
      <Sidebar>
        <Profile user={user} />      {/* 여기서 이미 만들어 넘깁니다 */}
      </Sidebar>
    </Layout>
  );
}
// Layout과 Sidebar는 user를 몰라도 됩니다. children을 그냥 렌더링할 뿐입니다.

이 방법의 장점은 Layout과 Sidebar가 재사용 가능해진다는 것입니다. user를 알아야 하는 컴포넌트는 user가 없는 화면에서는 못 씁니다.
전달 단계가 2~3단계라면 props가 오히려 명확합니다. "어디서 왔는지" 코드에 드러나기 때문입니다. 정말 넓은 범위(테마·로그인 정보)에서만 Context를 씁니다(65장).

컴파운드 컴포넌트

props가 많아지는 문제 
// ❌ props가 계속 늘어납니다
<Select
  options={options}
  placeholder="선택"
  showSearch
  searchPlaceholder="검색"
  renderOption={…}
  groupBy={…}
  footerText="더 보기"
  onFooterClick={…}
/>
✅ 구조를 쓰는 쪽이 정하게 합니다 
<Select value={value} onChange={setValue}>
  <Select.Trigger placeholder="선택" />
  <Select.Content>
    <Select.Search placeholder="검색" />
    <Select.Group label="수도권">
      <Select.Option value="seoul">서울</Select.Option>
      <Select.Option value="incheon">인천</Select.Option>
    </Select.Group>
  </Select.Content>
</Select>

내부적으로는 Context로 상태를 공유합니다(65장). HTML의 <select>·<option>, <table>·<tr>과 같은 구조입니다. Radix UI, Headless UI 같은 라이브러리가 이 방식을 씁니다.

⚖️ 항상 좋은 것은 아닙니다

컴파운드 패턴은 구현이 복잡하고 쓰는 쪽 코드도 길어집니다. 정말 다양한 조합이 필요한 컴포넌트(디자인 시스템의 Select, Tabs, Accordion)에만 쓰세요. 버튼 하나에 이 패턴을 적용하는 것은 과합니다.

좋은 컴포넌트 API

원칙설명
props 이름은 의도를isRed가 아니라 variant="danger". 나중에 색이 바뀌어도 이름이 맞습니다
불리언보다 유니온isPrimary+isSecondary는 둘 다 true인 불가능한 상태를 만듭니다(52장)
기본값을 주기대부분의 경우 아무것도 안 넘겨도 동작해야 합니다
나머지 props 전달{...rest}로 aria-*·data-*를 지원(56장)
제어·비제어 둘 다value가 오면 제어, 없으면 내부 상태 사용
콜백은 의미 있는 값으로onChange(value)가 onChange(event)보다 낫습니다(56장)
잘 설계된 버튼 
function Button({
  variant = "primary",
  size = "md",
  isLoading = false,
  leftIcon,
  children,
  className,
  disabled,
  ...rest
}) {
  return (
    <button
      className={cx("btn", `btn-${variant}`, `btn-${size}`, className)}
      disabled={disabled || isLoading}
      aria-busy={isLoading}
      {...rest}
    >
      {isLoading ? <Spinner size="sm" /> : leftIcon}
      {children}
    </button>
  );
}

로직과 화면 분리

// ❌ 한 컴포넌트가 데이터·상태·화면을 모두 담당
function UserList() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  useEffect(() => { /* 페칭 … */ }, []);
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}

// ✅ 로직은 훅으로 (66장), 화면은 순수하게
function useUsers() {
  const [state, setState] = useState({ status: "loading" });
  useEffect(() => { /* 페칭 … */ }, []);
  return state;
}

function UserList() {
  const state = useUsers();
  if (state.status === "loading") return <Spinner />;
  return <UserListView users={state.data} />;
}

// 데이터만 받아 그리는 컴포넌트 — 테스트와 스토리북에 쓰기 좋습니다
function UserListView({ users }) {
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}

✂️ 나누는 기준

"컨테이너/프레젠테이션"이라는 옛 규칙을 기계적으로 적용할 필요는 없습니다. 훅이 나온 뒤로는 로직을 커스텀 훅으로 빼는 것만으로 대부분 해결됩니다.
분리가 확실히 이득인 경우는 이럴 때입니다.

  • 같은 화면을 다른 데이터 출처로 재사용해야 할 때
  • 화면만 따로 테스트하거나 문서화하고 싶을 때
  • 컴포넌트가 200줄을 넘어 읽기 어려울 때

폴더 구조

기능 기준 구조 (규모가 커져도 잘 버팁니다) 
src/
├── features/              ← 기능 단위로 묶기
│   ├── auth/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api.ts
│   │   └── types.ts
│   └── products/
│       ├── components/
│       ├── hooks/
│       └── api.ts
├── shared/                ← 여러 기능이 함께 쓰는 것
│   ├── ui/                   Button, Input, Modal …
│   ├── hooks/                useDebounce, useLocalStorage …
│   └── lib/                  formatDate, apiClient …
├── pages/                 ← 라우트별 화면
└── app/                   ← 전역 설정, 프로바이더

📁 타입별로 나누면 커질수록 불편해집니다

src/
├── components/     ← 100개가 뒤섞임
├── hooks/          ← 어느 기능의 것인지 모름
└── utils/

작은 프로젝트에서는 괜찮지만, 커지면 기능 하나를 고치려고 폴더 네 개를 오가야 합니다. 함께 바뀌는 것을 함께 두는 것이 좋은 구조의 기본 원칙입니다.
다만 처음부터 완벽한 구조를 만들려 하지 마세요. 작게 시작해서 불편해질 때 옮기는 것이 실제 순서입니다.

🛠️ 현장 노트 — 컴포넌트 설계 판단

  1. 세 번째 복사할 때 추출하세요. 두 번까지는 복사가 낫습니다. 성급한 추상화가 잘못된 추상화보다 흔한 문제입니다.
  2. props가 8개를 넘으면 컴포넌트가 너무 많은 일을 하는 것입니다. 나누거나 합성으로 바꾸세요.
  3. 이름이 안 떠오르면 잘못 나눈 것입니다. Wrapper, Container2 같은 이름이 그 신호입니다.
  4. "이 컴포넌트가 무엇을 하는가"를 한 문장으로 말할 수 있어야 합니다.
  5. 추상화는 되돌리기 어렵습니다. 확신이 없으면 중복을 유지하세요.

📌 요약

  • React에는 컴포넌트 상속이 없다. 합성으로 조립한다.
  • JSX는 값이므로 props로 넘길 수 있다. 여러 자리를 열어 두면 유연해진다.
  • props drilling은 합성으로 먼저 풀어 본다. Context는 정말 넓은 범위에만.
  • 컴파운드 컴포넌트는 조합이 다양한 UI에만 쓴다.
  • props는 의도를 담은 이름과 유니온 타입으로. 나머지는 {...rest}로 전달.
  • 로직은 커스텀 훅으로 빼고 화면은 데이터만 받게 한다.
  • 폴더는 기능 단위로. 함께 바뀌는 것을 함께 둔다.
  • 세 번째 복사할 때 추출한다. 성급한 추상화를 피한다.
