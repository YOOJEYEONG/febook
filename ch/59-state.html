59장. state와 렌더링

이 챕터에서 배우는 것

  • useState가 실제로 하는 일
  • 상태는 스냅샷 — setState 직후에 값이 안 바뀌는 이유
  • 불변성 — 객체·배열 상태를 다루는 법
  • 상태 끌어올리기
  • 무엇을 상태로 두고 무엇을 계산할지

읽는 데 약 26분 · React에서 가장 중요한 챕터입니다

왜 그냥 변수로는 안 되나

function Counter() {
  let count = 0;                       // ❌ 그냥 변수

  return (
    <button onClick={() => { count++; console.log(count); }}>
      {count}
    </button>
  );
}

콘솔에는 1, 2, 3이 찍히는데 화면은 0 그대로입니다. 두 가지 문제가 있습니다.

  1. React가 값이 바뀐 것을 모릅니다. 다시 그릴 이유를 찾지 못합니다.
  2. 다시 그린다 해도 함수가 처음부터 실행되어 count = 0으로 돌아갑니다.
function Counter() {
  const [count, setCount] = useState(0);
  //     ↑현재 값  ↑변경 함수        ↑초기값

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

🧠 useState가 하는 두 가지

  1. 값을 렌더링 사이에 기억합니다. 함수가 다시 실행되어도 유지됩니다. (31장의 클로저 개념 위에 만들어져 있습니다.)
  2. 값이 바뀌면 React에 알려 다시 그리게 합니다.

상태는 스냅샷입니다

function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count);        // 0 (!) — 방금 바꿨는데도
  }
}

📸 왜 바뀌지 않는가

count는 이번 렌더링에서 고정된 값입니다. 27·31장에서 배운 클로저가 이번 렌더링 시점의 값을 붙잡고 있습니다.
setCount는 변수를 바꾸는 것이 아니라 "다음 렌더링은 새 값으로 해 달라"고 예약하는 것입니다. 새 값은 다음 렌더링 때 새로 만들어진 count로 들어옵니다.
"상태는 렌더링마다 찍힌 사진"이라고 생각하면 정확합니다.

이 성질 때문에 생기는 함정 
function handleClick() {
  setCount(count + 1);     // count가 0이면 → 1로 예약
  setCount(count + 1);     // count는 여전히 0 → 또 1로 예약
  setCount(count + 1);     // 또 1
}
// 결과: 3이 아니라 1

// ✅ 이전 값을 기준으로 하려면 '함수형 갱신'을 씁니다
function handleClick() {
  setCount(prev => prev + 1);   // 0 → 1
  setCount(prev => prev + 1);   // 1 → 2
  setCount(prev => prev + 1);   // 2 → 3
}
// 결과: 3 ✅

🔁 함수형 갱신을 언제 쓰나

  • 이전 값을 기준으로 계산할 때 — 증가·토글·배열에 추가
  • 비동기 작업 뒤에 상태를 바꿀 때 — 그 사이에 값이 바뀌었을 수 있습니다
  • useEffect·useCallback의 의존성을 줄일 때(61·64장)

헷갈리면 함수형을 쓰세요. 손해 볼 일이 없습니다.

일괄 처리

React는 여러 setState를 모아 한 번에 처리합니다(배칭). 이벤트 핸들러 안에서 상태를 다섯 개 바꿔도 렌더링은 한 번입니다. React 18부터는 setTimeout·class="term" data-term="promise">Promise 안에서도 자동으로 일괄 처리됩니다.

불변성 — 반드시 지켜야 할 규칙

🚨 상태를 직접 수정하면 화면이 안 바뀝니다

// ❌ 원본을 수정
todos.push(newTodo);
setTodos(todos);              // 같은 배열이라 React가 "안 바뀌었다"고 판단

user.name = "새 이름";
setUser(user);                // 같은 객체

// ✅ 새로 만들기
setTodos([...todos, newTodo]);
setUser({ ...user, name: "새 이름" });

React는 Object.is로 이전 값과 새 값을 비교합니다. 같은 객체를 넘기면 내용이 달라졌어도 같다고 판단해 다시 그리지 않습니다. 25장의 참조 복사 개념이 여기서 결정적으로 작용합니다.

배열 상태 다루기 (29장의 표를 다시 보세요) 
const [items, setItems] = useState([]);

// 추가
setItems([...items, newItem]);              // 끝에
setItems([newItem, ...items]);              // 앞에

// 삭제
setItems(items.filter(i => i.id !== id));

// 수정 — map으로 해당 항목만 새 객체로
setItems(items.map(i =>
  i.id === id ? { ...i, done: !i.done } : i
));

// 정렬 — 원본을 바꾸지 않는 버전을 씁니다
setItems([...items].sort((a, b) => a.order - b.order));
setItems(items.toSorted((a, b) => a.order - b.order));

// ❌ 원본을 바꾸는 메서드는 쓰지 않습니다
// items.push / pop / splice / sort / reverse
중첩된 객체 — 바뀌는 경로를 전부 새로 만듭니다 
const [user, setUser] = useState({
  name: "홍길동",
  address: { city: "서울", zip: "04524" }
});

// ❌ 안쪽 객체가 그대로라 React가 못 알아챌 수 있습니다
setUser({ ...user, address: { ...user.address } });   // 값도 안 바뀜

// ✅
setUser({
  ...user,
  address: { ...user.address, city: "부산" }
});

🪜 중첩이 깊으면 구조를 의심하세요

3단계 이상 중첩된 상태를 매번 펼쳐 쓰는 것은 실수를 부릅니다.

  • 상태를 평평하게 나눕니다. user와 address를 따로 두면 됩니다.
  • 목록은 id를 키로 하는 객체로 관리하는 방법도 있습니다(29장의 reduce 패턴).
  • 정말 복잡하면 Immer 같은 라이브러리가 "수정하듯 쓰면 새 객체를 만들어" 줍니다.

상태 끌어올리기

두 컴포넌트가 같은 데이터를 써야 한다면, 그 상태를 공통 부모로 올립니다.

function App() {
  // ✅ 두 자식이 공유하므로 부모가 가집니다
  const [query, setQuery] = useState("");
  const filtered = items.filter(i => i.name.includes(query));

  return (
    <>
      <SearchBar value={query} onChange={setQuery} />
      <ItemList items={filtered} />
    </>
  );
}

function SearchBar({ value, onChange }) {
  return <input value={value} onChange={e => onChange(e.target.value)} />;
}

⬆️ 너무 높이 올리지는 마세요

모든 상태를 최상위로 올리면 props를 여러 단계 내려보내야 합니다(prop drilling). 그리고 부모가 바뀔 때마다 관련 없는 자식들까지 다시 렌더링됩니다.
원칙은 "그 상태를 쓰는 컴포넌트들의 가장 가까운 공통 부모"입니다. 그 이상 올릴 필요가 없습니다. 정말 넓게 필요하면 Context(65장)를 고려합니다.

상태 설계 — 가장 중요한 판단

🧮 계산할 수 있는 것은 상태로 두지 마세요

// ❌ 상태 세 개 — 서로 어긋날 수 있습니다
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);
const [isEmpty, setIsEmpty] = useState(true);
// items를 바꿀 때마다 나머지 둘도 갱신해야 합니다. 하나만 빠뜨리면 버그.

// ✅ 상태는 하나, 나머지는 계산
const [items, setItems] = useState([]);
const total = items.reduce((s, i) => s + i.price, 0);
const isEmpty = items.length === 0;
// 어긋날 수가 없습니다. 57장의 UI = f(state) 그대로입니다.
상태로 둘 것계산할 것
사용자가 입력한 값
서버에서 받은 원본 데이터
열림·닫힘 같은 UI 상태
현재 선택된 항목의 id		합계·평균·개수
필터링·정렬 결과
유효성 검사 결과
선택된 항목의 객체(id로 찾으면 됨)

🔗 객체 대신 id를 저장하세요

// ❌ 선택된 항목의 '객체'를 저장
const [selected, setSelected] = useState(null);
// items가 갱신되면 selected는 옛 데이터를 붙잡고 있습니다

// ✅ id만 저장하고 필요할 때 찾습니다
const [selectedId, setSelectedId] = useState(null);
const selected = items.find(i => i.id === selectedId);
// 항상 최신 데이터입니다

불가능한 상태를 만들지 않기

// ❌ 조합이 8가지인데 실제로 의미 있는 것은 4가지뿐입니다
const [isLoading, setIsLoading] = useState(false);
const [data, setData] = useState(null);
const [error, setError] = useState(null);
// 로딩 중인데 에러도 있는 상태? 데이터와 에러가 동시에 있는 상태?

// ✅ 하나의 상태로 (52장의 판별 유니온)
const [state, setState] = useState({ status: "idle" });
// { status: "loading" }
// { status: "success", data }
// { status: "error", error }

상태 초기화와 key

// 사용자를 바꿔도 폼 내용이 남아 있는 문제
<UserForm userId={selectedId} />

// ✅ key가 바뀌면 React는 '다른 컴포넌트'로 보고 상태를 초기화합니다
<UserForm key={selectedId} userId={selectedId} />

key는 목록에만 쓰는 것이 아닙니다. "이 컴포넌트를 완전히 새로 시작하라"는 신호로도 쓸 수 있습니다. useEffect로 상태를 초기화하는 것보다 훨씬 간단하고 안전합니다.

🛠️ 현장 노트 — 상태 관련 자가 점검

  1. 이 값을 다른 상태로 계산할 수 있는가? → 그렇다면 상태로 두지 않습니다.
  2. 불가능한 조합이 만들어질 수 있는가? → 하나의 상태로 합칩니다.
  3. 상태를 직접 수정하고 있지 않은가? → 항상 새 객체·배열을 만듭니다.
  4. 이 상태가 정말 여기 있어야 하는가? → 가장 가까운 공통 부모까지만.
  5. 객체를 저장하고 있지 않은가? → id를 저장하고 찾아 씁니다.

📌 요약

  • useState는 값을 기억하고 변경 시 다시 그리게 한다.
  • 상태는 스냅샷이다. setState 직후에는 값이 그대로다.
  • 이전 값 기준이면 함수형 갱신 setX(prev => …).
  • 불변성 필수. React는 Object.is로 비교하므로 같은 객체를 넘기면 갱신되지 않는다.
  • 중첩 상태는 바뀌는 경로 전부를 새로 만든다. 깊으면 구조를 의심한다.
  • 상태는 가장 가까운 공통 부모까지만 올린다.
  • 계산할 수 있는 것은 상태로 두지 않는다. 객체 대신 id를 저장한다.
  • 불가능한 상태를 만들 수 없게 설계한다.
  • key를 바꾸면 컴포넌트 상태가 초기화된다.
