스택과 힙

프로그램이 쓰는 메모리는 성격이 다른 두 영역으로 나뉩니다.

스택(stack)힙(heap)
담는 것함수 호출 정보와 작은 값객체·배열·함수 같은 '덩어리'
크기정해져 있다정해져 있지 않다
속도빠르다 (넣고 빼기만)상대적으로 느리다
정리함수가 끝나면 자동으로가비지 컬렉터가
용량작다 → 스택 오버플로(82장)크다

25장에서 배운 원시값과 참조값의 차이가 바로 이 구조에서 나옵니다. const a = 10은 값 자체를 들고 있고, const obj = {}는 힙에 있는 객체의 주소를 들고 있습니다.

복사가 다르게 동작하는 이유 
let a = 10;          스택 ┌─────────┐
let b = a;                │ a = 10  │   값 자체를 복사 → 서로 무관
                          │ b = 10  │
                          └─────────┘

let o1 = { n: 1 };   스택 ┌──────────┐      힙 ┌──────────┐
let o2 = o1;              │ o1 = @100├────────▶│ { n: 1 } │
                          │ o2 = @100├────────▶│          │
                          └──────────┘        └──────────┘
                          주소만 복사 → 같은 객체를 본다

🔬 정확히 말하면

"원시값은 스택, 객체는 힙"은 이해를 위한 모델입니다. 실제 배치는 엔진의 구현 사항입니다. V8은 작은 정수를 값 안에 직접 끼워 넣기도 하고, 탈출하지 않는 객체를 최적화로 스택에 두기도 합니다. 직접 관찰할 수도, 제어할 수도 없습니다. 중요한 건 "값을 복사하느냐 주소를 복사하느냐"라는 동작의 차이이고, 그 부분은 명세로 보장됩니다.

가비지 컬렉터는 무엇을 치우나

C 같은 언어에서는 개발자가 직접 메모리를 반납합니다. JavaScript는 가비지 컬렉터(GC)가 대신합니다. 기준은 하나입니다.

🧹 기준: 도달 가능한가

전역 객체, 현재 실행 중인 함수의 변수 같은 출발점(루트)에서 참조를 타고 갈 수 있는 값은 살려 두고, 갈 수 없는 값은 치웁니다.
"쓸모없어 보이는가"가 아니라 "닿을 수 있는가"입니다. 이 구분이 누수를 이해하는 열쇠입니다.

표시하고 쓸어 담기 (mark-and-sweep) 
루트 ──▶ A ──▶ B      ① 루트에서 출발해 닿는 것을 전부 '표시'
         └──▶ C       ② 표시 안 된 것을 회수

              D  ✗    D는 아무도 참조하지 않는다 → 회수 대상
         E ⇄ F  ✗     E와 F는 서로를 참조하지만
                      루트에서 닿을 수 없다 → 둘 다 회수 대상

🔗 "서로를 참조하면 GC가 못 지운다"는 옛말입니다

이건 참조 카운팅 방식의 한계였습니다. 참조 개수를 세는 방식은 순환 참조(A가 B를, B가 A를)에서 카운트가 0이 되지 않아 영원히 남았습니다. 현대 JavaScript 엔진은 도달 가능성 기반입니다. 서로 붙잡고 있어도 루트에서 닿을 수 없으면 통째로 회수됩니다. (구형 IE에서 DOM과 JS 객체의 순환 참조가 누수를 일으키던 것은 이제 옛날 이야기입니다.) 따라서 "순환 참조를 피하라"는 메모리 때문이 아닙니다. 순환 import를 피해야 하는 이유는 초기화 순서 문제이지(82장), GC 때문이 아닙니다.

GC는 언제 도나 — 제어할 수 없습니다

GC 실행 시점은 엔진이 정합니다. 코드로 강제할 방법이 없습니다. obj = null은 "이 변수가 더 이상 그 객체를 가리키지 않는다"는 뜻일 뿐, 즉시 메모리를 반납하라는 명령이 아닙니다.

V8은 세대별 GC를 씁니다. 대부분의 객체는 금방 죽는다는 관찰에 기반해, 새로 만든 객체는 작은 영역에서 자주, 빠르게 정리하고, 거기서 살아남은 것만 큰 영역으로 옮겨 가끔 정리합니다. 덕분에 대부분의 GC가 밀리초 단위로 끝나 화면이 끊기지 않습니다.

메모리 누수 — 닿을 수 있어서 못 치우는 것들

누수는 "GC가 고장 난 것"이 아닙니다. 더 이상 필요 없는데도 참조가 남아 있어서, GC 입장에서는 살려 둬야 하는 것입니다. 그래서 원인은 항상 "어디선가 아직 붙잡고 있다"입니다.

① 제거하지 않은 이벤트 리스너

가장 흔한 원인 
// ❌ 컴포넌트가 사라져도 리스너는 window에 남는다
useEffect(() => {
  const onScroll = () => setY(window.scrollY);
  window.addEventListener("scroll", onScroll);
}, []);
// window(루트)가 onScroll을 붙잡고,
// onScroll이 클로저로 setY와 컴포넌트 관련 데이터를 붙잡는다 → 전부 못 치운다

// ✅ 정리 함수로 끊는다
useEffect(() => {
  const onScroll = () => setY(window.scrollY);
  window.addEventListener("scroll", onScroll);
  return () => window.removeEventListener("scroll", onScroll);
}, []);

🎯 removeEventListener는 같은 함수 참조여야 합니다

// ❌ 새 화살표 함수라 등록된 것과 다른 함수 → 아무것도 안 지워짐
window.addEventListener("resize", () => handle());
window.removeEventListener("resize", () => handle());

// ✅ 변수에 담아 같은 참조를 넘긴다
const onResize = () => handle();
window.addEventListener("resize", onResize);
window.removeEventListener("resize", onResize);

// ✅ 여러 개를 한 번에 끊으려면 AbortController (38장)
const ac = new AbortController();
window.addEventListener("resize", onResize, { signal: ac.signal });
window.addEventListener("scroll", onScroll, { signal: ac.signal });
ac.abort();   // 둘 다 한 번에 해제

② 멈추지 않은 타이머

// ❌ 화면을 떠나도 5초마다 계속 돈다. 콜백이 잡은 데이터도 계속 살아 있다
useEffect(() => {
  setInterval(() => refetch(), 5000);
}, []);

// ✅
useEffect(() => {
  const id = setInterval(() => refetch(), 5000);
  return () => clearInterval(id);
}, []);

③ 분리된 DOM (detached DOM)

화면에서는 지웠는데 JavaScript 변수가 그 요소를 아직 들고 있는 경우입니다. DOM 트리에서 떨어져 나왔지만 참조가 있어 메모리에 남습니다. 자식 노드까지 통째로 남기 때문에 덩치가 큰 누수가 됩니다.

④ 끝없이 자라는 전역 캐시

// ❌ 모듈 최상단의 Map은 앱이 살아 있는 내내 남는다
const cache = new Map();
export function getUser(id) {
  if (!cache.has(id)) cache.set(id, fetchUser(id));
  return cache.get(id);   // 키가 무한정 늘어난다
}

// ✅ 개수를 제한하거나(LRU), 만료 시간을 두거나,
//    아예 TanStack Query 같은 라이브러리에 맡긴다 (67장)

WeakMap — 붙잡지 않는 참조

WeakMap·WeakSet은 키로 쓴 객체를 GC로부터 지켜 주지 않습니다. 그 객체를 가리키는 다른 참조가 모두 사라지면, WeakMap의 항목도 함께 정리됩니다.

일반 Map과의 차이 
const map = new Map();
const weak = new WeakMap();

let el = document.querySelector("#box");
map.set(el, { clicks: 0 });     // map이 el을 붙잡는다 → el은 절대 회수 안 됨
weak.set(el, { clicks: 0 });    // weak는 붙잡지 않는다

el.remove();
el = null;
// map  : el과 부가 데이터가 메모리에 남는다 (누수)
// weak : 다른 참조가 없으므로 el과 항목이 함께 정리된다

🛠️ 현장 노트 — WeakMap을 쓰는 경우

  1. DOM 요소에 부가 데이터를 붙일 때 — 요소가 사라지면 데이터도 함께 사라져야 합니다.
  2. 객체를 키로 하는 메모이제이션(83장) — 원본 객체가 없어지면 캐시도 정리됩니다.
  3. 클래스의 비공개 데이터 보관 — 요즘은 #private 필드(32장)가 더 낫습니다.
  4. 제약: 키는 객체여야 하고(문자열·숫자는 안 됨), 순회할 수 없으며 size도 없습니다. 언제 정리될지 관찰할 수 없기 때문입니다.
  5. 대부분의 경우 WeakMap은 필요 없습니다. 리스너와 타이머만 제대로 정리해도 누수의 90%는 사라집니다.

DevTools로 누수 찾기

Chrome DevTools · Memory 패널 (49장) 
1. 힙 스냅샷 비교 (가장 실용적)
   ① Memory 탭 → "Heap snapshot" → 스냅샷 1
   ② 의심되는 동작을 반복한다 (페이지 A→B→A 를 10번 이동 등)
   ③ 스냅샷 2 → 위쪽 드롭다운에서 "Comparison" 선택
   ④ Delta(증가량)가 큰 항목을 본다. 반복 후에도 계속 늘면 누수다

2. 분리된 DOM 찾기
   스냅샷의 필터 칸에 Detached 입력
   → "Detached HTMLDivElement" 같은 항목이 보이면
   → 아래 Retainers(무엇이 붙잡고 있나)를 펼쳐 범인 코드를 찾는다

3. 실시간 그래프
   Performance 탭에서 Memory 체크 → 녹화
   → JS Heap 선이 계단식으로 올라가기만 하고 내려오지 않으면 누수 신호

팁: 스냅샷을 찍기 전에 휴지통 아이콘(Collect garbage)을 눌러
    이미 회수 가능한 것들을 먼저 치워야 비교가 정확합니다.

🛠️ 현장 노트 — SPA라서 더 중요합니다

전통적인 웹사이트는 페이지를 이동할 때마다 전체가 새로 로드되어 메모리가 초기화됐습니다. SPA(React·Next.js)는 한 번 로드한 뒤 계속 같은 페이지 안에서 움직입니다. 그래서 화면 전환마다 조금씩 새는 메모리가 몇 시간 뒤에 쌓여 탭이 느려지거나 죽습니다. 관리자 대시보드, 채팅, 실시간 모니터링처럼 오래 켜 두는 화면에서 특히 문제가 됩니다.

예방은 단순합니다. useEffect에서 무언가를 등록했다면, 반드시 정리 함수에서 해제한다(61장). 리스너, 타이머, 구독, fetch(AbortController), WebSocket, Observer 전부입니다.

📌 요약

  • 스택은 호출 정보와 작은 값, 힙은 객체·배열·함수. 참조값 복사가 주소 복사인 이유다.
  • GC의 기준은 "쓸모"가 아니라 "루트에서 닿을 수 있는가"다.
  • 현대 엔진은 도달 가능성 기반이라 순환 참조도 회수한다. 참조 카운팅 시대의 이야기는 옛말이다.
  • GC 시점은 제어할 수 없다. = null은 참조를 끊는 것이지 즉시 반납이 아니다.
  • 누수 4대 원인: 리스너 · 타이머 · 분리된 DOM · 무한정 자라는 캐시.
  • removeEventListener는 같은 함수 참조여야 한다. 여러 개면 AbortController.
  • WeakMap은 키를 붙잡지 않아 원본과 함께 정리된다.
  • DevTools Memory → 힙 스냅샷 비교, 필터에 Detached. SPA는 누수가 누적된다.
