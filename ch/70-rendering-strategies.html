핵심 질문: HTML을 언제 만드는가

먼저 단어 하나를 정리합니다. 빌드(build)는 배포하기 전에 npm run build 같은 명령으로 우리가 쓴 코드를 브라우저와 서버가 바로 쓸 수 있는 파일로 한 번 묶고 변환하는 단계입니다(47장의 번들러). 사용자가 접속하기 전, 개발자 컴퓨터나 배포 서버에서 일어납니다.

🍱 음식에 비유하면

  • CSR = 밀키트 — 재료(빈 HTML + JS)만 보내고 손님(브라우저)이 직접 조리합니다. 받자마자 먹을 수는 없습니다.
  • SSR = 주문 즉시 조리 — 주문(요청)이 들어올 때마다 주방(서버)이 완성된 요리를 만들어 냅니다. 항상 따끈하지만 주방이 바쁩니다.
  • SSG = 미리 만든 도시락 — 문 열기 전(빌드)에 만들어 진열해 둡니다. 집어 가기만 하면 되니 가장 빠르지만 메뉴를 바꾸려면 다시 싸야 합니다.
  • ISR = 주기적으로 새로 싸는 도시락 — 진열은 도시락처럼 하되, 일정 시간이 지나면 새것으로 교체합니다.
네 가지 시점 
CSR   브라우저에서, 요청 후          → 빈 HTML을 받고 JS가 그림
SSR   서버에서, 요청이 올 때마다      → 완성된 HTML을 받음
SSG   빌드할 때 미리                 → 저장해 둔 HTML을 받음
ISR   빌드할 때 미리 + 주기적으로 갱신 → SSG인데 낡으면 다시 만듦

CSR — 클라이언트 렌더링

브라우저가 처음 받는 HTML 
<!doctype html>
<html>
  <body>
    <div id="root"></div>      <!-- 텅 비어 있습니다 -->
    <script src="/bundle.js"></script>
  </body>
</html>
진행 순서 
HTML(빈 껍데기) → JS 다운로드 → JS 실행 → API 호출 → 데이터 도착 → 화면
└──────────────── 이 시간 동안 사용자는 흰 화면을 봅니다 ─────────────┘

🔍 검색엔진과 CSR

구글 크롤러는 JavaScript를 실행할 수 있습니다. 그래서 CSR 페이지도 색인될 수 있습니다. 다만 JS 실행은 별도 큐에서 나중에 처리되어 색인이 늦어질 수 있고, 다른 검색엔진과 SNS 미리보기 크롤러는 대개 JS를 실행하지 않습니다. 카카오톡에 링크를 붙였을 때 미리보기가 안 나오는 이유가 이것입니다(10장).

SSR — 서버 렌더링

진행 순서 
요청 → 서버가 데이터 조회 → HTML 완성 → 전송 → 화면 보임(!) → JS 다운로드 → 하이드레이션 → 상호작용 가능
                                            └ 여기서 이미 읽을 수 있습니다 ┘
장점단점
첫 화면이 빠릅니다
SEO에 유리합니다
SNS 미리보기가 나옵니다
느린 기기에서도 내용은 보입니다		서버가 필요하고 비용이 듭니다
요청마다 서버가 일합니다
TTFB(첫 바이트까지)가 늦을 수 있습니다

하이드레이션

💧 마른 HTML에 물을 붓는다

서버가 보낸 HTML은 보이기만 하고 아무것도 안 됩니다. 버튼을 눌러도 반응이 없습니다.
브라우저에서 React가 다시 실행되어 이미 있는 DOM에 이벤트 핸들러와 상태를 연결하는 과정을 하이드레이션이라고 합니다. 이것이 끝나야 상호작용이 됩니다.

💥 하이드레이션 불일치 오류

// ❌ 서버와 클라이언트의 결과가 달라집니다
function Clock() {
  return <p>{new Date().toLocaleTimeString()}</p>;
}
// 서버: "오후 3:00:01" / 브라우저: "오후 3:00:02" → 불일치 오류

// ❌ 서버에는 window가 없습니다
const width = window.innerWidth;

// ✅ 브라우저에서만 쓰는 값은 Effect에서
const [time, setTime] = useState(null);
useEffect(() => { setTime(new Date().toLocaleTimeString()); }, []);

서버 HTML과 클라이언트의 첫 렌더링 결과가 일치해야 합니다. Date·Math.random()·window·localStorage가 대표적인 원인입니다. "Text content did not match" 오류를 보면 이 목록을 떠올리세요.

⏳ SSR의 함정 — 보이지만 눌리지 않는 시간

화면은 빨리 보이는데 JS 로딩과 하이드레이션이 끝날 때까지 버튼이 안 눌립니다. 사용자는 다 됐다고 생각하고 클릭했다가 반응이 없어 혼란스러워합니다. 이 지표를 INP(상호작용 반응성)로 측정합니다(76장).
이 문제를 줄이려는 것이 서버 컴포넌트(69장)와 부분 하이드레이션 계열의 기술입니다. 하이드레이션할 코드 자체를 줄이는 방향입니다.

SSG — 정적 생성

빌드 시점: 모든 페이지의 HTML을 미리 만들어 파일로 저장
요청 시점: 만들어 둔 파일을 그냥 전송 (CDN에서)
장점단점
가장 빠릅니다 (CDN에서 즉시)
가장 쌉니다 (서버 계산 없음)
서버가 죽어도 페이지는 살아 있습니다
SEO 완벽		내용이 바뀌면 다시 빌드해야 합니다
페이지가 많으면 빌드가 오래 걸립니다
사용자별 개인화 불가

블로그, 문서, 랜딩 페이지, 제품 소개처럼 모든 사용자에게 같은 내용을 보여주는 페이지에 최적입니다. (참고로 지금 보고 계신 이 책도 정적 페이지입니다.)

ISR — 증분 정적 재생성

① 빌드 때 HTML을 만들어 둠 (SSG처럼)
② 사용자에게는 저장된 HTML을 즉시 전송
③ 정해진 시간이 지나면 "낡음" 표시
④ 다음 요청이 오면 낡은 것을 그대로 주고, 뒤에서 새로 만들어 교체

♻️ SSG의 속도 + SSR의 최신성

67장에서 본 "낡은 것을 먼저 보여주고 뒤에서 갱신" 전략이 페이지 단위로 적용된 것입니다.
상품 10만 개짜리 쇼핑몰을 매번 전부 빌드할 수는 없습니다. ISR은 실제로 요청된 페이지만 만들고 주기적으로 갱신합니다. "1분마다 갱신"으로 설정하면 서버 부하는 SSG 수준인데 내용은 거의 최신입니다.
내용이 바뀌었을 때 즉시 갱신하도록 신호를 보내는 방식(온디맨드 재검증)도 있습니다.

Next.js 같은 프레임워크가 하는 일이 바로 이 선택을 화면 단위로 가능하게 하는 것입니다. 심지어 한 페이지 안에서도 정적인 부분과 동적인 부분을 나눌 수 있습니다 (부분 사전 렌더링, PPR). Next.js 16에서는 별도의 PPR 실험 플래그가 없어지고, cacheComponents: true로 켜는 Cache Components의 기본 동작이 되었습니다. 정적인 껍데기를 먼저 보내고 "use cache"를 붙인 부분은 캐시에서, 나머지는 요청 때 스트리밍으로 채웁니다(72장).

🚫 "SSR이 항상 더 좋다"는 오해

SSR은 서버 비용이 들고, 서버가 데이터를 조회하는 동안 첫 바이트가 늦어질 수 있습니다. 느린 API 하나가 전체 페이지 전송을 막습니다. SEO가 필요 없는 로그인 후 대시보드에 SSR을 쓰면 비용만 늘고 얻는 것이 거의 없습니다. 가능하면 SSG·ISR을 먼저 고려하세요. 가장 빠르고 가장 쌉니다. SSR은 정말 요청마다 달라져야 할 때만 씁니다.

🛠️ 현장 노트 — 판단 순서

  1. 모든 사용자에게 같은가? → 예: SSG / 아니오: 다음
  2. 어느 정도 낡아도 되는가? → 예: ISR / 아니오: 다음
  3. SEO나 첫 화면 속도가 중요한가? → 예: SSR / 아니오: CSR

그리고 측정하세요. "SSR로 바꾸면 빨라지겠지"라는 추측이 실제로는 TTFB만 늘리는 경우도 많습니다(49·76장).

📌 요약

  • 차이는 HTML을 언제 만드는가다. 브라우저(CSR)·요청마다(SSR)·빌드 때(SSG)·빌드+갱신(ISR). 빌드는 배포 전에 코드를 묶는 단계다.
  • CSR은 첫 화면이 느리고 SEO에 불리하다. SNS 미리보기도 안 나온다.
  • 하이드레이션은 서버 HTML에 상호작용을 연결하는 과정이고, 그동안은 눌러도 반응하지 않는다.
  • 서버와 클라이언트의 첫 렌더링 결과가 다르면 오류가 난다(Date·window 주의).
  • SSG가 가장 빠르고 싸다. ISR은 그 속도에 최신성을 더한다.
  • 화면마다 다른 전략을 쓸 수 있고, 그것이 프레임워크의 존재 이유다.
  • SSR이 항상 좋은 것은 아니다. 개인화 화면에는 비용만 늘어난다.
