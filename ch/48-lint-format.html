두 도구, 다른 일

Prettier (포매터)ESLint (린터)

🤝 둘 다 씁니다

예전에는 ESLint에도 서식 규칙이 있어 둘이 충돌했습니다. 지금은 역할을 나누는 것이 표준입니다. 서식은 Prettier에게 전부 맡기고, ESLint는 코드 품질만 봅니다.

Prettier

npm install -D prettier
.prettierrc 
{
  "semi": true,
  "singleQuote": false,
  "printWidth": 100,
  "tabWidth": 2,
  "trailingComma": "all"
}

🛑 서식 논쟁을 끝내는 것이 목적입니다

Prettier의 철학은 "의견을 강하게 가지되 옵션은 최소로"입니다. 설정 항목이 일부러 적습니다. 탭이냐 스페이스냐, 세미콜론을 붙이냐로 코드 리뷰에서 다투는 시간이 사라지는 것이 진짜 가치입니다.
어느 쪽을 고르든 상관없습니다. 팀이 하나를 정하고 자동화하면 됩니다.

ESLint

npm install -D eslint
npx eslint --init        # 대화형으로 설정 파일 생성
eslint.config.js (Flat Config — ESLint 9 이후 표준) 
import js from "@eslint/js";

export default [
  js.configs.recommended,
  {
    rules: {
      "no-unused-vars": "warn",
      "no-console": ["warn", { allow: ["warn", "error"] }],
      "eqeqeq": "error",              // == 대신 === 강제 (25장)
      "prefer-const": "error",        // 재할당 없으면 const (24장)
      "no-var": "error"
    }
  }
];

규칙의 수준은 세 가지입니다. "off"(끔), "warn"(경고), "error"(오류 — 빌드를 실패시킬 수 있음).

실제로 버그를 잡아 주는 규칙들

규칙잡아 주는 것
no-unused-vars안 쓰는 변수·import. 오타로 만든 변수도 여기서 걸립니다
no-undef선언하지 않은 변수 사용 (24장의 전역 오염)
eqeqeq==의 예상 못 한 형변환 (25장)
no-var, prefer-const스코프 문제 예방 (24장)
react-hooks/exhaustive-depsuseEffect 의존성 누락 — React 버그의 최대 원인(61장)
react-hooks/rules-of-hooks훅을 조건문 안에서 호출하는 실수(59장)
jsx-a11y/alt-textalt 없는 이미지 (8장)
no-floating-promisesawait 빠뜨린 Promise (36장). TypeScript 전용

🎯 이 두 규칙만으로도 값어치를 합니다

react-hooks/exhaustive-deps와 no-floating-promises는 실무에서 가장 자주, 가장 찾기 어려운 버그를 미리 잡아 줍니다. React·TypeScript 프로젝트라면 반드시 켜세요.

편집기 연동 — 여기서 진짜 가치가 나옵니다

.vscode/settings.json — 이 파일은 커밋해서 팀과 공유합니다 
{
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  }
}

이제 저장할 때마다 서식이 정리되고 자동 수정 가능한 ESLint 문제가 고쳐집니다. 명령어를 따로 실행할 필요가 없어야 도구가 실제로 쓰입니다. 수동으로 돌려야 하는 도구는 결국 아무도 안 씁니다.

Git 훅으로 강제하기

편집기 설정은 각자 안 켜면 그만입니다. 팀 전체에 확실히 적용하려면 커밋 시점에 검사합니다.

npm install -D husky lint-staged
npx husky init
package.json 
{
  "lint-staged": {
    "*.{js,jsx,ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{css,md,json}": ["prettier --write"]
  }
}

lint-staged는 커밋하려는 파일만 검사합니다. 프로젝트 전체를 매번 검사하면 너무 느려서 아무도 안 쓰게 되기 때문입니다.

🚦 훅은 최후의 방어선이지 유일한 방어선이 아닙니다

Git 훅은 --no-verify 옵션으로 건너뛸 수 있습니다. 그리고 각자 컴퓨터에서만 돕니다. 진짜 강제는 CI(GitHub Actions 등)에서 합니다. PR에서 린트·테스트가 실패하면 머지할 수 없게 막는 것이 최종 방어선입니다.

타입 검사와의 관계

도구잡는 것
Prettier서식
ESLint위험한 패턴. "될 수는 있지만 하면 안 되는 것"
TypeScript타입 오류. "이건 아예 말이 안 되는 것" (7부)
테스트동작. "의도대로 작동하는가" (75장)

넷은 겹치지 않고 서로를 대체하지 못합니다. TypeScript가 있어도 ESLint가 필요하고, 둘 다 있어도 테스트가 필요합니다.

🛠️ 현장 노트 — 린터를 대하는 태도

  1. 경고를 방치하지 마세요. 경고가 100개면 아무도 안 봅니다. 0개를 유지해야 새 경고가 눈에 띕니다.
  2. 규칙을 끄기 전에 이유를 이해하세요. 대부분의 규칙에는 실제 사고 사례가 있습니다. ESLint 문서에는 왜 그 규칙이 존재하는지가 적혀 있습니다.
  3. eslint-disable에는 이유를 적으세요. // eslint-disable-next-line no-console -- 배포 스크립트에서 필요
  4. 기존 프로젝트에 도입할 때는 점진적으로. 갑자기 규칙을 다 켜면 오류가 수천 개 나옵니다. 새 파일부터 적용하거나 warn으로 시작해 서서히 error로 올립니다.
  5. 규칙을 팀이 함께 정하세요. 한 사람이 정해서 강요하면 반발만 생깁니다.

📌 요약

  • Prettier는 모양, ESLint는 내용. 서식은 전부 Prettier에 맡긴다.
  • 서식 논쟁을 없애는 것 자체가 Prettier의 가치다. 어느 쪽이든 통일이 핵심.
  • ESLint는 실제 버그를 잡는다. 특히 exhaustive-deps, no-floating-promises.
  • 저장 시 자동 실행이 되어야 도구가 실제로 쓰인다.
  • Git 훅(husky + lint-staged)은 변경된 파일만 검사한다.
  • 진짜 강제는 CI에서. 훅은 우회 가능하다.
  • Prettier·ESLint·TypeScript·테스트는 서로를 대체하지 않는다.
  • 경고 0개를 유지해야 도구가 의미를 갖는다.
