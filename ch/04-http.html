HTTP는 대화의 규칙이다

HTTP는 브라우저와 서버가 대화할 때 쓰는 양식입니다. 사람으로 치면 "무엇을, 어떤 조건으로 달라"고 적는 신청서 서식이라고 보면 됩니다.

HTTP에는 중요한 성질이 하나 있습니다. 상태를 기억하지 않는다(stateless)는 것입니다. 서버는 방금 요청한 사람이 5초 전에 요청했던 그 사람인지 기본적으로 모릅니다. 매 요청이 완전히 독립적입니다. 그래서 로그인 상태를 유지하려면 따로 장치가 필요하고, 그것이 뒤에 나올 쿠키와 토큰입니다.

요청과 응답 메시지의 실제 모습

브라우저가 보내는 요청은 사실 이런 텍스트입니다.

HTTP 요청 
GET /products/42 HTTP/1.1           ← ① 시작 줄: 메서드, 경로, 버전
Host: shop.example.com              ← ② 헤더들: 부가 정보
Accept: text/html
Accept-Language: ko-KR
Cookie: session=abc123
                                    ← ③ 빈 줄 (헤더 끝을 알림)
                                    ← ④ 본문 (GET에는 보통 없음)

서버의 응답도 같은 모양입니다.

HTTP 응답 
HTTP/1.1 200 OK                     ← ① 상태 줄: 버전, 상태 코드, 설명
Content-Type: text/html; charset=utf-8   ← ② 헤더들
Content-Length: 1024
Cache-Control: max-age=3600
                                    ← ③ 빈 줄
<!doctype html><html>…             ← ④ 본문: 실제 내용

👀 직접 보는 법

아무 사이트에서 F12(맥은 ⌘⌥I)를 눌러 class="term" data-term="devtools">개발자 도구를 열고 Network 탭에서 새로고침해 보세요. 요청 하나를 클릭하면 위의 헤더가 그대로 보입니다. 이 화면을 읽을 줄 아는 것과 모르는 것의 차이가 디버깅 시간을 몇 시간씩 가릅니다. 49장에서 제대로 다룹니다.

메서드 — 무엇을 하려는가

메서드의미안전멱등

HEADGET과 같지만 본문 없이 헤더만OO

"안전"과 "멱등"이 뭔가요

  • 안전(safe) — 서버의 상태를 바꾸지 않는다. 몇 번을 불러도 데이터가 변하지 않음. 조회 전용.
  • 멱등(idempotent) — 여러 번 실행해도 결과가 한 번 실행한 것과 같다. 상태를 바꾸긴 하지만 반복해도 누적되지 않음.

🔀 엘리베이터 버튼으로 이해하기

엘리베이터 호출 버튼을 열 번 눌러도 엘리베이터는 한 번 옵니다. 이게 멱등입니다. 반면 자판기 결제 버튼을 열 번 누르면 열 번 결제됩니다. 이게 멱등이 아닌 것이고, POST가 여기 해당합니다. "결제 버튼을 두 번 눌렀는데 두 번 결제됐어요"라는 사고가 나오는 지점이 정확히 여깁니다.

⚠️ 실무에서 진짜 중요한 규칙

데이터를 바꾸는 일에 GET을 쓰면 안 됩니다. GET은 안전하다고 약속된 메서드라서 브라우저·CDN·검색엔진 크롤러가 마음대로 미리 호출하거나 캐시할 수 있습니다. GET /posts/42/delete 같은 주소를 만들어 두면, 검색 크롤러가 지나가며 글을 전부 지울 수 있습니다. 실제로 있었던 사고입니다.

상태 코드 — 세 자리로 읽는 결과

전부 외울 필요 없습니다. 첫 자리만 알면 절반은 읽힙니다.

대뜻한 줄 해석
1xx정보"계속 진행 중" (직접 볼 일 거의 없음)
2xx성공"됐습니다"
3xx리다이렉션"거기 아니고 저기로 가세요"
4xx클라이언트 오류"당신이 잘못 요청했습니다"
5xx서버 오류"우리가 잘못했습니다"

4xx와 5xx를 구분하는 것이 핵심입니다. 4xx면 요청을 고쳐야 하고, 5xx면 서버 담당자에게 알려야 합니다.

🚫 401과 403을 헷갈리지 마세요

401 Unauthorized — 이름과 달리 실제 뜻은 "인증되지 않음"입니다. 당신이 누군지 모르겠으니 로그인하세요. 403 Forbidden — 누군지는 알겠는데 그 일을 할 권한이 없습니다. 로그인해도 안 됩니다. 일반 회원이 관리자 페이지에 들어가려 하면 403입니다. 401이 아닙니다.

헤더 — 요청과 응답에 붙는 쪽지

헤더방향하는 일
Host요청어느 도메인에 온 요청인지. 한 서버가 여러 사이트를 운영할 수 있게 해 줍니다
Accept요청"나는 이런 형식을 받을 수 있다"
Authorization요청인증 토큰을 담습니다
User-Agent요청브라우저·기기 정보. 얼마든지 조작 가능하므로 신뢰하면 안 됩니다
Content-Type둘 다본문이 어떤 형식인지. application/json, text/html 등
Cache-Control응답이 응답을 얼마나 캐시해도 되는지
Set-Cookie응답브라우저에 쿠키를 저장시킵니다
Location응답3xx일 때 갈 곳

⚠️ Content-Type은 그냥 형식 표시가 아닙니다

브라우저는 이 헤더를 보고 내용을 어떻게 취급할지 결정합니다. text/html로 내려온 것은 HTML로 해석되고 그 안의 스크립트가 실행됩니다. 사용자가 올린 파일을 잘못된 Content-Type으로 내려주면 그 자체가 보안 사고가 됩니다(78장).

쿠키 — 상태 없는 HTTP에 기억을 붙이기

HTTP는 상태를 기억하지 않는다고 했습니다. 그런데 로그인은 유지되죠. 어떻게 할까요?

  1. 로그인에 성공하면 서버가 응답에 Set-Cookie: session=abc123을 담아 보냅니다.
  2. 브라우저는 이 값을 저장합니다.
  3. 이후 같은 사이트로 가는 모든 요청에 브라우저가 자동으로 Cookie: session=abc123을 붙입니다.
  4. 서버는 그 값을 보고 "아, 이 사람은 아까 로그인한 그 사람"이라고 알아봅니다.

중요한 것은 브라우저가 자동으로 붙인다는 점입니다. 편리하지만 동시에 위험합니다. 공격자가 만든 페이지에서 여러분의 은행 사이트로 요청을 보내면 쿠키도 같이 따라갑니다. 이 공격을 CSRF라고 하고, 이를 막기 위한 SameSite 같은 쿠키 옵션이 78장에 나옵니다.

쿠키 옵션하는 일
HttpOnlyJavaScript에서 읽을 수 없게 만듭니다. XSS 공격으로 세션을 훔쳐가는 것을 막습니다
SecureHTTPS 연결에서만 전송합니다
SameSite다른 사이트에서 시작된 요청에 이 쿠키를 붙일지 통제합니다
Max-Age / Expires유효 기간. 없으면 브라우저를 닫을 때 사라집니다

HTTPS — 무엇을 지키고 무엇을 못 지키나

HTTPS는 HTTP에 TLS라는 암호화 계층을 씌운 것입니다. (SSL은 TLS의 옛 이름입니다. 지금은 TLS를 쓰면서 관행적으로 "SSL 인증서"라고 부릅니다.)

HTTPS는 세 가지를 보장합니다.

  • 기밀성 — 중간에서 들여다봐도 내용을 알 수 없습니다.
  • 무결성 — 중간에서 내용을 바꾸면 들킵니다.
  • 인증 — 접속한 서버가 정말 그 도메인의 주인인지 인증서로 확인합니다.

🚫 HTTPS에 대한 가장 위험한 오해

오해 — HTTPS를 쓰면 사이트가 안전하다. 사실 — HTTPS는 이동 중인 구간만 보호합니다. 자물쇠 아이콘은 "이 연결은 도청되지 않는다"는 뜻이지 "이 사이트는 착하다"는 뜻이 아닙니다. 피싱 사이트도 무료로 HTTPS 인증서를 받을 수 있습니다. 그리고 데이터가 도착한 뒤 브라우저 안에서는 전부 평문이므로, JavaScript에 적어 둔 비밀은 HTTPS와 무관하게 그대로 노출됩니다.

HTTP/1.1, 2, 3

버전핵심 변화남은 문제
HTTP/1.1
(1997)		연결을 재사용(keep-alive). 텍스트 기반한 연결에서 요청을 하나씩 처리. 앞 요청이 느리면 뒤가 전부 밀립니다(HOL 블로킹)
HTTP/2
(2015)		하나의 연결에서 여러 요청을 동시에(멀티플렉싱). 헤더 압축. 이진 형식TCP 자체의 특성 때문에 패킷 하나가 유실되면 그 연결의 모든 스트림이 함께 기다립니다
HTTP/3
(2022)		TCP 대신 QUIC(UDP 기반)을 사용해 TCP 수준의 막힘을 제거. 연결 수립도 더 빠릅니다—

🛠️ 현장 노트 — 옛 최적화가 지금은 손해가 되는 경우

HTTP/1.1 시절에는 요청 수를 줄이는 것이 최우선이라, 작은 이미지를 하나로 합치거나 JS 파일을 전부 하나로 묶는 기법이 표준이었습니다. HTTP/2 이후에는 여러 요청을 동시에 처리할 수 있어, 무조건 하나로 합치는 것이 오히려 손해일 수 있습니다. 파일 하나만 바뀌어도 전체를 다시 받아야 하기 때문입니다. "예전에 좋다고 배운 최적화"를 지금도 그대로 적용하면 안 되는 대표적인 예입니다.

📌 요약

  • HTTP 메시지 = 시작 줄 + 헤더 + 빈 줄 + 본문. 요청과 응답 모두 같은 구조.
  • HTTP는 상태를 기억하지 않는다. 로그인 유지는 쿠키·토큰으로 따로 만든다.
  • 안전 = 상태를 바꾸지 않음, 멱등 = 여러 번 해도 결과가 같음. GET은 둘 다, POST는 둘 다 아니다.
  • 상태 코드는 첫 자리로 읽는다. 4xx는 요청자 잘못, 5xx는 서버 잘못.
  • 401은 "누군지 모름", 403은 "권한 없음".
  • 쿠키는 브라우저가 자동으로 붙인다. 편리함이 곧 CSRF의 원인이다.
  • HTTPS는 전송 구간만 보호한다. 사이트의 선의를 보장하지 않는다.
  • HTTP/2는 멀티플렉싱, HTTP/3은 QUIC으로 TCP 수준의 막힘까지 해결했다.
