스택 — 마지막에 넣은 것이 먼저 나온다

스택(stack)은 쌓아 올린 접시입니다. 넣을 때도 위, 뺄 때도 위. 마지막에 넣은 것이 가장 먼저 나오므로 LIFO(Last In, First Out)라고 부릅니다.

프론트엔드에서 스택이 쓰이는 곳 
콜 스택            함수를 호출하면 쌓이고, 끝나면 걷어낸다 (30·35장)
실행 취소(Undo)     마지막 동작부터 되돌린다
브라우저 히스토리   뒤로 가기는 가장 최근 방문부터
괄호 · 태그 짝 검사  여는 것을 쌓고, 닫는 것이 오면 꺼내서 맞춰 본다
DFS(깊이 우선 탐색) 재귀 자체가 콜 스택을 쓰는 것

스택 오버플로

콜 스택에는 한계가 있습니다. 함수가 자기를 계속 부르면 스택이 꽉 차고 RangeError: Maximum call stack size exceeded가 납니다. 한계는 엔진·환경마다 다르며 대략 수천에서 수만 단계 수준입니다.

🔁 "JavaScript는 꼬리 호출 최적화가 되니 재귀가 안전하다"

사실상 아닙니다. 꼬리 호출 최적화(TCO)는 ES2015 명세에 들어갔지만, 실제로 구현한 엔진은 Safari(JavaScriptCore)뿐입니다. V8(Chrome·Node)과 SpiderMonkey(Firefox)는 구현하지 않았습니다. 그래서 깊은 재귀를 실무 코드에 쓰면 안 됩니다. 데이터가 어디까지 깊어질지 모르는 트리 순회는 명시적 스택(배열)을 쓰는 반복문으로 바꾸는 편이 안전합니다. 반대로 깊이가 뻔한 경우(카테고리 3단계, 댓글 2단계)는 재귀가 훨씬 읽기 쉽습니다. 상황으로 판단하세요.

큐 — 먼저 온 것이 먼저 나간다

큐(queue)는 줄 서기입니다. 뒤로 들어와 앞으로 나갑니다. FIFO(First In, First Out).

35장의 태스크 큐와 마이크로태스크 큐가 정확히 이것입니다. 이벤트 루프는 큐 앞에서 하나씩 꺼내 실행합니다. 그래서 먼저 등록된 콜백이 먼저 실행됩니다.

🐢 큰 큐에 shift()를 쓰지 마세요

배열의 shift()는 앞을 빼고 나머지를 전부 당기는 동작입니다(81장). 항목이 수만 개인 큐에서 shift를 반복하면 눈에 띄게 느려집니다. 대안은 읽기 위치를 가리키는 인덱스를 따로 두고 arr[head++]로 꺼내는 방식입니다. 다만 대부분의 프론트엔드 큐는 항목이 수십 개 수준이라 shift로 충분합니다. 규모를 보고 판단하세요.

연결 리스트 — React 안에 들어 있는 구조

연결 리스트는 값과 "다음 노드를 가리키는 참조"를 한 묶음으로 만들어 사슬처럼 이은 구조입니다. 메모리에 흩어져 있어도 됩니다.

배열 vs 연결 리스트 
배열        [10][20][30][40]     인덱스 접근 즉시 / 중간 삽입은 전부 이동
연결 리스트  10 → 20 → 30 → 40    인덱스 접근은 처음부터 / 중간 삽입은 참조만 바꾸면 끝

                     ↓ 20과 30 사이에 25 삽입
            10 → 20 → 25 → 30 → 40     (이동 없음)

프론트엔드에서 연결 리스트를 직접 만들 일은 거의 없습니다. 하지만 React 내부가 이 구조를 씁니다. 컴포넌트의 훅들은 호출 순서대로 연결 리스트에 저장되고, React는 렌더링마다 그 사슬을 순서대로 따라갑니다.

💡 "훅을 조건문 안에서 부르지 마라"의 진짜 이유

React는 훅을 이름으로 찾지 않습니다. 호출 순서로 사슬의 몇 번째 칸인지를 셉니다. if (cond) useState(...)처럼 조건에 따라 호출 개수가 달라지면 두 번째 렌더링에서 칸이 어긋나 엉뚱한 상태를 읽게 됩니다. 그래서 훅 규칙은 "취향"이 아니라 자료구조에서 나온 제약입니다. (61·66장)

트리 — 프론트엔드에서 가장 많이 만나는 구조

트리는 하나의 루트에서 가지가 뻗어 나가되 고리가 생기지 않는 구조입니다. 프론트엔드 개발자는 트리를 하루 종일 다룹니다.

전부 같은 구조입니다 
DOM 트리          html → body → div → p           (5·38장)
컴포넌트 트리      App → Layout → Sidebar → Item   (58장)
폴더 구조         src/ → components/ → Button.tsx
JSON 데이터       { user: { address: { city } } }
라우트 트리        / → /posts → /posts/[id]        (68·71장)
카테고리 · 댓글    대댓글은 댓글의 자식

용어는 가족 관계로 부릅니다. 루트(맨 위), 부모·자식, 형제, 잎(leaf)(자식이 없는 노드), 깊이(루트에서 몇 단계 아래인가).

DFS와 BFS — 트리를 훑는 두 가지 방법

같은 트리, 다른 순서 
            A
          /   \
         B     C
        / \     \
       D   E     F

DFS (깊이 우선) A B D E C F   한 갈래를 끝까지 파고든 뒤 되돌아온다. 재귀/스택.
BFS (너비 우선) A B C D E F   같은 깊이를 전부 본 뒤 다음 층으로. 큐.

🛠️ 현장 노트 — 언제 무엇을 쓰나

  1. DFS — 전체를 빠짐없이 훑을 때(모든 노드에 함수 적용, 합계 계산, 중첩 댓글 렌더링). 코드가 짧고 자연스럽습니다. querySelectorAll이 돌려주는 문서 순서도 DFS 순서입니다.
  2. BFS — 가장 가까운 것을 찾을 때(최단 경로, "제일 가까운 부모 중 조건에 맞는 것"). 깊이별로 처리해야 할 때도 BFS입니다.
  3. 깊이를 모르는 사용자 데이터(무한 중첩 가능한 폴더·댓글)는 반복 + 스택으로 짜서 스택 오버플로를 피하세요.
  4. DOM에는 이미 좋은 도구가 있습니다. 조상 찾기는 직접 올라가지 말고 element.closest(".card")를 쓰세요.

실무 코드 — 평면 배열을 트리로

서버는 보통 평평한 배열을 줍니다. 화면에는 중첩해서 그려야 합니다. 이 변환은 실무에서 정말 자주 씁니다.

그래프 — 고리가 있어도 되는 구조

그래프는 트리에서 제약을 푼 것입니다. 노드끼리 자유롭게 연결되고, 고리(순환)가 있어도 됩니다. 트리는 "고리 없는 그래프"의 특수한 경우입니다.

프론트엔드에서 만나는 그래프 
모듈 의존성 그래프   A가 B를 import하고 B가 C를 import… (47장 번들러)
순환 참조            A → B → A  로 되돌아오는 import. 값이 undefined로 보이는 버그의 원인
링크 구조            페이지끼리 서로 연결
상태 전이            로딩 → 성공 → 다시 로딩 …

🔄 순환 import가 만드는 유령 버그

a.js가 b.js를, b.js가 다시 a.js를 import하면 둘 중 하나는 아직 초기화가 끝나지 않은 상태에서 상대를 읽게 됩니다. 그 결과 undefined is not a function이나 Cannot access 'X' before initialization이 엉뚱한 파일에서 납니다. 원인을 찾기 매우 어렵습니다.

해결은 대개 공통 부분을 제3의 모듈로 빼는 것입니다. eslint-plugin-import의 import/no-cycle 규칙으로 미리 잡을 수 있습니다. (34·48장)

📌 요약

  • 스택은 LIFO — 콜 스택, 실행 취소, 괄호 검사, DFS. 배열의 push/pop.
  • 재귀가 깊어지면 스택 오버플로. JS는 사실상 꼬리 호출 최적화가 없다(Safari 제외).
  • 큐는 FIFO — 태스크 큐, 요청 대기열. 큰 큐에서는 shift 대신 인덱스를 쓴다.
  • 연결 리스트는 참조로 이은 사슬. React 훅이 이 구조라서 훅 호출 순서 규칙이 있다.
  • DOM·컴포넌트·라우트·폴더·JSON은 전부 트리다.
  • DFS=재귀/스택(전체 훑기), BFS=큐(가장 가까운 것 찾기).
  • 평면 배열 → 트리 변환은 Map으로 한 번, 부모 연결로 한 번, 두 번만 훑으면 된다.
  • 순환 import는 초기화 순서 버그를 만든다. import/no-cycle로 막는다.
