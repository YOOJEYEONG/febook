직접 만들면 부족한 것들

61장에서 useEffect로 데이터를 가져오는 코드를 봤습니다. 거기에 아직 없는 것들이 이만큼입니다.

필요한 것없으면
캐싱같은 화면을 다시 열 때마다 처음부터 로딩. 뒤로 가기가 느립니다
중복 요청 제거세 컴포넌트가 같은 데이터를 쓰면 요청이 세 번 나갑니다
재검증다른 탭에 갔다 오면 낡은 데이터가 그대로 보입니다
경쟁 상태 처리늦게 온 옛 응답이 최신 데이터를 덮어씁니다(37·61장)
재시도일시적인 네트워크 오류에 바로 실패 화면
변경 후 갱신글을 쓰고 목록으로 돌아가면 새 글이 없습니다
페이지네이션·무한 스크롤직접 구현하면 상태가 매우 복잡해집니다

🎯 이것들은 전부 "서버 상태"의 문제입니다

65장에서 말한 그대로입니다. 서버 데이터는 우리가 가진 사본일 뿐이고 언제든 낡을 수 있습니다. 이 문제를 전담하는 도구가 TanStack Query(옛 React Query)와 SWR입니다.

기본 사용법

import { useQuery } from "@tanstack/react-query";

function UserProfile({ userId }) {
  const { data, isPending, isError, error, refetch } = useQuery({
    queryKey: ["user", userId],          // ⭐ 캐시의 이름표
    queryFn: async () => {
      const res = await fetch(`/api/users/${userId}`);
      if (!res.ok) throw new Error(`HTTP ${res.status}`);   // 37장
      return res.json();
    },
    staleTime: 60_000                     // 1분간은 "신선하다"고 간주
  });

  if (isPending) return <Spinner />;
  if (isError) return <ErrorBox message={error.message} onRetry={refetch} />;
  return <div>{data.name}</div>;
}

🔑 queryKey가 전부입니다

queryKey는 캐시의 이름표이자 의존성 배열입니다.

  • 같은 키 = 같은 데이터. 여러 컴포넌트가 써도 요청은 한 번입니다.
  • 키가 바뀌면 자동으로 다시 가져옵니다. useEffect 의존성을 손으로 관리할 필요가 없습니다.
  • 쿼리에 쓰는 모든 변수를 키에 넣어야 합니다. ["todos", { page, filter }]

캐시 모델 — 두 가지 시간

설정뜻
staleTime이 시간 동안은 데이터를 신선하다고 간주해 다시 가져오지 않습니다. 기본값 0
gcTime화면에서 사라진 데이터를 메모리에 남겨 두는 시간. 기본 5분
동작 흐름 
화면 진입
  ↓
캐시에 데이터가 있는가?
  ├─ 있고 신선함(staleTime 이내) → 그대로 사용. 요청 없음
  ├─ 있지만 낡음 → 캐시를 '즉시 화면에 보여주고' 뒤에서 새로 받아 교체
  └─ 없음 → 로딩 표시 후 요청

⚡ "낡은 것을 먼저 보여주고 뒤에서 갱신"

이 전략(stale-while-revalidate)이 체감 속도를 극적으로 바꿉니다. 목록 → 상세 → 뒤로 가기를 했을 때 로딩 스피너 없이 즉시 목록이 나타나고, 변경분만 조용히 반영됩니다.
직접 만든 useEffect 페칭은 뒤로 갈 때마다 흰 화면 + 스피너입니다. 차이가 큽니다.

기본 재검증 시점 
{
  refetchOnWindowFocus: true,   // 다른 탭 갔다 돌아오면
  refetchOnReconnect: true,     // 네트워크가 복구되면
  refetchOnMount: true          // 컴포넌트가 다시 마운트되면
}
// 모두 "낡았을 때만" 동작합니다. staleTime 이내면 요청하지 않습니다.

데이터 변경

import { useMutation, useQueryClient } from "@tanstack/react-query";

function AddTodo() {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: (newTodo) =>
      fetch("/api/todos", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(newTodo)
      }).then(r => {
        if (!r.ok) throw new Error("추가 실패");
        return r.json();
      }),

    onSuccess: () => {
      // ⭐ 목록 캐시를 무효화 → 자동으로 다시 가져옵니다
      queryClient.invalidateQueries({ queryKey: ["todos"] });
    }
  });

  return (
    <button
      onClick={() => mutation.mutate({ text: "새 할 일" })}
      disabled={mutation.isPending}          // 중복 제출 방지 (62장)
    >
      {mutation.isPending ? "추가 중…" : "추가"}
    </button>
  );
}

♻️ 무효화가 핵심 개념입니다

"글을 썼으니 목록을 다시 불러와야지"를 직접 호출하지 않습니다. "이 키의 데이터는 이제 낡았다"고 표시하면, 그 데이터를 보고 있는 화면들이 알아서 다시 가져옵니다.
화면이 여러 개여도, 어느 화면이 그 데이터를 쓰는지 몰라도 됩니다. 57장의 선언형 사고가 데이터 계층까지 확장된 것입니다.

낙관적 업데이트

const toggleTodo = useMutation({
  mutationFn: updateTodoOnServer,

  onMutate: async (newTodo) => {
    // ① 진행 중인 요청 취소 (덮어쓰기 방지)
    await queryClient.cancelQueries({ queryKey: ["todos"] });
    // ② 되돌리기용으로 현재 값 저장
    const previous = queryClient.getQueryData(["todos"]);
    // ③ 서버 응답을 기다리지 않고 화면부터 바꿈
    queryClient.setQueryData(["todos"], (old) =>
      old.map(t => t.id === newTodo.id ? newTodo : t)
    );
    return { previous };
  },

  onError: (error, variables, context) => {
    // ④ 실패하면 되돌립니다
    queryClient.setQueryData(["todos"], context.previous);
    showToast("변경에 실패했습니다");
  },

  onSettled: () => {
    // ⑤ 성공·실패 관계없이 서버 기준으로 다시 맞춥니다
    queryClient.invalidateQueries({ queryKey: ["todos"] });
  }
});

👍 언제 쓰나

거의 항상 성공하고, 실패해도 되돌리기 쉬운 동작에 씁니다. 좋아요, 체크박스 토글, 즐겨찾기. 체크박스를 눌렀는데 0.5초 뒤에 체크되는 것과 즉시 체크되는 것의 체감은 완전히 다릅니다.
반대로 결제·삭제처럼 되돌리기 어려운 것에는 쓰지 마세요. 잘못된 상태를 사용자에게 보여주는 위험이 이득보다 큽니다.

로딩과 에러 UI

상태의미화면
isPending캐시가 없고 처음 가져오는 중스켈레톤 또는 스피너
isFetching배경에서 갱신 중 (데이터는 이미 있음)작은 표시만. 전체를 가리지 마세요
isError실패메시지 + 다시 시도 버튼
데이터가 빈 배열성공했지만 결과 없음빈 상태 화면 — 오류와 구분해야 합니다

💀 스켈레톤을 쓰세요

스피너보다 실제 콘텐츠 모양의 회색 뼈대가 낫습니다.

  • 레이아웃이 미리 잡혀 데이터가 와도 화면이 튀지 않습니다(8장 CLS)
  • 무엇이 올지 예상되어 체감 대기 시간이 짧아집니다

다만 200ms 안에 끝날 로딩에는 아무것도 보여주지 않는 편이 낫습니다. 번쩍이는 스켈레톤이 더 거슬립니다.

🛠️ 현장 노트

  1. queryKey를 한곳에서 관리하세요. 문자열을 여기저기 흩어 쓰면 오타로 캐시가 안 맞습니다. const todoKeys = { all: ["todos"], detail: (id) => ["todos", id] } 같은 팩토리를 만듭니다.
  2. staleTime을 상황에 맞게. 기본값 0은 화면에 들어올 때마다 요청합니다. 자주 안 바뀌는 데이터라면 몇 분으로 늘리세요.
  3. DevTools를 켜 두세요. 어떤 쿼리가 언제 실행되고 캐시가 어떤 상태인지 눈으로 볼 수 있습니다.
  4. 에러 처리를 UI로 만드세요. "다시 시도" 버튼이 없는 에러 화면은 사용자를 막다른 길에 세웁니다.
  5. 빈 상태를 잊지 마세요. 데이터가 0개일 때 "아직 항목이 없습니다 + 만들기 버튼"을 보여줘야 합니다.

📌 요약

  • 직접 만든 페칭에는 캐싱·중복 제거·재검증·재시도가 없다.
  • queryKey가 캐시의 이름표이자 의존성이다. 쓰는 변수를 전부 넣는다.
  • staleTime이 "얼마나 신선하다고 볼지"를 정한다. 기본값은 0.
  • 낡은 캐시를 먼저 보여주고 뒤에서 갱신하는 전략이 체감 속도를 바꾼다.
  • 변경 후에는 invalidateQueries로 무효화만 하면 관련 화면이 알아서 갱신된다.
  • 낙관적 업데이트는 되돌리기 쉬운 동작에만. 결제·삭제에는 쓰지 않는다.
  • isPending(첫 로딩)과 isFetching(배경 갱신)을 구분해서 UI를 만든다.
  • 빈 상태와 에러 상태를 반드시 따로 설계한다.
