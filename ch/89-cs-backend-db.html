🤝 왜 프론트엔드가 이걸 알아야 하나

백엔드를 만들려는 게 아닙니다. 세 가지 때문입니다.
① API 설계 회의에서 말이 통해야 합니다. "이 필드도 같이 주세요"가 왜 어려운 요구인지 알아야 합니다.
② 느린 원인이 어디인지 판단해야 합니다(87장 TTFB).
③ 잘못된 화면 설계를 미리 피할 수 있습니다. 목록마다 상세 API를 부르는 화면은 설계 단계에서 막아야 합니다.

서버가 하는 일

요청 하나가 서버 안에서 거치는 길 
GET /api/orders?page=1
   │
   ├─ ① 인증·인가    누구인가? 이 자원을 볼 권한이 있나?
   ├─ ② 입력 검증    page가 숫자인가? 범위는 타당한가?
   ├─ ③ 비즈니스 로직 정책 적용 (할인, 재고, 권한별 필터)
   ├─ ④ 데이터 접근   DB에 질의
   └─ ⑤ 응답 직렬화   결과를 JSON으로 만들어 반환

프론트엔드가 어떤 언어로 쓰였든 서버는 상관하지 않습니다.
그래서 웹·앱·다른 서버가 같은 API를 공유할 수 있습니다.

🛡️ 검증은 양쪽 다 해야 합니다

프론트엔드의 유효성 검사는 사용자 경험을 위한 것이지 보안이 아닙니다. 브라우저 개발자 도구로 누구나 요청을 조작할 수 있고, 아예 curl로 서버에 직접 보낼 수도 있습니다. 서버 검증이 진짜 방어선입니다(78장). 반대로 서버만 검증하면 사용자가 제출 버튼을 누르고 한참 기다려야 오류를 알게 됩니다. 둘 다 필요합니다.

데이터베이스 — SQL과 NoSQL

관계형(SQL)문서형 등(NoSQL)
제품PostgreSQL, MySQLMongoDB, DynamoDB, Redis, Firestore
저장표(테이블)와 관계로JSON 비슷한 문서로
구조스키마가 정해져 있다유연하다
질의여러 표를 조인해서중첩 구조를 통째로 읽는다
트랜잭션강력하다제품마다 지원 수준이 다르다
언제기본값으로 삼기 좋다 (대부분의 서비스)특정 용도에 (캐시=Redis, 로그, 초대용량, 실시간 동기화)

⚖️ "NoSQL이 더 현대적이다"는 아닙니다

한때 그런 분위기가 있었지만, 지금 대부분의 웹 서비스는 관계형 DB(주로 PostgreSQL)를 기본으로 씁니다. 데이터는 결국 서로 관계를 맺고, 그 관계를 안전하게 다루는 일은 관계형 DB가 압도적으로 잘합니다. NoSQL은 "대체"가 아니라 "용도에 맞는 선택"입니다.

읽을 줄은 알아야 하는 SQL

-- 사용자 목록에서 조건에 맞는 것 10개
SELECT id, name, email          -- 어떤 열을
FROM users                      -- 어떤 표에서
WHERE status = 'active'         -- 어떤 조건으로
ORDER BY created_at DESC        -- 어떤 순서로
LIMIT 10;                       -- 몇 개나

-- 조인: 주문에 사용자 이름을 붙인다 (81장의 Map 조회표와 같은 일)
SELECT o.id, o.total, u.name
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.created_at >= '2026-01-01';

인덱스 — 책 뒤의 색인

1,000만 행짜리 표에서 WHERE email = 'a@b.com'을 실행하면 DB는 전부 훑습니다(풀 스캔). 83장의 O(n)입니다.

인덱스는 책 뒤의 찾아보기와 같습니다. 특정 열에 대해 정렬된 별도의 구조(보통 B-트리)를 만들어 두면 O(log n)으로 찾습니다. 1,000만 행에서 스무 번 남짓이면 도달합니다.

⚖️ 공짜는 아닙니다

  • 조회가 극적으로 빨라집니다.
  • 저장 공간을 더 씁니다.
  • INSERT·UPDATE·DELETE가 느려집니다 — 색인도 같이 고쳐야 하니까요.

그래서 자주 조회 조건으로 쓰는 열에만 겁니다. 프론트엔드가 할 일은 "이 화면은 category와 created_at으로 정렬·필터합니다"를 백엔드에 정확히 알려 주는 것입니다. 그래야 맞는 인덱스를 걸 수 있습니다.

N+1 문제 — 프론트엔드도 만든다

이름의 유래: 요청 1번 + 항목 수(N)번 
// ❌ 목록 1번 + 각 항목마다 1번 = 1 + 50 = 51번 요청
const posts = await fetch("/api/posts").then(r => r.json());
const withAuthor = await Promise.all(
  posts.map(async (p) => ({
    ...p,
    author: await fetch(`/api/users/${p.authorId}`).then(r => r.json())
  }))
);

// ✅ 방법 1 — 서버가 한 번에 주게 한다
//    GET /api/posts?include=author

// ✅ 방법 2 — 필요한 id만 모아서 한 번에 조회
const ids = [...new Set(posts.map(p => p.authorId))];   // 중복 제거 (81장)
const users = await fetch(`/api/users?ids=${ids.join(",")}`).then(r => r.json());
const byId = new Map(users.map(u => [u.id, u]));
const withAuthor2 = posts.map(p => ({ ...p, author: byId.get(p.authorId) }));

🛠️ 현장 노트 — 화면 설계 단계에서 잡으세요

N+1은 코드 문제이기 전에 설계 문제입니다. "목록에 작성자 프로필과 좋아요 수도 보여 주세요"라는 요구가 들어오면, 그 데이터를 목록 API가 함께 줄 수 있는지 먼저 확인하세요. 나중에 발견하면 요청 51개가 이미 배포된 뒤입니다.

백엔드에도 같은 문제가 있습니다. ORM이 자동으로 쿼리를 만들다가 루프 안에서 매번 DB에 질의하는 경우입니다. "이 목록 API 느린데 N+1 아닐까요?"라고 물어볼 수 있으면 협업이 훨씬 수월해집니다. GraphQL 쪽에서는 DataLoader로 요청을 묶어 해결합니다.

트랜잭션과 멱등성

트랜잭션 — 전부 성공하거나 전부 취소하거나 
계좌 이체
  ① A의 잔액 -10,000
  ② B의 잔액 +10,000

①만 되고 ②에서 서버가 죽으면? 돈이 사라진다.
트랜잭션은 "①②를 한 덩어리로 묶고, 중간에 실패하면 전부 되돌린다".

ACID
  원자성(Atomicity)    전부 되거나 전부 안 된다
  일관성(Consistency)  규칙(제약 조건)을 깨지 않는다
  격리성(Isolation)    동시에 실행돼도 서로 간섭하지 않는다
  지속성(Durability)   성공했다면 정전이 나도 남아 있다

💳 프론트엔드가 반드시 알아야 할 것: 멱등성

멱등(idempotent)하다 = 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같다.

GET    멱등하다  (몇 번 읽어도 같다)
PUT    멱등하다  (같은 값으로 덮어쓰기)
DELETE 멱등하다  (이미 지워졌으면 그대로)
POST   멱등하지 않다  ← 결제·주문 생성. 두 번 보내면 두 건이 생긴다

그래서 결제 버튼 연타, 응답이 느려서 사용자가 새로고침, 네트워크 불안으로 클라이언트가 자동 재시도가 전부 중복 주문이 될 수 있습니다.

프론트엔드가 할 수 있는 방어 
// ① 제출 중에는 버튼을 잠근다 (기본이지만 자주 빠뜨립니다)
<button disabled={isSubmitting}>결제하기</button>

// ② 멱등성 키를 보낸다 — 서버가 중복을 걸러낼 수 있게
const idempotencyKey = useRef(crypto.randomUUID());
fetch("/api/orders", {
  method: "POST",
  headers: { "Idempotency-Key": idempotencyKey.current },
  body: JSON.stringify(order)
});
// 재시도해도 같은 키 → 서버는 "이미 처리한 요청"으로 인식해 기존 결과를 돌려준다

// ③ POST를 자동 재시도하지 않는다
//    GET은 재시도해도 안전하지만 POST는 위험하다.
//    라이브러리의 retry 설정을 메서드별로 확인하세요.

인증 — 토큰을 어디에 둘 것인가

세션 쿠키JWT(토큰)
방식서버가 세션을 저장하고 브라우저에 세션 ID 쿠키를 준다서명된 토큰 자체에 정보가 들어 있고 서버는 서명만 검증한다
장점서버에서 즉시 무효화 가능 (강제 로그아웃)서버가 상태를 안 가져도 되고, 여러 서비스에서 공유하기 쉽다
단점서버가 상태를 가져야 한다발급 후 만료 전까지 무효화가 어렵다 → '짧은 액세스 토큰 + 긴 리프레시 토큰' 조합을 쓴다

🔑 localStorage에 토큰을 저장하지 마세요

localStorage는 JavaScript로 읽을 수 있습니다. XSS가 한 번이라도 성공하면 토큰이 통째로 유출됩니다(78장). 광고 스크립트나 npm 패키지 하나만 오염돼도 충분합니다.

권장은 HttpOnly + Secure + SameSite 쿠키입니다. JavaScript가 읽을 수 없으므로 XSS로도 훔칠 수 없습니다. 쿠키는 자동 전송되므로 CSRF 대비가 추가로 필요하지만, SameSite=Lax(기본값)와 CSRF 토큰으로 막습니다.

결정은 대개 백엔드와 함께 내립니다. 프론트엔드가 할 일은 "localStorage에 넣읍시다"라는 제안이 나왔을 때 위험을 설명하는 것입니다.

🛠️ 현장 노트 — API 설계 회의에서 물어볼 것

  1. "이 목록에 필요한 필드를 한 번에 받을 수 있나요?" (N+1 예방)
  2. "페이지네이션은 오프셋인가요 커서인가요?" (무한 스크롤 설계에 직결)
  3. "에러 응답 형식이 정해져 있나요?" ({ code, message, fields }처럼 일관된 형식이어야 프론트에서 처리할 수 있습니다)
  4. "이 POST는 재시도해도 안전한가요? 멱등성 키를 받나요?"
  5. "큰 정수 ID는 문자열로 주실 수 있나요?" (80장 — 안전 정수 한계)
  6. "날짜는 ISO 8601 UTC 문자열인가요?" (43장 — 시간대 사고 예방)
  7. "이 화면은 category·created_at으로 정렬합니다" (인덱스를 걸 수 있게 미리 공유)

📌 요약

  • 서버는 인증 → 검증 → 로직 → DB → 직렬화를 한다. 검증은 클라이언트·서버 양쪽에서.
  • 대부분의 서비스는 관계형 DB가 기본. NoSQL은 대체가 아니라 용도별 선택이다.
  • 인덱스는 조회를 O(log n)으로 만들지만 쓰기를 느리게 한다. 조회 조건을 백엔드에 알려 주자.
  • N+1은 프론트엔드도 만든다. 목록 API가 필요한 데이터를 한 번에 주게 설계한다.
  • 트랜잭션은 전부 성공하거나 전부 취소. 중간 상태를 가정하지 않는다.
  • POST는 멱등하지 않다. 버튼 잠금 + 멱등성 키 + POST 자동 재시도 금지.
  • 페이지네이션은 무한 스크롤=커서, 페이지 번호=오프셋.
  • 인증 토큰은 localStorage가 아니라 HttpOnly 쿠키로. XSS 한 번에 전부 털린다.
