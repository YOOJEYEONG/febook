Node.js 설치

23장에서 본 것처럼 Node.js는 브라우저 밖에서 JavaScript를 실행하는 환경입니다. 프론트엔드 개발에서는 서버를 만들지 않더라도 반드시 필요합니다. 빌드 도구·테스트 도구·개발 서버가 전부 Node 위에서 돌기 때문입니다.

📥 공식 설치 파일보다 버전 관리 도구를 권합니다

프로젝트마다 요구하는 Node 버전이 다릅니다. 버전 관리 도구를 쓰면 폴더를 옮기는 것만으로 버전이 바뀝니다.

# fnm (빠르고 가볍습니다) 또는 nvm 을 설치한 뒤
fnm install --lts        # 최신 LTS 설치
fnm use 20               # 특정 버전 사용
node --version
npm --version

🏷️ LTS 버전을 쓰세요

LTS(Long Term Support)는 장기 지원 버전으로, 짝수 번호가 붙습니다. 홀수 버전은 실험적 기능이 들어간 단기 버전이라 실무에 적합하지 않습니다. 프로젝트에는 .nvmrc나 package.json의 engines 필드로 팀이 쓸 버전을 명시해 두는 것이 좋습니다.

🔀 한 프로젝트에서 하나만 쓰세요

npm과 yarn을 섞어 쓰면 lock 파일이 두 개가 되어 사람마다 다른 버전이 설치되는 최악의 상황이 됩니다. 저장소에 package-lock.json이 있으면 npm을, pnpm-lock.yaml이 있으면 pnpm을 쓰세요.

package.json

{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest",
    "lint": "eslint ."
  },
  "dependencies": {
    "react": "^19.0.0"
  },
  "devDependencies": {
    "vite": "^6.0.0",
    "eslint": "^9.0.0"
  },
  "engines": {
    "node": ">=20"
  }
}
항목의미
type: "module"이 프로젝트의 .js 파일을 ES 모듈로 해석(34장). 없으면 CommonJS
scripts자주 쓰는 명령에 별명 붙이기. npm run dev로 실행
dependencies실행에 필요한 패키지. 사용자에게 전달되는 코드에 포함됩니다
devDependencies개발할 때만 필요한 것. 빌드 도구, 테스트, 린터
engines필요한 Node 버전 명시

🎬 scripts가 실무의 진입점입니다

낯선 프로젝트를 받았을 때 가장 먼저 볼 곳이 scripts입니다. 어떻게 실행하고, 어떻게 빌드하고, 어떻게 테스트하는지가 전부 여기 적혀 있습니다. npm run만 입력하면 사용 가능한 스크립트 목록이 나옵니다.

semver — 버전 번호 읽기

MAJOR.MINOR.PATCH 
    19  .  2  .  3
    │      │     └── PATCH — 버그 수정. 사용법이 바뀌지 않음
    │      └──────── MINOR — 기능 추가. 기존 코드는 그대로 동작 (하위 호환)
    └─────────────── MAJOR — 깨지는 변경. 코드 수정이 필요할 수 있음
표기허용 범위설명
^19.2.319.2.3 ~ 19.x.xMAJOR는 고정. npm 기본값
~19.2.319.2.3 ~ 19.2.xPATCH만 허용. 더 보수적
19.2.3정확히 이 버전완전 고정
* 또는 latest아무 최신 버전절대 쓰지 마세요

📌 "제 컴퓨터에서는 되는데요"의 원인

^19.2.3은 범위입니다. 같은 package.json으로 오늘 설치한 사람과 한 달 뒤 설치한 사람이 서로 다른 버전을 받을 수 있습니다. 그래서 lock 파일이 필요합니다.

lock 파일

package-lock.json(또는 pnpm-lock.yaml, yarn.lock)은 실제로 설치된 정확한 버전을 전부 기록합니다. 직접 설치한 것뿐 아니라 그것들이 의존하는 패키지까지 전부입니다.

🔒 lock 파일은 반드시 커밋하세요

  • 커밋하면 모든 팀원과 CI 서버가 완전히 같은 버전을 설치합니다.
  • .gitignore에 넣으면 안 됩니다. 재현 가능한 빌드의 근거가 사라집니다.
  • 충돌이 나면 손으로 고치지 말고, lock 파일을 지우고 npm install을 다시 실행하세요.
npm install       # package.json 기준으로 설치. lock 파일을 갱신할 수 있음
npm ci            # lock 파일 그대로 정확히 설치. 빠르고 결정적
                  # → CI·배포 환경에서는 항상 npm ci 를 씁니다

의존성과 보안

🕸️ 패키지 하나가 수백 개를 데려옵니다

패키지 3개를 설치했는데 node_modules에 폴더가 800개 생기는 일이 흔합니다. 여러분이 설치한 것들이 또 다른 패키지에 의존하기 때문입니다. 즉 여러분의 앱에는 얼굴도 모르는 수백 명의 코드가 들어 있습니다. 이것을 공급망(supply chain) 위험이라고 부릅니다.

npm audit              # 알려진 취약점 확인
npm audit fix          # 자동으로 고칠 수 있는 것 수정
npm outdated           # 오래된 패키지 확인
npm ls react           # 이 패키지가 어디서 왔는지 추적

🛠️ 현장 노트 — 패키지를 설치하기 전에

  1. 정말 필요한가? 40장에서 말했듯 표준 API로 되는 일이 많습니다. 날짜 표시에 라이브러리를 넣기 전에 Intl을 확인하세요.
  2. 얼마나 무거운가? bundlephobia.com에서 설치 전에 용량을 확인할 수 있습니다.
  3. 살아 있는 프로젝트인가? 마지막 배포일, 이슈 응답, 다운로드 수를 봅니다.
  4. 의존성이 몇 개인가? 작은 기능에 의존성 50개짜리 패키지를 쓸 이유는 없습니다.

"직접 20줄 짜기 vs 패키지 설치" 사이에서, 신입은 대개 설치 쪽으로 기웁니다. 경험이 쌓일수록 작은 기능은 직접 쓰는 편이 낫다는 판단이 늘어납니다. 설치한 패키지는 영원히 관리 대상이 되기 때문입니다.

npx

npx create-vite my-app        # 설치하지 않고 한 번만 실행
npx serve                      # 로컬 서버 (44장)
npx eslint .                   # 프로젝트에 설치된 eslint 실행

npx는 패키지를 전역 설치하지 않고 실행합니다. 프로젝트 생성 도구처럼 한 번만 쓰는 명령에 적합하며, 전역 설치로 인한 버전 충돌을 피할 수 있습니다.

📌 요약

  • Node.js는 버전 관리 도구(fnm·nvm)로 설치하고 LTS를 쓴다.
  • 한 프로젝트에서 패키지 매니저는 하나만 쓴다.
  • dependencies는 실행에, devDependencies는 개발에만 필요한 것.
  • ^19.2.3은 MAJOR 고정, ~는 PATCH만. *는 쓰지 않는다.
  • lock 파일은 반드시 커밋한다. CI에서는 npm ci.
  • node_modules는 커밋하지 않고, 이상하면 지우고 다시 설치한다.
  • 패키지 하나가 수백 개를 데려온다. 설치 전에 필요성·용량·관리 상태를 확인한다.
  • 일회성 실행은 npx.
