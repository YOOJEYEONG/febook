의존성 방향 — 가장 중요한 규칙

➡️ 구조가 무너지는 진짜 원인

폴더를 아무리 잘 나눠도 서로 마구 참조하면 의미가 없습니다. "A를 고치려면 B를 봐야 하고, B를 보려면 C를 봐야 하는" 상태가 되면 폴더 이름은 장식일 뿐입니다.

허용되는 방향 
app  →  pages  →  features  →  shared
                     ↓            ↑
                  (기능끼리 직접 참조 금지)

✅ features/auth 가 shared/ui/Button 을 쓴다
✅ pages/LoginPage 가 features/auth 를 쓴다
❌ shared/ui/Button 이 features/auth 를 쓴다     ← 재사용 불가능해집니다
❌ features/products 가 features/auth 의 내부를 직접 쓴다

🔀 기능끼리 연결이 필요하면

  • 공개 인터페이스(index.ts)를 통해서만 참조합니다
  • 양쪽이 쓰는 공통 부분은 shared로 올립니다
  • 조합은 더 위 계층(pages)에서 합니다

두 기능이 서로를 참조하기 시작하면 둘을 나눈 의미가 사라집니다. 그럴 바에는 하나로 합치는 것이 정직합니다.

// model/calculate.ts — React를 전혀 모릅니다. 그래서 테스트가 쉽습니다 (75장)
export function calculateOrderTotal(items: OrderItem[], coupon?: Coupon): number {
  const subtotal = items.reduce((sum, i) => sum + i.price * i.quantity, 0);
  const discount = coupon ? applyCoupon(subtotal, coupon) : 0;
  return Math.max(0, subtotal - discount);
}

// hooks/useOrder.ts — 화면과 로직을 잇습니다
export function useOrder(orderId: string) {
  const { data } = useQuery({ queryKey: ["order", orderId], queryFn: fetchOrder });
  const total = data ? calculateOrderTotal(data.items, data.coupon) : 0;
  return { order: data, total };
}

// components/OrderSummary.tsx — 받아서 그리기만 합니다
export function OrderSummary({ total }: { total: number }) {
  return <p>합계: {total.toLocaleString()}원</p>;
}

🧠 도메인 로직을 프레임워크에서 떼어내세요

"할인은 어떻게 계산되는가"는 React와 아무 상관이 없습니다. 이것을 컴포넌트 안에 두면 테스트하기 어렵고, 재사용할 수 없고, 프레임워크를 바꾸면 다시 써야 합니다.
class="term" data-term="pure-function">순수 함수로 분리해 두면 테스트가 쉽고(75장), 서버에서도 쓸 수 있고, 비즈니스 규칙이 한곳에 모여 읽기 좋습니다. 프로젝트가 커질수록 이 분리의 가치가 커집니다.

구조는 자라는 것입니다

🌱 처음부터 완벽한 구조를 만들지 마세요

파일 5개짜리 프로젝트에 계층 구조를 만드는 것은 쓸데없는 복잡도만 더합니다.
실제 순서는 이렇습니다.

  1. 한 파일에 다 쓴다
  2. 길어지면 나눈다
  3. 같은 것이 반복되면 shared로 올린다 (63장 — 세 번째 복사할 때)
  4. 기능이 여러 개가 되면 features로 묶는다
  5. 기능 안이 복잡해지면 계층을 나눈다

🏗️ 구조를 바꿔야 하는 신호

  • 파일 하나를 고치려고 폴더 다섯 개를 오갑니다
  • 어디에 넣을지 매번 고민합니다
  • utils.ts가 1000줄이 되었습니다
  • 기능을 삭제하려는데 무엇을 지워야 할지 모릅니다
  • 새 팀원이 파일을 못 찾습니다

기능을 통째로 지우기 쉬운 구조가 좋은 구조입니다. "이 기능 폴더를 지우면 끝"이라면 잘 나뉜 것이고, "여기저기 흩어져 있어서 못 지운다"면 잘못 나뉜 것입니다.

🛠️ 현장 노트 — 구조에 대한 현실적인 조언

  1. 정답은 없습니다. 팀이 이해하고 지킬 수 있으면 좋은 구조입니다.
  2. 일관성이 완벽함보다 중요합니다. 규칙이 조금 아쉬워도 전체가 같은 규칙이면 읽을 수 있습니다.
  3. 기존 프로젝트에 들어가면 그 규칙을 따르세요. 혼자 다른 방식으로 쓰는 것이 최악입니다.
  4. 구조 논쟁에 시간을 너무 쓰지 마세요. 실제 가치는 코드 자체에서 나옵니다.
  5. ESLint로 의존성 방향을 강제할 수 있습니다(import/no-restricted-paths 등). 사람의 의지에만 맡기면 결국 무너집니다.

📌 요약

  • 규모에 맞는 구조를 쓴다. 작으면 단순하게.
  • 기능 단위로 묶어 함께 바뀌는 것을 함께 둔다.
  • 의존성 방향이 구조의 핵심이다. shared가 features를 참조하면 안 된다.
  • 기능끼리는 공개 인터페이스를 통해서만 연결한다.
  • 도메인 로직을 순수 함수로 분리하면 테스트·재사용이 쉬워진다.
  • 파일명 대소문자를 정확히 맞춘다. 배포 후에야 터진다.
  • 경로 별칭으로 상대 경로 지옥을 피한다.
  • 기능을 통째로 지우기 쉬운 구조가 좋은 구조다.
  • 일관성이 완벽함보다 중요하다.
