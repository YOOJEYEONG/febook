읽는 데 약 32분 · 사전 지식: interface와 type(52장), 제네릭과 keyof(53장)

핵심 원칙: 복사하지 말고 파생시키세요

실제 서비스에서는 같은 "회원" 데이터가 화면마다 조금씩 다른 모양으로 쓰입니다. 가입할 때는 아직 id가 없고, 프로필 화면에서는 비밀번호를 빼야 하고, 정보 수정 화면에서는 일부 항목만 보냅니다. 이 모양들을 하나하나 새로 적으면 처음에는 편하지만, 원본 User에 속성이 추가되거나 이름이 바뀔 때마다 여러 곳을 찾아 고쳐야 합니다.

스프레드시트로 비유하면 이해가 쉽습니다. 다른 시트의 값을 복사해서 붙여 넣으면 원본이 바뀌어도 그대로 남지만, =A1처럼 수식으로 참조하면 원본을 따라 자동으로 바뀝니다. 유틸리티 타입은 타입 세계의 수식입니다.

interface User {
  id: number;
  name: string;
  email: string;
  password: string;
  createdAt: Date;
}

// ❌ 손으로 다시 씁니다 — User가 바뀌면 여기도 고쳐야 합니다
interface UserProfileCopy {
  id: number;
  name: string;
  email: string;
}

// ✅ User에서 파생시킵니다 — 자동으로 따라옵니다
type UserProfile = Omit<User, "password">;
type UserSummary = Pick<User, "id" | "name">;
type UserDraft = Partial<User>;

▶ Playground에 붙여 보세요. UserProfile에 마우스를 올리면 password가 빠진 결과가 펼쳐져 보입니다. 이제 User에 phone: string을 추가하고 다시 마우스를 올려 보세요. UserProfile에는 자동으로 들어가고, 손으로 쓴 UserProfileCopy에는 들어가지 않습니다. 꺾쇠 안에 원본 타입과 조건을 넣는 모양은 53장의 제네릭 그대로입니다. 유틸리티 타입은 TypeScript가 미리 만들어 둔 제네릭 타입입니다.

🔗 이것이 유틸리티 타입의 존재 이유입니다

타입을 손으로 복사하면 원본이 바뀔 때 조용히 어긋납니다. 파생시켜 두면 User에 속성을 추가하는 순간 관련된 모든 타입이 자동으로 갱신되고, 맞지 않는 코드가 즉시 오류로 드러납니다.

내장 유틸리티 타입

TypeScript에는 이런 "수식"이 여러 개 내장되어 있습니다. 전부 외울 필요는 없고, 표의 위쪽 여섯 개(Partial~Record)가 실무 사용의 대부분을 차지합니다. 나머지는 필요할 때 이 표로 돌아와 찾아보면 됩니다. 이름이 하는 일을 그대로 말해 주기 때문에 처음 보는 코드에서도 대개 뜻을 짐작할 수 있습니다.

타입하는 일
Partial<T>모든 속성을 선택적으로. 수정 폼, PATCH 요청에
Required<T>모든 속성을 필수로
Readonly<T>모든 속성을 읽기 전용으로
Pick<T, K>일부 속성만 골라내기
Omit<T, K>일부 속성을 빼기
Record<K, V>키·값 타입으로 객체 만들기
Exclude<T, U>유니온에서 제거
Extract<T, U>유니온에서 추출
NonNullable<T>null·undefined 제거
ReturnType<F>함수의 반환 타입
Parameters<F>함수의 매개변수 타입들(튜플)
Awaited<P>Promise가 풀린 타입
실제 사용 예 
interface User {
  id: number; name: string; email: string; password: string; createdAt: Date;
}

// 생성할 때는 서버가 정하는 값이 없습니다
type CreateUserInput = Omit<User, "id" | "createdAt">;

// 수정할 때는 일부만 보냅니다
type UpdateUserInput = Partial<Omit<User, "id" | "createdAt">>;

// 화면에 보여줄 때는 비밀번호를 뺍니다
type PublicUser = Omit<User, "password">;

// 목록에는 최소한만
type UserListItem = Pick<User, "id" | "name">;

// 상태별 라벨
type Status = "idle" | "loading" | "error";
const labels: Record<Status, string> = {
  idle: "대기", loading: "불러오는 중", error: "오류"
};
// 상태를 하나 추가하면 여기서 "누락됐다"고 오류가 납니다 ✅

// 함수에서 타입 뽑기
function createUser(input: CreateUserInput) { return { id: 1, ...input }; }
type CreatedUser = ReturnType<typeof createUser>;
type CreateArgs = Parameters<typeof createUser>[0];

// 비동기 함수의 결과
async function fetchUsers(): Promise<User[]> { return []; }
type Users = Awaited<ReturnType<typeof fetchUsers>>;    // User[]

▶ Playground에 붙여 보세요. 각 타입 이름에 마우스를 올리며 결과를 확인하는 것이 가장 빠른 공부법입니다. Partial<Omit<…>>처럼 안쪽부터 바깥으로 읽으면 됩니다. "id와 createdAt을 빼고(Omit), 남은 것을 모두 선택적으로(Partial)". labels 객체에서 한 줄을 지우면 "속성이 빠졌다"는 오류가 나는데, Record<Status, string>이 모든 상태에 라벨이 있어야 한다고 요구하기 때문입니다. 마지막 두 예제의 typeof createUser는 "함수 값의 타입"을 뜻하며 바로 아래 절에서 설명합니다.

🤔 자주 하는 오해 — Omit이 객체에서 속성을 지워 준다

오해 — PublicUser = Omit<User, "password"> 타입의 변수에 넣으면 비밀번호가 빠진 객체가 된다. 사실 — 유틸리티 타입도 타입이라 빌드 후 사라집니다(50장). 값에는 아무 영향이 없습니다. password가 들어 있는 객체를 변수에 담아 넘기면 구조적 타이핑(52장)상 통과하고, 화면이나 서버로 그대로 나갑니다. 실제로 빼려면 const { password, ...publicUser } = user;처럼 JavaScript 코드로 지워야 합니다(28장의 구조 분해).

⚠️ Omit은 오타를 잡아 주지 않습니다

type A = Omit<User, "passwrod">;   // 오타인데 오류가 안 납니다
// 결과: User와 똑같은 타입 (아무것도 안 빠짐)

type B = Pick<User, "passwrod">;   // ❌ Pick은 오타를 잡습니다

Omit은 키가 존재하지 않아도 허용하도록 정의되어 있습니다. 오타를 잡고 싶다면 키를 keyof T로 제한한 엄격한 버전을 한 줄로 만들어 쓰기도 합니다.

type StrictOmit<T, K extends keyof T> = Omit<T, K>;
type C = StrictOmit<User, "passwrod">;   // ❌ 이제 오타가 잡힙니다

keyof와 typeof

유틸리티 타입이 원본에서 타입을 만들어 내려면 원본을 "읽는" 도구가 필요합니다. 그 기본 도구가 keyof와 typeof입니다. keyof는 객체 타입의 키 이름 목록을 유니온으로, typeof는 이미 있는 값의 타입을 꺼냅니다. 51장과 53장에서 "나중에 설명한다"고 미뤄 두었던 keyof typeof, typeof X[number]가 바로 이 둘의 조합입니다.

interface User { id: number; name: string; }

type UserKeys = keyof User;         // "id" | "name"
type IdType = User["id"];           // number
type AnyValue = User[keyof User];   // number | string

// typeof — '값'에서 '타입'을 뽑습니다
const defaultConfig = {
  theme: "dark",
  fontSize: 16,
  features: { search: true }
};
type Config = typeof defaultConfig;
// { theme: string; fontSize: number; features: { search: boolean } }

// as const 와 조합 (51장)
const ROLES = ["admin", "editor", "viewer"] as const;
type Role = typeof ROLES[number];    // "admin" | "editor" | "viewer"

// 배열 하나로 값과 타입을 함께 관리합니다
ROLES.forEach(role => { /* role: "admin" | "editor" | "viewer" */ });

▶ Playground에 붙여 보세요. User["id"]처럼 대괄호로 속성 타입을 꺼내는 것을 인덱스 접근 타입이라고 합니다. JavaScript에서 user["id"]로 값을 꺼내는 것과 같은 모양을 타입 자리에서 쓰는 것입니다. 이제 51장의 typeof STATUS[keyof typeof STATUS]를 풀어 읽을 수 있습니다. typeof STATUS(객체의 타입) → keyof 그것(키들: "IDLE" | "LOADING" | …) → 그 키들로 인덱스 접근(값들: "idle" | "loading" | …)입니다. typeof defaultConfig처럼 설정 객체에서 타입을 뽑으면, 기본값 객체가 곧 타입의 원본이 되어 두 곳을 따로 관리할 필요가 없습니다.

🔄 typeof가 두 가지 뜻인 이유

JavaScript의 typeof는 값의 타입 이름을 문자열로 돌려주는 연산자입니다(25장). TypeScript의 typeof는 타입을 쓰는 자리에서만 쓰이며 값으로부터 타입을 얻는 다른 기능입니다. 헷갈리지만 위치로 구분됩니다. 타입 자리에 있으면 후자입니다.

매핑드 타입 — 유틸리티는 이렇게 만들어졌습니다

내장 유틸리티는 마법이 아니라 누구나 쓸 수 있는 문법으로 만들어져 있습니다. 그 문법이 매핑드 타입입니다. 배열의 map(29장)이 요소를 하나씩 돌며 새 배열을 만들듯이, 매핑드 타입은 키를 하나씩 돌며 새 객체 타입을 만듭니다. [K in keyof T]는 "T의 키 각각을 K라고 부르며"라는 반복문이라고 읽으면 됩니다. 직접 만들 일은 드물지만, 라이브러리 타입 정의를 읽을 때 자주 만납니다.

// Partial의 실제 정의
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};
//  ↑ T의 모든 키를 순회하며 각 속성을 선택적으로 만듭니다

// Readonly
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};

// 수식어 제거는 앞에 마이너스
type Mutable<T> = {
  -readonly [K in keyof T]: T[K];
};
type Concrete<T> = {
  [K in keyof T]-?: T[K];      // 선택적 제거
};

// 키 이름 바꾸기 (as)
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

type UserGetters = Getters<{ name: string; age: number }>;
// { getName: () => string; getAge: () => number }

첫 번째 MyPartial을 소리 내어 읽어 보면 이렇습니다. "T의 키 각각(K in keyof T)에 대해, 그 키를 선택적(?)으로 만들고, 값 타입은 원래 것(T[K]) 그대로 둔다." readonly와 ? 앞에 붙은 마이너스(-)는 반대로 그 표시를 떼어 낸다는 뜻입니다. 마지막 Getters는 키 이름까지 바꾸는 고급 예시로, 백틱(`) 안에 문자열을 조립하는 템플릿 리터럴(25장) 문법이 타입에서도 쓰입니다. ▶ Playground에 붙여 UserGetters에 마우스를 올리면 결과를 확인할 수 있습니다.

조건부 타입

조건부 타입은 타입 세계의 삼항 연산자(26장)입니다. A extends B ? X : Y는 "A가 B에 들어맞으면 X, 아니면 Y"입니다. extends는 53장의 제약에서처럼 "~에 들어맞는"으로 읽습니다. infer는 "이 자리에 무엇이 있는지 알아내서 이름을 붙여라"라는 뜻으로, ReturnType이 함수에서 반환 타입을 꺼낼 수 있는 비밀이 여기에 있습니다.

// T가 U에 할당 가능하면 X, 아니면 Y
type IsString<T> = T extends string ? true : false;

type A = IsString<"hello">;   // true
type B = IsString<42>;        // false

// infer — 타입 안에서 값을 '꺼냅니다'
type ElementOf<T> = T extends (infer E)[] ? E : never;
type C = ElementOf<string[]>;   // string

// ReturnType의 실제 정의
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

// 유니온에 적용하면 각 항목에 따로 적용됩니다 (분배 조건부 타입)
type ToArray<T> = T extends any ? T[] : never;
type D = ToArray<string | number>;   // string[] | number[]

ElementOf는 "T가 어떤 것의 배열 모양이라면, 그 어떤 것(E)을 꺼내라. 아니면 never"라고 읽습니다. infer E는 "여기 있는 타입을 E라는 이름으로 잡아 두라"는 표시입니다. 마치 패턴 맞추기 퍼즐에서 빈 조각 자리에 들어간 조각을 집어 드는 것과 같습니다. 마지막 예는 유니온을 넣으면 각 멤버에 따로 적용된다는 특이한 성질을 보여 줍니다. (string | number)[]가 아니라 string[] | number[]가 되는 것에 주의하세요.

🧩 여기부터는 몰라도 됩니다

매핑드·조건부 타입은 주로 라이브러리를 만드는 사람의 도구입니다. 애플리케이션 개발에서는 내장 유틸리티만으로 거의 다 해결됩니다.
다만 읽을 수는 있어야 합니다. 라이브러리 타입 정의를 보다가 이런 문법을 만났을 때 "아 이건 조건부 타입이구나" 정도만 알아보면 충분합니다. 지금 당장 외우려 하지 마세요.

실무에서 자주 쓰는 조합

앞의 도구들을 조합하면 실무에서 반복되는 문제를 타입 한 줄로 해결할 수 있습니다. 아래 네 가지 중 ①과 ④는 직접 쓸 일이 많고, ②와 ③은 "이런 것도 된다"는 예시로 읽기만 하면 됩니다. 특히 ④는 API 주소와 응답 타입을 한 표로 묶어, 주소만 넘기면 응답 타입이 자동으로 정해지게 만드는 패턴입니다.

// ① 폼 상태 — 각 필드의 에러 메시지
type FormErrors<T> = Partial<Record<keyof T, string>>;
const errors: FormErrors<User> = { email: "형식이 올바르지 않습니다" };

// ② 최소 하나는 필수
type AtLeastOne<T, K extends keyof T = keyof T> =
  Omit<T, K> & { [P in K]-?: Required<Pick<T, P>> }[K];

// ③ 깊은 읽기 전용
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};

// ④ API 경로별 응답 타입 매핑
type ApiRoutes = {
  "/users": User[];
  "/users/:id": User;
  "/posts": Post[];
};
function apiGet<P extends keyof ApiRoutes>(path: P): Promise<ApiRoutes[P]> {
  return fetch(path).then(r => r.json());
}
const users = await apiGet("/users");   // User[] 로 추론됩니다

🛠️ 현장 노트 — 타입이 복잡해지면

  1. 추론 결과를 확인하세요. 편집기에서 타입 이름 위에 마우스를 올리면 펼쳐진 결과가 보입니다. Playground에서 실험하는 것이 가장 빠릅니다.
  2. 중간 타입에 이름을 붙이세요. 한 줄에 다 넣지 말고 단계로 나누면 읽기 쉽고 오류 메시지도 명확해집니다.
  3. 복잡한 타입은 대개 설계 문제의 신호입니다. 타입 곡예로 억지로 맞추기 전에 데이터 구조 자체를 단순하게 바꿀 수 있는지 보세요.
  4. type-fest 같은 라이브러리에 잘 만들어진 유틸리티가 많습니다. 직접 만들기 전에 찾아보세요.

타입 실력의 목표는 화려한 타입을 만드는 것이 아닙니다. 동료가 5초 안에 읽을 수 있는 타입이 좋은 타입입니다.

📌 요약

  • 타입을 복사하지 말고 파생시킨다. 원본이 바뀌면 자동으로 따라온다.
  • 자주 쓰는 것: Partial·Pick·Omit·Record·ReturnType.
  • Record<유니온, T>는 모든 경우를 처리했는지 검사해 준다.
  • Omit은 오타를 잡아 주지 않는다. Pick은 잡는다. 필요하면 StrictOmit을 만든다.
  • 유틸리티 타입은 값을 바꾸지 않는다. 실제로 속성을 빼려면 JavaScript 코드로 뺀다.
  • keyof는 키를, typeof는 값에서 타입을 뽑는다.
  • as const + typeof X[number]로 값과 타입을 한 곳에서 관리한다.
  • 매핑드·조건부 타입은 읽을 수만 있으면 충분하다.
  • 동료가 읽을 수 있는 타입이 좋은 타입이다.
