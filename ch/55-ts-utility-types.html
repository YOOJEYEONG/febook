  • 매핑드 타입과 조건부 타입 읽는 법

읽는 데 약 20분

핵심 원칙: 복사하지 말고 파생시키세요

interface User {
  id: number;
  name: string;
  email: string;
  password: string;
  createdAt: Date;
}

// ❌ 손으로 다시 씁니다 — User가 바뀌면 여기도 고쳐야 합니다
interface UserProfile {
  id: number;
  name: string;
  email: string;
}

// ✅ User에서 파생시킵니다 — 자동으로 따라옵니다
type UserProfile = Omit<User, "password">;
type UserSummary = Pick<User, "id" | "name">;
type UserDraft = Partial<User>;

🔗 이것이 유틸리티 타입의 존재 이유입니다

타입을 손으로 복사하면 원본이 바뀔 때 조용히 어긋납니다. 파생시켜 두면 User에 속성을 추가하는 순간 관련된 모든 타입이 자동으로 갱신되고, 맞지 않는 코드가 즉시 오류로 드러납니다.

내장 유틸리티 타입

타입하는 일
Partial<T>모든 속성을 선택적으로. 수정 폼, PATCH 요청에
Required<T>모든 속성을 필수로
Readonly<T>모든 속성을 읽기 전용으로
Pick<T, K>일부 속성만 골라내기
Omit<T, K>일부 속성을 빼기
Record<K, V>키·값 타입으로 객체 만들기
Exclude<T, U>유니온에서 제거
Extract<T, U>유니온에서 추출
NonNullable<T>null·undefined 제거
ReturnType<F>함수의 반환 타입
Parameters<F>함수의 매개변수 타입들(튜플)
Awaited<P>Promise가 풀린 타입
실제 사용 예 
interface User {
  id: number; name: string; email: string; password: string; createdAt: Date;
}

// 생성할 때는 서버가 정하는 값이 없습니다
type CreateUserInput = Omit<User, "id" | "createdAt">;

// 수정할 때는 일부만 보냅니다
type UpdateUserInput = Partial<Omit<User, "id" | "createdAt">>;

// 화면에 보여줄 때는 비밀번호를 뺍니다
type PublicUser = Omit<User, "password">;

// 목록에는 최소한만
type UserListItem = Pick<User, "id" | "name">;

// 상태별 라벨
type Status = "idle" | "loading" | "error";
const labels: Record<Status, string> = {
  idle: "대기", loading: "불러오는 중", error: "오류"
};
// 상태를 하나 추가하면 여기서 "누락됐다"고 오류가 납니다 ✅

// 함수에서 타입 뽑기
function createUser(input: CreateUserInput) { return { id: 1, ...input }; }
type CreatedUser = ReturnType<typeof createUser>;
type CreateArgs = Parameters<typeof createUser>[0];

// 비동기 함수의 결과
async function fetchUsers(): Promise<User[]> { return []; }
type Users = Awaited<ReturnType<typeof fetchUsers>>;    // User[]

⚠️ Omit은 오타를 잡아 주지 않습니다

type A = Omit<User, "passwrod">;   // 오타인데 오류가 안 납니다
// 결과: User와 똑같은 타입 (아무것도 안 빠짐)

type B = Pick<User, "passwrod">;   // ❌ Pick은 오타를 잡습니다

Omit은 키가 존재하지 않아도 허용하도록 정의되어 있습니다. 안전하게 하려면 Omit<User, keyof User & "password">처럼 제약을 걸거나, 직접 만든 엄격한 버전을 쓰기도 합니다.

keyof와 typeof

interface User { id: number; name: string; }

type UserKeys = keyof User;         // "id" | "name"
type IdType = User["id"];           // number
type AnyValue = User[keyof User];   // number | string

// typeof — '값'에서 '타입'을 뽑습니다
const defaultConfig = {
  theme: "dark",
  fontSize: 16,
  features: { search: true }
};
type Config = typeof defaultConfig;
// { theme: string; fontSize: number; features: { search: boolean } }

// as const 와 조합 (51장)
const ROLES = ["admin", "editor", "viewer"] as const;
type Role = typeof ROLES[number];    // "admin" | "editor" | "viewer"

// 배열 하나로 값과 타입을 함께 관리합니다
ROLES.forEach(role => { /* role: "admin" | "editor" | "viewer" */ });

🔄 typeof가 두 가지 뜻인 이유

class="term" data-term="javascript">JavaScript의 typeof는 값의 타입 이름을 문자열로 돌려주는 연산자입니다(25장). TypeScript의 typeof는 타입을 쓰는 자리에서만 쓰이며 값으로부터 타입을 얻는 다른 기능입니다. 헷갈리지만 위치로 구분됩니다. 타입 자리에 있으면 후자입니다.

매핑드 타입 — 유틸리티는 이렇게 만들어졌습니다

// Partial의 실제 정의
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};
//  ↑ T의 모든 키를 순회하며 각 속성을 선택적으로 만듭니다

// Readonly
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};

// 수식어 제거는 앞에 마이너스
type Mutable<T> = {
  -readonly [K in keyof T]: T[K];
};
type Concrete<T> = {
  [K in keyof T]-?: T[K];      // 선택적 제거
};

// 키 이름 바꾸기 (as)
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

type UserGetters = Getters<{ name: string; age: number }>;
// { getName: () => string; getAge: () => number }

조건부 타입

// T가 U에 할당 가능하면 X, 아니면 Y
type IsString<T> = T extends string ? true : false;

type A = IsString<"hello">;   // true
type B = IsString<42>;        // false

// infer — 타입 안에서 값을 '꺼냅니다'
type ElementOf<T> = T extends (infer E)[] ? E : never;
type C = ElementOf<string[]>;   // string

// ReturnType의 실제 정의
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

// 유니온에 적용하면 각 항목에 따로 적용됩니다 (분배 조건부 타입)
type ToArray<T> = T extends any ? T[] : never;
type D = ToArray<string | number>;   // string[] | number[]

🧩 여기부터는 몰라도 됩니다

매핑드·조건부 타입은 주로 라이브러리를 만드는 사람의 도구입니다. 애플리케이션 개발에서는 내장 유틸리티만으로 거의 다 해결됩니다.
다만 읽을 수는 있어야 합니다. 라이브러리 타입 정의를 보다가 이런 문법을 만났을 때 "아 이건 조건부 타입이구나" 정도만 알아보면 충분합니다. 지금 당장 외우려 하지 마세요.

실무에서 자주 쓰는 조합

// ① 폼 상태 — 각 필드의 에러 메시지
type FormErrors<T> = Partial<Record<keyof T, string>>;
const errors: FormErrors<User> = { email: "형식이 올바르지 않습니다" };

// ② 최소 하나는 필수
type AtLeastOne<T, K extends keyof T = keyof T> =
  Omit<T, K> & { [P in K]-?: Required<Pick<T, P>> }[K];

// ③ 깊은 읽기 전용
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};

// ④ API 경로별 응답 타입 매핑
type ApiRoutes = {
  "/users": User[];
  "/users/:id": User;
  "/posts": Post[];
};
function apiGet<P extends keyof ApiRoutes>(path: P): Promise<ApiRoutes[P]> {
  return fetch(path).then(r => r.json());
}
const users = await apiGet("/users");   // User[] 로 추론됩니다

🛠️ 현장 노트 — 타입이 복잡해지면

  1. 추론 결과를 확인하세요. 편집기에서 타입 이름 위에 마우스를 올리면 펼쳐진 결과가 보입니다. Playground에서 실험하는 것이 가장 빠릅니다.
  2. 중간 타입에 이름을 붙이세요. 한 줄에 다 넣지 말고 단계로 나누면 읽기 쉽고 오류 메시지도 명확해집니다.
  3. 복잡한 타입은 대개 설계 문제의 신호입니다. 타입 곡예로 억지로 맞추기 전에 데이터 구조 자체를 단순하게 바꿀 수 있는지 보세요.
  4. type-fest 같은 라이브러리에 잘 만들어진 유틸리티가 많습니다. 직접 만들기 전에 찾아보세요.

타입 실력의 목표는 화려한 타입을 만드는 것이 아닙니다. 동료가 5초 안에 읽을 수 있는 타입이 좋은 타입입니다.

📌 요약

  • 타입을 복사하지 말고 파생시킨다. 원본이 바뀌면 자동으로 따라온다.
  • 자주 쓰는 것: Partial·Pick·Omit·Record·ReturnType.
  • Record<유니온, T>는 모든 경우를 처리했는지 검사해 준다.
  • Omit은 오타를 잡아 주지 않는다. Pick은 잡는다.
  • keyof는 키를, typeof는 값에서 타입을 뽑는다.
  • as const + typeof X[number]로 값과 타입을 한 곳에서 관리한다.
  • 매핑드·조건부 타입은 읽을 수만 있으면 충분하다.
  • 동료가 읽을 수 있는 타입이 좋은 타입이다.
