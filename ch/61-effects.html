useEffect란

Effect는 React 바깥 세계와 동기화하는 장치입니다. 렌더링만으로는 할 수 없는 일 — 네트워크 요청, 타이머, 구독, 직접적인 DOM 조작 — 즉 부수 효과(27장)를 다룹니다.

useEffect(() => {
  // 부수 효과
  document.title = `${count}개의 알림`;

  return () => {
    // 정리 함수 (선택)
  };
}, [count]);   // 의존성 배열
실행 시점 
렌더링 → 화면에 그리기(paint) → Effect 실행

의존성 배열에 따라:
  [ ]        → 마운트 후 한 번만
  [a, b]     → a나 b가 바뀌었을 때만
  (생략)      → 매 렌더링마다  ← 거의 항상 실수입니다

⏱️ Effect는 화면이 그려진 뒤 실행됩니다

그래서 Effect 안에서 레이아웃을 측정해 위치를 바꾸면 사용자가 깜빡임을 볼 수 있습니다. 그런 경우에만 useLayoutEffect를 쓰는데, 이것은 그리기 전에 동기적으로 실행되어 화면을 잠깐 막습니다. 기본은 useEffect이고, 깜빡임 문제가 실제로 확인될 때만 바꾸세요.

의존성 배열

// ❌ 배열 생략 — 매 렌더링마다 실행
useEffect(() => {
  fetchData();      // 데이터를 받아 상태를 바꾸면 → 다시 렌더링 → 또 실행 → 무한 루프
});

// ✅ 한 번만
useEffect(() => {
  fetchData();
}, []);

// ✅ userId가 바뀔 때마다
useEffect(() => {
  fetchUser(userId);
}, [userId]);

🔗 의존성을 거짓말하지 마세요

// ❌ userId를 쓰면서 의존성에 안 넣음
useEffect(() => {
  fetchUser(userId);
}, []);
// → userId가 바뀌어도 다시 실행되지 않습니다.
//   클로저가 첫 렌더링의 userId를 붙잡고 있습니다(31장).
//   "사용자를 바꿨는데 이전 사람 정보가 그대로"인 버그가 됩니다.

Effect 안에서 쓰는 모든 반응형 값(props·state·그로부터 계산된 값)은 전부 의존성에 들어가야 합니다. 48장에서 말한 react-hooks/exhaustive-deps 규칙이 이것을 자동으로 검사해 줍니다. 이 경고를 끄지 마세요.

🔧 의존성이 너무 많다면 — 배열이 아니라 코드를 고치세요

// 문제: 객체·함수는 매 렌더링마다 새로 만들어져 의존성이 계속 바뀝니다
const options = { id: userId };          // 매번 새 객체 (25장)
useEffect(() => { fetch(options); }, [options]);   // 매번 실행됨

// ✅ 해법 1: 원시 값만 의존성으로
useEffect(() => { fetch({ id: userId }); }, [userId]);

// ✅ 해법 2: 객체·함수를 Effect 안으로 옮기기
useEffect(() => {
  const options = { id: userId };
  fetch(options);
}, [userId]);

// ✅ 해법 3: 함수형 갱신으로 의존성 제거 (59장)
useEffect(() => {
  const timer = setInterval(() => setCount(prev => prev + 1), 1000);
  return () => clearInterval(timer);
}, []);   // count를 의존성에 넣지 않아도 됩니다

정리 함수

Effect가 구독·타이머·연결을 만들었다면 반드시 정리해야 합니다. 정리 함수는 다음 Effect가 실행되기 전과 컴포넌트가 사라질 때 호출됩니다.

정리가 필요한 대표적인 경우 
// ① 타이머
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);
}, []);

// ② 이벤트 리스너 (38장)
useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener("resize", onResize);
  return () => window.removeEventListener("resize", onResize);
}, []);

// ③ Observer (40장)
useEffect(() => {
  const observer = new IntersectionObserver(callback);
  observer.observe(ref.current);
  return () => observer.disconnect();
}, []);

// ④ 네트워크 요청 취소 (37장)
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/users/${userId}`, { signal: controller.signal })
    .then(r => r.json())
    .then(setUser)
    .catch(err => {
      if (err.name !== "AbortError") setError(err);
    });

  return () => controller.abort();
}, [userId]);

🏁 요청 취소가 막아 주는 실제 버그

사용자를 빠르게 A → B로 바꾸면 두 요청이 나갑니다. A의 응답이 B보다 늦게 도착하면 화면에 A의 데이터가 표시됩니다. 이것을 경쟁 상태(race condition)라고 하고, 정리 함수에서 이전 요청을 취소하면 사라집니다.
취소가 불가능한 상황이라면 플래그 방식도 씁니다.

useEffect(() => {
  let ignore = false;
  fetchUser(userId).then(data => { if (!ignore) setUser(data); });
  return () => { ignore = true; };
}, [userId]);

개발 모드에서 두 번 실행되는 이유

// StrictMode 안에서는 개발 중에만 이렇게 동작합니다
Effect 실행 → 정리 함수 실행 → Effect 다시 실행

🔁 버그가 아니라 검사입니다

React 18부터 <StrictMode>는 개발 모드에서 Effect를 일부러 한 번 더 실행합니다. 정리 함수를 제대로 만들었는지 확인하기 위해서입니다.
정리를 올바르게 했다면 두 번 실행해도 결과가 같아야 합니다. 두 번 실행돼서 문제가 생긴다면 그것은 실제 버그입니다. (사용자가 페이지를 이동했다 돌아오면 같은 일이 일어납니다.)
StrictMode를 끄지 마세요. 운영 빌드에서는 한 번만 실행됩니다.

Effect가 필요 없는 경우 — 이 챕터에서 가장 중요합니다

🚫 신입이 가장 많이 하는 실수

useEffect를 "무언가 바뀌면 실행" 용도로 남용하는 것입니다. 대부분의 경우 더 간단하고 정확한 방법이 있습니다.

① 다른 상태로 계산할 수 있는 값 
// ❌ 불필요한 Effect + 불필요한 상태
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);
useEffect(() => {
  setTotal(items.reduce((s, i) => s + i.price, 0));
}, [items]);
// 렌더링이 두 번 일어나고, 한 프레임 동안 값이 어긋납니다

// ✅ 그냥 계산합니다 (59장)
const total = items.reduce((s, i) => s + i.price, 0);
② 사용자 이벤트에 대한 반응 
// ❌ 상태를 감시해서 반응
useEffect(() => {
  if (isSubmitted) {
    sendAnalytics();
    showToast();
  }
}, [isSubmitted]);

// ✅ 이벤트 핸들러에서 바로 하세요
function handleSubmit() {
  setIsSubmitted(true);
  sendAnalytics();
  showToast();
}

🎯 판단 기준 한 줄

"이 코드는 무엇 때문에 실행되는가?"
사용자의 행동 때문이라면 → 이벤트 핸들러
화면에 나타났기 때문이라면 → Effect
데이터를 받아오는 것은 "화면에 나타나서"이므로 Effect가 맞습니다. 버튼을 눌러 저장하는 것은 "사용자가 눌러서"이므로 핸들러가 맞습니다.

③ props가 바뀔 때 상태 초기화 
// ❌
useEffect(() => { setDraft(""); }, [userId]);

// ✅ key로 컴포넌트 자체를 새로 시작 (59장)
<Editor key={userId} userId={userId} />
④ 부모에게 데이터 전달 
// ❌ 자식이 상태를 갖고 Effect로 부모에게 알림
useEffect(() => { onChange(value); }, [value]);

// ✅ 상태를 부모로 올리거나(59장), 이벤트 시점에 함께 알립니다
function handleChange(next) {
  setValue(next);
  onChange(next);
}

데이터 페칭

직접 쓴다면 최소 이 정도는 필요합니다 
function UserProfile({ userId }) {
  const [state, setState] = useState({ status: "loading" });

  useEffect(() => {
    const controller = new AbortController();
    setState({ status: "loading" });

    fetch(`/api/users/${userId}`, { signal: controller.signal })
      .then(res => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);   // 37장
        return res.json();
      })
      .then(data => setState({ status: "success", data }))
      .catch(error => {
        if (error.name === "AbortError") return;
        setState({ status: "error", error });
      });

    return () => controller.abort();
  }, [userId]);

  if (state.status === "loading") return <Spinner />;
  if (state.status === "error") return <ErrorMessage error={state.error} />;
  return <div>{state.data.name}</div>;
}

🛠️ 현장 노트 — 그래서 실무에서는 라이브러리를 씁니다

위 코드에도 아직 없는 것이 많습니다. 캐싱, 중복 요청 제거, 재시도, 창 포커스 시 갱신, 낙관적 업데이트, 페이지네이션… 이걸 전부 직접 만들면 버그투성이가 됩니다.
그래서 TanStack Query나 SWR을 씁니다(67장). React 공식 문서도 직접 만든 Effect 페칭 대신 라이브러리나 프레임워크 기능을 쓰라고 권합니다. Effect로 데이터를 가져오는 법을 아는 것은 필요하지만, 실무에서 그대로 쓰지는 않습니다.

📌 요약

  • Effect는 React 바깥 세계와 동기화하는 도구다. 화면이 그려진 뒤 실행된다.
  • 의존성을 거짓말하지 마라. 안에서 쓰는 반응형 값은 전부 넣는다.
  • 의존성이 문제면 배열이 아니라 코드를 고친다 — 객체를 안으로, 원시 값만, 함수형 갱신.
  • 정리 함수로 타이머·리스너·구독·요청을 반드시 정리한다.
  • 요청 취소가 경쟁 상태를 막는다.
  • StrictMode의 두 번 실행은 검사다. 문제가 생기면 정리가 잘못된 것이다.
  • 대부분의 Effect는 필요 없다. 계산할 수 있으면 계산하고, 사용자 행동이면 핸들러에서.
  • 판단 기준: 사용자 행동 → 핸들러, 화면에 나타남 → Effect.
  • 데이터 페칭은 실무에서 전용 라이브러리를 쓴다.
