왜 "기다리는 코드"가 필요한가

지금까지의 코드는 한 줄이 끝나면 바로 다음 줄로 갔습니다. 1 + 2는 눈 깜짝할 새 끝나니까요. 하지만 서버에서 데이터를 받아 오는 일은 다릅니다. 0.1초가 걸릴 수도, 3초가 걸릴 수도, 실패할 수도 있습니다.

35장에서 봤듯 JavaScript는 한 번에 하나만 합니다. 서버 응답을 그 자리에 서서 기다리면 그동안 클릭도 스크롤도 화면 갱신도 전부 멈춥니다. 그래서 "요청은 보내 두고, 결과가 오면 알려 줘"라는 방식이 필요합니다.

📳 푸드코트 진동벨 비유

푸드코트에서 음식을 주문하면 음식 대신 진동벨을 받습니다. 진동벨을 들고 자리로 가서 다른 일을 하다가, 벨이 울리면 음식을 받으러 갑니다. 가끔은 "재료가 떨어졌습니다"라는 연락이 오기도 합니다.

  • 진동벨 = Promise. "결과는 아직 없지만, 나중에 꼭 알려 주겠다"는 약속(promise)입니다.
  • 벨이 울리기 전 = pending(대기), 음식이 나옴 = fulfilled(이행), 품절 연락 = rejected(거부).
  • "벨이 울리면 음식을 받아 와" = .then(), "품절이면 다른 메뉴로" = .catch().
  • 벨을 받자마자 줄을 떠날 수 있어서, 그동안 다른 일(클릭 처리, 화면 갱신)을 할 수 있습니다.

콜백에서 시작하기

콜백 지옥 
getUser(userId, function (user) {
  getOrders(user.id, function (orders) {
    getOrderDetail(orders[0].id, function (detail) {
      getShipping(detail.shippingId, function (shipping) {
        console.log(shipping);
        // 오른쪽으로 계속 밀려납니다.
        // 게다가 각 단계마다 에러 처리를 따로 해야 합니다.
      });
    });
  });
});

Promise 이전에는 "끝나면 이 함수를 불러 줘"라고 콜백(27장)을 넘기는 방식만 있었습니다. 단계가 이어지면 이렇게 됩니다. 이 모양을 콜백 지옥이라고 불렀습니다. 읽기 어렵고, 에러 처리가 흩어지고, 중간에 병렬 처리를 넣기도 까다로웠습니다. 이를 해결하려고 Promise가 도입되었습니다.

Promise의 세 가지 상태

상태 전이 
      ┌──────────────┐
      │   pending    │  대기 중 (아직 결과 없음)
      └──────┬───────┘
             │
    ┌────────┴────────┐
    ▼                 ▼
┌─────────┐      ┌──────────┐
│fulfilled│      │ rejected │
│ 이행됨   │      │  거부됨   │
└─────────┘      └──────────┘

한 번 결정되면 다시 바뀌지 않습니다.

Promise를 만드는 구조 읽기

대부분은 fetch처럼 이미 Promise를 돌려주는 함수를 쓰지만, 구조를 한 번은 읽을 줄 알아야 합니다.

const promise = new Promise((resolve, reject) => {
  // ① 여기에 "시간이 걸리는 일"을 시작합니다. 이 함수는 즉시 실행됩니다
  // ② 성공하면 resolve(결과값)  → 상태가 fulfilled로, .then에 결과값 전달
  // ③ 실패하면 reject(에러)     → 상태가 rejected로, .catch에 에러 전달
});
  • new Promise(…)에 넘기는 화살표 함수는 Promise가 대신 불러 주는 함수입니다(new는 32장).
  • Promise는 그 함수를 부를 때 버튼 두 개를 쥐여 줍니다. 첫 번째가 "성공 버튼" resolve, 두 번째가 "실패 버튼" reject입니다. 이름은 마음대로 지어도 되지만 순서가 의미를 정합니다.
  • 둘 중 먼저 누른 버튼 하나만 효과가 있습니다.

async / await

async/await는 Promise를 동기 코드처럼 보이게 쓰는 문법입니다. 내부 동작은 Promise 그대로입니다.

// Promise 체이닝
function loadData() {
  return fetchUser()
    .then(user => fetchOrders(user.id))
    .then(orders => orders.filter(o => o.active))
    .catch(error => { console.error(error); return []; });
}

// 같은 코드, async/await
async function loadData() {
  try {
    const user = await fetchUser();
    const orders = await fetchOrders(user.id);
    return orders.filter(o => o.active);
  } catch (error) {
    console.error(error);
    return [];
  }
}
규칙내용
async 함수는항상 Promise를 반환합니다. return 1을 해도 호출한 쪽은 1로 이행되는 Promise를 받습니다
await는Promise가 결정될 때까지 그 함수만 멈춥니다. 페이지 전체가 멈추는 것이 아닙니다
await를 쓸 수 있는 곳async 함수 안. 그리고 ES 모듈의 최상위(top-level await)
에러 처리try/catch가 그대로 동작합니다

순차 vs 병렬 — 성능이 갈리는 지점

🐢 실무에서 가장 흔한 성능 실수

// ❌ 서로 관계없는 요청인데 순서대로 기다립니다
const user = await getUser();
const posts = await getPosts();      // user를 안 쓰는데도 기다림
const notices = await getNotices();

// ✅ 동시에 시작
const [user, posts, notices] = await Promise.all([
  getUser(), getPosts(), getNotices()
]);

// ⚠️ 단, 뒤 요청이 앞 결과에 의존하면 순차가 맞습니다
const user = await getUser();
const orders = await getOrders(user.id);   // user.id가 필요 → 순차

Promise 조합 메서드

메서드동작언제 쓰나
Promise.all모두 성공하면 결과 배열. 하나라도 실패하면 즉시 실패전부 성공해야 의미가 있을 때
Promise.allSettled전부 기다린 뒤 각각의 성공·실패를 모두 알려줌일부 실패해도 나머지를 쓰고 싶을 때
Promise.race가장 먼저 끝난 것 하나 (성공이든 실패든)타임아웃 구현
Promise.any가장 먼저 성공한 것 하나여러 서버 중 아무거나 응답하면 될 때

⏹️ race 타임아웃은 원래 작업을 취소하지 않습니다

위 withTimeout은 "더 기다리지 않겠다"는 뜻일 뿐입니다. 진동벨을 버리고 가도 주방은 음식을 계속 만듭니다. 네트워크 요청이라면 응답은 계속 내려받아지고, 데이터와 배터리가 쓰입니다.

fetch를 진짜로 중단하려면 37장의 AbortController나 fetch(url, { signal: AbortSignal.timeout(3000) })를 씁니다. 이쪽은 시간이 지나면 요청 자체를 끊고 TimeoutError로 거부됩니다.

반복문과 비동기

🕳️ 처리되지 않은 거부

// ❌ 반환하지 않으면 에러가 밖으로 전달되지 않습니다
async function bad() {
  doAsyncWork();          // await도 return도 없음 → 실패해도 아무도 모름
}

// ✅
async function good() {
  await doAsyncWork();    // 또는 return doAsyncWork();
}

// ❌ .catch 없는 Promise
fetchData().then(render);       // 실패 시 unhandledrejection

// ✅
fetchData().then(render).catch(showError);

🛠️ 현장 노트 — 비동기 체크리스트

  1. 서로 의존하지 않는 요청은 Promise.all로 묶습니다. 가장 쉬운 성능 개선입니다.
  2. 일부 실패를 허용해야 하면 allSettled.
  3. forEach에 async를 쓰지 마세요. for...of나 map+all.
  4. 모든 비동기 호출에 에러 처리 경로가 있는지 확인합니다.
  5. 로딩 상태는 finally에서 해제합니다(33장).
  6. 사용자가 화면을 떠났을 때를 대비해 AbortController로 취소할 수 있게 만듭니다(37장).

📌 요약

  • Promise는 pending → fulfilled/rejected. 한 번 결정되면 바뀌지 않는다.
  • async 함수는 항상 Promise를 반환한다.
  • await는 그 함수만 멈춘다. 페이지는 멈추지 않는다.
  • async/await에서는 try/catch가 그대로 동작한다.
  • 독립적인 요청은 Promise.all로 병렬 — 가장 쉬운 성능 개선.
  • all은 하나라도 실패하면 전체 실패, allSettled는 전부 결과를 준다.
  • Promise는 진동벨이다. new Promise((resolve, reject) => …)에서 성공 시 resolve, 실패 시 reject를 부른다.
  • race로 타임아웃을 만들 수 있지만 원래 작업은 취소되지 않는다. 요청을 끊으려면 AbortSignal.timeout(37장).
  • forEach에 async를 쓰지 않는다.
