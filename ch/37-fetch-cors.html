fetch 기본

async function loadUsers() {
  const response = await fetch("https://api.example.com/users");

  // ⚠️ 이 줄이 없으면 404·500을 성공으로 착각합니다
  if (!response.ok) {
    throw new Error(`요청 실패: ${response.status} ${response.statusText}`);
  }

  const data = await response.json();
  return data;
}
Response의 속성·메서드내용
response.ok상태 코드가 200~299이면 true
response.status숫자 상태 코드 (4장)
response.headers.get("...")응답 헤더 읽기
await response.json()본문을 JSON으로 파싱. Promise를 반환합니다
await response.text()본문을 문자열로
await response.blob()이미지·파일 등 이진 데이터로

💥 fetch의 가장 큰 함정

오해 — 서버가 404나 500을 돌려주면 catch로 간다. 사실 — 가지 않습니다. fetch는 응답을 받는 데 성공했으면 그 내용이 무엇이든 이행(fulfilled)으로 처리합니다. "서버가 응답을 줬다"는 것 자체가 성공이라는 관점입니다. fetch가 거부(rejected)되는 경우는 이런 것들뿐입니다: 네트워크 연결 실패, CORS 차단, 요청 취소, DNS 실패. 그래서 if (!response.ok) throw ...를 반드시 써야 합니다. 이것을 빠뜨려 "에러 페이지의 HTML을 JSON으로 파싱하려다 이상한 오류가 나는" 상황이 매우 흔합니다.

요청 취소하기

const controller = new AbortController();

fetch("/api/search?q=자바스크립트", { signal: controller.signal })
  .then(res => res.json())
  .catch(error => {
    if (error.name === "AbortError") {
      console.log("취소됨 — 정상 동작입니다");
      return;
    }
    console.error(error);
  });

// 어디서든 취소할 수 있습니다
controller.abort();
타임아웃 (표준 방법) 
// AbortSignal.timeout — Chrome 103+, Safari 16+, Firefox 100+
await fetch(url, { signal: AbortSignal.timeout(5000) });

🔄 왜 취소가 필요한가

  • 검색어 자동완성 — 이전 검색 요청이 늦게 도착해 최신 결과를 덮어쓰는 문제(경쟁 상태)를 막습니다.
  • 화면 이동 — 사용자가 다른 페이지로 갔는데 이전 화면의 응답이 도착해 오류가 나는 것을 막습니다.
  • React에서는 useEffect의 정리 함수에서 abort()를 호출하는 것이 정석입니다(61장).

CORS — 가장 많이 겪는 오류

언젠가 반드시 보게 될 메시지 
Access to fetch at 'https://api.other.com/data' from origin
'http://localhost:3000' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.

왜 막는가

3장에서 배운 동일 출처 정책이 출발점입니다. 브라우저는 다른 출처의 응답을 JavaScript가 읽는 것을 기본적으로 막습니다.

🛡️ 없으면 무슨 일이 벌어질까

여러분이 은행에 로그인한 상태로 공격자의 사이트에 방문했다고 합시다. 그 사이트의 스크립트가 fetch("https://mybank.com/api/account")를 호출합니다. 쿠키는 브라우저가 자동으로 붙이므로(4장) 서버는 정상 요청으로 처리합니다.
동일 출처 정책이 없다면 공격자는 여러분의 계좌 정보를 그대로 읽을 수 있습니다. CORS는 이것을 막기 위한 장치입니다.

어떻게 허용하는가

서버가 응답 헤더로 허락을 표시해야 합니다.

Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true

🚫 프론트엔드에서는 CORS를 고칠 수 없습니다

오해 — 요청 헤더를 잘 설정하면 CORS를 통과할 수 있다. 사실 — 허가는 서버가 응답으로 내려주는 것입니다. 클라이언트가 스스로에게 허가를 줄 수 있다면 보안 장치의 의미가 없겠죠. 요청 코드를 아무리 고쳐도 서버가 헤더를 주지 않으면 브라우저가 차단합니다. 참고로 요청은 실제로 서버에 도달했고 서버는 처리까지 마쳤을 수 있습니다. 브라우저가 응답을 JavaScript에 넘겨주지 않을 뿐입니다. 그래서 개발자 도구 Network 탭에는 200이 보이는데 코드에서는 오류가 나는 상황이 생깁니다.

사전 요청(preflight)

어떤 요청은 본 요청을 보내기 전에 OPTIONS 요청으로 먼저 물어봅니다. "이런 요청을 보내도 될까요?"라고 확인하는 것입니다.

사전 요청이 없는 경우 (단순 요청)사전 요청이 필요한 경우
GET, HEAD, POST 중 하나이고
Content-Type이 text/plain,
application/x-www-form-urlencoded,
multipart/form-data 중 하나이며
특별한 헤더가 없을 때 		PUT·DELETE·PATCH 사용
Content-Type: application/json
Authorization 등 커스텀 헤더 사용

거의 모든 실무 API 요청은 사전 요청을 유발합니다. JSON을 보내는 순간 Content-Type: application/json이 붙기 때문입니다. 그래서 개발자 도구에 요청이 두 번 보이는 것을 자주 보게 됩니다.

해결 방법

상황해결책
내가 서버도 관리한다서버에 CORS 헤더를 추가합니다. 정공법입니다
개발 중 로컬에서만 막힌다개발 서버의 프록시 기능을 씁니다. 같은 출처인 것처럼 우회합니다(47장)
서버를 고칠 수 없다내 서버를 하나 두고 대신 호출하게 합니다. 서버 간 통신에는 CORS가 없습니다
API 키가 필요한 외부 API반드시 서버를 경유해야 합니다. 키를 프론트엔드에 두면 노출됩니다(1·78장)

🍪 쿠키를 함께 보내려면

fetch(url, { credentials: "include" });   // 다른 출처에도 쿠키 전송

이때 서버는 Access-Control-Allow-Credentials: true를 보내야 하고, Access-Control-Allow-Origin에 *를 쓸 수 없습니다. 정확한 출처를 명시해야 합니다. 보안상 당연한 제약입니다.

🛠️ 현장 노트 — 요청 함수를 한 곳에 모으세요

// api/client.js — 모든 요청이 이 함수를 통과하게 만듭니다
const BASE_URL = import.meta.env.VITE_API_URL;

export async function apiRequest(path, options = {}) {
  const response = await fetch(BASE_URL + path, {
    headers: {
      "Content-Type": "application/json",
      ...(getToken() && { Authorization: `Bearer ${getToken()}` }),
      ...options.headers
    },
    signal: AbortSignal.timeout(10000),
    ...options
  });

  if (!response.ok) {
    if (response.status === 401) redirectToLogin();
    throw new HttpError(response.status, await response.text());
  }
  if (response.status === 204) return null;   // 본문 없음
  return response.json();
}

이렇게 모아 두면 인증 토큰·타임아웃·에러 처리·재시도를 한 곳에서 관리할 수 있습니다. 실무에서는 이 역할을 axios나 TanStack Query 같은 도구가 대신하기도 합니다(67장).

📌 요약

  • fetch는 404·500에도 거부되지 않는다. if (!response.ok) throw를 반드시 쓴다.
  • fetch가 거부되는 경우는 네트워크 실패·CORS 차단·요청 취소 정도다.
  • JSON 전송은 Content-Type: application/json + JSON.stringify(...).
  • FormData를 보낼 때는 Content-Type을 지정하지 않는다.
  • AbortController로 요청을 취소한다. 자동완성·화면 이동에 필수.
  • CORS는 서버가 헤더로 허락하는 것이다. 프론트엔드에서 고칠 수 없다.
  • JSON을 보내면 대부분 사전 요청(OPTIONS)이 먼저 나간다.
  • API 키는 반드시 서버를 경유해야 한다.
