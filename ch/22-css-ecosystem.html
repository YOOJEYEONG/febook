CSS의 세 가지 오래된 문제

도구를 이해하려면 무엇이 불편했는지부터 알아야 합니다.

문제내용
① 전역 이름 공간모든 클래스가 전역이다. 어딘가에서 .title을 정의하면 문서 전체에 영향을 준다. 팀이 커질수록 충돌이 잦아진다
② 표현력 부족변수도, 중첩도, 반복 처리도 없었다. 같은 색을 스무 곳에 손으로 적어야 했다
③ 죽은 코드어떤 규칙이 아직 쓰이는지 알 수 없다. 무서워서 못 지운다. 파일은 계속 커진다

Sass / SCSS

문제 ②를 풀려고 2006년에 나왔습니다. CSS에 없던 기능을 얹은 확장 언어입니다.

SCSS 문법 
$primary: #1f5f4f;          // 변수

@mixin flex-center {         // 재사용 블록
  display: flex;
  align-items: center;
  justify-content: center;
}

.card {
  color: $primary;
  @include flex-center;

  &__title {                // 중첩 + 부모 참조 → .card__title
    font-weight: 700;
  }
  &:hover { opacity: .9; }
}

📉 Sass가 예전보다 덜 필요해진 이유

표준 CSS가 Sass의 핵심 기능을 따라잡았습니다.

Sass 기능표준 CSS 대체
변수 $xclass="term" data-term="css-variable">CSS 변수 --x (오히려 더 강력합니다)
중첩네이티브 중첩 — Chrome 112+, Safari 16.5+, Firefox 117+
@import 파일 분할번들러가 처리
색 계산 함수color-mix(), oklch(), 상대 색상 문법

여전히 유용한 것은 @mixin·@each 같은 반복·논리 기능과 기존 프로젝트의 방대한 코드베이스입니다. 새 프로젝트에서 Sass가 필수는 아닙니다.

PostCSS

언어가 아니라 CSS를 변환하는 도구입니다. 플러그인을 끼워 쓰는 방식이라, "CSS 파일을 읽어 → 원하는 대로 고쳐 → 다시 CSS로 내보내는" 파이프라인입니다.

  • Autoprefixer — 필요한 브라우저 접두사(-webkit- 등)를 자동으로 붙여 줍니다.
  • 최신 문법 변환 — 아직 지원되지 않는 신문법을 구형 문법으로 바꿔 줍니다.
  • Tailwind CSS도 내부적으로 PostCSS 생태계 위에서 동작해 왔습니다.

대부분 직접 설정할 일 없이 프레임워크에 내장되어 있습니다. 있다는 것만 알면 충분합니다.

CSS Modules

문제 ①(전역 충돌)을 푸는 가장 단순하고 확실한 방법입니다. 빌드할 때 클래스 이름을 고유한 이름으로 바꿔 버립니다.

Button.module.css 
.button { background: #1f5f4f; color: white; }
Button.jsx 
import styles from "./Button.module.css";

export function Button() {
  return <button className={styles.button}>확인</button>;
}

실제 HTML에는 class="Button_button__x7f2k"처럼 중복될 수 없는 이름이 들어갑니다. 다른 파일에 .button이 백 개 있어도 서로 간섭하지 않습니다.

  • 장점 — 문법은 그냥 CSS. 배울 것이 거의 없고, 런타임 비용이 0입니다.
  • 단점 — 컴포넌트마다 파일이 하나씩 늘고, 동적인 값(props에 따라 색 바꾸기)은 다루기 번거롭습니다.

Tailwind CSS

문제 ①과 ③을 동시에 푸는 접근입니다. 클래스를 새로 만들지 않고 이미 정해진 작은 클래스들을 HTML에서 조합합니다.

<button class="px-4 py-2 bg-emerald-800 text-white rounded-lg
               hover:bg-emerald-700 focus-visible:ring-2">
  확인
</button>
장점단점
이름을 고민할 필요가 없다HTML이 길고 처음엔 지저분해 보인다
실제 사용된 클래스만 최종 CSS에 포함 → CSS 파일이 거의 안 큰다클래스 이름을 새로 배워야 한다
디자인 값이 정해진 척도 안에서만 선택되어 일관성이 생긴다정해진 척도를 벗어나려면 별도 설정이 필요하다
파일을 오갈 필요 없이 한 곳에서 작업같은 조합을 반복하면 컴포넌트로 묶어야 한다

🤔 "인라인 스타일과 뭐가 다른가요?"

가장 흔한 비판이자 오해입니다. 세 가지가 다릅니다. ① 제약이 있습니다. p-4는 아무 값이나 되는 게 아니라 정해진 간격 척도 중 하나입니다. 팀 전체가 같은 값을 쓰게 됩니다. ② 상태와 조건을 다룹니다. 인라인 스타일로는 :hover, :focus-visible, 미디어 쿼리, 다크 모드를 쓸 수 없습니다. Tailwind는 hover:, md:, dark: 접두사로 전부 가능합니다. ③ 명시도가 평평합니다. 인라인 스타일은 명시도가 매우 높아 덮어쓰기가 어렵습니다.

CSS-in-JS

JavaScript 안에서 스타일을 정의하는 방식입니다. styled-components, Emotion이 대표적입니다.

const Button = styled.button`
  background: ${props => props.$primary ? "#1f5f4f" : "#eee"};
  padding: 8px 16px;
  &:hover { opacity: 0.9; }
`;
  • 장점 — props에 따라 스타일을 바꾸기가 자연스럽고, 스타일과 컴포넌트가 한 파일에 있으며, 자동으로 범위가 격리됩니다.
  • 단점 — 런타임 비용이 있습니다. 브라우저에서 스타일을 만들어 주입하므로 그만큼 느려집니다.

⚠️ 서버 컴포넌트와의 충돌 — 지형이 바뀌었습니다

React 서버 컴포넌트(69장)와 Next.js App Router(71장)가 등장하면서 런타임 CSS-in-JS는 서버 컴포넌트에서 그대로 쓸 수 없게 되었습니다. 스타일을 만들려면 브라우저의 JavaScript 실행이 필요한데 서버 컴포넌트에는 그것이 없기 때문입니다. 그래서 최근에는 빌드 시점에 CSS 파일로 뽑아내는 방식(vanilla-extract, Panda CSS, StyleX 등 이른바 "제로 런타임 CSS-in-JS")이 대안으로 쓰입니다. 새 프로젝트에서 런타임 CSS-in-JS를 선택할 때는 이 제약을 반드시 확인하세요.

🛠️ 현장 노트 — 신입에게 가장 중요한 조언

도구를 먼저 배우지 마세요. Tailwind만 배운 사람은 flex items-center는 쓸 줄 알아도 왜 세로 정렬이 안 되는지 설명하지 못합니다. 결국 CSS를 아는 만큼만 도구를 쓸 수 있습니다.

면접에서도 "Tailwind를 쓸 줄 아는가"가 아니라 "이 레이아웃을 왜 이렇게 짰는가"를 묻습니다. 12~21장의 내용이 여러분의 실력이고, 이 챕터의 도구들은 그 실력을 빠르게 쓰는 방법일 뿐입니다.

📌 요약

  • CSS 도구는 전역 충돌·표현력 부족·죽은 코드 세 문제를 풀려고 나왔다.
  • Sass는 표현력을 풀었지만, 표준 CSS가 변수·중첩을 따라잡아 필수는 아니게 되었다.
  • PostCSS는 언어가 아니라 CSS 변환 도구. 대개 프레임워크에 내장되어 있다.
  • CSS Modules는 클래스 이름을 고유하게 바꿔 충돌을 없앤다. 런타임 비용 0.
  • Tailwind는 정해진 유틸리티 조합. 인라인 스타일과 달리 제약·상태·평평한 명시도가 있다.
  • 런타임 CSS-in-JS는 서버 컴포넌트와 충돌한다. 제로 런타임 방식이 대안이다.
  • 도구보다 CSS 자체를 먼저 익힌다. 도구는 아는 만큼만 쓸 수 있다.
