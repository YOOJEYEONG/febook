가장 위험한 상태

🕳️ "사용자는 겪었는데 개발자는 모르는 오류"

개발자의 컴퓨터에서는 잘 됩니다. QA도 통과했습니다. 그런데 특정 브라우저·특정 데이터·특정 순서에서만 터집니다.
사용자는 대부분 신고하지 않습니다. 그냥 떠납니다. 그래서 모니터링이 없으면 문제가 있다는 사실조차 모릅니다.

에러 추적

직접 만들면 (33장) 
window.addEventListener("error", (event) => {
  report({ message: event.message, file: event.filename, line: event.lineno });
});

window.addEventListener("unhandledrejection", (event) => {
  report({ reason: String(event.reason) });
});

여기에 그룹화, 중복 제거, 발생 빈도, 사용자 수, 스택 복원, 알림을 더하면 결국 전용 도구가 됩니다. 그래서 실무에서는 Sentry 같은 서비스를 씁니다.

Sentry 예 
import * as Sentry from "@sentry/react";

Sentry.init({
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,
  environment: process.env.NODE_ENV,
  release: process.env.NEXT_PUBLIC_VERSION,     // ⭐ 어느 배포에서 났는지
  tracesSampleRate: 0.1,                         // 성능 추적은 10%만
  replaysOnErrorSampleRate: 1.0,                 // 오류 시에는 재현 기록
  beforeSend(event) {
    // ⭐ 개인정보 제거
    if (event.request?.cookies) delete event.request.cookies;
    return event;
  }
});
도구가 해 주는 것
같은 오류를 묶어 보여줍니다 — 1000건이 아니라 "1개 오류, 1000회 발생, 사용자 340명"
스택 트레이스를 원본 코드로 복원합니다 (소스맵)
발생 환경 — 브라우저, OS, 화면 크기, 이전 동작 기록
세션 재현 — 사용자가 무엇을 눌렀는지 영상처럼 재생
배포 연결 — 어느 버전부터 발생했는지, 회귀인지

소스맵 있음:  at handleSubmit (LoginForm.tsx:42)  ← 바로 찾아갑니다

47장에서 말한 방식이 여기서 쓰입니다. 소스맵을 생성하되 공개 배포에는 포함하지 않고, 오류 추적 서비스에만 업로드합니다. 그러면 코드는 노출되지 않으면서 디버깅은 편해집니다.

🍞 "무엇을 하다가 터졌는가"가 절반입니다

스택 트레이스만으로는 재현이 안 되는 경우가 많습니다. 어떤 화면에서, 무엇을 누르고, 어떤 데이터였는지가 있어야 원인을 찾습니다. 빵부스러기(breadcrumb)와 태그를 잘 남기면 디버깅 시간이 몇 배로 줄어듭니다.

개인정보

🔒 모니터링 도구가 개인정보 유출 경로가 될 수 있습니다

  • URL에 담긴 정보 — /orders?email=hong@example.com 같은 주소가 그대로 전송됩니다
  • 폼 입력값 — 세션 재현 기능이 비밀번호·카드번호까지 녹화할 수 있습니다
  • 오류 메시지 안의 데이터 — "사용자 홍길동(010-…)를 찾을 수 없음"
  • 쿠키·헤더 — 토큰이 그대로 전송될 수 있습니다

대응: 세션 재현에서 입력값 마스킹을 기본으로 켜고, beforeSend로 민감한 필드를 제거하고, URL 파라미터를 정제하고, 법적 요구사항(개인정보 처리방침, 동의)을 확인하세요. "오류를 잘 잡으려고" 개인정보를 수집하는 것은 정당화되지 않습니다.

성능 모니터링

76장의 class="term" data-term="field-data">실제 사용자 데이터 수집 
import { onLCP, onINP, onCLS, onTTFB } from "web-vitals";

function send(metric) {
  navigator.sendBeacon("/api/vitals", JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,          // "good" | "needs-improvement" | "poor"
    path: location.pathname,
    connection: navigator.connection?.effectiveType
  }));
}
[onLCP, onINP, onCLS, onTTFB].forEach(fn => fn(send));

📊 평균이 아니라 백분위를 보세요

"평균 LCP 1.8초"는 거의 쓸모없는 숫자입니다. 사용자 대부분이 0.5초인데 10%가 15초여도 평균은 좋게 나옵니다.
p75(상위 25%가 이보다 느림)를 보세요. 구글의 Core Web Vitals 평가 기준도 p75입니다. "우리 사용자 4명 중 1명은 LCP가 4초를 넘는다"가 행동으로 이어지는 정보입니다.

함께 보면 좋은 것이유
페이지별 지표전체 평균은 문제를 감춥니다
기기·네트워크별저사양 기기에서만 나쁜 경우가 많습니다
배포 전후 비교어느 변경이 성능을 떨어뜨렸는지
비즈니스 지표와 연결"LCP가 1초 늘면 이탈률이 얼마나 오르는가"

수준언제

🗑️ console.log를 커밋하지 마세요

디버깅용 로그가 운영에 남으면 콘솔이 시끄러워져 진짜 오류가 묻힙니다. 그리고 민감한 데이터가 노출될 수 있습니다. 48장의 ESLint no-console 규칙으로 막고, 빌드 설정에서 자동 제거하기도 합니다.

알림

🔔 알림 피로 — 가장 흔한 실패

모든 오류에 알림을 걸면 하루에 수백 개가 옵니다. 그러면 아무도 안 봅니다. 그리고 진짜 장애를 놓칩니다.
알림은 "지금 사람이 행동해야 하는 것"에만 걸어야 합니다.

알림을 걸 것대시보드로만 볼 것
새로운 오류가 처음 등장
오류 발생률이 급증
결제·로그인 등 핵심 흐름의 실패
성능 지표의 급격한 악화 		알려진 오류의 일상적 발생
개별 사용자의 네트워크 오류
브라우저 확장 프로그램이 일으키는 오류
전체적인 추세

🧹 잡음 걸러내기

실제 운영을 하면 우리 코드와 무관한 오류가 대량으로 들어옵니다. 브라우저 확장 프로그램, 광고 차단기, 봇, 아주 오래된 브라우저. 이것들을 필터로 걸러내지 않으면 진짜 문제가 묻힙니다. Sentry 등에는 무시 목록 기능이 있으니 초기에 정리해 두세요.

🛠️ 현장 노트 — 운영을 시작할 때

  1. 에러 추적부터 붙이세요. 성능보다 먼저입니다. 오류는 사용자가 바로 이탈하는 원인입니다.
  2. 소스맵을 올리세요. 없으면 오류 정보가 거의 쓸모없습니다.
  3. 배포 버전을 태그하세요. "언제부터"를 알아야 원인을 좁힙니다.
  4. 알림은 최소로 시작해서 필요할 때 늘리세요. 반대로 하면 무시하게 됩니다.
  5. 개인정보 처리를 먼저 확인하세요. 나중에 정리하기 어렵습니다.
  6. 주기적으로 오류 목록을 보세요. 알림이 안 왔어도 쌓이는 오류가 있습니다.

"오류가 0건"이 목표가 아닙니다. 목표는 "오류가 나면 안다"와 "무엇이 문제인지 안다"입니다. 관찰할 수 없는 시스템은 고칠 수도 없습니다.

📌 요약

  • 가장 위험한 것은 사용자만 겪고 개발자는 모르는 오류다. 대부분 신고하지 않는다.
  • 에러 추적 도구가 그룹화·스택 복원·환경 정보·세션 재현을 제공한다.
  • 소스맵을 서비스에 업로드하되 공개 배포에는 포함하지 않는다.
  • 빵부스러기와 태그로 "무엇을 하다 터졌는가"를 남긴다.
  • 모니터링이 개인정보 유출 경로가 될 수 있다. 마스킹과 필터링이 필수다.
  • 성능은 평균이 아니라 p75로 본다.
  • 로그에는 무엇을·어디서·어떤 값으로를 남긴다. console.log를 커밋하지 않는다.
  • 알림은 지금 행동해야 하는 것에만. 알림 피로가 가장 흔한 실패다.
