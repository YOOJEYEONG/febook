useRef

용도 ① DOM 요소 참조 
function SearchBox() {
  const inputRef = useRef(null);

  useEffect(() => {
    inputRef.current?.focus();     // 화면에 나타나면 포커스
  }, []);

  return <input ref={inputRef} />;
}
용도 ② 렌더링과 무관한 값 저장 
function Timer() {
  const [seconds, setSeconds] = useState(0);
  const intervalRef = useRef(null);        // 화면에 안 보이는 값

  function start() {
    if (intervalRef.current) return;
    intervalRef.current = setInterval(() => setSeconds(s => s + 1), 1000);
  }
  function stop() {
    clearInterval(intervalRef.current);
    intervalRef.current = null;
  }

  useEffect(() => stop, []);   // 정리 (61장)
}

🚫 ref로 화면에 보이는 값을 관리하지 마세요

// ❌ 화면이 갱신되지 않습니다
const countRef = useRef(0);
<button onClick={() => countRef.current++}>{countRef.current}</button>

"불필요한 렌더링을 줄이려고" ref를 쓰는 것은 React를 거스르는 것입니다. 화면에 나오는 값은 반드시 상태여야 합니다.

🎯 ref가 맞는 경우

  • 포커스·스크롤·미디어 재생 등 명령형 DOM 조작
  • 타이머 ID, 이전 값 기억
  • 외부 라이브러리 인스턴스(차트, 지도)
  • 렌더링 결과에 영향을 주지 않는 모든 값

렌더링은 왜 일어나는가

🔄 정확히 이 세 가지입니다

  1. 자신의 상태가 바뀔 때
  2. 부모가 다시 렌더링될 때 ← 이것이 핵심입니다
  3. 구독 중인 class="term" data-term="context">Context 값이 바뀔 때(65장)

💡 "부모가 렌더링되면 자식도 렌더링된다"

props가 바뀌지 않아도 자식은 다시 렌더링됩니다. React는 props를 비교하지 않고 그냥 다시 실행합니다. 하지만 이것이 곧 성능 문제는 아닙니다. "렌더링"은 컴포넌트 함수를 실행해 가상 DOM을 만드는 것이고, 결과가 같으면 실제 DOM은 건드리지 않습니다(57장). 함수 실행 자체는 대개 매우 빠릅니다. 문제가 되는 것은 렌더링이 정말 무거울 때뿐입니다. 목록 수천 개, 복잡한 계산, 큰 트리 같은 경우입니다.

memo

const ExpensiveList = memo(function ExpensiveList({ items }) {
  // props가 이전과 같으면 다시 실행하지 않고 이전 결과를 재사용합니다
  return <ul>{items.map(i => <li key={i.id}>{i.name}</li>)}</ul>;
});

💔 memo가 쉽게 무력해지는 이유

function Parent() {
  return (
    <ExpensiveList
      items={items.filter(i => i.active)}   // ❌ 매번 새 배열
      onSelect={() => {}}                    // ❌ 매번 새 함수
      config={{ mode: "list" }}              // ❌ 매번 새 객체
    />
  );
}

memo는 props를 얕게 비교합니다. 객체·배열·함수는 내용이 같아도 매 렌더링마다 새로 만들어져 참조가 다릅니다(25장). 그래서 memo만 붙이면 아무 효과가 없습니다. props도 함께 안정시켜야 하고, 그것이 useMemo·useCallback의 역할입니다.

useMemo와 useCallback

// useMemo: 계산 결과를 기억
const sorted = useMemo(
  () => items.toSorted((a, b) => a.price - b.price),
  [items]
);

// useCallback: 함수 자체를 기억
const handleSelect = useCallback((id) => {
  setSelectedId(id);
}, []);

// 사실 useCallback은 useMemo의 축약입니다
const fn = useCallback(f, deps);
const fn = useMemo(() => f, deps);   // 같은 뜻
도구기억하는 것주 목적
memo컴포넌트 렌더링 결과부모 렌더링 시 자식 건너뛰기
useMemo계산 결과값비싼 계산 반복 방지, 참조 안정화
useCallback함수 자체함수 참조 안정화

언제 써야 하나

✅ 쓸 만한 경우

  1. 진짜로 비싼 계산 — 수천 개 항목 정렬·필터링, 무거운 변환. "비싸다"의 기준은 Performance 탭으로 측정한 결과입니다(49장).
  2. memo된 자식에게 넘기는 객체·함수 — 위에서 본 무력화를 막기 위해
  3. useEffect의 의존성으로 쓰이는 값 — 매번 바뀌면 Effect가 계속 실행됩니다(61장)
  4. Context의 value 객체 — 매번 새 객체면 모든 소비자가 다시 렌더링됩니다(65장)

🚫 쓰지 말아야 할 경우 — 대부분이 여기 해당합니다

// ❌ 이런 것에 useMemo는 손해입니다
const doubled = useMemo(() => count * 2, [count]);
const name = useMemo(() => `${first} ${last}`, [first, last]);
const isValid = useMemo(() => email.includes("@"), [email]);

useMemo도 공짜가 아닙니다. 의존성 배열을 만들고, 비교하고, 이전 값을 메모리에 들고 있어야 합니다. 계산 자체가 비교보다 싸다면 최적화가 아니라 손해입니다. 게다가 코드가 읽기 어려워지는 비용이 항상 따라옵니다.

🛠️ 현장 노트 — 순서를 지키세요

  1. 먼저 측정합니다. React DevTools Profiler로 어느 컴포넌트가 얼마나 걸리는지 봅니다. 추측으로 최적화하지 마세요.
  2. 구조를 먼저 고칩니다. 상태를 아래로 내리기, 컴포넌트 나누기, 계산을 줄이기. 대개 이것만으로 해결됩니다.
  3. 그래도 느리면 메모이제이션을 적용합니다.
  4. 적용 후 다시 측정해 실제로 빨라졌는지 확인합니다.

React 팀의 오랜 조언은 "필요할 때까지 최적화하지 말라"입니다. 신입이 useCallback을 모든 함수에 붙이는 것은 거의 항상 순손실입니다.

메모이제이션 대신 구조 바꾸기

// ❌ 입력할 때마다 무거운 목록까지 전부 다시 렌더링
function Page() {
  const [query, setQuery] = useState("");
  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <HeavyList />              {/* query와 무관한데 함께 렌더링됩니다 */}
    </>
  );
}

// ✅ 상태를 필요한 곳으로 내립니다 — memo 없이 해결
function Page() {
  return (
    <>
      <SearchInput />            {/* query 상태를 여기가 갖습니다 */}
      <HeavyList />
    </>
  );
}

// ✅ 또는 무거운 부분을 children으로 받습니다
function Page() {
  return (
    <SearchLayout>
      <HeavyList />              {/* Page에서 만들어졌으므로 다시 만들어지지 않습니다 */}
    </SearchLayout>
  );
}

React Compiler

React 팀은 메모이제이션을 자동으로 넣어 주는 컴파일러를 만들고 있습니다. 빌드 시점에 코드를 분석해 useMemo·useCallback·memo를 필요한 곳에 알아서 적용합니다.

🤖 무엇이 달라지나

컴파일러가 널리 쓰이게 되면 손으로 메모이제이션을 붙일 일이 크게 줄어듭니다. 지금 useCallback을 습관적으로 붙이는 코드는 미래에 불필요한 잡음이 됩니다.
다만 컴파일러가 제대로 동작하려면 컴포넌트가 규칙을 지켜야 합니다 — 렌더링 중 부수 효과 없음, 상태를 직접 수정하지 않음, 훅 규칙 준수. 결국 "React를 규칙대로 쓰는 것"이 최선의 최적화라는 결론은 변하지 않습니다. 도입 여부는 프로젝트의 React 버전과 공식 안내를 확인하세요.

📌 요약

  • useRef는 DOM 참조와 렌더링과 무관한 값에 쓴다. 바꿔도 다시 그리지 않는다.
  • 화면에 보이는 값은 반드시 상태로 관리한다.
  • 렌더링 원인은 자기 상태 변경 · 부모 렌더링 · Context 변경 셋뿐이다.
  • 부모가 렌더링되면 자식도 렌더링되지만, 그것이 곧 성능 문제는 아니다.
  • memo는 얕은 비교를 한다. 객체·함수 props가 매번 새로 만들어지면 무력해진다.
  • useMemo·useCallback도 비용이 있다. 싼 계산에 쓰면 손해다.
  • 측정 → 구조 개선 → 그래도 안 되면 메모이제이션 → 재측정.
  • 상태를 필요한 곳으로 내리는 것이 대부분의 렌더링 문제를 해결한다.
