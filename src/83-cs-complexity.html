이 챕터에서 배우는 것

  • Big-O 표기법을 수학 없이 이해하기
  • JavaScript 메서드가 각각 얼마나 비싼지
  • 데이터가 늘면 갑자기 느려지는 코드의 정체
  • 그런데 프론트엔드의 진짜 병목은 대개 알고리즘이 아니라는 사실

읽는 데 약 22분 · 면접 필수 · 실무 판단의 기준

"10개일 땐 괜찮았는데요"

개발 중에는 테스트 데이터가 20개입니다. 다 잘 됩니다. 운영에 올라가니 데이터가 8,000개가 되고, 목록 화면이 3초 동안 얼어붙습니다.

이때 필요한 것이 시간 복잡도입니다. "지금 몇 밀리초 걸리는가"가 아니라 "데이터가 10배 늘면 몇 배 느려지는가"를 보는 눈입니다.

📐 Big-O를 한 문장으로

입력이 커질 때 작업량이 어떤 모양으로 늘어나는지를 나타낸 표기법. 정확한 시간이 아니라 증가 추세만 봅니다. 그래서 상수와 계수는 버립니다. 3n + 100 도 n 도 똑같이 O(n)입니다. "입력이 두 배면 작업량도 두 배"라는 모양이 같기 때문입니다.

복잡도 계급표

입력 n이 커질 때 작업 횟수 (대략) 
표기         이름          n=10      n=1,000      n=1,000,000   예시
O(1)        상수           1           1                1       obj.key, map.get, arr[i], push
O(log n)    로그          ~3          ~10              ~20       정렬된 배열의 이진 탐색
O(n)        선형          10        1,000        1,000,000       for 한 번, find, includes, map
O(n log n)  선형로그       33       10,000       20,000,000      sort
O(n²)       제곱         100    1,000,000    1,000,000,000,000   이중 for, 반복문 안의 find
O(2ⁿ)       지수       1,024   우주가 끝남              ―        메모이제이션 없는 재귀

표에서 봐야 할 것은 가로가 아니라 세로입니다. n이 1,000일 때 O(n)은 1,000번, O(n²)은 100만 번입니다. 데이터가 1,000배 늘면 O(n)은 1,000배 느려지지만 O(n²)은 100만 배 느려집니다. "갑자기 멈춘다"는 체감은 여기서 나옵니다.

자주 쓰는 것들 (평균 기준) 
O(1)   arr[i]                    인덱스 접근
       arr.push() / arr.pop()    끝에서 넣고 빼기 (분할 상환 기준)

O(n log n)
       arr.sort()

🪤 함정은 안쪽에 숨어 있습니다

겉보기엔 반복문이 하나인데 실제로는 제곱인 경우가 대부분입니다.

// 반복문은 하나지만…
const result = items.map(item =>
  users.find(u => u.id === item.userId)   // ← 여기가 또 O(n)
);                                        // 전체 O(n × m)

// 이것도 마찬가지
const unique = [];
for (const x of list) {
  if (!unique.includes(x)) unique.push(x); // ← includes가 O(n) → 전체 O(n²)
}

이진 탐색 — O(log n)이 얼마나 강력한가

정렬되어 있다면 절반씩 잘라 가며 찾을 수 있습니다. 100만 개에서 원하는 값을 찾는 데 스무 번이면 충분합니다.

🛠️ 현장 노트 — 프론트엔드에서 이진 탐색을 직접 쓸 일은 드뭅니다

데이터가 정렬돼 있고 수만 개 이상일 때만 의미가 있는데, 그 정도 데이터는 애초에 서버에서 걸러 내려받는 것이 맞습니다. 직접 구현할 일이 있다면 가상 스크롤(보이는 행만 그리는 기법)에서 "스크롤 위치에 해당하는 행 찾기" 정도입니다. 그래도 원리는 알아 두세요. 면접에 나오고, "정렬하면 탐색이 싸진다"는 감각 자체가 유용합니다.

정렬 — sort()의 함정

🔒 sort()는 안정 정렬입니다

값이 같은 항목들의 원래 순서가 그대로 유지되는 정렬을 안정 정렬이라 합니다. ES2019부터 명세가 안정성을 요구하므로 현대 브라우저·Node에서 믿고 써도 됩니다.
덕분에 "먼저 이름순 정렬 → 다시 점수순 정렬"을 하면 점수가 같은 사람끼리는 이름순이 유지됩니다. 다중 기준 정렬을 이렇게 만들 수 있습니다.

지수 복잡도와 메모이제이션

같은 결과인데 호출 횟수가 269만 번에서 59번으로 줄었습니다. 같은 입력에 같은 결과가 나오는 무거운 계산은 기억해 두면 됩니다. React의 useMemo(64장)와 TanStack Query의 캐시(67장)가 같은 발상입니다.

💾 메모이제이션은 공짜가 아닙니다

시간을 메모리와 맞바꾸는 기법입니다. 캐시가 무한정 커지면 메모리 누수가 됩니다(84장). 키 개수를 제한하거나(LRU), 키가 객체라면 WeakMap을 써서 원본이 사라질 때 함께 정리되게 하세요. 또한 계산이 가벼우면 캐시 관리 비용이 더 큽니다. 측정하고 적용하세요.

그런데, 프론트엔드의 진짜 병목은

🎯 "느리면 알고리즘부터 고쳐라"는 대체로 틀립니다

웹 화면이 느린 원인의 순서는 대개 이렇습니다. ① 네트워크(큰 번들, 최적화 안 된 이미지, 폭포수 요청) → ② 렌더링(불필요한 리렌더링, 레이아웃 스래싱) → ③ 알고리즘. 2MB짜리 JS를 내려받는 3초를 놔둔 채 find를 Map으로 바꿔 0.5ms를 아끼는 것은 의미가 없습니다. 76장의 측정을 먼저 하세요. 다만 알고리즘 문제는 다르게 나타납니다. 네트워크 문제는 "전반적으로 느림"이고, 알고리즘 문제는 "데이터가 일정 수를 넘으면 갑자기 멈춤"입니다. 이 신호가 보이면 반복문 안을 들여다보세요.

🛠️ 현장 노트 — 실무 판단 기준

  1. n이 작으면 복잡도는 신경 쓰지 마세요. 항목 50개짜리 드롭다운에서 find는 완벽히 괜찮습니다. 가독성이 더 중요합니다.
  2. 수천 개를 넘어가면 반복문 안의 find·includes·filter를 의심하세요.
  3. Big-O는 상수를 버립니다. 이론상 더 나쁜 알고리즘이 작은 n에서 더 빠를 수 있습니다. 추측 대신 performance.now()나 Performance 패널로 재세요.
  4. 공간 복잡도도 같은 방식으로 봅니다. 10만 개 배열을 map으로 세 번 변환하면 중간 배열 3개가 메모리에 생깁니다. 한 번의 reduce로 합칠 수 있는지 보세요.
  5. 면접에서는 "이 코드는 O(n²)입니다. n이 커지면 Map으로 바꾸겠습니다"처럼 복잡도를 말로 설명할 수 있는지를 봅니다. 알고리즘을 외우는 것보다 이게 중요합니다.

📌 요약

  • Big-O는 입력이 커질 때의 증가 추세다. 상수와 계수는 버린다.
  • 핵심 계급: O(1) → O(log n) → O(n) → O(n log n) → O(n²).
  • find·includes·filter는 O(n). 반복문 안에 들어가면 O(n²)이 된다.
  • 해결은 대개 Map·Set으로 조회표 만들기(81장).
  • sort()는 기본이 문자열 비교고 원본을 바꾼다. 비교 함수를 반드시 넘긴다.
  • sort()는 ES2019부터 안정 정렬이 보장된다 — 다중 기준 정렬에 활용할 수 있다.
  • 중복 계산은 메모이제이션으로 없앤다. 단 캐시는 메모리를 쓴다.
  • 프론트엔드 병목은 대개 네트워크 → 렌더링 → 알고리즘 순이다. 측정이 먼저다.
