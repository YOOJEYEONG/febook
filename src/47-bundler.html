번들러가 푸는 문제

문제번들러가 하는 일
파일이 너무 많다수백 개의 모듈을 몇 개의 파일로 묶습니다
브라우저가 node_modules를 모른다import "react"를 실제 경로로 바꿔 줍니다
최신 문법을 못 쓴다구형 브라우저용 문법으로 변환합니다
JS가 아닌 것도 import 하고 싶다CSS·이미지·SVG를 다룰 수 있게 합니다
안 쓰는 코드가 들어간다제거합니다 (트리 셰이킹)
파일이 크다공백·주석 제거, 이름 축약 (압축)

🌐 브라우저는 import "react"를 이해하지 못합니다

import React from "react";              // ❌ 브라우저: 어디 있는 파일인지 모름
import React from "/node_modules/react/index.js";   // ✅ 이렇게 바꿔 줘야 함

34장에서 확장자를 생략할 수 없다고 한 이유가 이것입니다. 번들러가 "react" 같은 패키지 이름(bare specifier)을 실제 경로로 해석해 줍니다.

⚡ Vite가 빠른 이유

  • 개발 중에는 번들하지 않습니다. 브라우저의 네이티브 ES 모듈(34장)을 그대로 씁니다. 파일을 고치면 그 파일 하나만 다시 보내면 됩니다. 프로젝트가 커져도 시작 속도가 거의 그대로입니다.
  • 변환(JSX·TypeScript를 브라우저용 JavaScript로 바꾸기)과 압축은 Rust로 만든 Oxc가, 번들은 역시 Rust로 만든 Rolldown이 담당해 JavaScript로 만든 도구보다 훨씬 빠릅니다. (2026년 11월 기준 최신 메이저인 Vite 8 기준)
  • 배포용 빌드에서만 앱 코드 전체를 실제로 번들합니다.

webpack은 개발 중에도 전체를 번들해서 시작이 느렸습니다. 이것이 체감 차이의 핵심입니다.

🚫 자주 하는 오해

오해 — Vite는 개발할 때 esbuild, 배포할 때 Rollup을 쓴다. 사실 — Vite 7까지의 설명입니다. 두 도구의 동작 차이로 "개발 때는 되는데 빌드하면 다르다"는 문제가 생기곤 해서, Vite 8은 둘을 하나로 합친 Rolldown과 Oxc로 내부를 바꿨습니다. 2026년 이전에 쓰인 글이나 블로그에는 옛 설명이 많으니, 버전을 확인하고 읽으세요. 쓰는 입장에서 명령(npm run dev, npm run build)은 달라지지 않습니다.

지원 범위를 넓게 잡을수록 변환과 폴리필이 늘어 파일이 커지고 느려집니다. 실제 사용자 통계를 보고 정하세요. 아무도 쓰지 않는 브라우저를 위해 모든 사용자에게 무거운 코드를 보내는 것은 손해입니다. Internet Explorer는 2022년에 지원이 종료되었으므로 더 이상 대상이 아닙니다.

최적화 기법

트리 셰이킹

// utils.js — 함수가 50개 있다고 합시다
export function formatDate() { }
export function formatPrice() { }
// … 48개 더

// main.js
import { formatPrice } from "./utils.js";
// → 번들에는 formatPrice 만 포함됩니다. 나머지 49개는 제거

34장에서 말한 "ESM만 트리 셰이킹이 가능한" 이유가 이것입니다. import는 정적으로 분석할 수 있어 번들러가 실행 전에 무엇이 쓰이는지 알 수 있습니다.

🌳 트리 셰이킹이 안 되는 경우

  • CommonJS 패키지 — require는 실행 시점에 결정되어 분석할 수 없습니다.
  • 부수 효과가 있는 모듈 — 불러오기만 해도 무언가 실행되는 코드는 지울 수 없습니다. (package.json의 "sideEffects": false로 "안전하다"고 알릴 수 있습니다.)
  • 전체를 가져오는 import — import * as _ from "lodash"보다 import debounce from "lodash/debounce"가 훨씬 가볍습니다.

코드 분할

// 34장의 동적 import가 분할 지점이 됩니다
const { Chart } = await import("./chart.js");

// React에서
const AdminPage = lazy(() => import("./AdminPage"));

번들러는 이 지점을 인식해 별도 파일로 분리하고, 그 코드가 실제로 필요할 때 내려받습니다. 관리자 페이지 코드를 일반 사용자에게 보내지 않는 것만으로 초기 로딩이 크게 줄어듭니다.

파일 이름 해시

main.a3f19c2b.js
style.7e2d81f0.css

파일 내용이 바뀌면 이름도 바뀝니다. 그러면 브라우저와 CDN이 "새 파일"로 인식해 반드시 새로 받습니다(3장 캐시 문제). 반대로 내용이 그대로면 이름도 그대로라 캐시를 계속 씁니다. "배포했는데 옛 화면이 보여요"를 구조적으로 해결하는 방법입니다.

소스맵

압축된 코드는 사람이 읽을 수 없습니다. 소스맵은 "압축된 코드의 이 위치는 원본의 몇 번째 줄"이라는 대응표입니다. 덕분에 개발자 도구에서 원본 코드로 디버깅할 수 있습니다.

🔍 운영 환경의 소스맵

소스맵을 함께 배포하면 누구나 원본 코드를 볼 수 있습니다. 프론트엔드 코드는 어차피 공개되지만(1장), 주석과 변수명까지 그대로 노출되는 것이 부담일 수 있습니다. 실무에서는 소스맵을 생성하되 공개 배포에는 포함하지 않고, 오류 추적 서비스에만 올리는 방식을 자주 씁니다(79장).

빌드 시점에 값이 코드에 그대로 박힙니다. 번들 파일을 열면 누구나 볼 수 있습니다. 1장의 원칙 그대로입니다.
VITE_·NEXT_PUBLIC_ 같은 접두사 규칙이 있는 이유가 바로 이것입니다. "이 값은 공개된다는 것을 알고 넣는다"는 명시적 선언입니다. 비밀 키는 서버에만 두고, 프론트엔드는 서버를 경유해 호출해야 합니다(37·78장).

실습 — 첫 React 앱 띄우기

번들러를 직접 설정할 일은 생각보다 적습니다. 대부분은 프로젝트 생성 도구가 다 해 줍니다. 여기서는 Vite로 React 앱을 만들어 화면에 띄우고, 코드를 고쳐 저장하는 즉시 화면이 바뀌는 것까지 확인합니다. React 문법은 57장부터 배우니 지금은 "어느 파일을 고치면 무엇이 바뀌는지"만 보면 됩니다. 준비물은 46장에서 설치한 Node.js(node --version이 나오는 상태)입니다.

1단계 — 프로젝트 만들기

cd ~/Desktop                    # 프로젝트를 만들 위치로 이동 (pwd로 확인)
npm create vite@latest my-app   # my-app 이라는 폴더가 새로 생깁니다

처음 실행하면 Need to install the following packages: create-vite@… Ok to proceed? (y)라고 묻습니다. y를 누르고 Enter. 그다음 몇 가지 질문이 나옵니다. 화살표 키(↑↓)로 고르고 Enter로 확정합니다. (아래는 2026년 11월 기준 create-vite 9의 질문입니다. 버전에 따라 순서나 문구가 조금 다를 수 있습니다.)

🧭 막혔을 때

  • Missing script: "dev" 또는 Could not read package.json — cd my-app을 안 했습니다. pwd로 위치를 확인하세요.
  • npm: command not found — Node.js 설치 문제입니다(46장).
  • PowerShell에서 running scripts is disabled — 46장의 Set-ExecutionPolicy 상자를 보세요.
  • 주소가 5174로 나옴 — 5173번이 이미 쓰이고 있어 Vite가 다음 번호를 고른 것입니다. 터미널에 나온 주소를 그대로 쓰면 됩니다(44장 포트).

3단계 — 생성된 폴더 둘러보기

VS Code에서 파일 → 폴더 열기로 my-app 폴더를 엽니다.

my-app 폴더 구조 
my-app/
├── index.html        ← 브라우저가 처음 여는 HTML. <div id="root"> 하나와 main.jsx를 부르는 script가 전부
├── package.json      ← scripts(dev·build·preview)와 의존성 목록 (46장)
├── package-lock.json ← 정확한 설치 버전 기록. 커밋합니다
├── vite.config.js    ← Vite 설정. React 플러그인 한 줄만 들어 있습니다
├── .gitignore        ← node_modules, dist 등이 이미 적혀 있습니다
├── node_modules/     ← npm install로 생긴 패키지들. 건드리지 않습니다
├── public/           ← 가공 없이 그대로 복사될 파일 (favicon 등)
└── src/              ← ⭐ 내가 코드를 쓰는 곳
    ├── main.jsx      ← 시작점. App을 #root 안에 그립니다
    ├── App.jsx       ← 화면에 보이는 내용. 처음에 고칠 파일
    ├── App.css       ← App 화면의 스타일
    ├── index.css     ← 전체 공통 스타일
    └── assets/       ← import해서 쓰는 이미지

흐름은 index.html → src/main.jsx → src/App.jsx입니다. index.html은 거의 비어 있고, 실제 화면은 JavaScript가 그린다는 점이 6장에서 만든 HTML 파일과 가장 큰 차이입니다. .jsx는 JavaScript 안에 HTML처럼 생긴 문법(JSX, 58장)을 쓸 수 있는 파일이고, 이것을 브라우저가 이해하는 JavaScript로 바꿔 주는 것이 바로 이 장에서 배운 Vite의 변환입니다.

4단계 — App.jsx 고치고 즉시 반영 확인

  1. src/App.jsx를 엽니다.
  2. <h1>Get started</h1>을 찾아 <h1>내 첫 React 앱</h1>으로 바꿉니다.
  3. 저장(Ctrl/Cmd+S)하고 브라우저를 봅니다. 새로고침하지 않아도 제목이 바뀌어 있습니다.
  4. 버튼을 몇 번 눌러 숫자를 올린 다음, 제목을 한 번 더 바꾸고 저장해 보세요. 숫자가 0으로 돌아가지 않고 그대로 유지됩니다.

이것이 HMR(Hot Module Replacement, 핫 모듈 교체)입니다. 페이지 전체를 다시 불러오지 않고 바뀐 모듈 하나만 갈아 끼워서, 화면 상태를 유지한 채 변경을 보여 줍니다. 앞에서 본 "개발 중에는 번들하지 않고 바뀐 파일 하나만 다시 보낸다"는 Vite의 방식 덕분입니다.

🧯 오타를 내면?

예를 들어 </h1>을 지우고 저장하면 브라우저 화면 위에 빨간 오류 창(오버레이)이 뜨고, 터미널에도 같은 오류가 나옵니다. 파일 이름과 줄 번호가 적혀 있으니 그 위치를 고치고 저장하면 오류 창이 사라집니다. 6장의 HTML과 달리 JSX는 틀리면 오류를 냅니다.

5단계 — 서버 끄기와 빌드해 보기

# 서버가 돌던 터미널에서
Ctrl + C           # 개발 서버 종료 (macOS도 Cmd가 아니라 Ctrl)

npm run build      # 배포용 번들 생성 → dist/ 폴더에 해시 붙은 파일들
npm run preview    # 빌드 결과를 로컬에서 확인 (기본 주소 http://localhost:4173)

Ctrl+C 후 브라우저를 새로고침하면 "연결할 수 없음"이 뜹니다. 서버가 꺼졌다는 뜻이니 정상입니다. 다시 작업할 때는 my-app 폴더에서 npm run dev만 하면 됩니다(npm install은 처음 한 번, 또는 의존성이 바뀌었을 때만). dist/ 안의 파일 이름에 붙은 index-…js 해시가 앞에서 본 파일 이름 해시입니다. 이 폴더를 45장처럼 Git에 올리고 싶다면 my-app 폴더에서 git init부터 하면 되고, 배포는 74장에서 다룹니다.

📌 요약

  • 번들러는 모듈 해석·변환·최적화를 담당한다. 브라우저는 import "react"를 모른다.
  • 트랜스파일은 문법 변환, 폴리필은 없는 기능 채우기. 폴리필은 용량을 늘린다.
  • 트리 셰이킹은 ESM에서만 제대로 동작한다. 전체 import를 피한다.
  • 코드 분할은 동적 import()가 지점이 된다.
  • 파일 이름 해시가 캐시 문제를 구조적으로 해결한다.
  • 소스맵으로 압축 코드를 원본으로 디버깅한다. 공개 배포 여부는 신중히.
  • 프론트엔드 환경 변수는 비밀이 아니다. 빌드 시 코드에 박힌다.
  • Vite는 개발 중 번들하지 않고 네이티브 ESM을 써서 빠르다. Vite 8부터 내부 엔진은 Rolldown·Oxc다.
  • npm create vite@latest → cd → npm install → npm run dev. src/App.jsx를 저장하면 HMR로 즉시 반영되고, 서버는 Ctrl+C로 끈다.
