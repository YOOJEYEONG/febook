비트와 바이트

컴퓨터 부품은 결국 전기가 흐르느냐 안 흐르느냐 두 상태만 구분합니다. 중간 값을 정확히 구분하려면 회로가 훨씬 비싸고 오류에 약해집니다. 그래서 모든 것을 0과 1로 표현하기로 한 것이고, 이 한 자리를 비트(bit)라고 부릅니다.

비트 8개를 묶은 것이 1바이트(byte)입니다. 8비트면 00000000부터 11111111까지 256가지(28)를 표현할 수 있습니다. 파일 크기, 네트워크 전송량, 메모리 사용량은 전부 바이트 단위로 셉니다.

📏 1KB는 1000바이트인가 1024바이트인가

둘 다 쓰입니다. 국제 단위계(SI) 기준으로 1 kB = 1000바이트, 2진 접두어 기준으로 1 KiB(키비바이트) = 1024바이트입니다. 하드디스크 제조사와 네트워크 속도는 1000 기준, 운영체제의 메모리 표시는 대개 1024 기준입니다. "500GB 디스크를 샀는데 466GB로 보인다"는 이 차이 때문입니다. 번들 크기를 이야기할 때는 관행적으로 1KB = 1024바이트로 셉니다. 숫자가 몇 % 다를 수 있다는 것만 알고 있으면 됩니다.

진법 — 2진수, 10진수, 16진수

같은 수를 몇 개의 기호로 표현하느냐의 차이일 뿐입니다. 16진수(hex)는 0~9에 a~f를 더해 16개 기호를 씁니다.

16진수를 쓰는 이유는 단순합니다. 16진수 한 자리가 정확히 4비트고, 두 자리가 정확히 1바이트입니다. 그래서 바이트 단위 데이터를 사람이 읽기에 가장 깔끔합니다. CSS 색상 #ff8800이 바로 빨강 1바이트, 초록 1바이트, 파랑 1바이트입니다.

0.1 + 0.2 는 왜 0.3이 아닌가

프론트엔드에서 가장 자주 마주치는 CS 문제입니다. 결제 금액을 더했는데 29.999999999999996이 나오는 그 버그입니다.

JavaScript의 number는 IEEE 754 배정밀도 부동소수점(64비트) 하나로 정수와 소수를 모두 표현합니다. 이 형식은 수를 2진 소수로 저장합니다. 그런데 0.1을 2진수로 쓰면 무한소수입니다. 10진수에서 1⁄3을 0.3333…으로 끝없이 써야 하는 것과 똑같은 상황입니다.

무한소수를 64비트에 담으려면 어딘가에서 잘라야 합니다. 그 잘린 오차가 더해지면서 마지막 자리에 드러난 것이 0.30000000000000004입니다.

🧯 "JavaScript가 계산을 못 한다"는 오해

JavaScript의 버그가 아닙니다. Python, Java, C, Go, Swift 모두 같은 결과가 나옵니다. IEEE 754를 쓰는 거의 모든 언어의 공통 동작입니다. 다른 언어가 멀쩡해 보이는 건 출력할 때 자릿수를 줄여 보여 주거나, Decimal·BigDecimal 같은 별도의 10진 타입을 기본처럼 쓰기 때문입니다. 진짜 원인은 2진법으로는 0.1을 유한하게 적을 수 없다는 수학적 사실입니다.

실무 대처법

🆔 서버가 준 ID를 number로 받지 마세요

안전하게 다룰 수 있는 정수는 Number.MAX_SAFE_INTEGER = 253−1 = 9,007,199,254,740,991까지입니다. 백엔드의 64비트 정수 ID(예: 트위터 스노우플레이크 ID)는 이 범위를 넘습니다.

JSON.parse는 큰 수를 말없이 뭉갭니다. 그래서 대용량 서비스의 API는 ID를 문자열로 내려 주는 경우가 많습니다. 그럴 땐 문자열 그대로 쓰세요. 숫자로 바꾸는 순간 서로 다른 두 ID가 같은 값이 될 수 있습니다.

글자는 어떻게 저장되나

컴퓨터에는 숫자만 있습니다. 그래서 "글자 하나에 번호 하나"를 붙이기로 약속했습니다. 이 약속이 문자 집합입니다.

문자 인코딩의 역사, 세 줄 요약 
ASCII (1963)     영문자·숫자·기호 128개. 1바이트로 충분했다.
국가별 인코딩      한국은 EUC-KR, 일본은 Shift_JIS … 서로 호환 안 됨 → 글자 깨짐(뷁)
유니코드 + UTF-8  전 세계 모든 문자에 번호 하나씩. 지금의 표준.

유니코드는 "어떤 글자에 몇 번을 줄 것인가"를 정한 표입니다. 이 번호를 코드 포인트라 하고 U+AC00(가)처럼 U+ 뒤에 16진수로 씁니다. 현재 15만 자 이상이 등록돼 있습니다.

UTF-8은 "그 번호를 실제 바이트로 어떻게 적을 것인가"를 정한 방식입니다. 핵심은 가변 길이라는 점입니다.

UTF-8 — 글자에 따라 1~4바이트 
A       U+0041     1바이트     ← 영문·숫자는 ASCII와 완전히 동일
é       U+00E9     2바이트
가      U+AC00     3바이트     ← 한글·한자·대부분의 문자
😀      U+1F600    4바이트     ← 이모지

영문이 1바이트라 기존 ASCII 문서가 그대로 유효한 UTF-8 문서가 됩니다. 이 하위 호환성 덕분에 UTF-8이 웹의 표준이 됐고, HTML 명세는 <meta charset="utf-8">를 쓰라고 규정합니다.

"😀".length 가 2인 이유

여기서부터가 실제 버그를 만드는 구간입니다.

JavaScript의 문자열은 UTF-16 코드 유닛의 나열입니다. 코드 유닛 하나는 2바이트고, .length는 글자 수가 아니라 코드 유닛 개수를 돌려줍니다.

유니코드 번호가 U+FFFF까지인 문자는 코드 유닛 하나에 들어갑니다. 그보다 큰 문자(이모지 대부분, 일부 한자)는 코드 유닛 두 개를 짝지어 표현합니다. 이 짝을 서로게이트 페어라고 부릅니다. 그래서 .length가 2가 됩니다.

🛠️ 현장 노트 — 글자 수를 어디 기준으로 셀 것인가

  1. 화면에 "n자 남음"을 보여 줄 때 → Intl.Segmenter. 사용자가 세는 방식과 같습니다. (Chrome 87+, Safari 14.1+, Firefox 125+ 지원. 구형 대응이 필요하면 [...str].length로 폴백하세요.)
  2. 서버 DB 컬럼 길이에 맞출 때 → 바이트 수. new TextEncoder().encode(s).length. 한글은 UTF-8에서 3바이트라 VARCHAR(10)에 한글 10자가 안 들어갈 수 있습니다.
  3. HTML maxlength 속성은 UTF-16 코드 유닛 기준입니다. 이모지 하나가 2로 셉니다. 정확한 제한이 필요하면 직접 검사하세요.
  4. API 명세를 받을 때 "길이 20자"의 기준을 반드시 물어보세요. 프론트와 백엔드가 다른 기준을 쓰면 "분명 20자인데 저장이 안 된다"는 버그가 납니다.

보이는 글자는 같은데 === 가 false

한글 한은 두 가지로 저장될 수 있습니다. 완성형(U+D55C 한 글자)과 조합형(ᄒ+ᅡ+ᆫ 세 글자)입니다. 화면에는 똑같이 보이지만 문자열로는 다른 값입니다.

macOS는 파일명을 조합형에 가까운 형태로 저장합니다. 그래서 맥에서 업로드한 사진.png가 서버의 사진.png와 문자열 비교에서 어긋나는 일이 생깁니다. 사용자 입력을 비교·저장하기 전에는 normalize("NFC")를 습관화하세요.

📌 요약

  • 비트는 0/1 한 자리, 8비트 = 1바이트. 16진수 두 자리가 정확히 1바이트라 색·바이트 표기에 쓴다.
  • 0.1 + 0.2 !== 0.3은 JS 버그가 아니라 2진 부동소수점(IEEE 754)의 필연적 결과다.
  • 돈은 정수(최소 단위)로 계산하고, 비교는 오차 허용 범위로 한다.
  • 안전 정수 한계는 253−1. 큰 ID는 문자열이나 BigInt로 다룬다.
  • 유니코드는 번호표, UTF-8은 그 번호를 바이트로 적는 방식(1~4바이트, 한글 3바이트).
  • .length는 UTF-16 코드 유닛 수다. 사람 기준 글자 수는 Intl.Segmenter.
  • 같아 보이는 한글이 ===에서 다를 수 있다. 비교 전 normalize("NFC").
