왜 쓰는가

🎯 "버그를 잡으려고"는 절반만 맞습니다

테스트가 주는 진짜 가치는 이것입니다. ① 겁내지 않고 고칠 수 있게 됩니다. 테스트가 없으면 "건드리면 뭐가 깨질지 몰라서" 나쁜 코드를 그대로 둡니다. 이것이 프로젝트가 썩는 가장 큰 이유입니다. ② 같은 버그가 다시 나지 않습니다. 버그를 고칠 때 테스트를 하나 추가하면 그 버그는 영원히 재발하지 않습니다. ③ 문서가 됩니다. 잘 쓴 테스트는 "이 코드는 이럴 때 이렇게 동작한다"는 실행 가능한 명세입니다.

🏆 왜 통합·컴포넌트 테스트가 중심인가

단위 테스트를 아무리 많이 써도 조각들이 잘 붙는지는 알 수 없습니다. 반대로 E2E만 쓰면 느리고 불안정해서 결국 아무도 안 돌립니다.
"컴포넌트 몇 개가 함께 동작하는 수준"이 사용자가 실제로 겪는 단위에 가깝고, 속도도 감당할 만합니다. 그래서 여기에 가장 많이 투자합니다.

단위 테스트

npm install -D vitest
formatPrice.test.ts 
import { describe, it, expect } from "vitest";
import { formatPrice } from "./formatPrice";

describe("formatPrice", () => {
  it("천 단위에 콤마를 넣는다", () => {
    expect(formatPrice(1234567)).toBe("1,234,567원");
  });

  it("0원도 표시한다", () => {
    expect(formatPrice(0)).toBe("0원");
  });

  it("음수는 마이너스를 유지한다", () => {
    expect(formatPrice(-1000)).toBe("-1,000원");
  });

  it("숫자가 아니면 오류를 던진다", () => {
    expect(() => formatPrice("abc" as never)).toThrow();
  });
});

🧪 순수 함수는 테스트가 쉽습니다

27장에서 말한 순수 함수(같은 입력 → 같은 출력, 부수 효과 없음)는 입력을 넣고 출력을 확인하면 끝입니다.
테스트하기 어려운 코드는 대개 설계가 나쁜 코드입니다. 전역 상태를 읽고, 시간에 의존하고, 네트워크를 직접 부르는 함수는 테스트가 어렵습니다. 테스트를 쓰다 보면 자연스럽게 설계가 좋아지는 이유입니다.

경계값을 노리세요 
// 가장 버그가 많이 숨는 곳
expect(calculate([])).toBe(0);              // 빈 배열
expect(calculate([1])).toBe(1);             // 하나
expect(getDiscount(0)).toBe(0);             // 0
expect(paginate(items, 0)).toEqual([]);     // 첫 페이지 / 범위 밖
expect(truncate("가나다", 3)).toBe("가나다"); // 정확히 경계

컴포넌트 테스트

npm install -D vitest @testing-library/react @testing-library/user-event jsdom
LoginForm.test.tsx 
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { LoginForm } from "./LoginForm";

it("이메일 형식이 잘못되면 오류를 보여준다", async () => {
  const user = userEvent.setup();
  render(<LoginForm onSubmit={() => {}} />);

  // 사용자가 보는 이름으로 요소를 찾습니다
  await user.type(screen.getByLabelText("이메일"), "잘못된값");
  await user.click(screen.getByRole("button", { name: "로그인" }));

  expect(await screen.findByText("이메일 형식이 아닙니다")).toBeInTheDocument();
});

it("올바른 값이면 제출 함수를 호출한다", async () => {
  const user = userEvent.setup();
  const handleSubmit = vi.fn();
  render(<LoginForm onSubmit={handleSubmit} />);

  await user.type(screen.getByLabelText("이메일"), "hong@example.com");
  await user.type(screen.getByLabelText("비밀번호"), "12345678");
  await user.click(screen.getByRole("button", { name: "로그인" }));

  expect(handleSubmit).toHaveBeenCalledWith({
    email: "hong@example.com",
    password: "12345678"
  });
});

👤 Testing Library의 철학

"테스트는 소프트웨어가 쓰이는 방식과 닮을수록 신뢰할 수 있다."
그래서 내부 상태나 함수 이름이 아니라 사용자가 보는 것으로 찾습니다. state.email을 확인하지 않고 화면에 오류 메시지가 보이는지를 확인합니다.
덕분에 구현을 바꿔도 테스트가 안 깨집니다. useState를 useReducer로 바꾸든 클래스로 바꾸든, 사용자에게 보이는 결과가 같으면 테스트는 통과합니다.

요소 찾는 방법의 우선순위 
// 1순위 — 접근성 기준 (11장)
screen.getByRole("button", { name: "저장" });
screen.getByLabelText("이메일");
screen.getByPlaceholderText("검색어 입력");
screen.getByText("환영합니다");

// 최후의 수단
screen.getByTestId("submit-button");   // data-testid="submit-button"

♿ 테스트가 접근성을 강제합니다

getByRole("button")으로 못 찾는다면 그 요소는 스크린 리더에게도 버튼이 아닙니다(11장의 div 클릭 문제). getByLabelText로 못 찾는다면 label이 연결되지 않은 것입니다(9장).
테스트를 이 방식으로 쓰면 접근성 문제가 자동으로 드러납니다. data-testid를 남발하면 이 이점이 사라집니다.

모킹

// ❌ fetch를 직접 가로채면 구현에 묶입니다
global.fetch = vi.fn();

// ✅ MSW로 '네트워크 수준'에서 가짜 서버를 만듭니다
import { http, HttpResponse } from "msw";
import { setupServer } from "msw/node";

const server = setupServer(
  http.get("/api/users", () => HttpResponse.json([{ id: 1, name: "홍길동" }])),
  http.post("/api/users", () => HttpResponse.json({ id: 2 }, { status: 201 }))
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

MSW를 쓰면 fetch를 쓰든 axios를 쓰든 TanStack Query를 쓰든 테스트가 그대로입니다. 같은 정의를 개발 중 가짜 서버로도 쓸 수 있어 백엔드를 기다리지 않고 작업할 수 있습니다.

E2E 테스트

import { test, expect } from "@playwright/test";

test("회원가입 후 로그인할 수 있다", async ({ page }) => {
  await page.goto("/signup");

  await page.getByLabel("이메일").fill("new@example.com");
  await page.getByLabel("비밀번호").fill("password123");
  await page.getByRole("button", { name: "가입" }).click();

  await expect(page).toHaveURL("/welcome");
  await expect(page.getByText("환영합니다")).toBeVisible();
});

🎬 E2E는 핵심 흐름 몇 개만

E2E는 진짜 브라우저에서 진짜 서버로 동작합니다. 그래서 가장 신뢰할 수 있지만 가장 느리고 잘 깨집니다. 네트워크 지연, 애니메이션, 데이터 상태에 따라 가끔 실패하는 테스트가 되기 쉽습니다.
돈이 오가는 흐름(가입·로그인·결제·주문) 몇 개만 다루세요. 모든 화면을 E2E로 덮으려 하면 유지보수가 개발보다 비싸집니다.
Playwright는 실패 시 스크린샷·비디오·추적 기록을 남겨 주므로 반드시 켜 두세요.

📊 커버리지 100%를 목표로 삼지 마세요

커버리지는 "코드가 실행됐다"만 알려 줍니다. "올바른지"는 알려 주지 않습니다. 아무것도 검증하지 않는 테스트로도 100%를 만들 수 있습니다.
커버리지의 유용한 사용법은 낮은 곳을 찾는 것입니다. "결제 계산 모듈이 20%네"는 의미 있는 신호이고, "전체 87%를 90%로 올리자"는 대개 시간 낭비입니다.

테스트하기 쉬운 코드

// ❌ 테스트하기 어렵습니다
function calculateTotal() {
  const items = store.getState().cart.items;       // 전역 의존
  const rate = new Date().getMonth() === 11 ? 0.9 : 1;  // 시간 의존
  fetch("/api/log", { method: "POST" });           // 부수 효과
  return items.reduce(…) * rate;
}

// ✅ 필요한 것을 인자로 받습니다
function calculateTotal(items: Item[], discountRate = 1) {
  return items.reduce((s, i) => s + i.price, 0) * discountRate;
}
// 로깅과 시간 판단은 호출하는 쪽에서

🛠️ 현장 노트 — 현실적인 시작

  1. 전부 테스트하려 하지 마세요. 그러다 하나도 못 씁니다.
  2. 버그가 나면 그때 테스트를 쓰세요. 재현하는 테스트를 먼저 쓰고, 고치고, 통과시킵니다. 가장 투자 대비 효과가 좋은 방법입니다.
  3. 순수 함수부터 시작하세요. 쉽고 빠르게 성공을 경험할 수 있습니다.
  4. 불안정한 테스트는 바로 고치거나 지우세요. 가끔 실패하는 테스트가 몇 개만 있어도 팀 전체가 빨간불을 무시하게 되고, 그 순간 테스트는 죽습니다.
  5. CI에서 자동 실행되게 하세요(74장). 사람이 기억해서 돌리는 테스트는 결국 안 돌아갑니다.

테스트가 하나도 없는 프로젝트에서 시작한다면, 가장 중요한 계산 로직 하나에 테스트를 다는 것부터 하세요. 완벽함보다 시작이 중요합니다.

📌 요약

  • 테스트의 진짜 가치는 겁내지 않고 고칠 수 있게 되는 것이다.
  • 정적(TS·ESLint) → 단위 → 컴포넌트(중심) → E2E(핵심 흐름만).
  • Testing Library는 사용자가 보는 것으로 찾는다. 구현이 바뀌어도 안 깨진다.
  • getByRole·getByLabelText가 접근성을 강제한다. data-testid는 최후 수단.
  • 네트워크는 MSW로 모킹하면 구현에 묶이지 않는다.
  • E2E는 돈이 오가는 흐름 몇 개만. 전부 덮으려 하면 유지보수가 더 비싸다.
  • 커버리지 100%는 목표가 아니다. 낮은 곳을 찾는 용도로 쓴다.
  • 버그가 나면 그때 테스트를 추가하는 것이 가장 효율적이다.
  • 불안정한 테스트는 없는 것보다 나쁘다.
