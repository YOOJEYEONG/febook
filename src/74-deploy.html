🧪 배포 전에 반드시 로컬에서 빌드해 보세요

개발 서버에서는 잘 되는데 빌드에서 실패하는 경우가 많습니다.

  • 타입 오류 — 개발 중에는 경고로 넘어가지만 빌드는 실패합니다
  • 서버에 없는 API 사용 — window, document(70장)
  • 환경 변수 누락
  • 대소문자 — macOS는 구분하지 않고 리눅스 서버는 구분합니다. import Button from "./button"이 로컬에서만 되는 전형적인 사고입니다

└ ƒ /dashboard                 15 kB        142 kB   ← 큽니다. 확인 필요

First Load JS가 그 페이지를 열 때 받아야 하는 총 JS 용량입니다. 어떤 페이지가 유난히 크다면 동적 임포트로 나눌 수 있는지 확인하세요(47·68장). 그리고 각 라우트가 정적인지 동적인지가 여기 표시되므로, 72장에서 말한 "실수로 동적이 된 페이지"를 여기서 발견할 수 있습니다.

환경 변수

파일 구분 
.env                 모든 환경 공통 (커밋함 — 비밀 없는 값만)
.env.local           내 컴퓨터 전용 (⚠️ 반드시 .gitignore)
.env.development     개발용
.env.production      운영용
.env.example         ⭐ 어떤 변수가 필요한지 알려주는 예시 (커밋함, 값은 비움)
# .env.example — 이 파일을 커밋해 두면 새 팀원이 무엇이 필요한지 압니다
DATABASE_URL=
NEXTAUTH_SECRET=
NEXT_PUBLIC_API_URL=

🔓 접두사가 붙으면 공개됩니다

DATABASE_URL=postgres://…              # 서버에서만 — 안전
NEXT_PUBLIC_API_URL=https://api.…      # 브라우저 코드에 박힙니다 — 공개

47장에서 말한 그대로입니다. NEXT_PUBLIC_(Vite는 VITE_)이 붙은 값은 빌드 결과물에 문자열로 들어갑니다. 개발자 도구로 누구나 볼 수 있습니다. 비밀 키에 이 접두사를 붙이는 것이 실제로 자주 일어나는 사고입니다.

✅ 환경 변수를 시작할 때 검증하세요

// env.ts — 54장의 Zod 활용
import { z } from "zod";

const schema = z.object({
  DATABASE_URL: z.string().url(),
  NEXTAUTH_SECRET: z.string().min(32),
  NEXT_PUBLIC_API_URL: z.string().url()
});

export const env = schema.parse(process.env);
// 변수가 없거나 형식이 틀리면 '시작하자마자' 명확한 오류가 납니다

검증하지 않으면 배포 후 사용자가 특정 기능을 눌렀을 때 undefined 때문에 터집니다. 그때는 원인 찾기가 훨씬 어렵습니다.

🔍 미리보기 배포가 협업을 바꿉니다

PR을 올리면 그 브랜치만의 실제 URL이 자동 생성됩니다(45장).

  • 리뷰어가 코드가 아니라 실제 화면을 보고 확인합니다
  • 기획자·디자이너가 개발 환경 없이 결과를 봅니다
  • 모바일 실기기에서 바로 테스트할 수 있습니다(49장)

"제 컴퓨터에서는 되는데요"가 사라지는 가장 효과적인 장치입니다.

CI/CD

.github/workflows/ci.yml 
name: CI
on: [push, pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci               # lock 파일 그대로 설치 (46장)
      - run: npm run lint         # 48장
      - run: npx tsc --noEmit     # 50장 — 타입 검사
      - run: npm test             # 75장
      - run: npm run build        # 빌드가 되는지 확인

🚦 CI가 최종 방어선입니다

48장에서 말했듯 Git 훅은 우회할 수 있습니다. CI는 모든 PR에서 반드시 실행되고, 실패하면 머지를 막을 수 있습니다.
검사 순서도 중요합니다. 빠른 것(린트·타입)을 먼저 돌려 몇 초 만에 실패하게 하면 피드백이 빨라집니다.

배포 후 확인

✅ 배포 직후 점검표

  1. 실제 주소로 접속해 봅니다. 로컬이 아니라 진짜 URL로.
  2. 주요 흐름을 직접 해 봅니다. 회원가입 → 로그인 → 핵심 기능.
  3. 새로고침해 봅니다. 하위 경로에서 404가 나면 서버 폴백 설정 문제입니다(68장).
  4. 모바일 실기기로 열어 봅니다(49장).
  5. 콘솔에 오류가 없는지 확인합니다.
  6. 느린 네트워크로 테스트합니다(49장).
  7. OG 미리보기를 실제로 링크를 붙여 확인합니다(10·73장).
  8. Lighthouse를 운영 주소에서 돌립니다. 개발 서버와 결과가 다릅니다.
  9. 404 페이지가 제대로 나오는지 봅니다.

"배포했으니 끝"이 아닙니다. 개발 환경과 운영 환경은 항상 다릅니다. 캐시, 환경 변수, HTTPS, 도메인, CDN — 로컬에는 없던 것들이 전부 개입합니다.

문제가 생기면

상황대응
배포 후 심각한 오류즉시 이전 버전으로 롤백. 원인 분석은 그다음입니다
일부 사용자만 문제브라우저·기기·캐시 상태를 확인. 79장의 오류 추적 도구가 알려 줍니다
옛 화면이 계속 보임CDN·브라우저 캐시(3장). 해시 파일명이 제대로 적용됐는지 확인
환경 변수 문제호스팅 대시보드에서 값을 확인하고 재배포. 변수만 바꾸면 반영되지 않는 경우가 많습니다

↩️ 롤백이 가능한 것이 큰 가치입니다

현대 호스팅 플랫폼은 이전 배포를 그대로 보관하고 버튼 하나로 되돌릴 수 있습니다. "고치려고 급하게 코드를 수정해 다시 배포"하는 것보다 일단 되돌리고 침착하게 원인을 찾는 것이 항상 낫습니다.

🔐 배포 관련 보안 기본

  • HTTPS는 필수입니다. 요즘은 대부분 자동으로 설정됩니다(4장)
  • 소스맵을 공개 배포에 포함할지 결정하세요(47장)
  • 오류 화면에 서버 내부 정보를 노출하지 마세요(33장)
  • 보안 헤더(CSP 등)를 설정하세요(78장)
  • 관리자 페이지는 서버에서 권한을 검사하세요. 라우트 가드만으로는 부족합니다(68장)

📌 요약

  • 배포 전에 반드시 로컬 빌드를 돌린다. 대소문자·타입·서버 API 문제가 여기서 드러난다.
  • 빌드 출력에서 라우트별 크기와 정적/동적 여부를 확인한다.
  • .env.local은 절대 커밋하지 않고, .env.example은 커밋한다.
  • NEXT_PUBLIC_이 붙으면 공개된다. 비밀 키에 붙이지 않는다.
  • 환경 변수를 시작 시점에 검증하면 문제를 일찍 발견한다.
  • 미리보기 배포가 협업 방식을 바꾼다.
  • CI가 최종 방어선이다. 빠른 검사를 먼저 돌린다.
  • 배포 후 실제 주소·실기기·느린 네트워크로 확인한다.
  • 문제가 생기면 먼저 롤백하고 원인은 그다음에 찾는다.
