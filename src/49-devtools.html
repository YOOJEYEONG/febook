🎨 실시간 편집이 가장 큰 가치입니다

Styles 패널에서 값을 화살표 키로 올리고 내리며 즉시 결과를 봅니다. (Shift+화살표는 10씩, Alt+화살표는 0.1씩) 코드를 고치고 저장하고 새로고침하는 것보다 훨씬 빠릅니다. 여기서 값을 확정한 뒤 코드에 옮기는 것이 CSS 작업의 정석입니다.

🎯 콘솔 필터를 쓰세요

로그가 쏟아질 때는 콘솔 상단의 필터 입력창에 검색어를 넣으면 됩니다. 레벨(Errors만 보기)로도 거를 수 있고, 정규식도 됩니다. 또 Preserve log를 켜면 페이지가 이동해도 로그가 지워지지 않아 로그인 리다이렉트 같은 흐름을 추적할 수 있습니다.

Network — API 문제의 진단소

"데이터가 안 나와요"라는 문제의 90%는 이 탭에서 답이 나옵니다.

확인 순서 
① 요청이 나갔는가?
   → 목록에 없다 = JS가 호출을 안 했다. 코드 흐름을 확인

② 상태 코드는? (4장)
   → 4xx = 요청이 잘못됨 (주소, 파라미터, 토큰)
   → 5xx = 서버 문제. 백엔드에 전달
   → CORS 오류 = 서버가 허용 헤더를 안 줌 (37장)

③ 요청 내용이 맞는가?
   → Headers 탭: 주소, 메서드, Authorization 헤더
   → Payload 탭: 실제로 보낸 본문

④ 응답이 맞는가?
   → Response 탭: 서버가 준 원본
   → Preview 탭: JSON을 보기 좋게

⑤ 왜 느린가?
   → Timing 탭: 어느 구간에서 시간이 걸렸는지
유용한 기능설명
Fetch/XHR 필터이미지·CSS를 빼고 API 요청만 봅니다
Disable cache캐시를 무시하고 항상 새로 받습니다. 개발 중에는 켜 두세요
네트워크 속도 제한Slow 4G로 바꿔 느린 환경을 재현합니다. 반드시 해 보세요
Copy as fetch / cURL요청을 그대로 복사해 재현하거나 백엔드에 전달
Waterfall무엇이 무엇을 기다리는지 시각적으로 확인

🐌 느린 네트워크를 반드시 테스트하세요

개발자의 컴퓨터는 빠르고, 서버는 옆에 있고, 캐시는 따뜻합니다. 실제 사용자의 환경은 전혀 다릅니다. Slow 4G로 바꾸면 로딩 상태를 안 만든 화면, 깜빡이는 레이아웃, 두 번 눌리는 버튼 같은 문제가 즉시 드러납니다.

Sources — 중단점 디버깅

🛑 console.log보다 강력합니다

console.log는 미리 정한 값만 볼 수 있고, 고칠 때마다 새로고침해야 합니다. 중단점은 그 순간 멈춰서 모든 변수를 살펴보고 코드를 직접 실행해 볼 수 있습니다. 한 번 익히면 되돌아가지 않게 됩니다.

쓰는 법 
1. Sources 탭에서 파일을 열고 줄 번호를 클릭 → 중단점 설정
2. 그 코드가 실행되면 화면이 멈춥니다
3. 오른쪽 패널에서
   - Scope: 지금 이 시점의 모든 변수 값
   - Call Stack: 여기까지 어떻게 왔는지 (35장)
   - Watch: 특정 식을 계속 감시
4. 콘솔에서 그 시점의 변수를 직접 조작해 볼 수 있습니다
5. 실행 제어
   - ▶ 계속        F8
   - ⤼ 다음 줄     F10  (함수 안으로 안 들어감)
   - ↓ 안으로      F11  (함수 안으로 들어감)
   - ↑ 밖으로      Shift+F11
고급 중단점설명
조건부 중단점줄 번호 우클릭 → 조건 입력. id === 42일 때만 멈춥니다. 반복문 디버깅의 핵심
로그포인트멈추지 않고 로그만 출력. 코드를 수정하지 않고 console.log를 넣는 효과
DOM 중단점Elements에서 요소 우클릭 → "이 요소가 바뀔 때 멈춤". 누가 이걸 바꿨는지 찾을 때
이벤트 중단점특정 이벤트가 발생할 때 멈춤
debugger 문코드에 debugger;를 쓰면 그 지점에서 멈춥니다. 커밋 전에 지우세요

도구쓰임
Lighthouse성능·접근성·SEO·모범 사례를 점수와 개선 목록으로. 가장 쉽게 시작하는 방법

📊 Lighthouse 점수를 맹신하지 마세요

Lighthouse는 여러분의 컴퓨터에서 한 번 측정한 결과입니다. 실제 사용자는 더 느린 기기와 네트워크를 씁니다. 점수 100점이 "빠르다"의 증명은 아니며, 접근성 항목은 자동으로 검사 가능한 것만 봅니다(11장). 그럼에도 개선 목록은 실질적으로 유용하니 출발점으로 삼기에 좋습니다. 진짜 판단은 실제 사용자 데이터(76장)로 합니다.

모바일 디버깅

  • 기기 툴바(⌘⇧M) — 화면 크기·터치 시뮬레이션. 완벽하지 않습니다. 실제 기기와 스크롤·폰트가 다릅니다.
  • Android 실기기 — USB 연결 후 Chrome에서 chrome://inspect. 진짜 기기의 콘솔을 봅니다.
  • iOS 실기기 — 설정에서 웹 검사 활성화 후 macOS Safari의 개발자 메뉴에서 연결.

🛠️ 현장 노트 — 디버깅 순서

  1. Console에 빨간 오류가 있는가? 있다면 그것부터.
  2. Network에서 요청이 나갔는가, 상태 코드는? (데이터 문제의 대부분)
  3. Elements에서 실제 DOM이 예상과 같은가?
  4. Sources에서 중단점으로 값이 어디서부터 잘못됐는지 추적.
  5. 여전히 모르겠다면 재현 조건을 최소화하세요. 코드를 지워 가며 문제가 사라지는 지점을 찾습니다.

가장 흔한 실수는 "코드를 노려보는 것"입니다. 도구는 실제로 무슨 일이 일어났는지를 보여 줍니다. 추측보다 관찰이 항상 빠릅니다.

📌 요약

  • 명령 메뉴(⌘⇧P) 하나로 모든 기능을 찾을 수 있다.
  • Elements의 취소선이 CSS가 안 먹는 이유를 알려 준다.
  • Network 탭이 API 문제의 90%를 설명한다. 요청 유무 → 상태 코드 → 내용 순으로 확인.
  • Slow 4G로 반드시 테스트한다.
  • 중단점은 console.log보다 강력하다. 조건부 중단점과 로그포인트를 익혀 두자.
  • Lighthouse는 출발점이지 최종 판단이 아니다.
  • 모바일은 시뮬레이터가 아니라 실기기 원격 디버깅으로 확인한다.
  • 추측하지 말고 관찰한다.
