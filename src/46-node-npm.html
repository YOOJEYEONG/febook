Node.js 설치

23장에서 본 것처럼 Node.js는 브라우저 밖에서 JavaScript를 실행하는 환경입니다. 프론트엔드 개발에서는 서버를 만들지 않더라도 반드시 필요합니다. 빌드 도구·테스트 도구·개발 서버가 전부 Node 위에서 돌기 때문입니다.

📥 공식 설치 파일보다 버전 관리 도구를 권합니다

프로젝트마다 요구하는 Node 버전이 다릅니다. 버전 관리 도구를 쓰면 여러 버전을 함께 설치해 두고 명령 한 줄로 바꿀 수 있고, sudo 없이 전역 패키지를 설치할 수 있습니다(44장). 이 책은 macOS·Windows 모두에서 같은 명령으로 쓰는 fnm을 기준으로 설명합니다. (nvm도 널리 쓰이지만 macOS·리눅스 전용이고, Windows에는 이름만 비슷한 별개 프로그램 nvm-windows가 있습니다.)

macOS에 설치하기

둘 중 하나만 하면 됩니다.

방법 A — Homebrew가 있다면 
brew install fnm

# 설치 후, 셸이 fnm을 쓰도록 설정 파일에 한 줄 추가
echo 'eval "$(fnm env --use-on-cd --shell zsh)"' >> ~/.zshrc
방법 B — 공식 설치 스크립트 (Homebrew가 없을 때) 
curl -fsSL https://fnm.vercel.app/install | bash
# 스크립트가 셸 설정 파일에 필요한 줄을 자동으로 추가합니다

Homebrew는 macOS용 프로그램 설치 도구입니다. brew --version을 입력했을 때 버전이 나오면 설치되어 있는 것이고, command not found면 방법 B를 쓰세요.

Windows에 설치하기

PowerShell 
winget install Schniz.fnm

# PowerShell 설정 파일 열기 (없으면 새로 만들어집니다)
if (!(Test-Path $PROFILE)) { New-Item $PROFILE -Force }
notepad $PROFILE
# 열린 메모장 맨 끝에 아래 한 줄을 붙여 넣고 저장
fnm env --use-on-cd --shell powershell | Out-String | Invoke-Expression

winget은 Windows 10·11에 들어 있는 프로그램 설치 도구입니다. Git Bash를 쓴다면 ~/.bashrc에 eval "$(fnm env --use-on-cd --shell bash)"를 추가합니다.

🧱 PowerShell: "running scripts is disabled on this system"

Windows는 기본적으로 PowerShell 스크립트 실행을 막아 둡니다. 그래서 설정 파일($PROFILE)이나 npm 명령이 이 오류로 멈출 수 있습니다. PowerShell에서 아래를 한 번 실행하면 내 계정에 한해 내 컴퓨터에서 만든 스크립트 실행이 허용됩니다.
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

🚪 fnm 설치 후 기능 확인 전에 터미널을 완전히 닫았다가 다시 여세요

이미 열려 있던 터미널은 설치 전 설정을 그대로 들고 있습니다. VS Code 안의 터미널이라면 VS Code를 완전히 종료했다가 다시 실행하세요. 그다음 fnm --version으로 확인합니다.

🧰 도구 설치가 계속 막힌다면 — 공식 설치 프로그램

nodejs.org 다운로드 페이지에서 LTS 버전의 설치 프로그램(Windows .msi, macOS .pkg)을 받아 "다음"만 눌러도 됩니다. 한 버전만 쓰는 학습 단계에서는 충분합니다. 나중에 여러 버전이 필요해지면 이 Node를 제거하고 fnm으로 옮기세요. 두 방식을 동시에 쓰면 어느 node가 실행되는지 헷갈리니 하나만 남깁니다.

증상해결
fnm: command not found
(PowerShell: fnm is not recognized…)		터미널(또는 VS Code 전체)을 닫고 다시 엽니다. 그래도 안 되면 설치 명령이 오류 없이 끝났는지 확인하고 다시 실행합니다
fnm --version은 되는데 node: command not found셸 설정 줄(fnm env …)이 빠졌거나 저장되지 않았습니다. ~/.zshrc 또는 $PROFILE을 열어 확인하고, fnm install --lts를 했는지도 봅니다
새 터미널을 열 때마다 Node가 사라짐fnm list로 설치된 버전을 보고 fnm default 26처럼 기본 버전을 지정합니다
running scripts is disabled위 경고 상자의 Set-ExecutionPolicy 명령을 실행합니다
버전이 예상과 다름which node(PowerShell: Get-Command node)로 어느 위치의 node가 실행되는지 봅니다. 공식 설치 프로그램으로 깐 Node가 남아 있는 경우가 많습니다

🏷️ LTS 버전을 쓰세요

LTS(Long Term Support)는 장기 지원 버전입니다. 운영 서비스에는 LTS만 씁니다. 2026년 11월 기준으로 Node 26이 최신 LTS이고, 24와 22도 아직 LTS로 보안 수정을 받습니다. 20 이하는 지원이 끝났습니다.

Node.js는 26까지는 짝수 번호만 LTS가 되고 홀수 번호는 6개월만 지원하는 단기 버전이었습니다. 27부터는 1년에 한 번 새 메이저가 나오고, 알파·Current 기간을 거쳐 모든 메이저가 LTS가 되는 방식으로 바뀝니다. 그래서 "짝수 = LTS"라는 공식은 26까지만 맞습니다.

버전 번호는 계속 바뀝니다. 지금 무엇이 LTS인지는 Node.js 릴리스 일정에서 확인하세요. fnm install --lts를 쓰면 항상 그 시점의 최신 LTS가 설치됩니다. 프로젝트에는 .nvmrc나 package.json의 engines 필드로 팀이 쓸 버전을 명시해 두는 것이 좋습니다.

🔀 한 프로젝트에서 하나만 쓰세요

npm과 yarn을 섞어 쓰면 lock 파일이 두 개가 되어 사람마다 다른 버전이 설치되는 최악의 상황이 됩니다. 저장소에 package-lock.json이 있으면 npm을, pnpm-lock.yaml이 있으면 pnpm을 쓰세요.

package.json

{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest",
    "lint": "eslint ."
  },
  "dependencies": {
    "react": "^19.0.0"
  },
  "devDependencies": {
    "vite": "^8.0.0",
    "eslint": "^9.0.0"
  },
  "engines": {
    "node": ">=22"
  }
}
항목의미
type: "module"이 프로젝트의 .js 파일을 ES 모듈로 해석(34장). 없으면 CommonJS
scripts자주 쓰는 명령에 별명 붙이기. npm run dev로 실행
dependencies실행에 필요한 패키지. 사용자에게 전달되는 코드에 포함됩니다
devDependencies개발할 때만 필요한 것. 빌드 도구, 테스트, 린터
engines필요한 Node 버전 명시

🎬 scripts가 실무의 진입점입니다

낯선 프로젝트를 받았을 때 가장 먼저 볼 곳이 scripts입니다. 어떻게 실행하고, 어떻게 빌드하고, 어떻게 테스트하는지가 전부 여기 적혀 있습니다. npm run만 입력하면 사용 가능한 스크립트 목록이 나옵니다.

semver — 버전 번호 읽기

MAJOR.MINOR.PATCH 
    19  .  2  .  3
    │      │     └── PATCH — 버그 수정. 사용법이 바뀌지 않음
    │      └──────── MINOR — 기능 추가. 기존 코드는 그대로 동작 (하위 호환)
    └─────────────── MAJOR — 깨지는 변경. 코드 수정이 필요할 수 있음
표기허용 범위설명
^19.2.319.2.3 ~ 19.x.xMAJOR는 고정. npm 기본값
~19.2.319.2.3 ~ 19.2.xPATCH만 허용. 더 보수적
19.2.3정확히 이 버전완전 고정
* 또는 latest아무 최신 버전절대 쓰지 마세요

📌 "제 컴퓨터에서는 되는데요"의 원인

^19.2.3은 범위입니다. 같은 package.json으로 오늘 설치한 사람과 한 달 뒤 설치한 사람이 서로 다른 버전을 받을 수 있습니다. 그래서 lock 파일이 필요합니다.

lock 파일

package-lock.json(또는 pnpm-lock.yaml, yarn.lock)은 실제로 설치된 정확한 버전을 전부 기록합니다. 직접 설치한 것뿐 아니라 그것들이 의존하는 패키지까지 전부입니다.

🔒 lock 파일은 반드시 커밋하세요

  • 커밋하면 모든 팀원과 CI 서버가 완전히 같은 버전을 설치합니다.
  • .gitignore에 넣으면 안 됩니다. 재현 가능한 빌드의 근거가 사라집니다.
  • 충돌이 나면 손으로 고치지 말고, lock 파일을 지우고 npm install을 다시 실행하세요.
npm install       # package.json 기준으로 설치. lock 파일을 갱신할 수 있음
npm ci            # lock 파일 그대로 정확히 설치. 빠르고 결정적
                  # → CI·배포 환경에서는 항상 npm ci 를 씁니다

node_modules

사실설명

지우고 다시 설치 — 반드시 프로젝트 폴더 안에서 
# macOS · 리눅스 · Git Bash
rm -rf node_modules package-lock.json
npm install

# Windows PowerShell
Remove-Item -Recurse -Force node_modules, package-lock.json
npm install

💀 44장에서 rm -rf를 조심하라더니?

44장의 경고는 "무엇을 지우는지 모르는 rm -rf"에 대한 것입니다. 이 명령은 지우는 대상이 현재 폴더 안의 node_modules와 lock 파일로 정확히 정해져 있고, 둘 다 npm install로 다시 만들 수 있어 안전합니다. 다만 실행 전에 pwd로 지금 프로젝트 폴더 안에 있는지를 꼭 확인하세요. 이름 앞에 /나 ~가 붙으면 전혀 다른 곳을 가리키게 됩니다. 또 lock 파일을 지우면 버전이 새로 정해지므로, 팀 프로젝트에서는 먼저 node_modules만 지워 보고 그래도 안 될 때 lock 파일까지 지웁니다.

의존성과 보안

🕸️ 패키지 하나가 수백 개를 데려옵니다

패키지 3개를 설치했는데 node_modules에 폴더가 800개 생기는 일이 흔합니다. 여러분이 설치한 것들이 또 다른 패키지에 의존하기 때문입니다. 즉 여러분의 앱에는 얼굴도 모르는 수백 명의 코드가 들어 있습니다. 이것을 공급망(supply chain) 위험이라고 부릅니다.

npm audit              # 알려진 취약점 확인
npm audit fix          # 자동으로 고칠 수 있는 것 수정
npm outdated           # 오래된 패키지 확인
npm ls react           # 이 패키지가 어디서 왔는지 추적

🛠️ 현장 노트 — 패키지를 설치하기 전에

  1. 정말 필요한가? 40장에서 말했듯 표준 API로 되는 일이 많습니다. 날짜 표시에 라이브러리를 넣기 전에 Intl을 확인하세요.
  2. 얼마나 무거운가? bundlephobia.com에서 설치 전에 용량을 확인할 수 있습니다.
  3. 살아 있는 프로젝트인가? 마지막 배포일, 이슈 응답, 다운로드 수를 봅니다.
  4. 의존성이 몇 개인가? 작은 기능에 의존성 50개짜리 패키지를 쓸 이유는 없습니다.

"직접 20줄 짜기 vs 패키지 설치" 사이에서, 신입은 대개 설치 쪽으로 기웁니다. 경험이 쌓일수록 작은 기능은 직접 쓰는 편이 낫다는 판단이 늘어납니다. 설치한 패키지는 영원히 관리 대상이 되기 때문입니다.

npx

npx create-vite my-app        # 설치하지 않고 한 번만 실행
npx serve                      # 로컬 서버 (44장)
npx eslint .                   # 프로젝트에 설치된 eslint 실행

npx는 패키지를 전역 설치하지 않고 실행합니다. 프로젝트 생성 도구처럼 한 번만 쓰는 명령에 적합하며, 전역 설치로 인한 버전 충돌을 피할 수 있습니다.

📌 요약

  • Node.js는 버전 관리 도구(fnm)로 설치하고 LTS를 쓴다. 2026년 11월 기준 최신 LTS는 26.
  • 설치 후에는 터미널을 새로 열고 node --version으로 확인한다. 안 되면 셸 설정 줄과 PATH를 본다.
  • node_modules 삭제는 rm -rf(PowerShell은 Remove-Item -Recurse -Force)로, 프로젝트 폴더 안에서만.
  • 한 프로젝트에서 패키지 매니저는 하나만 쓴다.
  • dependencies는 실행에, devDependencies는 개발에만 필요한 것.
  • ^19.2.3은 MAJOR 고정, ~는 PATCH만. *는 쓰지 않는다.
  • lock 파일은 반드시 커밋한다. CI에서는 npm ci.
  • node_modules는 커밋하지 않고, 이상하면 지우고 다시 설치한다.
  • 패키지 하나가 수백 개를 데려온다. 설치 전에 필요성·용량·관리 상태를 확인한다.
  • 일회성 실행은 npx.
