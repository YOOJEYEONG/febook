화면이 그려지기까지

서버에서 받은 HTML은 그저 긴 문자열입니다. 이것이 화면의 픽셀이 되기까지 브라우저는 이런 일을 합니다.

렌더링 파이프라인 
HTML 문자열 ──파싱──▶ DOM ──┐
                            ├──▶ 렌더 트리 ──▶ 레이아웃 ──▶ 페인트 ──▶ 합성 ──▶ 화면
CSS 문자열  ──파싱──▶ CSSOM ─┘

① 파싱 — DOM과 CSSOM 만들기

브라우저는 HTML을 위에서부터 읽으며 DOM이라는 나무 모양 구조를 만듭니다. DOM은 HTML 파일 그 자체가 아니라, 브라우저가 해석해서 메모리에 만든 결과물입니다. 이 구분이 중요합니다.

HTML이 DOM이 되는 모습 
<body>                          body
  <h1>제목</h1>        ─────▶     ├── h1 ── "제목"
  <p>본문 <b>강조</b></p>        └── p ──┬── "본문 "
</body>                                   └── b ── "강조"

같은 방식으로 CSS는 CSSOM이라는 구조가 됩니다. "어떤 요소에 어떤 스타일이 최종 적용되는지"를 계산해 둔 표라고 생각하면 됩니다.

⚠️ DOM ≠ HTML 파일

닫는 태그를 빠뜨린 잘못된 HTML을 줘도 브라우저는 알아서 고쳐서 DOM을 만듭니다. 그래서 "소스 보기"에 보이는 HTML과 개발자 도구 Elements 탭에 보이는 구조가 다를 수 있습니다. JavaScript로 요소를 추가하면 DOM에는 있지만 원본 HTML 파일에는 없습니다. 개발자 도구가 보여주는 것은 항상 DOM입니다.

② 렌더 트리 — 화면에 그릴 것만 추리기

DOM과 CSSOM을 합쳐 실제로 화면에 그려질 것들만 모은 것이 렌더 트리입니다. display: none인 요소, <head> 안의 내용처럼 보이지 않는 것은 여기서 빠집니다.

🙈 display:none 과 visibility:hidden 의 차이

display: none은 렌더 트리에서 빠집니다. 공간도 차지하지 않습니다. visibility: hidden은 렌더 트리에 남아 있고 자리도 차지하지만 칠해지지 않을 뿐입니다. "숨겼는데 빈 공간이 남아요"의 원인이 대개 이겁니다.

③ 레이아웃(리플로우) — 위치와 크기 계산

각 요소가 화면 어디에 얼마만 한 크기로 놓일지 계산합니다. "너비 50%"처럼 상대적으로 적힌 값이 이 단계에서 실제 픽셀로 확정됩니다. 이 계산을 다시 하는 것을 리플로우(reflow)라고 하며, 가장 비싼 작업입니다. 요소 하나의 크기가 바뀌면 그 주변, 때로는 문서 전체를 다시 계산해야 하기 때문입니다.

④ 페인트 — 픽셀 칠하기

글자·색·그림자·테두리를 실제로 칠합니다. 위치는 이미 정해졌으니 모양만 그립니다.

⑤ 합성 — 레이어 겹치기

브라우저는 화면을 여러 레이어로 나눠 그린 뒤 마지막에 겹칩니다. 포토샵의 레이어와 같은 개념입니다. 레이어의 위치나 투명도만 바뀐다면, 레이아웃과 페인트를 건너뛰고 겹치기만 다시 하면 됩니다. 이게 결정적으로 중요합니다.

🛠️ 현장 노트 — 애니메이션에 transform을 쓰는 이유

움직이는 애니메이션을 만들 때 두 가지 방법이 있습니다.

  • left: 0 → 100px — 위치가 바뀌므로 레이아웃부터 다시. 매 프레임 전체 계산.
  • transform: translateX(100px) — 대개 합성 단계만 다시. 훨씬 쌉니다.

부드러운 화면은 1초에 60프레임, 즉 한 프레임에 약 16.7밀리초 안에 모든 걸 끝내야 합니다. 레이아웃까지 다시 계산하면 이 예산을 넘기기 쉽고, 그 결과가 "버벅임"입니다. 그래서 실무 원칙은 "움직임은 transform, 사라짐은 opacity"입니다. 20장에서 다시 다룹니다.

CSS와 JavaScript가 렌더링을 막는 방식

CSS는 렌더링을 막는다

CSSOM이 완성되기 전에 화면을 그리면 스타일 없는 날것의 HTML이 잠깐 보였다가 바뀝니다. 이 깜빡임을 피하려고 브라우저는 CSS를 다 받을 때까지 첫 화면 그리기를 미룹니다. 그래서 CSS 파일이 크고 느리면 흰 화면 시간이 길어집니다.

JavaScript는 파싱 자체를 막는다

브라우저가 HTML을 읽다가 <script>를 만나면, HTML 읽기를 멈추고 스크립트를 내려받아 실행이 끝날 때까지 기다립니다.

왜 그럴까요? 스크립트가 document.write()로 HTML을 바꿔 버릴 수도 있기 때문입니다. 브라우저는 그럴 가능성을 배제할 수 없어서 일단 멈추고 기다립니다.

작성 방식내려받기실행 시점실행 순서
<script src>파싱 중단 후즉시 (파싱 멈춤)작성 순서
<script defer src>파싱과 동시에HTML 파싱이 모두 끝난 뒤작성 순서 보장
<script async src>파싱과 동시에내려받는 즉시 (파싱 잠깐 멈춤)보장 안 됨 — 먼저 받아진 순

✅ 실무에서의 기본 선택

  • 대부분의 경우 defer. 순서가 보장되고 DOM이 완성된 뒤 실행되므로 안전합니다.
  • 다른 코드와 아무 상관 없는 독립적인 스크립트(예: 방문 분석 도구)만 async.
  • <script type="module">은 기본으로 defer처럼 동작합니다(34장).
  • 옛날 책에서 보는 "스크립트는 </body> 직전에 두라"는 조언은 defer가 없던 시절의 우회법입니다. 지금은 <head>에 defer로 두는 편이 낫습니다.

"흰 화면"의 정체

페이지를 열었을 때 잠깐 아무것도 없는 시간이 있습니다. 그 시간 동안 브라우저는 이 일을 합니다.

  1. HTML을 받는다
  2. HTML을 읽다가 CSS 링크를 만나면 그것도 받는다 (이게 끝날 때까지 못 그림)
  3. defer 없는 스크립트를 만나면 받아서 실행한다 (여기서도 멈춤)
  4. DOM + CSSOM → 렌더 트리 → 레이아웃 → 페인트
  5. 비로소 첫 픽셀이 보인다

이 첫 픽셀까지 걸린 시간을 FCP(First Contentful Paint)라고 부르고, "의미 있는 큰 콘텐츠"가 보인 시점을 LCP(Largest Contentful Paint)라고 부릅니다. LCP는 구글이 검색 순위에도 반영하는 지표입니다. 자세한 내용은 76장에 있습니다.

🚫 자주 하는 오해

오해 — 화면에 안 보이게 하려면 display: none을 쓰면 되고, 그러면 성능에도 이득이다. 사실 — 렌더 트리에서는 빠지지만 DOM에는 그대로 남아 있습니다. 이미지가 있으면 다운로드도 되고, 요소 개수도 그대로입니다. 목록 1만 개를 만들어 놓고 display:none으로 숨기는 것은 성능 개선이 아닙니다. 정말 필요 없다면 DOM에 만들지 않는 것이 답입니다.

📌 요약

  • 파이프라인: 파싱(DOM·CSSOM) → 렌더 트리 → 레이아웃 → 페인트 → 합성.
  • DOM은 HTML 파일이 아니라 브라우저가 해석해 만든 결과물이다.
  • 레이아웃(리플로우)이 가장 비싸다. transform·opacity는 합성만으로 처리될 수 있어 싸다.
  • CSS는 렌더링을 막고, 스크립트는 HTML 파싱 자체를 막는다.
  • defer는 순서 보장 + 파싱 후 실행, async는 순서 미보장 + 받는 즉시 실행.
  • 한 프레임 예산은 약 16.7ms(60fps).
  • display:none은 렌더 트리에서만 빠질 뿐 DOM에는 남는다.
