이 챕터에서 배우는 것

  • 컴파일러와 인터프리터의 차이, 그리고 JavaScript는 어느 쪽인가
  • AST — ESLint·Prettier·Babel이 공통으로 서 있는 땅
  • JIT 컴파일 — 엔진이 실행 중에 코드를 다시 컴파일한다
  • 소스맵이 없으면 왜 에러 로그가 쓸모없어지는가

읽는 데 약 20분 · 47·48장의 뒷면

번역이 필요한 이유

CPU가 이해하는 것은 기계어뿐입니다. 우리가 쓰는 const sum = a + b는 CPU에게 그냥 글자입니다. 그래서 누군가 번역해야 합니다. 번역 방식은 크게 둘입니다.

컴파일러 (번역가)인터프리터 (통역사)
방식실행 전에 전부 번역해 기계어 파일을 만든다한 줄씩 읽으며 그때그때 실행
장점실행이 빠르다 · 오류를 미리 잡는다바로 실행된다 · 플랫폼을 안 가린다
단점빌드 시간이 필요하다 · 플랫폼별로 다시 빌드매번 해석하므로 느리다 · 오류를 실행해 봐야 안다
예C, Rust, Go초창기 JavaScript, Python

🐢 "JavaScript는 인터프리터 언어라 느리다"

1990년대에는 맞았습니다. 지금은 아닙니다. 현대 엔진(V8·JavaScriptCore·SpiderMonkey)은 인터프리터와 컴파일러를 둘 다 씁니다. 처음에는 빠르게 시작하려고 해석해서 실행하다가, 자주 실행되는 함수를 발견하면 기계어로 컴파일해 버립니다. 이것이 JIT(Just-In-Time) 컴파일입니다. 그래서 "JavaScript는 인터프리터 언어"라는 말 자체가 부정확합니다. 언어가 아니라 구현(엔진)이 정하는 문제이고, 현대 구현은 하이브리드입니다.

AST — 코드를 나무로 바꾸기

엔진이든 ESLint든, 코드를 다루려면 먼저 구조로 바꿔야 합니다. 과정은 두 단계입니다.

글자 → 토큰 → 나무 
원본        const sum = a + b;

① 토큰화    [const] [sum] [=] [a] [+] [b] [;]
             의미 있는 최소 단위로 쪼갠다

② 파싱      VariableDeclaration (const)
              └ VariableDeclarator
                  ├ Identifier: sum
                  └ BinaryExpression (+)
                      ├ Identifier: a
                      └ Identifier: b

  이 나무가 AST (Abstract Syntax Tree, 추상 구문 트리)

AST는 82장에서 배운 트리입니다. 그리고 우리가 쓰는 도구 대부분이 이 트리 위에서 동작합니다.

도구AST로 무엇을 하나
ESLint (48장)트리를 훑으며 규칙 위반을 찾습니다. "VariableDeclaration 중 kind가 var인 노드" → no-var 경고
Prettier트리를 읽고 원래 서식을 버린 뒤 처음부터 다시 출력합니다. 그래서 내가 어떻게 띄어 썼든 결과가 같습니다
Babel (47장)트리를 변형합니다. 화살표 함수 노드를 일반 함수 노드로 바꾸는 식입니다
TypeScript트리에 타입 정보를 얹어 검사하고, 타입을 지운 트리를 출력합니다
번들러 (82장)import/export 노드를 읽어 의존성 그래프를 만듭니다

🔭 직접 보고 싶다면

astexplorer.net에 코드를 붙여 넣으면 AST가 실시간으로 보입니다. ESLint 커스텀 규칙을 만들거나, Babel 플러그인을 쓸 일이 생기면 반드시 들르게 되는 곳입니다.

JIT — 실행하면서 더 빨라지는 코드

V8(Chrome·Node)의 처리 과정은 대략 이렇습니다.

V8의 실행 단계 (개략) 
소스 코드
   │ 파서
   ▼
  AST
   │
   ▼
바이트코드  ──────▶  Ignition (인터프리터)
                      한 줄씩 실행하면서 통계를 모은다
                      "이 함수 몇 번 불렸나, 인자 타입은 뭐였나"
                          │
                          │ 자주 불리는 '뜨거운' 함수 발견
                          ▼
                     최적화 컴파일러 (Sparkplug → Maglev → TurboFan)
                      수집한 정보를 '가정'으로 삼아 기계어를 만든다
                      예: "이 함수의 x는 항상 숫자였으니 숫자로 가정하고 짜자"
                          │
                          │ 가정이 깨지면 (갑자기 문자열이 들어옴)
                          ▼
                     역최적화 (deoptimization)
                      최적화 코드를 버리고 바이트코드로 되돌아간다

🎭 왜 "가정"을 하나

JavaScript는 타입을 미리 알 수 없습니다. a + b는 숫자 덧셈일 수도, 문자열 연결일 수도 있습니다. 모든 경우를 다 처리하는 기계어는 느립니다.
그래서 엔진은 실제 실행을 관찰한 뒤 "지금까지 항상 숫자였으니 숫자로 가정하자"고 결정합니다. 대신 가정이 틀리면 즉시 되돌릴 수 있게 안전장치를 겁니다. 이 도박이 성공하기 때문에 JS가 빠릅니다.

🛠️ 현장 노트 — 이게 실무에 주는 유일한 조언

객체의 모양과 값의 타입을 일정하게 유지하세요. 같은 함수에 어떤 때는 숫자, 어떤 때는 문자열을 넘기거나, 같은 종류의 객체인데 어떤 건 {id, name}이고 어떤 건 {name, id, extra}면 엔진의 가정이 계속 깨져 최적화가 풀립니다.

다만 이걸 위해 코드를 비틀지는 마세요. TypeScript를 제대로 쓰고(7부), 데이터 모양을 일관되게 설계하면 자연스럽게 충족됩니다. 엔진 최적화를 겨냥한 미시 튜닝은 엔진이 바뀌면 무의미해지고, 실제 이득도 대개 측정 오차 수준입니다. 76장의 측정이 먼저입니다.

트랜스파일 — 같은 높이의 번역

컴파일이 고수준 언어 → 저수준(기계어)이라면, 트랜스파일은 고수준 → 고수준 번역입니다. 결과물도 사람이 읽을 수 있는 코드입니다.

무엇 → 무엇하는 일
TypeScript → JavaScript타입 표기를 지웁니다 (타입 검사는 별개 단계)
JSX → JavaScript<div/>를 함수 호출로 바꿉니다
최신 문법 → 구형 문법?.나 ??를 구형 브라우저용으로 (Babel)
Sass → CSS(22장)
TypeScript는 '타입을 지우는' 것이다 
// 입력 (.ts)
function greet(name: string): string {
  return `안녕 ${name}`;
}

// 출력 (.js) — 타입 표기만 사라진다. 런타임 검사는 생기지 않는다
function greet(name) {
  return `안녕 ${name}`;
}

🧊 그래서 타입은 런타임을 지켜 주지 않습니다

타입 표기는 빌드할 때 전부 사라집니다. 서버가 number라고 약속한 필드에 null을 보내면 TypeScript는 아무것도 못 막습니다. 외부에서 들어오는 데이터(API 응답, localStorage, URL 쿼리)는 Zod 같은 런타임 검증을 따로 거쳐야 합니다. (50장)

트랜스파일 도구는 최근 몇 년 사이 크게 바뀌었습니다. Babel(JavaScript로 작성)에서 esbuild(Go), SWC(Rust)로 옮겨 가면서 빌드 속도가 수십 배 빨라졌습니다. Next.js·Vite 같은 도구는 이미 내부적으로 이들을 씁니다. 대부분의 경우 직접 설정할 일은 없습니다. Node.js도 24 기준으로 타입 표기를 지운 채 .ts 파일을 바로 실행할 수 있습니다.

소스맵 — 빌드 결과를 원본으로 되돌리는 지도

배포된 코드는 압축돼 있습니다. 변수 이름은 a, b가 되고 줄바꿈도 사라집니다. 그 상태에서 에러가 나면 스택 트레이스가 이렇게 보입니다.

TypeError: Cannot read properties of undefined (reading 'name')
    at main-4f2a9c.js:1:48293      ← 어디인지 전혀 알 수 없다

소스맵은 "압축된 파일의 1번 줄 48293번째 글자는 원본 UserCard.tsx의 27번째 줄"이라는 대응표입니다. 빌드 도구가 .map 파일로 만들어 주고, 파일 끝의 주석이 그 위치를 가리킵니다.

// 번들 파일 마지막 줄
//# sourceMappingURL=main-4f2a9c.js.map

브라우저 개발자 도구와 에러 추적 도구(Sentry 등, 79장)가 이 파일을 읽어
압축된 위치를 원본 파일·줄·변수 이름으로 되돌려 보여 준다.

🛠️ 현장 노트 — 프로덕션 소스맵을 어떻게 할 것인가

  1. 소스맵을 아예 안 만든다 → 에러 로그가 a.js:1:48293으로만 남아 디버깅이 사실상 불가능합니다. 권하지 않습니다.
  2. 공개 배포한다 → 누구나 원본 소스를 복원할 수 있습니다. 오픈소스라면 문제없지만, 사내 로직이 그대로 노출됩니다.
  3. 권장: "숨김 소스맵" — 소스맵을 생성하되 번들에 sourceMappingURL 주석을 남기지 않고, 파일은 Sentry 같은 에러 추적 서비스에만 업로드합니다. 일반 사용자는 볼 수 없고, 에러 로그는 원본으로 읽힙니다.
  4. 어떤 경우든 .map 파일을 저장소에 커밋하지 마세요. 빌드 산출물입니다.

웹어셈블리(WebAssembly) 한 눈에

WebAssembly(Wasm)는 브라우저가 실행할 수 있는 저수준 바이너리 형식입니다. C·C++·Rust로 짠 코드를 컴파일해 웹에서 돌릴 수 있습니다.

  1. JavaScript를 대체하지 않습니다. 함께 씁니다. 무거운 계산 부분만 Wasm으로 두고 나머지는 JS가 맡습니다.
  2. DOM에 직접 접근할 수 없습니다. JS를 거쳐야 합니다.
  3. 항상 빠른 것도 아닙니다. JS ↔ Wasm 경계를 오가는 비용이 있어 자잘한 호출이 많으면 오히려 느려집니다.
  4. 실제로 쓰이는 곳: 이미지·영상 처리(ffmpeg.wasm), 3D·게임 엔진, 디자인 툴(Figma), 암호화, 물리 시뮬레이션, 브라우저 안의 코드 실행기.
  5. 일반적인 웹 서비스(쇼핑몰, 대시보드, 블로그)에는 거의 필요 없습니다. "느리다"의 원인은 대개 네트워크와 렌더링입니다(83장).

📌 요약

  • 컴파일러는 미리 전부 번역, 인터프리터는 한 줄씩 실행. 현대 JS 엔진은 둘 다 쓴다.
  • 코드는 토큰 → AST(트리)로 바뀐다. ESLint·Prettier·Babel·번들러가 전부 AST 위에서 동작한다.
  • JIT: 자주 쓰이는 함수를 실행 중에 기계어로 컴파일한다. 가정이 깨지면 되돌린다(역최적화).
  • 실무 조언은 하나 — 타입과 객체 모양을 일정하게. 그 이상의 미시 튜닝은 하지 않는다.
  • 트랜스파일은 고수준 → 고수준 번역. TypeScript는 타입을 지울 뿐이라 런타임을 지켜 주지 않는다.
  • 소스맵은 압축된 위치를 원본으로 되돌리는 대응표. 숨김 소스맵 + 에러 추적 서비스 업로드가 권장 조합이다.
  • Wasm은 JS의 대체가 아니라 무거운 계산용 보조. 대부분의 웹 서비스에는 필요 없다.
