프로그램, 프로세스, 스레드

세 단어의 차이 
프로그램   디스크에 저장된 파일. 아직 아무것도 하지 않는다. (Chrome.app)
프로세스   실행되어 메모리를 받은 상태. 자기만의 주소 공간을 갖는다.
스레드     프로세스 안에서 실제로 코드를 실행하는 흐름. 여러 개일 수 있다.
핵심 차이 하나: 메모리를 공유하는가 
프로세스 A          프로세스 B        서로의 메모리에 접근할 수 없다
┌──────────┐       ┌──────────┐      → 하나가 죽어도 다른 쪽은 멀쩡하다
│ 메모리 A  │       │ 메모리 B  │      → 대화하려면 별도의 통신 수단 필요
│ 스레드1   │       │ 스레드1   │      → 만들고 전환하는 비용이 크다
│ 스레드2   │       └──────────┘
└──────────┘
  ↑ 같은 프로세스의 스레드끼리는 메모리를 공유한다
    → 데이터 주고받기가 빠르다
    → 동시에 같은 값을 건드리면 망가진다 (경쟁 조건)

브라우저는 왜 프로세스를 여러 개 쓰나

초기 브라우저는 전체가 하나의 프로세스였습니다. 탭 하나가 죽으면 브라우저 전체가 죽었습니다. 지금의 브라우저는 역할별로 프로세스를 나눕니다.

Chrome 계열의 프로세스 구성 (개략) 
브라우저 프로세스    주소창, 탭, 북마크, 나머지 프로세스 관리
렌더러 프로세스      실제 웹 페이지를 그린다. ★ 우리 코드가 도는 곳
                    보통 탭/사이트마다 따로 만들어진다
네트워크 프로세스    HTTP 요청 처리
GPU 프로세스        화면 합성·그리기 가속
유틸리티 프로세스    오디오, 확장 프로그램 등

🛡️ 사이트 격리 (Site Isolation)

현대 브라우저는 서로 다른 사이트를 다른 렌더러 프로세스에 둡니다. <iframe>으로 들어온 광고도 별도 프로세스입니다.

이유는 두 가지입니다. ① 안정성 — 한 탭이 뻗어도 나머지는 살아 있습니다. ② 보안 — CPU 취약점(Spectre 계열)을 이용해 같은 프로세스 메모리를 훔쳐보는 공격이 가능하다는 것이 밝혀졌습니다. 사이트를 물리적으로 다른 프로세스에 두면, 애초에 읽을 메모리가 거기 없습니다.

대가는 메모리 사용량입니다. "Chrome이 램을 많이 먹는다"는 말은 상당 부분 이 설계 때문이고, 의도된 교환입니다.

렌더러 프로세스 안 — 메인 스레드가 하는 일

우리 코드는 렌더러 프로세스의 메인 스레드 하나에서 돕니다. 그리고 이 스레드는 전부를 합니다.

메인 스레드의 업무 목록 
JavaScript 실행
스타일 계산 (어떤 CSS가 적용되는가)
레이아웃     (무엇이 어디에 얼마 크기로)
페인트       (픽셀로 어떻게 칠할까)
이벤트 처리  (클릭, 입력, 스크롤)

→ 전부 한 줄에서 차례로 처리한다
→ JS가 200ms 붙잡고 있으면 그동안 클릭도, 애니메이션도, 스크롤도 멈춘다 (35장)

다행히 메인 스레드만 있는 것은 아닙니다. 브라우저는 일부 작업을 다른 스레드로 뺍니다.

메인 스레드 밖의 스레드들 
컴포지터 스레드   이미 그려 둔 레이어를 합성하고 화면에 올린다
래스터 스레드     레이어를 실제 픽셀로 굽는다

→ transform 과 opacity 애니메이션은 레이아웃·페인트를 다시 하지 않아도 되므로
  컴포지터 스레드에서 처리할 수 있다 → 메인 스레드가 바빠도 부드럽다 (20·76장)
→ 반면 width, top, margin 애니메이션은 레이아웃을 다시 계산해야 해서
  메인 스레드를 거친다 → 끊긴다

🛠️ 현장 노트 — 이 한 줄이 실무 지식의 핵심입니다

애니메이션은 transform과 opacity로 만드세요. left를 바꾸면 브라우저는 매 프레임 레이아웃을 다시 계산합니다. transform: translateX()는 이미 구워 둔 레이어를 다른 위치에 얹기만 합니다. 같은 움직임인데 비용이 완전히 다릅니다. "왜?"의 답이 바로 스레드가 다르기 때문입니다.

동시성과 병렬성은 다른 말이다

요리사 비유 — 이 구분만은 정확히 
동시성(Concurrency)   요리사 1명이 여러 요리를 번갈아 다룬다.
                      국이 끓는 동안 채소를 썬다.
                      → 진짜 동시에 하는 건 아니지만 기다림이 사라진다
                      → JavaScript의 이벤트 루프 (35장)

병렬성(Parallelism)   요리사 3명이 각자 다른 요리를 정말로 동시에 만든다.
                      → CPU 코어가 여러 개여야 가능
                      → Web Worker, 서버의 멀티프로세스

JavaScript는 싱글 스레드입니다. 하지만 느려 보이지 않는 이유는 동시성 덕분입니다. fetch로 요청을 보내면 기다리는 일은 네트워크 프로세스가 하고, 메인 스레드는 그동안 다른 코드를 실행합니다. 응답이 오면 콜백이 큐에 들어갑니다.

그래서 기다리는 작업(I/O)은 싱글 스레드로도 충분합니다. 문제가 되는 건 계산하는 작업(CPU)입니다. 계산은 대신해 줄 곳이 없습니다.

⚡ "async를 붙이면 병렬로 실행된다"

아닙니다. async/await는 기다리는 동안 자리를 비켜 주는 문법입니다. 새 스레드를 만들지 않습니다. 그래서 Promise.all로 네트워크 요청 3개를 묶으면 실제로 빨라지지만, 무거운 계산 3개를 묶으면 전혀 빨라지지 않습니다. 여전히 한 줄에서 차례로 돕니다. JavaScript에서 진짜 병렬을 얻는 방법은 Web Worker(브라우저)나 worker_threads·자식 프로세스(Node.js)뿐입니다.

Web Worker — 진짜 별도 스레드

Web Worker는 별도의 스레드에서 JavaScript를 실행합니다. 메인 스레드를 전혀 막지 않습니다.

기본 사용법 
// main.js
const worker = new Worker(new URL("./heavy.worker.js", import.meta.url), { type: "module" });

worker.postMessage({ numbers: bigArray });        // 일을 보낸다

worker.onmessage = (e) => {
  console.log("결과:", e.data);                    // 결과를 받는다
};
worker.onerror = (e) => console.error(e.message);

// 다 쓰면 반드시 정리 (84장 — 안 하면 스레드가 계속 살아 있습니다)
// worker.terminate();
heavy.worker.js 
self.onmessage = (e) => {
  const { numbers } = e.data;
  const result = numbers.reduce((a, b) => a + b, 0);   // 오래 걸려도 메인은 멀쩡
  self.postMessage(result);
};

🚧 Worker의 제약 — 알고 써야 합니다

  1. DOM에 접근할 수 없습니다. document, window가 없습니다. 화면을 바꾸려면 결과를 메인 스레드로 보내야 합니다. (fetch, WebSocket, IndexedDB는 쓸 수 있습니다.)
  2. 메모리를 공유하지 않습니다. postMessage로 보내는 데이터는 구조화 복제로 복사됩니다. 함수·DOM 노드·클래스 인스턴스의 메서드는 복사되지 않습니다.
  3. 복사 비용이 있습니다. 아주 큰 데이터라면 postMessage(buffer, [buffer])로 소유권을 넘기면(Transferable) 복사 없이 이동합니다. 단, 넘긴 쪽에서는 그 버퍼를 더 이상 쓸 수 없게 됩니다.
  4. 진짜 메모리 공유가 필요하면 SharedArrayBuffer가 있지만, 보안상 교차 출처 격리(COOP: same-origin + COEP: require-corp 헤더)가 필요합니다. 난도가 높습니다.
  5. Worker를 만드는 것도 비용입니다. 짧은 작업에 매번 새로 만들면 오히려 손해입니다. 재사용하거나 풀을 만드세요.

🛠️ 현장 노트 — Worker를 쓸 때와 안 쓸 때

  1. 쓸 만한 경우: 수만 행 CSV·JSON 파싱, 이미지 필터·리사이즈, 암호화·해시, 대용량 검색 색인 생성, 지도·차트 데이터 전처리.
  2. 쓰지 말아야 할 경우: 단순 API 호출(이미 비동기라 메인을 막지 않음), 가벼운 계산, DOM 조작. Worker로 옮긴다고 네트워크가 빨라지지는 않습니다.
  3. 먼저 해야 할 것: 알고리즘 개선(83장)과 작업 쪼개기. 큰 반복을 나눠 중간에 제어권을 돌려주면(scheduler.yield()나 setTimeout) Worker 없이도 멈춤이 사라지는 경우가 많습니다.
  4. 현실적 난이도: 직접 쓰기보다 comlink 같은 라이브러리로 감싸면 함수 호출처럼 쓸 수 있어 훨씬 편합니다.

JavaScript에도 경쟁 조건이 있다

스레드가 하나라 전통적인 의미의 경쟁 조건(두 스레드가 동시에 같은 변수를 써서 값이 깨지는 것)은 없습니다. 한 번 실행이 시작된 동기 코드는 끝까지 중단되지 않기 때문입니다.

하지만 비동기 응답의 도착 순서가 만드는 경쟁은 매우 흔합니다.

실무에서는 AbortController로 이전 요청을 취소하거나, TanStack Query(67장)처럼 이 문제를 이미 해결해 둔 라이브러리를 씁니다. React 18+의 useEffect 정리 함수에서 ignore 플래그를 쓰는 패턴도 같은 목적입니다(61장).

📌 요약

  • 프로세스는 독립된 메모리 공간, 스레드는 그 안에서 실행되는 흐름(메모리 공유).
  • 브라우저는 탭·사이트마다 렌더러 프로세스를 나눈다 — 안정성과 보안(사이트 격리) 때문.
  • 우리 코드는 메인 스레드 하나에서 돈다. JS·스타일·레이아웃·페인트·이벤트가 전부 여기 있다.
  • transform·opacity는 컴포지터 스레드에서 처리돼 메인이 바빠도 부드럽다.
  • 동시성(번갈아 하기)과 병렬성(정말 동시에)은 다르다. JS 기본은 동시성이다.
  • async는 새 스레드를 만들지 않는다. 기다림은 빨라지고, 계산은 안 빨라진다.
  • 진짜 병렬은 Web Worker. DOM 접근 불가, 데이터는 복사, 만드는 비용이 있다.
  • 싱글 스레드에도 비동기 응답 순서로 인한 경쟁은 있다. 요청 번호나 AbortController로 막는다.
