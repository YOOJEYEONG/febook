인터넷 ≠ 웹

일상에서는 두 단어를 섞어 씁니다. 하지만 기술적으로는 명확히 다릅니다.

인터넷 (Internet)웹 (World Wide Web)
정체전 세계 컴퓨터를 잇는 물리적·논리적 통신망그 통신망 위에서 돌아가는 서비스 중 하나
비유도로망도로 위를 달리는 택배 서비스
등장1960~70년대 (ARPANET)1989년 제안, 1991년 공개
쓰는 규칙TCP/IPHTTP

인터넷 위에서 돌아가는 서비스는 웹만이 아닙니다. 이메일(SMTP·IMAP), 파일 전송(FTP), 화상 통화, 온라인 게임의 통신도 전부 인터넷을 씁니다. 웹은 그중 "주소로 문서를 요청하면 문서를 돌려주는" 방식의 서비스입니다.

📜 웹은 어디서 왔나

1989년, 스위스의 입자물리연구소 CERN에서 일하던 팀 버너스리(Tim Berners-Lee)가 연구자들끼리 문서를 쉽게 공유할 방법을 제안하는 문서를 씁니다. 여기서 세 가지가 함께 나왔습니다 — 문서를 쓰는 언어(HTML), 문서를 주고받는 규칙(HTTP), 문서의 주소(URL). 1991년에 공개되었고, 지금 여러분이 보는 웹은 이 세 가지 위에 30년 넘게 쌓아 올린 것입니다. 프론트엔드 공부가 HTML·HTTP·URL에서 시작하는 건 우연이 아닙니다.

클라이언트와 서버

웹에서 통신은 항상 둘 사이에서 일어납니다.

  • 클라이언트 — 요청하는 쪽. 보통 여러분의 브라우저입니다.
  • 서버 — 응답하는 쪽. 요청을 받아 파일이나 데이터를 돌려줍니다.

⚠️ 서버는 "특별한 기계"가 아니다

서버는 부품 이름이 아니라 역할 이름입니다. 여러분의 노트북에 프로그램 하나만 띄우면 그 순간 노트북도 서버가 됩니다. 실제로 이 책을 만들 때도 여러분 컴퓨터에서 서버를 띄워 확인합니다(44장). 다만 진짜 서비스용 서버는 24시간 켜져 있고, 인터넷에서 찾아갈 수 있는 고정 주소를 가지며, 동시에 수많은 요청을 처리할 수 있게 준비되어 있을 뿐입니다.

역할은 고정되지 않는다

한 컴퓨터가 어떤 통신에서는 클라이언트, 다른 통신에서는 서버일 수 있습니다. 예를 들어 웹 서버가 데이터베이스에서 정보를 가져올 때, 그 웹 서버는 데이터베이스 입장에서 클라이언트입니다. "클라이언트/서버"는 그 통신에서 누가 물었고 누가 답했는가를 가리키는 말입니다.

IP 주소 — 인터넷의 우편번호

전 세계에 컴퓨터가 수십억 대인데, 내 요청이 정확히 그 서버 한 대에 도착하려면 주소가 필요합니다. 그 주소가 IP 주소입니다.

종류모양개수
IPv4142.250.196.110 — 0~255 숫자 4개약 43억 개 (32비트). 이미 부족합니다
IPv62001:0db8:85a3::8a2e:0370:7334사실상 무한 (128비트)

숫자 주소는 사람이 외우기 어렵습니다. 그래서 google.com 같은 도메인 이름을 쓰고, 이것을 IP 주소로 바꿔 주는 시스템이 DNS입니다. 3장에서 자세히 봅니다.

기억해 두면 좋은 특별한 주소

  • 127.0.0.1 — 자기 자신을 가리키는 IP. 별명이 localhost입니다. 개발 중 "내 컴퓨터에서 띄운 서버"에 접속할 때 씁니다.
  • 192.168.x.x, 10.x.x.x — 사설 IP. 집이나 회사 공유기 안에서만 통하는 주소입니다. 인터넷에서 직접 찾아갈 수 없습니다.

패킷과 TCP — 편지를 잘라 보내기

인터넷은 데이터를 통째로 보내지 않습니다. 패킷(packet)이라는 작은 조각으로 쪼개서 보냅니다. 각 조각에는 "어디로 가는지", "몇 번째 조각인지"가 적혀 있습니다.

📦 이사 비유

냉장고를 통째로 옮기는 대신 상자 여러 개로 나눠 보냅니다. 각 상자에는 받는 주소와 "3/10" 같은 번호가 붙습니다. 상자들은 서로 다른 길로 갈 수도 있고 순서가 뒤바뀌어 도착할 수도 있습니다. 받는 쪽에서 번호를 보고 다시 조립합니다. 중간에 하나가 사라지면 "3번 상자 다시 보내 주세요"라고 요청합니다.

이 "조립하고, 빠진 것을 다시 요청하고, 순서를 맞추는" 일을 담당하는 규칙이 TCP입니다. 그래서 웹 페이지는 중간에 글자가 뭉텅이로 사라진 채 도착하지 않습니다.

TCPUDP
보장순서·도착을 보장. 빠진 조각은 재전송보장하지 않음. 빠지면 그냥 빠진 채로
대가확인 절차 때문에 상대적으로 느림빠르고 가벼움
쓰임웹(HTTP/1.1·HTTP/2), 이메일, 파일 전송실시간 영상·음성 통화, 게임, 그리고 HTTP/3의 기반

🛠️ 현장 노트

프론트엔드 개발자가 TCP 패킷을 직접 다룰 일은 거의 없습니다. 하지만 "요청이 왜 느린가"를 따질 때 이 그림이 필요합니다. 연결을 새로 맺는 데도 시간이 들고(핸드셰이크), 조각이 유실되면 재전송을 기다려야 합니다. 그래서 요청 횟수를 줄이는 것이 성능 최적화의 오래된 기본기입니다(76장).

포트 — 같은 주소 안의 방 번호

서버 컴퓨터 한 대에는 여러 프로그램이 동시에 돌아갈 수 있습니다. 웹 서버도 있고, 데이터베이스도 있고, 메일 서버도 있죠. IP 주소만으로는 "그 컴퓨터"까지만 갑니다. 어느 프로그램에 전달할지 정하는 번호가 포트(port)입니다.

  • 80 — HTTP 기본 포트
  • 443 — HTTPS 기본 포트
  • 3000, 5173, 8080 — 개발 중 로컬 서버가 자주 쓰는 포트

https://example.com은 사실 https://example.com:443입니다. 기본 포트는 생략할 수 있어서 안 보일 뿐입니다. 반면 개발할 때 보는 http://localhost:3000은 기본 포트가 아니라 반드시 적어야 합니다.

주소창에 주소를 치면 벌어지는 일

이 질문은 프론트엔드 면접의 고전입니다. 지금 단계에서는 큰 흐름만 잡으면 됩니다. 각 단계의 자세한 내용은 3·4·5장에서 이어집니다.

  1. 주소 해석 — 브라우저가 https://example.com/about을 프로토콜·호스트·경로로 나눕니다. (3장)
  2. DNS 조회 — example.com의 IP 주소를 찾습니다. (3장)
  3. 연결 수립 — 그 IP의 443 포트에 TCP 연결을 맺고, HTTPS라면 암호화 준비(TLS 핸드셰이크)까지 합니다. (4장)
  4. HTTP 요청 전송 — "/about 문서 주세요"라는 메시지를 보냅니다. (4장)
  5. 서버 처리와 응답 — 서버가 상태 코드와 함께 HTML을 돌려줍니다. (4장)
  6. 렌더링 — 브라우저가 HTML을 읽어 화면을 그립니다. 도중에 CSS·이미지·JavaScript가 필요하면 2~5번을 다시 반복합니다. (5장)

💡 여기서 놓치기 쉬운 사실

한 페이지를 여는 데 요청은 한 번이 아닙니다. HTML 하나를 받은 뒤, 그 안에 적힌 CSS 파일·이미지·글꼴·JavaScript 파일마다 요청이 또 나갑니다. 평범한 웹 페이지 하나가 수십~수백 번의 요청을 만듭니다. 개발자 도구의 Network 탭을 열고 아무 사이트나 새로고침해 보면 바로 보입니다(49장).

🚫 자주 하는 오해

오해 — 웹사이트에 접속하면 그 사이트의 컴퓨터에 "들어가는" 것이다. 사실 — 들어가지 않습니다. 파일 사본을 받아오는 것입니다. 편지로 "그 문서 한 부 보내 주세요"라고 요청하면 사본이 오는 것과 같습니다. 받은 사본은 내 브라우저 안에서 열립니다. 그래서 내 브라우저에서 그 페이지를 아무리 고쳐도 원본 사이트는 바뀌지 않습니다. (개발자 도구로 남의 사이트 글자를 바꿔 봐도 나만 보입니다.)

📌 요약

  • 인터넷은 통신망, 웹은 그 위에서 돌아가는 서비스 하나다.
  • 클라이언트는 요청하는 쪽, 서버는 응답하는 쪽. 기계 종류가 아니라 역할이다.
  • IP 주소가 컴퓨터를, 포트가 그 안의 프로그램을 지정한다. HTTP는 80, HTTPS는 443.
  • 데이터는 패킷으로 쪼개져 이동하고, TCP가 순서와 도착을 책임진다.
  • 페이지 하나를 여는 데 요청은 수십~수백 번 일어난다.
  • 웹 접속은 서버에 들어가는 게 아니라 사본을 받아오는 것이다.
