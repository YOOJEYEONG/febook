🎯 무엇을 쓸까 — 한눈에

  • 사용자 설정(테마, 언어, 사이드바 접힘) → localStorage
  • 이 탭에서만 유지할 임시 상태(작성 중인 폼, 마법사 단계) → sessionStorage
  • 서버가 알아야 하는 것(세션 식별자) → 쿠키. 그것도 HttpOnly로
  • 대용량·구조화된 데이터(오프라인 캐시, 이미지) → IndexedDB

localStorage / sessionStorage

💥 저장소 접근은 예외를 던질 수 있습니다

localStorage를 읽기만 해도 오류가 나는 환경이 있습니다.

  • 브라우저 설정에서 사이트 데이터 저장을 차단한 경우
  • 일부 브라우저의 시크릿 모드
  • 용량을 초과했을 때 (QuotaExceededError)
  • 일부 iframe 안에서 (서드파티 쿠키 차단 정책)

따라서 모든 접근을 try/catch로 감싸고, 실패하면 기능만 조용히 꺼지고 페이지 자체는 정상 동작하게 만들어야 합니다. (이 책의 진도 저장 기능도 그렇게 만들어져 있습니다.)

🐌 localStorage는 동기적입니다

읽고 쓰는 동안 메인 스레드가 멈춥니다(35장). 작은 값 몇 개는 문제없지만, 큰 JSON을 매 렌더링마다 읽고 쓰면 화면이 버벅입니다. 스크롤·입력 이벤트 안에서 localStorage를 호출하는 코드는 특히 위험합니다. 큰 데이터에는 비동기인 IndexedDB를 쓰세요.

다른 탭과 동기화

// 같은 사이트의 '다른 탭'에서 값이 바뀌면 발생합니다 (자기 탭에서는 발생하지 않음)
window.addEventListener("storage", (event) => {
  if (event.key === "theme") {
    applyTheme(event.newValue);
  }
});

"한 탭에서 로그아웃하면 다른 탭도 로그아웃되게" 만들 때 유용합니다.

쿠키

// JavaScript에서 다루는 방법 — API가 옛날 방식이라 불편합니다
document.cookie = "theme=dark; path=/; max-age=3600; SameSite=Lax";
console.log(document.cookie);   // "a=1; b=2" 형태의 문자열 전체

4장에서 본 것처럼 쿠키는 매 요청마다 자동으로 서버에 전송됩니다. 이것이 장점(로그인 유지)이자 단점(용량이 곧 트래픽)입니다.

📦 쿠키에 큰 데이터를 넣지 마세요

4KB짜리 쿠키가 있으면 모든 요청에 4KB가 추가로 붙습니다. 이미지·CSS·JS 요청에도 전부 따라갑니다. 서버가 알 필요 없는 정보는 localStorage에 두세요.

IndexedDB

브라우저 안에 있는 진짜 데이터베이스입니다. 객체를 그대로 저장할 수 있고, 색인을 만들어 검색할 수 있으며, 용량이 큽니다.

// 원본 API는 이벤트 기반이라 상당히 장황합니다
const request = indexedDB.open("myDB", 1);

request.onupgradeneeded = (event) => {
  const db = event.target.result;
  const store = db.createObjectStore("users", { keyPath: "id" });
  store.createIndex("byEmail", "email", { unique: true });
};

request.onsuccess = (event) => {
  const db = event.target.result;
  const tx = db.transaction("users", "readwrite");
  tx.objectStore("users").put({ id: 1, name: "홍길동", email: "a@b.c" });
};

📚 실무에서는 래퍼 라이브러리를 씁니다

// idb 라이브러리를 쓰면 Promise 기반으로 훨씬 간결해집니다
import { openDB } from "idb";

const db = await openDB("myDB", 1, {
  upgrade(db) { db.createObjectStore("users", { keyPath: "id" }); }
});
await db.put("users", { id: 1, name: "홍길동" });
const user = await db.get("users", 1);

원본 API를 외울 필요는 없습니다. "큰 데이터·객체·오프라인이면 IndexedDB"라는 판단만 할 수 있으면 됩니다.

토큰을 어디에 저장할까

가장 자주 논쟁되는 주제입니다. 정답이 하나가 아니라 위협 모델에 따라 다릅니다.

저장 위치XSS에 취약?CSRF에 취약?
localStorage매우 취약 — 스크립트가 읽어 갈 수 있음안전 (자동 전송되지 않음)
일반 쿠키취약 — document.cookie로 읽힘취약
HttpOnly + Secure + SameSite 쿠키훨씬 안전 — JS가 읽을 수 없음SameSite로 크게 완화

🔐 현실적인 결론

  • 가능하다면 HttpOnly 쿠키가 가장 안전합니다. 서버 설정이 필요하므로 백엔드와 협의해야 합니다.
  • localStorage에 토큰을 두면, XSS가 한 번만 성공해도 토큰이 통째로 유출됩니다. "우리는 XSS가 없다"는 가정은 위험합니다. 광고 스크립트나 npm 패키지 하나로도 뚫릴 수 있습니다.
  • 어느 쪽을 쓰든 XSS를 막는 것이 근본입니다. 저장 위치는 피해를 줄일 뿐입니다(78장).
  • 토큰 만료 시간을 짧게 하고 리프레시 토큰을 쓰는 것도 피해를 줄이는 방법입니다.

🚫 절대 저장하면 안 되는 것

비밀번호 — 어떤 형태로도, 어디에도 저장하지 않습니다. 주민등록번호·카드번호 — 브라우저 저장소는 암호화되어 있지 않습니다. 개발자 도구에서 누구나 평문으로 볼 수 있습니다. 서버 비밀 키 — 1장에서 말한 그대로입니다. 공용 컴퓨터에서 사용자가 브라우저를 닫아도 localStorage는 남아 있습니다.

🛠️ 현장 노트 — 저장소 실무 규칙

  1. 항상 try/catch로 감싸고, 실패해도 앱이 동작하게 만듭니다.
  2. 키에 접두사를 붙입니다. myapp:theme 처럼요. 같은 도메인의 다른 앱과 충돌을 막습니다.
  3. 버전을 관리합니다. 저장 형식이 바뀌면 옛 데이터를 읽다가 오류가 납니다. { version: 2, data: … } 형태를 권합니다.
  4. 용량을 가정하지 마세요. 5MB는 보장이 아니라 관행입니다. 큰 데이터는 IndexedDB로.
  5. 사용자가 데이터를 지울 수 있는 방법을 제공합니다.

📌 요약

  • localStorage는 영구·출처별, sessionStorage는 탭별이며 탭을 닫으면 사라진다.
  • 둘 다 문자열만 저장한다. 객체는 JSON.stringify/parse.
  • 접근 자체가 예외를 던질 수 있다. 항상 try/catch.
  • 동기 API라 메인 스레드를 막는다. 큰 데이터는 IndexedDB.
  • 쿠키는 매 요청에 자동 전송되므로 작게 유지한다. 약 4KB 제한.
  • 토큰은 가능하면 HttpOnly 쿠키. localStorage는 XSS에 통째로 노출된다.
  • 비밀번호·주민번호·카드번호는 어디에도 저장하지 않는다.
