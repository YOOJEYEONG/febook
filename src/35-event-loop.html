  • 콜 스택 · 태스크 큐 · 마이크로태스크 큐
  • setTimeout(fn, 0)이 즉시 실행이 아닌 이유
  • 이미 이행된 Promise의 콜백이 대기 중인 타이머보다 먼저 실행되는 이유 — 그리고 항상 그렇지는 않은 경우

JavaScript는 한 번에 하나만 합니다

JavaScript는 싱글 스레드 언어입니다. 코드를 실행하는 통로가 하나뿐입니다. 그런데도 서버 응답을 기다리면서 애니메이션이 돌고 버튼도 눌립니다. 어떻게 가능할까요?

☕ 1인 카페 비유

바리스타는 한 명입니다(싱글 스레드). 손님이 커피를 주문하면 바리스타는 기계에 넣고 기다리지 않습니다. 버튼만 누르고 다음 손님을 받습니다(비동기 요청). 커피가 다 되면 기계가 알려 주고(콜백), 바리스타는 지금 하던 일을 끝낸 뒤 커피를 내어 줍니다.
핵심: 기다리는 일은 바리스타가 아니라 기계(브라우저)가 합니다.

구성 요소 
┌─────────────┐   ┌──────────────────────────┐
│  콜 스택     │   │  브라우저가 제공하는 기능  │
│ (JS 엔진)   │   │  타이머 · 네트워크 · DOM  │
│  한 개뿐     │   │  (JS 엔진 밖에서 동작)    │
└──────┬──────┘   └────────────┬─────────────┘
       │                       │ 완료되면 콜백을 큐에 넣음
       │                       ▼
       │          ┌────────────────────────────┐
       │          │ 마이크로태스크 큐 (우선)     │ ← Promise, queueMicrotask
       │          ├────────────────────────────┤
       │          │ 태스크 큐                   │ ← setTimeout, 이벤트
       │          └────────────┬───────────────┘
       │                       │
       └───────── 이벤트 루프 ──┘
          "스택이 비면 큐에서 하나 꺼내 올린다"

콜 스택

함수를 호출하면 스택에 쌓이고, 끝나면 위에서부터 빠집니다. 접시를 쌓았다가 위에서부터 꺼내는 것과 같습니다.

실행 순서 — 이 챕터의 핵심

이벤트 루프의 규칙은 단순합니다.

  1. 태스크 하나를 실행한다. 처음엔 스크립트 전체(동기 코드)가 첫 태스크입니다. 콜 스택이 빌 때까지 끝까지 실행합니다.
  2. 스택이 비면 마이크로태스크 큐를 전부 비운다. 그 사이 새로 추가된 것까지 전부.
  3. 렌더링 기회 — 화면을 새로 그릴 때가 됐다면 requestAnimationFrame 콜백 → 스타일 계산 → 레이아웃 → 페인트(5장)를 합니다. 매 바퀴마다가 아니라 보통 화면 주사율에 맞춰(60Hz면 약 16.7ms마다) 일어납니다.
  4. 다시 1번으로 — 태스크 큐에서 다음 태스크 하나를 꺼낸다.

Promise의 .then(36장)은 "Promise가 끝나면 이 함수를 실행해 줘"라는 예약이고, 그 콜백은 마이크로태스크로 들어갑니다. setTimeout의 콜백, 클릭 같은 이벤트 핸들러는 태스크로 들어갑니다.

⚡ 마이크로태스크는 전부, 태스크는 하나만

이 비대칭이 중요합니다. 마이크로태스크 처리 중에 새 마이크로태스크가 추가되면 그것까지 다 처리한 뒤에야 다음 단계로 넘어갑니다. 그래서 마이크로태스크로 무한 루프를 만들면 브라우저가 완전히 멈춥니다.

// ⚠️ 절대 실행하지 마세요 — 브라우저가 응답하지 않게 됩니다
function loop() { Promise.resolve().then(loop); }

위 예제를 한 단계씩 큐의 상태로 풀어 보면 이렇습니다. [ ] 안이 대기 중인 것, 왼쪽이 먼저 꺼내집니다.

단계별 큐 스냅샷 
단계 ①  스크립트(첫 태스크) 실행
        출력: A
        setTimeout 두 개 등록 → 0ms가 지나 태스크 큐로
        Promise.resolve().then(B) → B가 마이크로태스크 큐로
        ─────────────────────────────────────────────
        마이크로태스크 큐: [ B ]
        태스크 큐:        [ D타이머, F타이머 ]

단계 ②  스택이 비었다 → 마이크로태스크 전부 비우기
        B 실행 → 출력: B → 다음 .then(C)이 큐에 추가됨
        마이크로태스크 큐: [ C ]           ← 아직 안 비었으니 계속
        C 실행 → 출력: C
        마이크로태스크 큐: [ ]  ✔ 다 비움
        태스크 큐:        [ D타이머, F타이머 ]

        (여기서 렌더링 기회가 있을 수 있음)

단계 ③  태스크 하나 꺼내기: D타이머
        출력: D → 안에서 Promise.then(E) → E가 마이크로태스크 큐로
        마이크로태스크 큐: [ E ]
        태스크 큐:        [ F타이머 ]       ← F는 아직 기다림

단계 ④  스택이 비었다 → 마이크로태스크 전부 비우기
        E 실행 → 출력: E
        마이크로태스크 큐: [ ]
        태스크 큐:        [ F타이머 ]

단계 ⑤  태스크 하나 꺼내기: F타이머
        출력: F
        모든 큐가 비었다 → 새 일이 올 때까지 대기

최종 출력: A → B → C → D → E → F

🚫 "Promise는 setTimeout보다 항상 먼저"가 아닙니다

오해 — Promise 콜백은 무조건 setTimeout 콜백보다 먼저 실행된다. 사실 — 정확한 규칙은 "이미 이행된(끝난) Promise의 콜백은, 대기 중인 다음 태스크보다 먼저 실행된다"입니다. .then 콜백이 마이크로태스크 큐에 들어가는 건 Promise가 끝나는 순간입니다. fetch(37장)처럼 서버 응답을 기다리는 Promise는 응답이 와야 끝나므로, 그 사이 이미 태스크 큐에 들어가 있던 타이머가 먼저 실행됩니다. 
setTimeout(() => console.log("타이머"), 0);
fetch("/api/data").then(() => console.log("fetch 완료"));
// 출력: 타이머 → fetch 완료
// 응답이 오기까지 수십~수백 ms가 걸리고, 타이머는 그 전에 이미 태스크 큐에 있습니다

setTimeout(fn, 0)의 진실

⏱️ "0ms니까 즉시 실행"이 아닙니다

setTimeout의 시간은 "이만큼 지난 뒤에 큐에 넣어 달라"는 뜻이지 "이만큼 뒤에 실행하라"가 아닙니다. 큐에 들어간 뒤에도 콜 스택이 비고 마이크로태스크가 다 처리될 때까지 기다립니다. 앞에 무거운 동기 코드가 있으면 setTimeout(fn, 0)이 몇 초 뒤에 실행될 수도 있습니다. 게다가 HTML 명세상 타이머 중첩이 5단계를 넘으면(6단계부터) 최소 4ms로 제한됩니다. 정확한 시간이 필요한 애니메이션에 setTimeout을 쓰면 안 되는 이유입니다.
그럼 setTimeout(fn, 0)은 언제 쓰나 
// "지금 하던 일을 다 끝내고 나서 실행해 줘"라는 뜻으로 씁니다
// 예: 무거운 작업을 쪼개 중간중간 브라우저에 차례를 넘겨줄 때
setTimeout(() => processNextChunk(), 0);

🎬 "display를 켠 뒤 setTimeout(0)으로 트랜지션 시작"은 보장되지 않습니다

흔히 보이는 아래 코드는 될 때도 있고 안 될 때도 있습니다. 타이머 태스크가 렌더링 기회보다 먼저 실행되면, 브라우저는 display: block과 visible을 한 번에 반영해 시작 상태가 없으니 전환 없이 바로 끝 상태로 나타납니다.

// ❌ 불안정
element.style.display = "block";
setTimeout(() => element.classList.add("visible"), 0);

// ✅ 방법 1: 강제 리플로우 — 레이아웃 값을 읽으면 브라우저가 그 자리에서 스타일을 계산합니다
element.style.display = "block";
element.offsetWidth;                  // 읽기만 해도 시작 상태가 확정됨 (5장 리플로우)
element.classList.add("visible");

// ✅ 방법 2: requestAnimationFrame 두 번 — 한 프레임이 실제로 그려진 뒤 변경
element.style.display = "block";
requestAnimationFrame(() => {
  requestAnimationFrame(() => element.classList.add("visible"));
});

rAF 한 번은 "이번 프레임을 그리기 직전"이라 아직 시작 상태가 그려지기 전입니다. 그래서 두 번 감쌉니다.

메인 스레드를 막으면

🛠️ 현장 노트 — 무거운 작업 다루기

  1. 작게 쪼개기 — 큰 반복을 나눠 중간중간 브라우저에 제어권을 돌려줍니다. 쪼갠 사이에 클릭 처리와 렌더링이 끼어들 수 있습니다.
  2. scheduler.yield() — 쪼개기를 위한 전용 도구입니다. await scheduler.yield()(36장)를 만나면 잠시 차례를 양보했다가, setTimeout과 달리 대기 중인 다른 작업보다 앞쪽으로 돌아와 이어서 실행됩니다. MDN 기준(2026년 11월) Chrome·Edge 129+, Firefox 142+에서 지원하고 Safari는 미지원이라, if ("scheduler" in window && "yield" in scheduler)로 확인하고 없으면 setTimeout으로 대신합니다.
  3. Web Worker(40장) — 진짜 별도 스레드에서 계산합니다. 메인 스레드를 전혀 막지 않습니다.
  4. requestIdleCallback — 브라우저가 한가할 때 실행합니다. MDN 기준(2026년 11월) Chrome 47+, Firefox 55+는 지원하지만 Safari는 정식 버전에서 지원하지 않습니다(Technology Preview에서 설정을 켜야만 동작). 기능 확인 후 setTimeout으로 대비해야 합니다.
  5. 알고리즘을 개선 — 대개 가장 효과가 큽니다. 3중 반복문을 하나로 줄이는 게 낫습니다.

애니메이션에는 requestAnimationFrame

// ❌ 타이밍이 부정확하고 화면 주사율과 어긋납니다
setInterval(() => { moveElement(); }, 16);

// ✅ 브라우저가 "다음 화면을 그리기 직전"에 호출해 줍니다
function animate() {
  moveElement();
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

requestAnimationFrame은 화면 주사율만큼(60Hz 화면이면 초당 60회, 120Hz면 120회) 호출되므로, 고정된 16ms를 가정하지 말고 콜백이 받는 시각 인자로 경과 시간을 계산해야 합니다. 또한 탭이 백그라운드로 가면 자동으로 멈춰 배터리를 아낍니다. 5장에서 본 "한 프레임 16.7ms"(60Hz 기준) 예산이 여기서 의미를 갖습니다.

📌 요약

  • JavaScript는 싱글 스레드다. 기다리는 일은 브라우저가 대신 한다.
  • 실행 순서: 태스크 하나(처음엔 동기 코드 전부) → 마이크로태스크 전부 → (때가 되면) 렌더링, 반복.
  • Promise 콜백은 마이크로태스크, setTimeout·이벤트는 태스크. 이미 이행된 Promise의 콜백은 대기 중인 다음 태스크보다 먼저다. 나중에 끝나는 Promise(fetch 등)는 그 전에 큐에 있던 타이머보다 늦다.
  • setTimeout(fn, 0)은 즉시 실행이 아니라 "지금 일을 다 끝낸 뒤"라는 뜻이다.
  • 마이크로태스크는 전부 비우고, 태스크는 하나씩 처리한다.
  • 메인 스레드를 막으면 클릭·애니메이션·렌더링이 전부 멈춘다.
  • 애니메이션에는 requestAnimationFrame. 렌더링 직전, 화면 주사율만큼 호출된다.
