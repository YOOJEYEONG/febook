이 챕터에서 배우는 것

  • 요청 하나가 실제로 거치는 단계 — 핸드셰이크부터 응답까지
  • 지연시간과 대역폭은 다른 문제다
  • HTTP/1.1 → 2 → 3 이 무엇을 고쳤나, 실무에서 무엇이 달라지나
  • Network 패널의 타이밍 막대를 읽고 원인을 짚는 법

읽는 데 약 24분 · 2~4장의 심화

계층 — 인터넷이 유지되는 방식

인터넷은 층으로 나뉘어 있습니다. 각 층은 아래 층이 어떻게 동작하는지 몰라도 됩니다. 이 덕분에 Wi-Fi가 5G로 바뀌어도 fetch 코드는 그대로입니다.

TCP/IP 4계층 — 우리가 실제로 쓰는 모델 
응용 계층      HTTP, WebSocket, DNS        ← 우리 코드가 사는 곳
                "무엇을 주고받을 것인가"

전송 계층      TCP, UDP                    ← 순서·재전송 담당
                "빠짐없이, 순서대로 보낼 것인가"

인터넷 계층    IP                          ← 주소와 길 찾기
                "어느 컴퓨터로 보낼 것인가"

링크 계층      이더넷, Wi-Fi, LTE          ← 실제 전기·전파
                "물리적으로 어떻게 전달할 것인가"

편지에 비유하면
  응용 = 편지 내용 / 전송 = 등기 여부 / 인터넷 = 주소 / 링크 = 트럭·비행기

교과서에 나오는 OSI 7계층은 더 잘게 나눈 이론 모델입니다. 면접에 이름이 나올 수 있지만, 실무에서는 위의 4계층으로 충분합니다.

TCP와 UDP

TCP                                  UDP
────────────────────────             ────────────────────────
연결을 맺고 시작한다                   그냥 보낸다
빠진 조각을 다시 보낸다                 빠져도 신경 안 쓴다
순서를 보장한다                        순서 안 맞을 수 있다
느리지만 정확하다                      빠르지만 손실 가능

웹 페이지, 파일 전송, 이메일           실시간 영상·음성 통화, 게임
HTTP/1.1, HTTP/2                     HTTP/3(QUIC), WebRTC

요청 하나가 거치는 단계

fetch("https://api.example.com/users") 한 줄 뒤에서 벌어지는 일입니다.

첫 요청의 전체 흐름 
① DNS 조회        api.example.com → 93.184.x.x     (3장)
                   캐시에 있으면 건너뛴다

② TCP 3방향 핸드셰이크                              1왕복(RTT)
   나 ──SYN──▶ 서버        "연결하고 싶다"
   나 ◀─SYN+ACK── 서버     "좋다, 나도 준비됐다"
   나 ──ACK──▶ 서버        "확인"

③ TLS 핸드셰이크 (https)                            TLS 1.3 기준 1왕복
   인증서 확인 + 암호화 키 합의

④ HTTP 요청 전송 ──▶
⑤ 서버 처리 (DB 조회 등)
⑥ 응답 수신 ◀──

여기서 ②③은 '왕복'이다. 서버가 아무리 빨라도
지구 반대편이면 왕복 1회에 150ms 이상 걸린다.

🔐 TLS가 대칭 키와 비대칭 키를 둘 다 쓰는 이유

비대칭 키(공개키/개인키)는 안전하지만 느립니다. 대칭 키(양쪽이 같은 열쇠)는 빠르지만 열쇠를 어떻게 전달하느냐가 문제입니다.
그래서 TLS는 핸드셰이크에서만 비대칭 방식으로 대칭 키를 안전하게 합의하고, 실제 데이터는 빠른 대칭 키로 암호화합니다. 인증서는 "이 서버가 진짜 그 도메인의 주인인지"를 신뢰할 수 있는 기관이 보증하는 문서입니다. (4·78장)

지연시간 vs 대역폭 — 프론트엔드가 반드시 구분해야 할 것

대역폭(bandwidth)   한 번에 얼마나 많이 보낼 수 있는가  = 도로의 차선 수
지연시간(latency)   한 번 갔다 오는 데 얼마나 걸리는가  = 도로의 길이

기가인터넷으로 업그레이드하면 대역폭은 10배가 된다.
그러나 서울 ↔ 미국 서버의 왕복 시간은 그대로다.
빛의 속도와 거리가 정하는 값이라 돈으로 줄일 수 없다.

  서울 ↔ 서울          약   5 ms
  서울 ↔ 도쿄          약  35 ms
  서울 ↔ 미국 서부      약 130 ms
  서울 ↔ 유럽          약 250 ms
  (실제 값은 경로와 회선에 따라 다릅니다)

🛠️ 현장 노트 — 그래서 이렇게 합니다

  1. CDN을 쓴다(3장). 정적 파일을 사용자와 물리적으로 가까운 서버에 두면 지연시간 자체가 줄어듭니다. 이게 CDN의 존재 이유입니다.
  2. 왕복 횟수를 줄인다. 요청 A의 응답을 받아야 요청 B를 보낼 수 있는 폭포수(waterfall) 구조가 최악입니다. Promise.all로 묶을 수 있는지 항상 확인하세요.
  3. 연결을 미리 맺어 둔다. 외부 도메인을 쓸 것이 확실하면 <link rel="preconnect" href="https://api.example.com">로 DNS·TCP·TLS를 미리 끝내 둡니다. 단, 꼭 쓸 도메인에만 — 남발하면 오히려 손해입니다.
  4. 측정할 때 네트워크를 조절하세요. DevTools Network 패널의 스로틀링을 Fast 4G / Slow 4G로 두고 테스트해야 실제 사용자 환경이 보입니다. 사무실 유선 인터넷 기준으로 만들면 현장에서 무너집니다.

HTTP 1.1 → 2 → 3

HTTP/1.1의 한계

연결 하나에 요청 하나씩, 순서대로만 처리한다.
앞의 응답이 늦으면 뒤가 전부 밀린다 → 대기 행렬 막힘(Head-of-Line Blocking)

브라우저는 도메인당 6개 정도의 연결을 동시에 열어 우회했다.
그래서 과거에는 이런 기법들을 썼다.
  · 파일 합치기(번들·스프라이트 이미지)   요청 수를 줄이려고
  · 도메인 샤딩(img1.x.com, img2.x.com)  연결 수를 늘리려고
  · 이미지 인라인(base64)                  요청 자체를 없애려고

HTTP/2 — 한 연결에 여러 요청

멀티플렉싱   연결 하나에서 여러 요청·응답을 동시에 주고받는다
             → 도메인 샤딩은 이제 오히려 해롭다(연결마다 핸드셰이크 비용)
헤더 압축     반복되는 헤더를 압축해 보낸다 (HPACK)
스트림 우선순위 중요한 리소스를 먼저

남은 문제: TCP 계층의 대기 행렬 막힘
  패킷 하나가 유실되면 TCP는 그 조각이 도착할 때까지
  뒤에 온 모든 스트림의 데이터를 상위 계층에 넘기지 않는다.
  → 논리적으로는 독립인 요청들이 함께 멈춘다.

⚰️ HTTP/2 서버 푸시는 사실상 폐기됐습니다

"요청하기 전에 서버가 미리 보내 준다"는 기능이었지만, 브라우저가 이미 캐시에 갖고 있는 파일까지 다시 보내는 낭비가 잦았고 제어가 까다로웠습니다. Chrome은 106 버전에서 지원을 제거했습니다. 오래된 블로그 글에서 이 기능을 권하는 내용을 보면 2026년 기준으로는 무시하세요. 대신 <link rel="preload">나 103 Early Hints를 씁니다.

HTTP/3 — TCP를 버리고 UDP 위로

QUIC이라는 새 전송 프로토콜 위에서 동작한다. 기반은 UDP.

· 스트림이 진짜로 독립적이다
  → 패킷 하나가 유실돼도 그 스트림만 기다린다. TCP 대기 행렬 막힘 해결.
· 연결 수립이 빠르다
  → TCP 핸드셰이크 + TLS 핸드셰이크가 하나로 합쳐진다
· 연결 마이그레이션
  → Wi-Fi에서 셀룰러로 바뀌어도 연결이 유지된다 (모바일에서 특히 유용)

"UDP는 못 믿는 프로토콜 아닌가?" → 신뢰성 기능을 QUIC이 직접 구현했다.
TCP를 안 쓰는 이유는 TCP가 운영체제 커널에 있어 바꾸기가 사실상 불가능하기 때문이다.

🛠️ 현장 노트 — 버전이 실무에 주는 영향

  1. HTTP/2·3은 대부분 자동입니다. Vercel·Netlify·Cloudflare 같은 호스팅은 이미 켜져 있습니다. 애플리케이션 코드는 바꿀 게 없습니다.
  2. 도메인 샤딩은 하지 마세요. HTTP/1.1 시대의 기법이고 지금은 손해입니다.
  3. "파일을 잘게 쪼개도 된다"는 것이지 "무제한"은 아닙니다. 요청마다 헤더·우선순위 처리 비용이 있고, 각 파일마다 압축 효율도 떨어집니다. 코드 스플리팅은 라우트·큰 라이브러리 단위가 적정선입니다(47·76장).
  4. 확인 방법: DevTools Network 패널에서 컬럼을 우클릭해 Protocol을 켜면 h2·h3가 보입니다.

실시간 통신 — 무엇을 고를까

폴링(Polling)          일정 간격으로 계속 물어본다
                       가장 단순. 낭비가 크고 지연도 있다. 그러나 대부분 충분하다.

SSE                    서버 → 클라이언트 단방향 스트림. HTTP 그대로 사용.
(Server-Sent Events)   자동 재연결 내장. 알림, 진행률, AI 응답 스트리밍에 적합.
                       EventSource API. 텍스트만 보낼 수 있다.

WebSocket              양방향 실시간. 연결을 한 번 맺고 계속 유지.
                       채팅, 협업 편집, 게임, 실시간 시세.
                       재연결·하트비트를 직접 구현해야 한다.

WebRTC                 브라우저 ↔ 브라우저 직접 연결. 화상 통화.
                       난도가 높다. 보통 라이브러리·서비스를 쓴다.

🎚️ 선택 기준

서버가 일방적으로 보내기만 하면 SSE, 양쪽이 주고받아야 하면 WebSocket입니다. 많은 팀이 습관적으로 WebSocket을 고르지만, 알림이나 진행률 표시는 SSE가 훨씬 단순합니다. 그리고 갱신 주기가 30초 이상이면 그냥 폴링이 낫습니다. 유지할 연결이 없으니 장애도 없습니다.

🛠️ 현장 노트 — 이 표가 실무에서 하는 일

"페이지가 느려요"라는 제보를 받으면 추측하지 말고 이 타이밍을 보세요. TTFB가 길면 백엔드 문제고, Content Download가 길면 프론트엔드 문제입니다. 이 한 가지 구분만 할 줄 알아도 엉뚱한 곳을 파느라 하루를 쓰는 일이 사라집니다. 전체 화면 로딩 지표는 76장의 Core Web Vitals로 봅니다.

📌 요약

  • 인터넷은 계층 구조다. 위층은 아래층의 구현을 몰라도 된다.
  • TCP는 정확하지만 연결 수립에 왕복이 필요하고, UDP는 빠르지만 보장이 없다.
  • 첫 요청은 DNS → TCP 핸드셰이크 → TLS 핸드셰이크 → 요청 → 응답을 거친다.
  • 지연시간은 돈으로 못 줄인다. 거리의 문제다 — 그래서 CDN과 왕복 횟수 줄이기가 답이다.
  • HTTP/2는 한 연결에서 멀티플렉싱. 도메인 샤딩은 이제 해롭다.
  • HTTP/2 서버 푸시는 폐기됐다(Chrome 106에서 제거). preload·Early Hints를 쓴다.
  • HTTP/3(QUIC)은 UDP 기반으로 TCP 대기 행렬 막힘을 없애고 연결 전환에도 강하다.
  • 실시간은 단방향이면 SSE, 양방향이면 WebSocket, 느긋하면 폴링.
  • TTFB가 길면 백엔드, Content Download가 길면 프론트엔드.
