읽는 데 약 20분

뷰포트 메타 태그

<meta name="viewport" content="width=device-width, initial-scale=1">

이 한 줄이 없으면 모바일 브라우저는 가상의 넓은 화면(보통 980px)에 페이지를 그린 뒤 통째로 축소해서 보여 줍니다. PC 화면을 멀리서 보는 것처럼 글자가 개미만 해집니다. width=device-width는 "실제 기기 너비를 기준으로 그려라"는 지시입니다.

🔍 확대를 막지 마세요

user-scalable=no나 maximum-scale=1은 사용자가 손가락으로 확대하는 것을 막습니다. 저시력 사용자에게는 사이트를 못 쓰게 만드는 조치이고, WCAG 위반이기도 합니다. "디자인이 깨져서"는 이유가 되지 않습니다. 확대해도 깨지지 않게 만드는 것이 우리 일입니다. (다행히 iOS Safari는 오래전부터 이 지시를 무시하고 확대를 허용합니다.)

모바일 퍼스트

미디어 쿼리는 두 방향으로 쓸 수 있습니다.

두 가지 방식 
/* ① 데스크톱 퍼스트 — 큰 화면 기본, 작아지면 덮어쓰기 */
.card { width: 33%; }
@media (max-width: 768px) { .card { width: 100%; } }

/* ② 모바일 퍼스트 — 작은 화면 기본, 커지면 덮어쓰기  ← 권장 */
.card { width: 100%; }
@media (min-width: 768px) { .card { width: 33%; } }

📱 모바일 퍼스트가 나은 세 가지 이유

  1. 기본 스타일이 단순해집니다. 좁은 화면은 대부분 "한 줄로 쌓기"라 덮어쓸 것이 적습니다.
  2. 성능. 모바일 기기가 처리해야 할 규칙이 줄어듭니다.
  3. 사고 순서가 맞습니다. 좁은 화면에서 무엇이 진짜 필요한지 먼저 정하면 자연스럽게 우선순위가 잡힙니다. 넓은 화면부터 만들면 "다 넣고 나중에 숨기는" 설계가 되기 쉽습니다.

미디어 쿼리 문법

/* 기본 */
@media (min-width: 768px) { … }

/* 범위 (구문법) */
@media (min-width: 768px) and (max-width: 1023px) { … }

/* 범위 (신문법 — Chrome 104+, Safari 16.4+, Firefox 102+) */
@media (768px <= width < 1024px) { … }

/* 화면 방향 */
@media (orientation: landscape) { … }

/* 인쇄용 */
@media print { .no-print { display: none; } }

/* 마우스처럼 정밀한 입력 장치가 있는가 */
@media (hover: hover) and (pointer: fine) {
  .card:hover { transform: translateY(-4px); }
}

👆 :hover만으로 기능을 만들지 마세요

터치 기기에는 마우스 오버라는 개념이 없습니다. 호버로만 나타나는 메뉴는 휴대폰에서 아예 열 수 없거나, "한 번 눌러야 나타나고 다시 눌러야 이동하는" 이상한 동작이 됩니다. 호버는 보조적인 시각 효과로만 쓰고, 필요한 기능은 클릭·탭으로도 되게 만드세요. 꼭 호버 효과를 주고 싶다면 위 예처럼 @media (hover: hover) 안에 넣습니다.

브레이크포인트 정하기

📏 기기 목록으로 정하지 마세요

나쁜 방식 — "아이폰 15는 393px, 아이패드는 768px이니까…" 기기는 매년 새로 나오고 크기도 제각각입니다. 따라잡을 수 없습니다. 좋은 방식 — 브라우저 창을 천천히 넓혀 보면서 레이아웃이 어색해지는 지점에서 브레이크포인트를 넣습니다. "글줄이 너무 길어졌다", "카드가 찌그러졌다" 하는 그 지점이 정답입니다. 콘텐츠가 브레이크포인트를 정하게 하세요.

그럼에도 팀에 기준이 필요하니, 널리 쓰이는 출발점을 참고할 수는 있습니다. 아래는 Tailwind CSS의 기본값이며 절대적인 기준이 아닙니다.

미디어 쿼리가 필요 없는 경우도 많습니다

현대 CSS에서는 상당수의 반응형이 미디어 쿼리 없이 해결됩니다.

쿼리 없는 반응형 4종 
/* ① 폭 제한 */
.container { width: 100%; max-width: 1200px; margin-inline: auto; padding-inline: 16px; }

/* ② 자동 줄바꿈 격자 (16장) */
.cards { display: grid; grid-template-columns: repeat(auto-fit, minmax(240px, 1fr)); gap: 16px; }

/* ③ 유동 타이포그래피 (14장) */
h1 { font-size: clamp(1.75rem, 4vw, 3rem); }

/* ④ 자동 줄바꿈되는 Flex */
.row { display: flex; flex-wrap: wrap; gap: 16px; }
.row > * { flex: 1 1 260px; }

컨테이너 쿼리

미디어 쿼리에는 근본적인 한계가 있습니다. 화면 크기만 볼 수 있다는 점입니다.

같은 카드 컴포넌트가 넓은 본문 영역에 놓일 때와 좁은 사이드바에 놓일 때는 다르게 보여야 합니다. 하지만 화면 크기는 두 경우 모두 같습니다. 미디어 쿼리로는 이것을 구분할 수 없습니다.

컨테이너 쿼리는 부모 요소의 크기를 기준으로 삼습니다.

/* ① 부모를 "측정 대상"으로 선언 */
.card-wrapper {
  container-type: inline-size;   /* 가로 크기를 기준으로 */
  container-name: card;          /* 이름은 선택 사항 */
}

/* ② 부모 크기에 따라 자식 스타일을 바꾼다 */
@container card (min-width: 400px) {
  .card { display: grid; grid-template-columns: 120px 1fr; gap: 16px; }
}

Chrome 105+, Safari 16+, Firefox 110+에서 지원되어 지금은 실무에서 쓸 수 있습니다.

🧩 왜 이게 중요한가

컴포넌트 기반 개발(React 등)에서는 같은 컴포넌트가 어디에 놓일지 미리 알 수 없습니다. 미디어 쿼리는 "화면이 넓으면"이라고밖에 말할 수 없어서, 컴포넌트가 자기 상황을 스스로 판단할 수 없었습니다. 컨테이너 쿼리는 컴포넌트를 진짜로 독립적으로 만들어 줍니다. CSS에서 가장 오래 요청되어 온 기능이 마침내 실현된 것입니다.

사용자 환경 설정 존중하기

/* 시스템이 다크 모드일 때 */
@media (prefers-color-scheme: dark) {
  :root { --bg: #14161a; --text: #e6e6e4; }
}

/* 동작 줄이기를 켠 사용자 — 전정기관 질환자에게는 실제 어지럼증을 유발합니다 */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

/* 대비 높이기를 켠 사용자 */
@media (prefers-contrast: more) { … }

🌀 prefers-reduced-motion은 선택 사항이 아닙니다

화면이 크게 움직이는 애니메이션은 전정기관 장애가 있는 사람에게 실제로 어지럼증과 메스꺼움을 유발합니다. 취향의 문제가 아닙니다. 운영체제에서 "동작 줄이기"를 켠 사용자에게는 반드시 애니메이션을 줄여야 합니다. 위 코드 블록을 프로젝트 초기 설정에 넣어 두는 것을 권합니다.

터치 대상 크기

손가락은 마우스 포인터보다 훨씬 굵습니다. 작은 버튼은 누르기 어렵고 오작동을 일으킵니다. WCAG 2.2는 터치 대상 최소 크기로 24×24 CSS 픽셀(AA 기준)을 요구하고, 더 높은 수준(AAA)에서는 44×44를 권장합니다. 실무에서는 44px 이상을 목표로 잡는 편이 안전합니다.

.icon-button {
  min-width: 44px;
  min-height: 44px;
  display: grid;
  place-items: center;   /* 아이콘은 작아도 누를 수 있는 영역은 넓게 */
}

🛠️ 현장 노트 — 반응형 점검 순서

  1. 개발자 도구에서 폭을 320px까지 줄여 봅니다. 가로 스크롤이 생기면 어딘가 고정 너비가 있는 것입니다.
  2. 가로 스크롤 범인 찾기: * { outline: 1px solid red; }를 잠깐 넣거나, 콘솔에서 넘치는 요소를 찾습니다.
  3. 글자 크기를 200%로 키워 봅니다. 잘리는 곳이 없어야 합니다.
  4. 실제 휴대폰에서 확인합니다. 시뮬레이터와 실기기는 다릅니다 — 특히 스크롤 감각, 폰트 렌더링, 주소창 동작.

📌 요약

  • 뷰포트 메타 태그가 없으면 모바일에서 축소되어 보인다. 확대는 막지 않는다.
  • 모바일 퍼스트(min-width)가 기본. 코드가 단순해지고 사고 순서가 맞다.
  • 브레이크포인트는 기기 목록이 아니라 콘텐츠가 깨지는 지점으로 정한다.
  • max-width, auto-fit, clamp(), flex-wrap이면 상당수는 미디어 쿼리 없이 해결된다.
  • 컨테이너 쿼리는 화면이 아니라 부모 크기를 본다. 컴포넌트를 진짜 독립적으로 만든다.
  • prefers-reduced-motion은 건강 문제다. 반드시 대응한다.
  • 터치 대상은 44×44px 이상을 목표로.
