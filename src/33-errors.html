try / catch / finally

🧹 finally는 무엇에 쓰나

성공하든 실패하든 반드시 해야 하는 정리 작업에 씁니다. 로딩 스피너 끄기, 버튼 다시 활성화하기, 연결 닫기 같은 것입니다.

setLoading(true);
try {
  const data = await fetchData();
  render(data);
} catch (error) {
  showError(error);
} finally {
  setLoading(false);   // 성공·실패 어느 쪽이든 스피너는 꺼야 합니다
}

내가 만드는 에러

가장 중요한 원칙: 에러를 삼키지 마라

🕳️ 최악의 코드

try {
  doSomething();
} catch (e) {
  // 아무것도 안 함
}

오류가 나도 아무도 모릅니다. 화면은 조용히 잘못된 상태가 되고, 나중에 전혀 다른 곳에서 이상한 증상으로 나타납니다. 버그를 고친 게 아니라 숨긴 것입니다. "일단 오류만 안 나게" 하려고 넣는 이 코드가 디버깅을 몇 배로 어렵게 만듭니다.

catch 안에서 해야 할 일 (최소 하나) 
catch (error) {
  // ① 기록한다 — 개발자가 알 수 있게
  console.error("주문 생성 실패:", error);

  // ② 사용자에게 알린다 — 무엇을 해야 할지 함께
  showToast("주문에 실패했습니다. 잠시 후 다시 시도해 주세요.");

  // ③ 대안을 실행한다
  useCachedData();

  // ④ 처리할 수 없으면 다시 던진다
  throw error;
}

🎯 처리할 수 없으면 던지세요

"여기서 이 에러를 의미 있게 처리할 수 있는가?"를 스스로 물어보세요. 답이 "아니오"라면 try/catch를 쓰지 말고 호출한 쪽으로 올려 보내는 것이 맞습니다. 에러 처리는 그것을 처리할 수 있는 층에서 하는 것이 원칙입니다.

비동기에서의 에러

⏱️ try/catch가 통하지 않는 경우

// ❌ 잡히지 않습니다
try {
  setTimeout(() => {
    throw new Error("나중에 터짐");
  }, 100);
} catch (error) {
  console.log("여기 안 옵니다");
}

// ✅ 콜백 안에서 처리해야 합니다
setTimeout(() => {
  try {
    riskyOperation();
  } catch (error) {
    console.error(error);
  }
}, 100);

try 블록은 그 순간 실행되는 코드만 감쌉니다. setTimeout은 콜백을 예약만 하고 즉시 끝나므로, 100ms 뒤 콜백이 실행될 때는 이미 try 블록을 빠져나온 상태입니다. 35·36장에서 이유를 정확히 다룹니다.

async/await 에서는 정상 동작합니다 (36장) 
async function loadUser(id) {
  try {
    const response = await fetch(`/api/users/${id}`);

    // ⚠️ fetch는 404·500에도 에러를 던지지 않습니다! (37장)
    if (!response.ok) {
      throw new NetworkError(response.status, response.url);
    }
    return await response.json();
  } catch (error) {
    if (error instanceof NetworkError) { /* … */ }
    throw error;   // 처리 못 하면 올려 보냅니다
  }
}

마지막 그물

// 잡히지 않은 동기 에러
window.addEventListener("error", (event) => {
  reportToServer({ message: event.message, source: event.filename });
});

// 잡히지 않은 Promise 거부
window.addEventListener("unhandledrejection", (event) => {
  reportToServer({ reason: String(event.reason) });
});

실제 서비스에서는 Sentry 같은 도구가 이 일을 대신 해 줍니다(79장). 사용자가 겪은 오류를 개발자가 모르는 상태가 가장 위험하기 때문입니다.

🛠️ 현장 노트 — 사용자용 메시지와 개발자용 정보를 분리하세요

catch (error) {
  // 개발자용: 전부 기록
  console.error("[주문 생성]", error);
  reportToSentry(error);

  // 사용자용: 짧고, 다음 행동을 알려 주는 문장
  showToast("주문에 실패했습니다. 잠시 후 다시 시도해 주세요.");
  // ❌ "TypeError: Cannot read properties of undefined" 를 그대로 보여주지 마세요
  // ❌ 서버 내부 경로·SQL·스택 트레이스 노출은 보안 문제이기도 합니다(78장)
}

📌 요약

  • finally는 성공·실패·return 어느 쪽이든 실행된다. 정리 작업에 쓴다.
  • Error는 name·message·stack·cause를 가진다.
  • extends Error로 커스텀 에러를 만들면 종류별 처리가 쉬워진다.
  • 빈 catch는 버그를 숨긴다. 기록·알림·대안·재던짐 중 최소 하나는 해야 한다.
  • 처리할 수 없으면 잡지 말고 올려 보낸다.
  • setTimeout 콜백의 에러는 바깥 try/catch로 잡히지 않는다.
  • window의 error·unhandledrejection으로 마지막 그물을 친다.
  • 사용자에게는 짧고 행동 가능한 문장, 개발자에게는 전체 정보.
