🔄 INP는 FID를 대체했습니다

예전 지표 FID는 첫 상호작용의 지연만 측정했습니다. 그래서 첫 클릭만 빠르면 좋은 점수가 나왔습니다.
INP는 페이지에 머무는 동안의 모든 상호작용을 보고, 반응이 화면에 그려지기까지를 잽니다. 훨씬 정직한 지표입니다. 2024년 3월부터 공식 Core Web Vital이 되었습니다.

LCP 개선

LCP 요소는 대개 큰 이미지나 큰 제목 텍스트입니다. LCP는 네 단계로 나뉘고, 어디가 느린지 알아야 고칠 수 있습니다.

① TTFB          서버가 첫 바이트를 보내기까지
② 자원 로드 지연  브라우저가 그 이미지를 '발견'하기까지
③ 자원 로드 시간  실제 다운로드
④ 렌더링 지연     받고 나서 화면에 그리기까지
원인대응
서버 응답이 느림 (①)캐싱, SSG·ISR(70장), CDN(3장), DB 쿼리 개선
이미지 발견이 늦음 (②)priority·preload(73장). JS로 삽입되는 이미지는 발견이 늦습니다
이미지가 큼 (③)WebP·AVIF, 적절한 크기, srcset(8장)
첫 화면 이미지에 lazy붙이면 안 됩니다(8·73장). 매우 흔한 실수
CSS·폰트가 렌더링을 막음 (④)첫 화면 CSS만 먼저(5장), font-display: swap(19장)
데이터를 받은 뒤에야 그림SSR·SSG로 HTML에 내용을 포함(70장)

INP 개선

INP는 메인 스레드가 막히는 문제입니다(35장). 클릭했을 때 브라우저가 다른 일을 하느라 반응하지 못하는 것입니다.

원인대응
긴 작업 (50ms 초과)쪼개기, Web Worker(40장), 알고리즘 개선
무거운 렌더링useTransition(69장), 가상 스크롤, 구조 개선(64장)
과도한 JS 실행번들 줄이기, 코드 분할(47·68장)
하이드레이션이 오래 걸림서버 컴포넌트로 클라이언트 코드 줄이기(69·71장)
서드파티 스크립트지연 로딩(73장). 범인인 경우가 매우 많습니다
이벤트 핸들러가 무거움디바운스·스로틀(31장), passive: true(38장)

👆 즉시 반응하는 것처럼 보이게

실제 처리가 오래 걸려도 사용자에게 즉시 반응을 보여주면 INP가 좋아집니다.

button.addEventListener("click", async () => {
  setLoading(true);                 // ① 즉시 시각 피드백
  await new Promise(r => setTimeout(r, 0));   // ② 브라우저에 그릴 기회를 줌
  doHeavyWork();                    // ③ 무거운 작업
});

67장의 낙관적 업데이트도 같은 원리입니다. "기다리는 느낌"을 줄이는 것이 실제 속도만큼 중요합니다.

😤 CLS는 사용자를 가장 화나게 합니다

읽던 줄이 갑자기 밀려 내려가고, 누르려던 버튼이 움직여서 광고를 누르게 되는 경험. 숫자로는 0.3 같은 작은 값이지만 체감 불쾌감은 가장 큽니다.
그리고 대부분 쉽게 고칠 수 있습니다. 이미지에 크기를 적는 것만으로 상당 부분 해결됩니다. 투자 대비 효과가 가장 좋은 항목입니다.

JavaScript 줄이기 — 가장 큰 레버

확인 순서 (47장) 
npm run build                    # 라우트별 크기 확인
npx vite-bundle-visualizer       # 무엇이 큰지 시각화
기법효과
라우트별 코드 분할초기 번들이 크게 줄어듭니다(68장)
필요한 것만 importimport * as _ 금지(47장)
무거운 라이브러리 교체날짜 표시는 Intl로 충분한 경우가 많습니다(43장)
서드파티 재검토정말 필요한지 다시 묻기(73장)
서버 컴포넌트해당 코드가 번들에 아예 없습니다(69장)

📉 가장 빠른 코드는 보내지 않은 코드

JS는 다운로드 → 파싱 → 컴파일 → 실행 네 단계를 거칩니다. 같은 100KB라도 이미지보다 JavaScript가 훨씬 비쌉니다. 저사양 기기에서는 이 차이가 몇 배로 벌어집니다.
그래서 번들 크기를 줄이는 것이 프론트엔드 성능 개선에서 가장 큰 레버입니다.

이미지와 캐싱

  • 적절한 크기로 줄이기 — 400px로 보일 것을 4000px로 올리지 않기(8장)
  • WebP·AVIF로 변환
  • 첫 화면 밖은 loading="lazy", 첫 화면은 priority
  • 정적 자원은 길게 캐시 — 해시 파일명이 있으면 1년도 안전합니다(3·47장)
  • CDN으로 거리 지연 줄이기(3장)

숫자를 정해 두면 관리가 됩니다

🚨 CI에서 자동으로 감시하세요

예산이 없으면 성능은 조금씩, 눈치채지 못하게 나빠집니다. 라이브러리 하나, 스크립트 하나씩 늘어나다 어느 날 "왜 이렇게 느리지?"가 됩니다.
CI에 번들 크기 검사나 Lighthouse CI를 붙여 예산을 넘으면 PR을 막으면 됩니다(74장). 사후에 고치는 것보다 늘어나지 않게 막는 것이 훨씬 쉽습니다.

🛠️ 현장 노트 — 최적화 순서

  1. 측정합니다. 실제 사용자 데이터로 "무엇이 문제인가"를 봅니다.
  2. 가장 큰 것부터. 500KB 라이브러리 하나가 나머지 최적화 전부보다 영향이 큽니다.
  3. 하나씩 바꾸고 다시 측정합니다. 여러 개를 동시에 바꾸면 무엇이 효과였는지 모릅니다.
  4. 느린 기기로 테스트합니다. 개발자 컴퓨터는 사용자의 기기가 아닙니다(49장의 CPU 스로틀링).

⚠️ 하지 말아야 할 것

추측으로 최적화 — useMemo를 여기저기 붙이는 것(64장) 미세 최적화 — for가 forEach보다 빠르다는 수준의 논쟁 가독성을 크게 해치는 최적화 — 측정으로 증명되지 않았다면 가장 흔한 진실 — 대부분의 성능 문제는 이미지 하나, 라이브러리 하나, 서드파티 스크립트 하나입니다.

📌 요약

  • LCP 2.5초 · INP 200ms · CLS 0.1이 기준선이다.
  • INP가 FID를 대체했다. 모든 상호작용의 반응성을 본다.
  • 실험실 데이터로 원인을, 실제 사용자 데이터로 진실을 확인한다.
  • LCP: 서버 응답·이미지 최적화·첫 화면 이미지에 lazy 금지.
  • INP: 메인 스레드를 막지 않기. 서드파티 스크립트가 범인인 경우가 많다.
  • CLS: 이미지에 크기 명시가 절반을 해결한다.
  • JavaScript 줄이기가 가장 큰 레버다. 같은 용량이라도 이미지보다 비싸다.
  • 성능 예산을 정하고 CI에서 감시한다.
  • 측정 없이 최적화하지 않는다.
