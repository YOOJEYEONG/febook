시작하기

React 컴포넌트는 결국 JavaScript 함수입니다(58장). 그러니 51장에서 배운 "함수의 매개변수에는 타입을 붙인다"는 원칙이 그대로 적용됩니다. React에서 TypeScript가 특히 빛나는 이유는 컴포넌트가 여러 사람이 가져다 쓰는 부품이기 때문입니다. 가전제품 뒷면의 "220V 전용" 표시처럼, 컴포넌트에 붙은 타입은 쓰는 사람에게 "이렇게 연결하세요"라고 알려 주는 규격표입니다.

npm create vite@latest my-app -- --template react-ts

파일 확장자는 .tsx입니다. JSX가 들어가면 .ts가 아니라 .tsx여야 합니다.

props 타입

props는 부모 컴포넌트가 자식에게 넘기는 값의 묶음입니다(58장). 함수 입장에서는 객체 하나를 매개변수로 받는 것이므로, 그 객체의 모양을 interface로 적어 주면 됩니다. 이렇게 하면 부모 쪽에서 <Button까지 입력했을 때 어떤 props가 필요한지 자동 완성으로 나오고, 필수 prop을 빠뜨리거나 오타를 내면 즉시 빨간 줄이 생깁니다.

interface ButtonProps {
  label: string;
  variant?: "primary" | "secondary";     // 리터럴 유니온 (51장)
  disabled?: boolean;
  onClick: () => void;
}

function Button({ label, variant = "primary", disabled, onClick }: ButtonProps) {
  return (
    <button className={variant} disabled={disabled} onClick={onClick}>
      {label}
    </button>
  );
}

▶ Playground에 붙여 보세요. 아래에 const el = <Button label="저장" />;를 추가하면 "onClick이 빠졌다"는 오류가 나고, variant="tertiary"를 넣으면 허용되지 않은 값이라는 오류가 납니다. 매개변수 자리의 { label, variant = "primary", … }는 구조 분해와 기본값(27·28장)이고, 그 뒤의 : ButtonProps가 타입입니다. variant처럼 ?가 붙은 prop에 기본값을 주면 함수 안에서는 undefined를 걱정하지 않아도 됩니다.

🤔 자주 하는 오해 — props 타입이 실행 중에도 지켜 준다

오해 — props 타입을 적어 두면 부모가 잘못된 값을 넘길 때 브라우저 콘솔에 경고가 뜬다. 사실 — props 타입도 다른 타입처럼 빌드 후 사라집니다(50장). 검사는 편집기와 tsc에서만 일어납니다. 서버에서 받은 값을 그대로 props로 넘기면 타입이 틀려도 화면은 그냥 그려지고 엉뚱한 곳에서 터집니다. 외부 데이터는 컴포넌트에 넘기기 전에 검증합니다(54장).

// ✅ 지금 권장되는 방식 — 그냥 함수로

과거 React.FC는 children을 자동으로 포함해서 받지 않는 컴포넌트에도 허용하는 문제가 있었습니다. 지금은 그 동작이 제거되었지만, 제네릭 컴포넌트를 만들기 불편하고 얻는 이점이 없어 평범한 함수 선언이 표준이 되었습니다.

children

<Card>여기 내용</Card>처럼 여는 태그와 닫는 태그 사이에 넣은 것은 children이라는 이름의 prop으로 전달됩니다. 글자, 다른 컴포넌트, 목록 등 무엇이든 들어올 수 있으므로 "화면에 그릴 수 있는 모든 것"을 뜻하는 React.ReactNode를 씁니다.

interface CardProps {

function Card({ title, children }: CardProps) {

이벤트 핸들러

이벤트 핸들러는 51장의 문맥 기반 추론이 가장 빛나는 곳입니다. JSX 안에 핸들러를 바로 적으면 React의 타입 정의가 "onSubmit에는 이런 이벤트가 온다"는 것을 이미 알고 있어 타입을 채워 줍니다. 타입을 직접 적어야 하는 것은 핸들러를 밖으로 꺼내 이름 붙인 함수로 만들 때뿐입니다.

function Form() {
  // 인라인이면 타입이 자동 추론됩니다 — 이게 가장 편합니다
  return (
    <form onSubmit={(event) => {
      event.preventDefault();      // ✅ event 타입을 이미 알고 있습니다
    }}>
      <input onChange={(event) => console.log(event.target.value)} />
    </form>
  );
}

// 함수를 밖으로 빼면 타입을 명시해야 합니다
function handleSubmit(event: React.SubmitEvent<HTMLFormElement>) {
  event.preventDefault();
}
function handleChange(event: React.ChangeEvent<HTMLInputElement>) {
  console.log(event.target.value);
}
function handleClick(event: React.MouseEvent<HTMLButtonElement>) { }
function handleKey(event: React.KeyboardEvent<HTMLInputElement>) {
  if (event.key === "Enter") { }
}

타입 이름이 기억나지 않으면 인라인으로 먼저 써 보고 event에 마우스를 올리세요. 편집기가 정확한 타입 이름을 알려 줍니다. 꺾쇠 안의 HTMLInputElement는 "이 이벤트가 붙은 요소의 종류"로, 그래서 event.target.value를 문자열로 안전하게 읽을 수 있습니다.

📅 폼 제출 이벤트 타입이 바뀌었습니다

예전 자료와 블로그 글에는 React.FormEvent<HTMLFormElement>가 나옵니다. 2026년 1월의 @types/react 19.2.10부터 FormEvent는 사용 중단(deprecated) 표시가 붙었고, onSubmit에는 React.SubmitEvent를 쓰도록 바뀌었습니다. 기존 코드도 당장은 동작하지만 편집기에 취소선이 그어집니다. 입력값 변경은 이전과 같이 React.ChangeEvent입니다.

💡 props로 받는 핸들러 타입

interface Props {
  onClick: () => void;                                    // 인자 없음 — 가장 흔함
  onChange: (value: string) => void;                      // 가공된 값을 넘길 때
  onSubmit: (event: React.SubmitEvent) => void;           // 이벤트 그대로
  onSelect: (id: number, name: string) => void;           // 여러 값
}

가능하면 이벤트 객체를 그대로 넘기지 마세요. onChange: (value: string) => void처럼 의미 있는 값을 넘기면 컴포넌트를 쓰는 쪽이 훨씬 편하고, 나중에 내부 구현을 바꾸기도 쉽습니다.

훅의 타입

훅은 53장에서 배운 제네릭 함수입니다. useState<T>의 T는 상태의 타입이고, 대부분은 초기값에서 추론됩니다. 문제는 초기값이 "아직 비어 있음"을 뜻할 때입니다. null이나 빈 배열만 보고는 나중에 무엇이 들어올지 알 수 없으므로, 그때만 꺾쇠로 직접 알려 줍니다.

const [items, setItems] = useState<string[]>([]);
//                               ↑ 없으면 never[] — 아무것도 넣을 수 없는 배열 (50장)

React 19부터 useRef는 인자가 반드시 필요하고, 돌려받은 current는 용도와 관계없이 직접 바꿀 수 있습니다. 예전 자료에서 "DOM용 ref는 읽기 전용(RefObject), 값 저장용은 MutableRefObject"라고 구분하던 것은 React 18까지의 타입 이야기입니다. DOM ref의 current는 요소가 화면에 붙기 전에는 null이므로 ?.로 확인하는 습관은 그대로 필요합니다.

useReducer — 판별 유니온과 함께 (52장) 
type State = { count: number; step: number };

type Action =
  | { type: "increment" }
  | { type: "decrement" }
  | { type: "setStep"; step: number }
  | { type: "reset" };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "increment": return { ...state, count: state.count + state.step };
    case "decrement": return { ...state, count: state.count - state.step };
    case "setStep":   return { ...state, step: action.step };   // ✅ step 존재 보장
    case "reset":     return { count: 0, step: 1 };
  }
}

const [state, dispatch] = useReducer(reducer, { count: 0, step: 1 });
dispatch({ type: "setStep", step: 5 });    // ✅
dispatch({ type: "setStep" });              // ❌ step 누락을 잡아 줍니다

useReducer는 상태를 바꾸는 "명령"을 객체로 보내는 방식입니다(65장에서 자세히 다룹니다). 명령의 종류를 판별 유니온으로 적어 두면 type마다 어떤 값이 함께 와야 하는지 TypeScript가 강제하므로, 명령을 잘못 보내는 실수가 사라집니다. 54장의 never 검사를 default에 추가하면 새 명령을 만들고 처리를 빠뜨리는 실수도 잡을 수 있습니다.

function useToggle(initial = false) {

HTML 속성 물려받기

버튼 컴포넌트를 만들었는데 누군가 type="submit"을, 또 누군가 aria-label을 넘기고 싶어 합니다. 그때마다 props에 하나씩 추가하면 끝이 없습니다. HTML <button>이 받을 수 있는 속성 목록은 이미 React 타입에 정의되어 있으니, 그 목록을 통째로 물려받고 내 것만 더하면 됩니다. 52장의 extends가 여기서 쓰입니다.

// button이 받을 수 있는 모든 속성을 그대로 지원하고 싶을 때
interface ButtonProps extends React.ComponentProps<"button"> {
  variant?: "primary" | "secondary";
}

function Button({ variant = "primary", className, ...rest }: ButtonProps) {
  return <button className={`btn btn-${variant} ${className ?? ""}`} {...rest} />;
}

// 이제 이런 것들이 전부 됩니다
<Button type="submit" disabled aria-label="저장" onClick={fn} />

이렇게 하지 않으면 aria-label이 필요할 때마다 컴포넌트를 고쳐야 합니다. ComponentProps<"button">을 확장하면 접근성 속성·데이터 속성·이벤트 핸들러가 전부 자동으로 지원됩니다. 63장의 컴포넌트 설계와 직결되는 내용입니다.

제네릭 컴포넌트

컴포넌트도 함수이므로 53장의 제네릭을 그대로 쓸 수 있습니다. 드롭다운 목록처럼 어떤 데이터를 넣어도 같은 모양으로 동작하는 컴포넌트가 대상입니다. 회원 목록을 넣으면 선택 결과도 회원으로, 상품 목록을 넣으면 상품으로 돌아오게 만들 수 있습니다.

interface SelectProps<T> {
  options: T[];
  value: T;
  onChange: (value: T) => void;
  getLabel: (option: T) => string;
  getKey: (option: T) => string;
}

function Select<T>({ options, value, onChange, getLabel, getKey }: SelectProps<T>) {
  return (
    <select
      value={getKey(value)}
      onChange={(e) => {
        const found = options.find(o => getKey(o) === e.target.value);
        if (found) onChange(found);
      }}
    >
      {options.map(option => (
        <option key={getKey(option)} value={getKey(option)}>
          {getLabel(option)}
        </option>
      ))}
    </select>
  );
}

// 사용할 때 T가 자동으로 추론됩니다
<Select
  options={users}
  value={selectedUser}
  onChange={setSelectedUser}       // ✅ (user: User) => void 임을 압니다
  getLabel={u => u.name}           // ✅ u는 User
  getKey={u => String(u.id)}
/>

options에 넘긴 배열의 요소 타입이 T가 되고, 그 T가 value·onChange·getLabel에 모두 전달됩니다. 53장의 "T가 두 곳 이상을 연결한다"는 원칙이 컴포넌트에서도 똑같이 적용되는 것입니다. 지금 이 코드를 전부 이해할 필요는 없습니다. 63장에서 재사용 컴포넌트를 설계할 때 다시 돌아오면 됩니다.

🛠️ 현장 노트

  1. 대부분은 추론에 맡기세요. React + TypeScript는 추론이 꽤 좋습니다. useState·이벤트 핸들러·map 콜백은 대개 안 써도 됩니다.
  2. props 타입은 반드시 씁니다. 컴포넌트의 사용 설명서 역할을 합니다.
  3. 리터럴 유니온을 적극 쓰세요. variant: string보다 variant: "primary" | "secondary"가 훨씬 유용합니다.
  4. 막히면 React TypeScript Cheatsheet를 보세요. 거의 모든 상황의 예제가 정리되어 있습니다.
  5. React 19부터 forwardRef가 필요 없어졌습니다. 함수 컴포넌트가 ref를 일반 prop으로 받을 수 있습니다. 옛 자료에서 forwardRef를 보면 이 변화를 떠올리세요.

📌 요약

  • JSX가 있는 파일은 .tsx.
  • React.FC 대신 평범한 함수 선언을 쓴다.
  • children은 React.ReactNode.
  • 인라인 이벤트 핸들러는 타입이 자동 추론된다. 밖으로 빼면 명시한다. 폼 제출은 React.SubmitEvent.
  • props 타입도 빌드 후 사라진다. 외부 데이터는 넘기기 전에 검증한다.
  • useState([])·useState(null)은 제네릭을 명시해야 한다.
  • 커스텀 훅이 배열을 반환하면 as const를 붙인다.
  • ComponentProps<"button"> 확장으로 HTML 속성을 전부 지원한다.
  • props 타입은 컴포넌트의 문서다. 리터럴 유니온을 적극 활용한다.
