인증과 인가 — 신분 확인과 출입 권한

둘은 이름이 비슷해서 자주 섞이지만, 하는 일이 다릅니다.

인증 (Authentication)인가 (Authorization)

로그인은 실제로 무슨 일을 하나

HTTP는 상태가 없습니다(4장). 서버는 방금 요청을 보낸 사람이 1초 전에 로그인한 그 사람인지 기억하지 못합니다. 그래서 로그인의 본질은 "비밀번호를 한 번 확인하고, 그 뒤로는 비밀번호 대신 쓸 출입증을 발급하는 것"입니다.

로그인 한 번과 그 이후 
[브라우저]                                  [서버]
  │ ① POST /login  {email, password}        │
  │ ──────────────────────────────────────▶ │ 비밀번호 해시 비교
  │                                         │ 맞으면 출입증 발급
  │ ② 200 OK + Set-Cookie: session=…        │
  │ ◀────────────────────────────────────── │
  │                                         │
  │ ③ GET /api/me   (쿠키 자동 첨부)         │
  │ ──────────────────────────────────────▶ │ 출입증 검사 → 누구인지 앎
  │ ④ 200 OK {name: "민지"}                 │
  │ ◀────────────────────────────────────── │

비밀번호는 ①에서 딱 한 번만 오갑니다. 이후 모든 요청은 출입증(세션 ID 또는 토큰)으로 신원을 증명합니다. 그래서 출입증을 도둑맞는 것 = 계정을 도둑맞는 것이고, 이 챕터의 보안 이야기는 대부분 "출입증을 어떻게 지키나"로 모입니다.

세션 쿠키 방식 vs 토큰 방식 — 실무에서 고르기

원리 비교는 89장에 있으니, 여기서는 구현할 때 무엇이 달라지는지에 집중합니다.

세션 쿠키토큰(JWT) + 리프레시
출입증의미 없는 긴 난수(세션 ID). 정보는 서버 DB에서명된 토큰. 사용자 ID·만료 시각이 안에 들어 있음
프론트 코드거의 없음. 쿠키가 자동 전송만료 처리·갱신 로직이 필요 (아래 리프레시)
강제 로그아웃서버에서 세션 삭제 → 즉시액세스 토큰은 만료까지 유효 → 짧게(수 분~수십 분) 잡음
잘 맞는 곳웹 하나, 같은 도메인의 서버모바일 앱·여러 서비스가 같은 인증을 공유
CSRF대비 필요 (SameSite, CSRF 토큰)쿠키에 담으면 똑같이 필요, 헤더로 보내면 불필요

🤔 "JWT를 쓰면 쿠키를 안 쓴다"는 오해

JWT는 출입증의 형식이고, 쿠키는 출입증을 담는 봉투입니다. 둘은 경쟁 관계가 아닙니다. 웹에서 가장 흔한 안전한 조합은 "JWT를 HttpOnly 쿠키에 담기"입니다. 반대로 "JWT를 localStorage에 넣고 Authorization 헤더로 보내기"는 튜토리얼에 많지만, XSS 한 번에 토큰이 통째로 유출되는 구조입니다(78장, 89장).

그래서 어디에 두나 — 결론만

  • 리프레시 토큰·세션 ID: 반드시 HttpOnly; Secure; SameSite=Lax 쿠키. JavaScript가 읽을 수 없어야 합니다.
  • 액세스 토큰을 굳이 JavaScript로 다뤄야 한다면 메모리(변수)에만 둡니다. 새로고침하면 사라지지만 리프레시 쿠키로 다시 받으면 됩니다.
  • 사용자 표시용 정보(이름, 프로필 사진)는 /api/me 같은 API로 받아 상태에 둡니다. 이건 비밀이 아닙니다.

쿠키는 서버가 Set-Cookie로 설정합니다. 프론트엔드가 document.cookie로 만든 쿠키에는 HttpOnly를 붙일 수 없습니다. 그래서 이 결정은 늘 백엔드와 함께 내립니다.

로그인 폼 만들기

62장의 폼 기술을 그대로 씁니다. 로그인 폼에서 특히 챙길 것은 로딩 중 중복 제출 막기, 에러를 화면과 스크린 리더에 모두 알리기, 브라우저 비밀번호 관리자가 알아보게 하기입니다.

LoginForm.jsx — 클라이언트에서 API를 부르는 방식 
function LoginForm({ onSuccess }) {
  const [status, setStatus] = useState("idle");   // idle | loading | error
  const [error, setError] = useState("");

  async function handleSubmit(e) {
    e.preventDefault();
    if (status === "loading") return;               // 중복 제출 방지
    const { email, password } = Object.fromEntries(new FormData(e.currentTarget));

    setStatus("loading");
    setError("");
    try {
      const res = await fetch("/api/login", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        credentials: "include",                       // 쿠키를 주고받기 (37장)
        body: JSON.stringify({ email, password }),
      });
      if (res.status === 401) throw new Error("이메일 또는 비밀번호가 올바르지 않습니다.");
      if (!res.ok) throw new Error("잠시 후 다시 시도해 주세요.");
      onSuccess(await res.json());                    // { user: { id, name } }
    } catch (err) {
      setError(err.message);
      setStatus("error");
    }
  }

  const loading = status === "loading";
  return (
    <form onSubmit={handleSubmit}>
      <label htmlFor="email">이메일</label>
      <input id="email" name="email" type="email" required
             autoComplete="username"
             aria-invalid={status === "error"}
             aria-describedby={error ? "login-error" : undefined} />

      <label htmlFor="password">비밀번호</label>
      <input id="password" name="password" type="password" required
             autoComplete="current-password"
             aria-invalid={status === "error"}
             aria-describedby={error ? "login-error" : undefined} />

      {error && <p id="login-error" role="alert">{error}</p>}

      <button type="submit" disabled={loading} aria-busy={loading}>
        {loading ? "로그인 중…" : "로그인"}
      </button>
    </form>
  );
}
코드이유
autoComplete="username", "current-password"비밀번호 관리자가 칸을 정확히 채웁니다. 회원가입 폼이면 "new-password"
role="alert"에러가 나타나는 순간 스크린 리더가 읽어 줍니다(77장)
aria-describedby입력 칸에 초점이 가면 어떤 에러인지 함께 읽힙니다
disabled + 문구 변경더블 클릭으로 요청이 두 번 가는 것을 막고, 진행 중임을 보여 줍니다
401과 그 외 에러를 나눔"비밀번호가 틀렸다"와 "서버가 아프다"는 사용자가 할 일이 다릅니다

🕵️ "이메일이 없습니다" vs "비밀번호가 틀렸습니다"

둘을 구분해서 알려 주면 친절해 보이지만, 공격자에게 "이 이메일은 가입되어 있다"는 정보를 줍니다. 로그인 실패 메시지는 "이메일 또는 비밀번호가 올바르지 않습니다"처럼 하나로 묶는 것이 OWASP 권장입니다. 또 비밀번호 칸에 onPaste를 막지 마세요. 비밀번호 관리자 사용을 방해해 오히려 약한 비밀번호를 부추깁니다.

Next.js를 쓴다면 같은 폼을 Server Action + useActionState로 만들 수도 있습니다(72장). 이때는 쿠키 설정까지 서버 코드 안에서 끝나서, 브라우저 JavaScript는 토큰을 한 번도 만지지 않습니다.

로그인 상태를 앱 전체에 알리기

헤더의 "로그인/로그아웃" 버튼, 마이페이지, 장바구니가 모두 "지금 누가 로그인했나"를 알아야 합니다. 65장의 Context가 딱 맞는 자리입니다.

AuthProvider.jsx — 토큰이 아니라 "사용자 정보"를 공유합니다 
const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const [checking, setChecking] = useState(true);   // 첫 확인 전에는 "모름"

  useEffect(() => {
    // 새로고침 직후: 쿠키가 살아 있는지 서버에 물어봅니다
    fetch("/api/me", { credentials: "include" })
      .then(res => (res.ok ? res.json() : null))
      .then(data => setUser(data?.user ?? null))
      .finally(() => setChecking(false));
  }, []);

  const value = { user, checking, setUser };
  return <AuthContext value={value}>{children}</AuthContext>;
}

export const useAuth = () => use(AuthContext);

⏳ 상태는 셋입니다: 로그인됨 · 안 됨 · 아직 모름

checking 없이 user === null만 보면, 새로고침 직후 0.2초 동안 "로그인하세요" 화면이 번쩍였다가 사라집니다. 확인 중에는 스켈레톤이나 빈 자리를 보여 주세요. 과제 리뷰에서 자주 지적되는 부분입니다.

보호 라우트 — Next.js 16 App Router

"로그인한 사람만 /dashboard에 들어올 수 있게"를 구현합니다. 아래 코드는 Next.js 16 기준, nextjs.org 공식 인증 가이드(2026년 9월 갱신본)의 구조를 따릅니다. Next.js 16부터 예전 middleware.ts는 proxy.ts로 이름이 바뀌었고, 내보내는 함수 이름도 proxy입니다.

공식 가이드는 검사를 두 겹으로 나눕니다.

낙관적 검사 (proxy.ts)확실한 검사 (데이터 접근 계층)
하는 일쿠키만 읽고 없으면 /login으로 돌려보냄세션을 검증하고, 필요하면 DB까지 확인한 뒤 데이터를 줌
언제모든 요청(프리페치 포함) 앞에서데이터를 읽거나 바꾸기 직전
주의DB 조회 금지 — 너무 자주 실행됨여기가 진짜 방어선
proxy.ts — 프로젝트 루트(또는 src/)에 둡니다 
import { NextRequest, NextResponse } from "next/server";
import { decrypt } from "@/app/lib/session";

const protectedRoutes = ["/dashboard"];
const publicRoutes = ["/login", "/signup", "/"];

export default async function proxy(req: NextRequest) {
  const path = req.nextUrl.pathname;
  const isProtected = protectedRoutes.some(p => path.startsWith(p));
  const isPublic = publicRoutes.includes(path);

  // 쿠키에서 세션을 꺼내 서명만 확인 (DB는 보지 않습니다)
  const session = await decrypt(req.cookies.get("session")?.value);

  if (isProtected && !session?.userId) {
    const url = new URL("/login", req.nextUrl);
    url.searchParams.set("next", path);            // 로그인 후 돌아올 곳
    return NextResponse.redirect(url);
  }
  if (isPublic && session?.userId && path !== "/") {
    return NextResponse.redirect(new URL("/dashboard", req.nextUrl));
  }
  return NextResponse.next();
}

// 정적 파일과 API에는 실행하지 않습니다
export const config = {
  matcher: ["/((?!api|_next/static|_next/image|.*\\.png$).*)"],
};
app/lib/dal.ts — 데이터 접근 계층(DAL) 
import "server-only";                       // 클라이언트 번들에 섞이면 빌드 에러
import { cache } from "react";
import { cookies } from "next/headers";
import { redirect } from "next/navigation";
import { decrypt } from "@/app/lib/session";

export const verifySession = cache(async () => {
  const cookie = (await cookies()).get("session")?.value;   // cookies()는 비동기
  const session = await decrypt(cookie);
  if (!session?.userId) redirect("/login");
  return { userId: session.userId, role: session.role };
});
app/dashboard/page.tsx — 서버 컴포넌트에서 확인 
import { verifySession } from "@/app/lib/dal";

export default async function DashboardPage() {
  const { userId } = await verifySession();     // 로그인 안 했으면 여기서 redirect
  const orders = await getOrders(userId);       // 내 데이터만 조회
  return <OrderList orders={orders} />;
}

🧱 레이아웃에서만 검사하면 뚫립니다

  • 공식 가이드는 레이아웃(layout.tsx)에서 인증을 검사하지 말라고 경고합니다. 레이아웃은 페이지 이동 때 다시 렌더링되지 않고, 레이아웃이 자식을 숨겨도 하위 세그먼트는 그대로 실행되기 때문입니다.
  • proxy.ts만 믿어도 안 됩니다. Server Action과 Route Handler는 공개 API와 같습니다(72장). 각각 안에서 verifySession()을 다시 불러야 합니다.
  • 원칙: 검사는 데이터에 가장 가까운 곳에서. DAL 함수를 거치지 않고는 데이터를 못 읽게 만들면, 누가 검사를 깜빡해도 안전합니다.

React만 쓰는 SPA(68장의 React Router)라면 "로그인 안 했으면 <Navigate to="/login" />"로 감싸는 컴포넌트를 만듭니다. 이건 사용자 경험을 위한 안내일 뿐이고, 실제 보호는 API 서버가 401·403을 돌려주는 것으로 이루어집니다.

액세스 토큰 만료와 리프레시

토큰 방식에서는 보통 두 개의 토큰을 씁니다.

  • 액세스 토큰 — API를 부를 때 쓰는 출입증. 도둑맞아도 피해가 짧도록 수 분~수십 분만 유효합니다.
  • 리프레시 토큰 — 새 액세스 토큰을 받는 데만 쓰는 열쇠. 며칠~몇 주 유효하고, HttpOnly 쿠키에 담아 갱신 API에만 보냅니다.
만료 → 갱신 → 재요청 
GET /api/orders  (액세스 토큰 A, 만료됨)
   ◀── 401 Unauthorized
POST /api/refresh (리프레시 쿠키 자동 첨부)
   ◀── 200 { accessToken: B }         ← 새 토큰
GET /api/orders  (액세스 토큰 B)       ← 원래 요청을 다시
   ◀── 200 [ … ]

리프레시도 401이면 → 진짜 로그아웃 상태 → /login 으로

동시 요청이 함께 401을 받으면

대시보드는 보통 주문·알림·프로필을 동시에 요청합니다. 토큰이 만료된 순간이라면 셋 다 401을 받고, 순진하게 짜면 갱신 요청도 세 번 나갑니다. 서버가 리프레시 토큰 회전(한 번 쓴 리프레시 토큰은 폐기하고 새로 발급)을 쓰면 두 번째, 세 번째 갱신은 이미 폐기된 토큰을 내밀게 되어 사용자가 강제로 로그아웃됩니다.

해법은 진행 중인 갱신 Promise를 하나만 두고 모두가 그것을 기다리게 하는 것입니다(36장의 Promise 공유). 아래 실행기에서 직접 확인해 보세요. 네트워크는 쓰지 않고, 가짜 서버 함수와 가짜 시계로 흉내 냅니다.

SINGLE_FLIGHT = true면 갱신은 1번이고 세 요청 모두 성공합니다. false로 바꾸면 갱신이 3번 나가고, 두 번째부터는 이미 회전된 토큰이라 거절되어 로그아웃됩니다. 실무에서는 이 로직을 fetch 래퍼나 axios 인터셉터 한 곳에 넣어 두고, 컴포넌트는 apiFetch만 부릅니다.

🛠️ 현장 노트 — 갱신 로직에서 자주 나는 버그

  • 무한 루프: 갱신 API 자체가 401을 받았는데 또 갱신을 시도. 갱신 요청은 래퍼를 거치지 않게 하거나 재시도는 한 번만.
  • 401과 403 혼동: 403은 "로그인은 됐지만 권한 없음"입니다. 갱신해도 결과가 같으니 갱신하지 말고 "권한이 없습니다"를 보여 주세요.
  • 탭이 여러 개: 다른 탭에서 로그아웃했는데 이 탭은 모름. BroadcastChannel이나 storage 이벤트(39장)로 "로그아웃됨" 신호만 공유하는 방법이 있습니다.

로그아웃은 세 군데를 지웁니다

  1. 서버: 세션을 삭제하거나 리프레시 토큰을 폐기합니다. POST /api/logout (상태를 바꾸므로 GET이 아닙니다).
  2. 쿠키: 서버가 Set-Cookie로 만료시킵니다. Next.js라면 Server Action 안에서 (await cookies()).delete("session") 후 redirect("/login").
  3. 클라이언트 상태: 메모리의 액세스 토큰, Context의 user, 그리고 서버 상태 캐시(67장의 TanStack Query 등)를 비웁니다. 캐시를 안 비우면 다음에 로그인한 사람에게 이전 사람의 데이터가 잠깐 보일 수 있습니다.

OAuth 2.0과 소셜 로그인

"구글로 로그인"은 우리 서비스가 비밀번호를 받지 않고, 구글에게 "이 사람이 맞는지 확인해 줘"라고 맡기는 방식입니다. 엄밀히 OAuth 2.0은 권한 위임(내 구글 캘린더를 이 앱이 읽어도 됨) 규격이고, 그 위에 로그인(신원 확인)을 얹은 것이 OpenID Connect(OIDC)입니다. 소셜 로그인은 대부분 OIDC입니다.

인가 코드 + PKCE 흐름 (가장 권장되는 방식) 
사용자        우리 앱(브라우저)          우리 서버            구글(인가 서버)
  │ "구글로 로그인" 클릭 │                      │                     │
  │ ───────────────────▶│ ① code_verifier 생성 │                     │
  │                     │   challenge = 해시(verifier)                │
  │                     │ ② 구글 로그인 페이지로 이동 ───────────────▶│
  │                     │   ?client_id&redirect_uri&state&code_challenge
  │ ◀──────────────────────────── ③ 구글 화면에서 로그인·동의 ─────────│
  │                     │ ④ redirect_uri?code=XYZ&state=… ◀──────────│
  │                     │ ⑤ state 확인 후 code 전달 ▶│                 │
  │                     │                      │ ⑥ code + verifier ─▶│
  │                     │                      │ ◀─ ⑦ 토큰(ID 토큰 등)│
  │                     │ ◀─ ⑧ 우리 세션 쿠키 발급 │                     │
  • state: 출발할 때 만든 난수를 돌아왔을 때 비교합니다. 공격자가 자기 계정의 code를 우리 사용자에게 밀어 넣는 CSRF를 막습니다.
  • code: URL로 돌아오는 것은 토큰이 아니라 한 번 쓰고 버리는 교환권입니다. 진짜 토큰은 ⑥⑦에서 서버끼리 주고받습니다.
  • ⑧이 핵심입니다. 구글 토큰을 브라우저에 그대로 두지 말고, 우리 서비스의 세션으로 바꿔서 앞에서 배운 방식대로 관리합니다.

PKCE — 교환권을 가로채도 못 쓰게

PKCE(Proof Key for Code Exchange, "픽시")는 ①에서 비밀 문자열(code_verifier)을 만들고, 그 해시값(code_challenge)만 구글에 먼저 보내 두는 장치입니다. 나중에 code를 토큰으로 바꿀 때 원래 비밀 문자열을 내밀어야 하므로, 중간에 누군가 code를 가로채도 비밀 문자열이 없어 토큰을 받을 수 없습니다. 원래는 비밀 키를 안전하게 숨길 수 없는 모바일 앱·SPA를 위해 만들어졌지만(RFC 7636), 현재 OAuth 보안 권고(RFC 9700)는 모든 클라이언트에 PKCE를 쓰라고 합니다. 예전 SPA에서 쓰던 암시적 흐름(Implicit, URL에 토큰을 바로 받음)은 더 이상 권장되지 않습니다.

직접 만들까, 라이브러리를 쓸까

Next.js 공식 가이드도 직접 구현 예제는 교육용이라고 밝히고, 실서비스에는 인증 라이브러리를 권합니다. 선택지는 크게 오픈소스 라이브러리(Auth.js, Better Auth 등 — 내 서버·DB에서 동작)와 호스팅형 인증 서비스(Clerk, Auth0, Supabase Auth 등 — 사용자 데이터를 외부가 보관)로 나뉩니다. 특정 제품보다 아래 질문으로 고르세요.

질문"예"라면
이메일 인증, 비밀번호 재설정, 소셜 로그인 여러 개, 2단계 인증이 필요한가?직접 만들 양이 매우 많습니다 → 라이브러리·서비스

흔한 보안 실수

🙈 "관리자 버튼을 숨겼으니 안전하다"

프론트에서 {user.role === "admin" && <DeleteButton />}로 버튼을 숨기는 것은 화면 정리일 뿐입니다. 누구나 개발자 도구나 curl로 DELETE /api/users/42를 직접 보낼 수 있습니다(78장의 첫 번째 원칙). 서버가 요청마다 "이 사람이 이걸 해도 되나"를 확인해야 하고, 남의 글 ID를 넣어 보는 공격(IDOR)까지 막아야 합니다. 프론트의 권한 검사는 사용자 경험, 서버의 권한 검사는 보안입니다.

🔗 토큰을 URL에 넣지 마세요

/reset?token=…, /dashboard?access_token=…처럼 URL에 들어간 값은 브라우저 기록, 서버 접속 로그, 분석 도구, 다른 사이트로 가는 Referer 헤더, 공유한 스크린샷에 그대로 남습니다. 액세스 토큰은 쿠키나 헤더로만 보냅니다. 비밀번호 재설정 링크처럼 URL이 불가피하면 한 번만 쓰고 짧게 만료되게 하고, 페이지에 Referrer-Policy: no-referrer를 둡니다(78장).

🍪 쿠키로 바꿨다면 CSRF도 같이

HttpOnly 쿠키로 XSS 위험을 줄이면, 대신 쿠키가 자동 전송되어 CSRF 문이 열립니다(78장). SameSite=Lax, 상태 변경은 GET 금지, 필요하면 CSRF 토큰. 로그인·로그아웃 요청도 예외가 아닙니다. Next.js Server Action은 요청의 Origin과 호스트를 비교하는 기본 방어가 있지만, 직접 만든 Route Handler는 스스로 챙겨야 합니다.

🔍 "JWT 안에 있으니 프론트에서 만료를 믿고 판단해도 된다"

프론트에서 JWT를 열어 exp를 보고 미리 갱신하는 것은 괜찮은 최적화입니다. 하지만 그 내용으로 권한을 결정하면 안 됩니다. 서명 검증은 비밀 키를 가진 서버만 할 수 있고, 사용자 컴퓨터의 시계는 틀릴 수 있습니다. 최종 판단은 늘 서버의 401·403입니다.

📌 요약

  • 인증은 누구인지(401), 인가는 해도 되는지(403). 로그인은 비밀번호를 한 번 확인하고 출입증을 발급하는 일이다.
  • JWT는 출입증의 형식, 쿠키는 봉투다. 웹에서는 HttpOnly; Secure; SameSite 쿠키에 담는 것이 기본이다.
  • 로그인 폼은 중복 제출 방지, role="alert" 에러, autoComplete를 챙긴다. 전역 상태에는 토큰이 아니라 사용자 정보를, 그리고 "아직 모름" 상태를 둔다.
  • Next.js 16은 proxy.ts로 낙관적 검사, DAL의 verifySession()으로 확실한 검사를 한다. 레이아웃만으로 보호하지 않는다.
  • 401이면 갱신은 한 번만(진행 중 Promise 공유), 재시도도 한 번만. 갱신까지 실패하면 로그인 화면으로.
  • 로그아웃은 서버 세션 · 쿠키 · 클라이언트 캐시 세 곳을 지운다.
  • 소셜 로그인은 인가 코드 + PKCE, state로 CSRF 방지. 받은 토큰은 우리 세션으로 바꿔 관리한다.
  • 프론트의 권한 검사는 UX일 뿐, 보안은 서버. 토큰을 URL에 넣지 않는다.
