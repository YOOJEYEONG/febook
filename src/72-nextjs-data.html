📅 캐싱 기본값은 버전마다 다릅니다

Next.js의 캐싱 동작은 메이저 버전마다 크게 바뀌어 왔습니다. 초기 App Router는 fetch를 기본으로 캐시했지만 이후 기본을 캐시하지 않는 쪽으로 바뀌었고, 최신 버전에서는 use cache 같은 명시적 캐시 지시어 방향으로 정리되고 있습니다.
따라서 "기본값이 무엇인지"를 외우지 마세요. 개념(무엇을 캐시할 수 있고, 언제 무효화하는가)을 이해하고 기본값은 여러분이 쓰는 버전의 문서에서 확인하는 것이 옳습니다.

읽는 데 약 24분

서버에서 데이터 가져오기

// 서버 컴포넌트는 async 함수가 될 수 있습니다 (69장)
export default async function ProductPage({ params }) {
  const { id } = await params;

  // ① 외부 API
  const res = await fetch(`https://api.example.com/products/${id}`);
  if (!res.ok) throw new Error("불러오기 실패");     // error.tsx가 잡습니다
  const product = await res.json();

  // ② 또는 DB 직접 조회
  // const product = await db.product.findUnique({ where: { id } });

  return <h1>{product.name}</h1>;
}

✨ 이것이 얼마나 단순해진 것인지

61장에서 본 useEffect 페칭과 비교해 보세요. useState도, useEffect도, 로딩 상태도, 경쟁 상태 처리도 없습니다. 그냥 await입니다. 로딩은 loading.tsx가, 오류는 error.tsx가 처리합니다(71장).
게다가 API 키가 브라우저로 가지 않고, 서버-DB 간 통신이라 왕복이 짧습니다.

캐싱 개념

Next.js는 여러 층의 캐시를 씁니다. 층마다 목적이 다릅니다.

층저장하는 것목적
데이터 캐시fetch·DB 조회 결과같은 데이터를 반복 조회하지 않기
전체 라우트 캐시렌더링된 HTML정적 페이지를 즉시 응답(SSG·ISR, 70장)
요청 메모이제이션같은 요청 중의 동일 호출한 렌더링 안에서 중복 호출 제거
라우터 캐시방문한 페이지뒤로 가기를 즉시 표시

♻️ 요청 메모이제이션이 주는 자유

// 같은 렌더링 안에서 세 컴포넌트가 각자 호출해도
// 실제 요청은 한 번만 나갑니다
async function Header()  { const user = await getUser(); /* … */ }
async function Sidebar() { const user = await getUser(); /* … */ }
async function Profile() { const user = await getUser(); /* … */ }

그래서 데이터를 props로 계속 내려보낼 필요가 없습니다. 필요한 컴포넌트가 각자 가져오면 됩니다. 63장의 props drilling 문제가 서버 컴포넌트에서는 다른 방식으로 해결됩니다.

재검증

① 시간 기반 — ISR과 같은 개념 (70장) 
// 페이지 단위
export const revalidate = 3600;    // 1시간마다 갱신

// 또는 fetch 단위
await fetch(url, { next: { revalidate: 60 } });
② 온디맨드 — 바뀐 순간 갱신 
import { revalidatePath, revalidateTag } from "next/cache";

// 데이터에 태그를 붙여 두고
await fetch(url, { next: { tags: ["products"] } });

// 변경이 일어나면 그 태그를 무효화합니다
revalidateTag("products");
revalidatePath("/products");

🔗 67장과 같은 사고방식입니다

TanStack Query의 invalidateQueries와 개념이 같습니다. "이 데이터는 이제 낡았다"고 표시하면 시스템이 알아서 갱신합니다. 어느 페이지가 그 데이터를 쓰는지 알 필요가 없습니다.

③ 캐시하지 않기 — 항상 최신이어야 할 때 
await fetch(url, { cache: "no-store" });

// 또는 라우트 전체를 동적으로
export const dynamic = "force-dynamic";

🍪 동적 함수를 쓰면 정적 생성이 해제됩니다

cookies()·headers()·searchParams를 읽는 순간 "요청마다 달라지는 페이지"가 되어 미리 만들어 둘 수 없습니다.
그래서 페이지 최상단에서 무심코 cookies()를 호출하면 정적일 수 있었던 페이지가 전부 SSR이 됩니다. 로그인 여부가 필요한 부분만 작은 컴포넌트로 분리하고 Suspense로 감싸면 나머지는 정적으로 유지됩니다.

Server Actions

서버에서 실행되는 함수를 클라이언트에서 직접 호출할 수 있게 하는 기능입니다. API 라우트를 만들지 않고도 데이터를 변경할 수 있습니다.

// app/actions.ts
"use server";                                    // ← 서버 전용 표시

import { revalidatePath } from "next/cache";
import { redirect } from "next/navigation";
import { z } from "zod";

const TodoSchema = z.object({ text: z.string().min(1).max(200) });

export async function createTodo(formData: FormData) {
  // ⭐ 클라이언트에서 오는 값이므로 반드시 검증합니다 (54·78장)
  const parsed = TodoSchema.safeParse({ text: formData.get("text") });
  if (!parsed.success) {
    return { error: "내용을 입력해 주세요" };
  }

  // ⭐ 권한 검사도 여기서 (엔드포인트나 마찬가지입니다)
  const session = await getSession();
  if (!session) return { error: "로그인이 필요합니다" };

  await db.todo.create({ data: { text: parsed.data.text, userId: session.userId } });

  revalidatePath("/todos");                      // 목록 갱신
  redirect("/todos");
}
폼에서 바로 쓰기 — JS 없이도 동작합니다 
import { createTodo } from "./actions";

export default function TodoForm() {
  return (
    <form action={createTodo}>
      <input name="text" required />
      <button>추가</button>
    </form>
  );
}

📜 점진적 향상

이 폼은 JavaScript가 로드되기 전이나 실패해도 동작합니다. 브라우저의 기본 폼 제출 동작을 그대로 쓰기 때문입니다(9장). JS가 준비되면 새로고침 없이 처리되는 방식으로 자연스럽게 향상됩니다.
69장의 useActionState·useFormStatus와 결합하면 로딩 상태와 오류 표시까지 깔끔하게 만들 수 있습니다.

🔓 Server Action은 공개 엔드포인트입니다

"서버에서 실행되니 안전하다"는 절반만 맞습니다. Server Action은 고유 주소를 가진 HTTP 엔드포인트로 노출되며, 누구나 직접 호출을 시도할 수 있습니다.
따라서 모든 Server Action에서 ① 입력 검증 ② 인증 확인 ③ 권한 확인을 반드시 해야 합니다. UI에서 버튼을 숨긴 것은 아무 보호도 되지 않습니다(78장).

스트리밍

import { Suspense } from "react";

export default function Page() {
  return (
    <>
      <Header />                              {/* 즉시 전송 */}
      <ProductInfo />                          {/* 빠른 데이터 */}

      <Suspense fallback={<ReviewSkeleton />}>
        <Reviews />                            {/* 느린 데이터 — 준비되면 나중에 */}
      </Suspense>

      <Suspense fallback={<RecommendSkeleton />}>
        <Recommendations />
      </Suspense>
    </>
  );
}

🌊 느린 하나가 전체를 막지 않게

70장에서 SSR의 단점으로 "느린 API 하나가 전체 전송을 막는다"고 했습니다. 스트리밍은 준비된 부분부터 먼저 보내고 나머지는 나중에 채웁니다.
추천 상품 API가 3초 걸려도 상품 정보는 0.2초 만에 보입니다. 그 자리에는 스켈레톤이 표시되다가 준비되면 교체됩니다.

워터폴 피하기

// ❌ 순차 실행 — 300ms (36장의 그 문제)
const user = await getUser(id);
const posts = await getPosts(id);
const stats = await getStats(id);

// ✅ 병렬 실행 — 100ms
const [user, posts, stats] = await Promise.all([
  getUser(id), getPosts(id), getStats(id)
]);

// ✅ 또는 컴포넌트를 나눠 각자 Suspense로 감싸면
//    각 컴포넌트가 독립적으로 데이터를 가져와 병렬이 됩니다

🪜 컴포넌트 중첩이 워터폴을 만들 수 있습니다

// ❌ Parent가 데이터를 받아야 Child가 렌더링되고, 그때서야 Child가 요청
async function Parent() {
  const user = await getUser();
  return <Child userId={user.id} />;
}
async function Child({ userId }) {
  const posts = await getPosts(userId);   // 앞이 끝나야 시작됩니다
}

진짜 의존 관계라면 어쩔 수 없지만, 독립적인 데이터라면 두 컴포넌트를 형제로 두고 각각 Suspense로 감싸세요. 그러면 병렬로 진행됩니다.

🛠️ 현장 노트

  1. 데이터를 쓰는 컴포넌트에서 가져오세요. 요청 메모이제이션 덕분에 중복 호출이 자동으로 제거됩니다.
  2. 동적 함수는 필요한 곳에만. cookies() 한 줄이 페이지 전체를 동적으로 만듭니다.
  3. 모든 Server Action에서 검증·인증·인가를 하세요. 예외 없습니다.
  4. 캐싱은 문서를 확인하세요. 버전마다 기본값이 다릅니다. npm run build 출력에 각 라우트가 정적인지 동적인지 표시되니 그것으로 확인하는 것이 확실합니다.
  5. 클라이언트 데이터 라이브러리가 여전히 필요할 수 있습니다. 클라이언트 컴포넌트에서 자주 갱신되는 데이터를 다룬다면 TanStack Query(67장)를 함께 씁니다.

📌 요약

  • 서버 컴포넌트에서는 그냥 await로 데이터를 가져온다. 로딩·오류는 특수 파일이 처리한다.
  • 요청 메모이제이션 덕분에 여러 컴포넌트가 각자 가져와도 요청은 한 번이다.
  • 재검증은 시간 기반과 온디맨드(태그·경로) 두 가지다.
  • cookies()·headers()를 쓰면 정적 생성이 해제된다.
  • Server Action으로 API 없이 데이터를 변경한다. JS 없이도 폼이 동작한다.
  • Server Action은 공개 엔드포인트다. 검증·인증·인가가 필수다.
  • 스트리밍으로 느린 부분이 전체를 막지 않게 한다.
  • 독립적인 데이터는 Promise.all이나 형제 Suspense로 병렬 처리한다.
  • 캐싱 기본값은 버전마다 다르다. 반드시 문서와 빌드 출력으로 확인한다.
