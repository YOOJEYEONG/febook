URL 해부하기

URL은 인터넷에서 어떤 자원이 어디 있는지 가리키는 주소입니다. 아무렇게나 생긴 문자열이 아니라 정해진 부위로 나뉩니다.

URL의 구조 
  https :// shop.example.com : 443 /products/42 ?color=red&size=m #reviews
  └─┬─┘     └───────┬───────┘  └┬┘ └─────┬────┘ └───────┬───────┘ └───┬──┘
  스킴          호스트         포트     경로          질의 문자열      프래그먼트
 (프로토콜)     (어느 서버)  (어느 프로그램) (무엇을)   (추가 조건)     (문서 안 위치)
부위예하는 일
스킴
scheme		https:어떤 규칙으로 통신할지. http, https, file(내 컴퓨터 파일), mailto(메일 앱 열기) 등
호스트
host		shop.example.com어느 서버인지. 도메인 이름 또는 IP 주소
포트
port		:443서버의 어느 프로그램인지. 기본값(80·443)이면 생략
경로
path		/products/42그 서버 안에서 무엇을 원하는지
질의 문자열

프래그먼트

⚠️ 프래그먼트는 서버에 가지 않는다

# 뒤의 내용은 브라우저가 스스로 처리합니다. 서버는 그런 게 있었는지도 모릅니다. 그래서 페이지 안의 특정 제목으로 점프하는 데 쓰이고, 서버 요청 없이 화면을 바꾸는 옛날 방식 라우팅에도 쓰였습니다. 이 사실은 68장(라우팅)에서 다시 필요합니다.

직접 분해해 보기

브라우저에는 URL을 분해해 주는 URL이라는 기능이 내장되어 있습니다. 직접 돌려 보세요.

도메인 이름의 계층

도메인은 오른쪽에서 왼쪽으로 읽습니다. 오른쪽이 더 큰 단위입니다.

도메인 읽는 순서 
shop . example . com
 │       │        └── 최상위 도메인 (TLD) — com, net, org, kr, io …
 │       └─────────── 2단계 도메인 — 보통 여기까지가 "우리가 산 도메인"
 └─────────────────── 서브도메인 — 도메인 주인이 마음대로 만들 수 있다
  • example.com을 등록하면 shop.example.com, blog.example.com, api.example.com 같은 서브도메인은 추가 비용 없이 얼마든지 만들 수 있습니다.
  • www도 그냥 서브도메인입니다. 특별한 의미는 없고, 관습적으로 붙여 온 이름입니다.
  • 한국의 .co.kr처럼 두 단계로 된 최상위 구조도 있습니다.

DNS — 이름을 주소로 바꾸는 전화번호부

브라우저는 example.com이라는 이름으로는 아무 데도 갈 수 없습니다. IP 주소가 필요합니다. 이 변환을 담당하는 것이 DNS(Domain Name System)입니다.

조회는 이 순서로 진행됩니다. 앞 단계에서 답을 찾으면 즉시 끝납니다.

  1. 브라우저 캐시 — 방금 전에 찾아본 적 있나?
  2. 운영체제 캐시 — 이 컴퓨터가 최근에 찾아본 적 있나? (hosts 파일도 여기서 확인)
  3. 재귀 리졸버 — 보통 통신사나 공개 DNS(예: 8.8.8.8)가 대신 찾아 줍니다.
  4. 루트 네임서버 — ".com은 저쪽에 물어보세요"
  5. TLD 네임서버 — "example.com은 저쪽에 물어보세요"
  6. 권한 네임서버 — "example.com의 IP는 93.184.x.x입니다" ← 최종 답

📞 왜 이렇게 복잡한가

전 세계 도메인을 한 곳에 다 저장할 수 없기 때문입니다. 그래서 "나는 모르지만 저쪽은 안다"를 반복하는 계단식 구조로 나눠 두었습니다. 그리고 각 단계에서 결과를 일정 시간 저장(캐시)해 두기 때문에, 실제로는 대부분 1~2단계에서 끝나고 전체 여행을 하는 일은 드뭅니다.

알아 둘 DNS 레코드

레코드뜻
A이 도메인의 IPv4 주소
AAAA이 도메인의 IPv6 주소
CNAME"이 이름은 저 이름의 별칭이다". 배포 서비스에 도메인을 연결할 때 자주 씁니다
MX이 도메인의 메일을 받을 서버
TXT자유 텍스트. 도메인 소유 증명 등에 쓰입니다
TTL레코드가 아니라 설정값. "이 답을 몇 초 동안 캐시해도 되는지"

⏱️ "DNS 전파(propagation)"라는 말

도메인 설정을 바꿨는데 바로 반영되지 않고 몇 시간 걸리는 경우가 있습니다. 새 정보가 세계로 "퍼져 나가서"가 아니라, 여기저기 캐시된 옛 답의 TTL이 아직 안 끝났기 때문입니다. 그래서 도메인 변경을 앞두고 있다면 미리 TTL을 짧게 낮춰 두는 것이 실무 요령입니다.

출처(origin) — 브라우저 보안의 기준선

앞으로 계속 나올 개념이라 여기서 확실히 잡고 갑니다. 출처(origin)는 스킴 + 호스트 + 포트 세 가지의 조합입니다. 셋 다 같아야 같은 출처입니다.

기준: https://example.com/page같은 출처?이유
https://example.com/otherO경로는 출처와 무관
https://example.com:443/xO443은 https의 기본 포트라 같은 값
http://example.com/pageX스킴이 다름 (http ≠ https)
https://api.example.com/pageX호스트가 다름 (서브도메인도 다른 호스트)
https://example.com:8080/pageX포트가 다름

브라우저는 다른 출처의 자원에 함부로 접근하지 못하게 막습니다. 이 규칙을 동일 출처 정책(Same-Origin Policy)이라고 하고, 이것 때문에 나중에 "서버 데이터를 부르는데 CORS 오류가 났다"는 상황을 반드시 만나게 됩니다(37장). 지금은 "출처 = 스킴+호스트+포트"만 외워 두면 충분합니다.

호스팅 — 내 파일을 세상에 두는 곳

만든 HTML 파일이 내 노트북에만 있으면 아무도 볼 수 없습니다. 24시간 켜져 있고 인터넷에서 접근 가능한 컴퓨터에 올려야 하고, 그 서비스를 호스팅이라고 합니다.

종류설명예
정적 호스팅HTML·CSS·JS·이미지 파일 그대로 돌려주는 방식. 서버가 계산할 게 없어 매우 빠르고 저렴합니다Vercel, Netlify, GitHub Pages, Cloudflare Pages
서버 호스팅요청마다 서버에서 코드를 실행해 결과를 만들어 보냅니다. 로그인·주문 처리 같은 일이 가능합니다Vercel Functions, AWS, 일반 클라우드 서버

지금 여러분이 보고 있는 이 책은 정적 호스팅으로 올릴 수 있는 형태입니다. 서버에서 돌아가는 코드가 하나도 없고 파일만 있기 때문입니다.

CDN — 가까운 곳에 사본을 두기

서버가 미국에 하나만 있다면, 한국에서 접속할 때마다 데이터가 태평양을 왕복해야 합니다. 빛의 속도는 정해져 있어서 이 지연은 돈으로도 줄일 수 없습니다.

CDN(Content Delivery Network)은 전 세계 곳곳에 사본 서버를 두고, 사용자에게 가장 가까운 곳에서 파일을 내려주는 방식입니다.

🏪 편의점 비유

본사 창고(원본 서버)가 하나뿐이면 모든 주문이 거기까지 갔다 와야 합니다. 동네마다 편의점(CDN 서버)을 두고 잘 팔리는 물건을 미리 채워 두면, 대부분의 손님은 걸어서 해결됩니다. 편의점에 물건이 없을 때만 본사에 요청합니다. 이때 "편의점에 있었다"를 캐시 적중(cache hit)이라고 부릅니다.

이미지·CSS·JS처럼 모든 사용자에게 똑같은 파일은 CDN에 두기 좋습니다. 반면 "로그인한 내 주문 목록"처럼 사람마다 다른 내용은 그렇게 할 수 없습니다. 무엇을 캐시할 수 있고 없는지는 76장에서 자세히 다룹니다.

🛠️ 현장 노트

"배포했는데 옛날 화면이 그대로 보여요"는 신입이 가장 자주 겪는 문제입니다. 원인은 대부분 브라우저 캐시 또는 CDN 캐시입니다. 그래서 실무에서는 파일 이름에 내용 기반 해시를 붙여 (main.a3f19c.js) 내용이 바뀌면 이름 자체가 달라지게 만듭니다. 이러면 캐시가 옛 파일을 붙잡고 있어도 새 이름은 새로 받아 갑니다. 47장에서 다시 나옵니다.

🚫 자주 하는 오해

오해 — www.example.com과 example.com은 항상 같은 곳이다. 사실 — 기술적으로는 서로 다른 호스트입니다. 둘 다 열리는 이유는 도메인 주인이 한쪽을 다른 쪽으로 연결하거나 리다이렉트하도록 설정해 두었기 때문입니다. 설정하지 않으면 한쪽만 열립니다. 그리고 출처가 다르므로 쿠키·CORS 동작도 달라질 수 있습니다.

📌 요약

  • URL = 스킴 + 호스트 + (포트) + 경로 + 질의 문자열 + 프래그먼트.
  • # 뒤 프래그먼트는 서버로 전송되지 않는다.
  • DNS는 도메인 이름을 IP로 바꾸는 계단식 조회 시스템이고, 각 단계에서 캐시된다.
  • "DNS 전파 지연"의 정체는 남아 있는 캐시(TTL)다.
  • 출처(origin) = 스킴 + 호스트 + 포트. 셋 다 같아야 같은 출처다.
  • 정적 호스팅은 파일을 그대로, 서버 호스팅은 코드를 실행해서 응답한다.
  • CDN은 사용자와 가까운 곳에 사본을 두어 거리 지연을 줄인다.
