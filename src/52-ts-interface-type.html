읽는 데 약 18분

둘 다 거의 같은 일을 합니다

interface User {
  id: number;
  name: string;
}

type User2 = {
  id: number;
  name: string;
};

// 두 정의는 사실상 같습니다. 서로 바꿔 써도 됩니다.
const a: User = { id: 1, name: "홍길동" };
const b: User2 = a;    // ✅ 문제없습니다

차이점

interfacetype
객체 모양 정의가능가능
확장extends& (교차 타입)
선언 병합가능불가 — 같은 이름 재선언 시 오류
유니온불가가능 — type A = B | C
원시 타입에 별명불가가능 — type ID = string
튜플불편가능
매핑드·조건부 타입(55장)불가가능
오류 메시지이름이 그대로 나와 읽기 좋음펼쳐져서 길어질 수 있음

type만 할 수 있는 것

type Status = "idle" | "loading" | "error";      // 유니온
type ID = string | number;                        // 원시 타입 조합
type Point = [number, number];                    // 튜플
type Handler = (e: Event) => void;                // 함수 (interface로도 가능하지만 어색)
type Nullable<T> = T | null;                      // 제네릭 유틸리티 (53장)
type Keys = keyof User;                           // 타입 연산 (55장)

interface만 할 수 있는 것 — 선언 병합

interface Window {
  myAppVersion: string;
}
// 브라우저가 이미 정의한 Window에 '내 속성을 추가'합니다
window.myAppVersion = "1.0.0";     // ✅

// type으로는 불가능합니다
type Window2 = { a: string };
type Window2 = { b: string };      // ❌ 중복 식별자 오류

🔌 선언 병합이 필요한 곳

직접 만든 코드에서는 거의 쓸 일이 없습니다. 하지만 라이브러리의 타입을 확장할 때는 이것이 유일한 방법입니다. 예를 들어 스타일 라이브러리의 테마 타입에 내 색상을 추가하거나, window에 전역 값을 붙일 때 씁니다.
반대로 말하면 남이 내 타입을 몰래 바꿀 수 있다는 뜻이기도 해서, "닫혀 있어야 하는" 타입에는 type이 나을 수 있습니다.

확장하기

// interface — extends
interface Animal {
  name: string;
}
interface Dog extends Animal {
  breed: string;
}

// type — 교차 타입(&)
type Animal2 = { name: string };
type Dog2 = Animal2 & { breed: string };

// 여러 개도 가능합니다
interface A extends B, C { }
type D = B & C & { extra: string };

⚔️ 충돌할 때 동작이 다릅니다

// interface — 충돌하면 즉시 오류. 실수를 바로 알려 줍니다
interface A { value: string }
interface B extends A { value: number }
// ❌ Interface 'B' incorrectly extends interface 'A'.

// type — 조용히 never가 됩니다
type C = { value: string };
type D = C & { value: number };
// D의 value는 string & number = never
// 오류가 나지 않고, 나중에 값을 넣으려 할 때야 이상함을 알게 됩니다

구조적 타이핑 — TypeScript의 핵심 원리

🦆 이름이 아니라 모양으로 판단합니다

"오리처럼 걷고 오리처럼 울면 오리다"라는 오리 타이핑과 같은 원리입니다. Java·C# 같은 언어는 "이 클래스를 상속했는가"를 보지만, TypeScript는 "필요한 속성을 갖고 있는가"만 봅니다.

interface Point { x: number; y: number; }

function draw(point: Point) { }

// 아무 관계도 선언하지 않았지만 통과합니다
const coord = { x: 1, y: 2 };
draw(coord);              // ✅ 모양이 맞으므로

// 속성이 더 많아도 통과합니다
const point3d = { x: 1, y: 2, z: 3 };
draw(point3d);            // ✅

// 하지만 객체 리터럴을 '직접' 넘기면 다릅니다
draw({ x: 1, y: 2, z: 3 });
// ❌ Object literal may only specify known properties, and 'z' does not exist
//    → 초과 속성 검사(excess property check)

🔍 초과 속성 검사는 왜 있나

변수를 거치면 통과하는데 리터럴을 직접 넘기면 막히는 것이 이상해 보입니다. 이유는 오타를 잡기 위해서입니다.

interface Options { color?: string; }
setOptions({ colour: "red" });    // ❌ 영국식 철자 오타를 잡아 줍니다

이 검사가 없으면 colour는 그냥 무시되고 색이 안 바뀌는 이유를 한참 찾게 됩니다.

판별 유니온 — 상태 관리의 정석 
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User[] }
  | { status: "error"; error: string };

function render(state: RequestState) {
  switch (state.status) {
    case "loading":
      return "불러오는 중…";
    case "success":
      return state.data.length + "명";   // ✅ data가 있다는 것이 보장됩니다
    case "error":
      return state.error;                 // ✅ error가 있다는 것이 보장됩니다
    case "idle":
      return "";
  }
}

판별 유니온은 불가능한 상태를 표현할 수 없게 만듭니다. 그러면 "로딩 중인데 에러도 뜬" 같은 버그가 애초에 발생할 수 없습니다. React의 상태 설계에서 매우 강력한 도구입니다(59·67장).

🛠️ 현장 노트 — 무엇을 쓸까

솔직히 대부분의 경우 아무거나 써도 됩니다. 다만 팀이 하나로 통일하는 것이 중요합니다. 널리 쓰이는 기준은 이렇습니다.

  • 객체 모양을 정의한다 → interface (오류 메시지가 읽기 좋습니다)
  • 유니온·튜플·타입 연산이 필요하다 → type
  • 라이브러리 타입을 확장해야 한다 → interface (선언 병합)
  • React props → 둘 다 널리 쓰입니다. 프로젝트 규칙을 따르세요

이 선택으로 고민하는 시간이 아깝습니다. 훨씬 중요한 것은 판별 유니온으로 상태를 설계하는 것과 타입을 실제 데이터 구조에 맞게 정확히 쓰는 것입니다.

📌 요약

  • 객체 모양 정의는 둘 다 가능하고 서로 호환된다.
  • type만 가능: 유니온·튜플·원시 별명·타입 연산.
  • interface만 가능: 선언 병합(라이브러리 타입 확장에 필수).
  • 확장 충돌 시 interface는 오류, type은 조용히 never.
  • TypeScript는 구조적 타이핑 — 이름이 아니라 모양으로 호환을 판단한다.
  • 초과 속성 검사는 객체 리터럴을 직접 넘길 때만 작동하며 오타를 잡아 준다.
  • 판별 유니온으로 불가능한 상태를 만들 수 없게 설계한다.
