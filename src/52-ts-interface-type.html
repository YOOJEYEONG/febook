읽는 데 약 28분 · 사전 지식: 객체 타입과 유니온·리터럴 타입(51장)

둘 다 거의 같은 일을 합니다

51장에서 객체 타입을 함수 매개변수 자리에 바로 적어 보았습니다. 그런데 같은 모양을 여러 함수가 쓴다면 매번 { id: number; name: string }을 반복해서 적어야 합니다. 그래서 모양에 이름을 붙여 재사용합니다. 이름을 붙이는 문법이 두 가지 있는데, interface와 type(타입 별칭)입니다. 같은 집을 그린 설계도를 A 양식으로 그리느냐 B 양식으로 그리느냐의 차이에 가깝습니다. 결과물인 집은 같습니다.

interface User {
  id: number;
  name: string;
}

type User2 = {
  id: number;
  name: string;
};

// 두 정의는 사실상 같습니다. 서로 바꿔 써도 됩니다.
const a: User = { id: 1, name: "홍길동" };
const b: User2 = a;    // ✅ 문제없습니다

▶ Playground에 붙여 보세요. a를 User2 변수에 넣어도 오류가 나지 않습니다. 이름이 다른 두 타입이 서로 호환되는 이유는 이 챕터 뒷부분의 구조적 타이핑에서 설명합니다. 문법을 보면 interface는 이름 뒤에 바로 중괄호가 오고, type은 등호(=) 뒤에 타입이 옵니다. type은 "오른쪽에 있는 어떤 타입이든 이 이름으로 부르겠다"는 뜻이라 객체 말고도 쓸 수 있습니다. 이 차이가 아래 표의 대부분을 설명합니다.

차이점

거의 같다면 왜 둘이 있을까요? 역사적으로 interface가 먼저 객체 모양을 위한 문법으로 자리 잡았고, type은 유니온처럼 객체가 아닌 타입에도 이름을 붙이기 위해 생겼습니다. 이후 버전이 올라가며 둘의 능력이 많이 겹치게 되었습니다. 실무에서 차이가 드러나는 지점은 아래 표 정도입니다.

interfacetype
객체 모양 정의가능가능
확장extends& (교차 타입)
선언 병합가능불가 — 같은 이름 재선언 시 오류
유니온불가가능 — type A = B | C
원시 타입에 별명불가가능 — type ID = string
튜플불편가능
매핑드·조건부 타입(55장)불가가능
오류 메시지이름이 그대로 나와 읽기 좋음펼쳐져서 길어질 수 있음

type만 할 수 있는 것

type Status = "idle" | "loading" | "error";      // 유니온
type ID = string | number;                        // 원시 타입 조합
type Point = [number, number];                    // 튜플
type Handler = (e: Event) => void;                // 함수 (interface로도 가능하지만 어색)
type Nullable<T> = T | null;                      // 제네릭 유틸리티 (53장)
type Keys = keyof User;                           // 타입 연산 (55장)

type은 등호 오른쪽에 무엇이든 올 수 있으므로 유니온, 튜플, 함수 모양 같은 객체가 아닌 타입에도 이름을 붙일 수 있습니다. type ID = string | number처럼 이름을 붙여 두면, ID 타입을 바꿔야 할 때 한 곳만 고치면 됩니다. Nullable<T>의 꺾쇠는 53장의 제네릭, keyof는 55장의 타입 연산자입니다. 지금은 "이런 것도 type으로만 된다"는 정도로 보면 됩니다.

interface만 할 수 있는 것 — 선언 병합

반대로 interface만의 기능은 선언 병합입니다. 같은 이름의 interface를 두 번 선언하면 오류 대신 두 내용이 합쳐집니다. 회의록에 나중에 덧붙인 메모가 원래 내용에 더해지는 것과 같습니다. 이 성질 덕분에 남이 만든 타입에 내 속성을 덧붙일 수 있습니다.

interface Window {
  myAppVersion: string;
}
// 브라우저가 이미 정의한 Window에 '내 속성을 추가'합니다
window.myAppVersion = "1.0.0";     // ✅

// type으로는 불가능합니다
type Window2 = { a: string };
type Window2 = { b: string };      // ❌ 중복 식별자 오류

▶ Playground에 붙여 보세요. window.myAppVersion이 오류 없이 통과하고, Window2의 두 번째 선언에서만 오류가 납니다. 한 가지 주의할 점이 있습니다. import나 export가 있는 파일(모듈, 34장)에서는 이렇게 쓰면 새 Window를 만든 것으로 처리됩니다. 실제 프로젝트에서는 declare global { interface Window { … } }로 감싸야 브라우저의 Window와 합쳐집니다.

🔌 선언 병합이 필요한 곳

직접 만든 코드에서는 거의 쓸 일이 없습니다. 하지만 라이브러리의 타입을 확장할 때는 이것이 유일한 방법입니다. 예를 들어 스타일 라이브러리의 테마 타입에 내 색상을 추가하거나, window에 전역 값을 붙일 때 씁니다.
반대로 말하면 남이 내 타입을 몰래 바꿀 수 있다는 뜻이기도 해서, "닫혀 있어야 하는" 타입에는 type이 나을 수 있습니다.

확장하기

"모든 동물은 이름이 있고, 개는 거기에 품종이 더 있다"처럼 기존 타입에 속성을 더한 새 타입이 필요할 때가 많습니다. 속성을 다시 다 적으면 원본이 바뀔 때 어긋나므로 기존 타입을 바탕으로 확장합니다. interface는 extends("~을 넓힌다")로, type은 &(교차 타입, "둘 다 만족")로 표현합니다.

// interface — extends
interface Animal {
  name: string;
}
interface Dog extends Animal {
  breed: string;
}

// type — 교차 타입(&)
type Animal2 = { name: string };
type Dog2 = Animal2 & { breed: string };

// 여러 개도 가능합니다
interface A extends B, C { }
type D = B & C & { extra: string };

교차 타입의 &는 "A의 조건과 B의 조건을 모두 만족하는 타입"이라는 뜻입니다. 그래서 결과는 두 타입의 속성을 다 가진 객체가 됩니다. 유니온(|, 이 중 하나)과 짝을 이루는 개념이라 함께 기억해 두면 좋습니다. 둘이 대부분 같은 결과를 내지만, 같은 속성의 타입이 충돌할 때는 다르게 행동합니다.

⚔️ 충돌할 때 동작이 다릅니다

// interface — 충돌하면 즉시 오류. 실수를 바로 알려 줍니다
interface A { value: string }
interface B extends A { value: number }
// ❌ Interface 'B' incorrectly extends interface 'A'.

// type — 조용히 never가 됩니다
type C = { value: string };
type D = C & { value: number };
// D의 value는 string & number = never
// 오류가 나지 않고, 나중에 값을 넣으려 할 때야 이상함을 알게 됩니다

구조적 타이핑 — TypeScript의 핵심 원리

앞에서 이름이 다른 User와 User2가 서로 호환되었습니다. 이것은 TypeScript가 타입을 비교하는 방식 때문입니다. TypeScript는 "이 값이 어떤 이름의 타입으로 만들어졌는가"를 묻지 않고, "필요한 속성을 다 갖고 있는가"만 묻습니다. 벽의 콘센트를 떠올려 보세요. 콘센트는 플러그의 제조사를 따지지 않고 핀 모양만 맞으면 전기를 줍니다.

🦆 이름이 아니라 모양으로 판단합니다

"오리처럼 걷고 오리처럼 울면 오리다"라는 오리 타이핑과 같은 원리입니다. Java·C# 같은 언어는 "이 클래스를 상속했는가"를 보지만, TypeScript는 "필요한 속성을 갖고 있는가"만 봅니다.

interface Point { x: number; y: number; }

function draw(point: Point) { }

// 아무 관계도 선언하지 않았지만 통과합니다
const coord = { x: 1, y: 2 };
draw(coord);              // ✅ 모양이 맞으므로

// 속성이 더 많아도 통과합니다
const point3d = { x: 1, y: 2, z: 3 };
draw(point3d);            // ✅

// 하지만 객체 리터럴을 '직접' 넘기면 다릅니다
draw({ x: 1, y: 2, z: 3 });
// ❌ Object literal may only specify known properties, and 'z' does not exist
//    → 초과 속성 검사(excess property check)

▶ Playground에 붙여 보세요. coord와 point3d는 Point와 아무 관계도 선언하지 않았지만 통과합니다. draw는 x와 y만 쓰므로, 그 두 속성만 있으면 나머지가 더 있어도 안전하기 때문입니다. 마지막 줄만 오류가 나는 이유는 바로 아래 상자에서 설명합니다. JavaScript는 원래 객체를 자유롭게 만들고 넘기는 언어이므로, 이 방식 덕분에 기존 JavaScript 코드에 타입을 자연스럽게 얹을 수 있습니다.

🤔 자주 하는 오해 — interface를 "구현"해야 들어간다

오해 — interface Point를 만들었으면 그 interface로 선언한 객체만 Point 자리에 넣을 수 있다. 사실 — TypeScript는 모양만 봅니다. 어디서 어떻게 만든 객체든 x와 y가 숫자로 있으면 Point입니다. 반대로 이름이 Point여도 속성이 하나 빠지면 거절됩니다. Java·C#처럼 "이 타입을 구현했다"고 선언하는 방식을 기대하면 헷갈립니다.

🔍 초과 속성 검사는 왜 있나

변수를 거치면 통과하는데 리터럴을 직접 넘기면 막히는 것이 이상해 보입니다. 이유는 오타를 잡기 위해서입니다.

interface Options { color?: string; }
function setOptions(options: Options) { }

setOptions({ colour: "red" });    // ❌ 영국식 철자 오타를 잡아 줍니다

이 검사가 없으면 colour는 그냥 무시되고 색이 안 바뀌는 이유를 한참 찾게 됩니다.

실전 패턴

문법을 알았으니 실제 프로젝트에서 타입을 어떻게 짜는지 봅시다. 프론트엔드에서 타입을 가장 많이 쓰는 곳은 서버에서 받는 데이터의 모양과 화면의 상태입니다. 첫 번째 예제는 API 응답, 두 번째는 상태입니다.

API 응답 타입 설계 
interface User {
  id: number;
  name: string;
  email: string;
}

// 목록 응답
interface UserListResponse {
  items: User[];
  total: number;
  page: number;
}

// 공통 응답 껍데기 (제네릭 — 53장)
interface ApiResponse<T> {
  data: T;
  message: string;
  timestamp: string;
}

type UsersResponse = ApiResponse<User[]>;

실제 서버 응답을 보고 그대로 옮겨 적는 것이 출발점입니다. 여러 응답이 공통 껍데기(data, message)를 공유한다면 ApiResponse<T>처럼 내용물 자리만 비워 둔 틀을 만들고, 쓸 때 User[]를 끼워 넣습니다. 이 "자리 비워 두기"가 53장의 제네릭입니다.

두 번째 예제는 화면 상태입니다. 데이터를 불러오는 화면은 "대기 → 불러오는 중 → 성공 또는 실패"를 오갑니다. 각 상태마다 필요한 데이터가 다릅니다. 성공했을 때만 데이터가 있고, 실패했을 때만 오류 메시지가 있습니다. 이것을 그대로 타입으로 옮긴 것이 판별 유니온입니다. 모든 갈래에 공통으로 있는 status 속성이 "어느 갈래인지 판별하는 꼬리표" 역할을 합니다.

판별 유니온 — 상태 관리의 정석 
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User[] }
  | { status: "error"; error: string };

function render(state: RequestState) {
  switch (state.status) {
    case "loading":
      return "불러오는 중…";
    case "success":
      return state.data.length + "명";   // ✅ data가 있다는 것이 보장됩니다
    case "error":
      return state.error;                 // ✅ error가 있다는 것이 보장됩니다
    case "idle":
      return "";
  }
}

▶ Playground에 붙여 보세요. 맨 위에 type User = { name: string }; 한 줄을 추가하면 됩니다. case "success": 안에서 state.를 입력하면 data가 후보로 나오고, case "loading": 안에서는 나오지 않습니다. switch가 status 값을 확인한 순간 TypeScript가 "지금은 이 갈래"라고 좁혀 주기 때문입니다(54장).

⭐ 판별 유니온이 막아 주는 실수

// ❌ 이렇게 하면 불가능한 상태가 표현됩니다
interface BadState {
  isLoading: boolean;
  data?: User[];
  error?: string;
}
// isLoading: true 이면서 error도 있는 상태? data와 error가 동시에 있는 상태?
// 코드로는 만들 수 있지만 논리적으로 말이 안 됩니다

판별 유니온은 불가능한 상태를 표현할 수 없게 만듭니다. 그러면 "로딩 중인데 에러도 뜬" 같은 버그가 애초에 발생할 수 없습니다. React의 상태 설계에서 매우 강력한 도구입니다(59·67장).

🛠️ 현장 노트 — 무엇을 쓸까

솔직히 대부분의 경우 아무거나 써도 됩니다. 다만 팀이 하나로 통일하는 것이 중요합니다. 널리 쓰이는 기준은 이렇습니다.

  • 객체 모양을 정의한다 → interface (오류 메시지가 읽기 좋습니다)
  • 유니온·튜플·타입 연산이 필요하다 → type
  • 라이브러리 타입을 확장해야 한다 → interface (선언 병합)
  • React props → 둘 다 널리 쓰입니다. 프로젝트 규칙을 따르세요

이 선택으로 고민하는 시간이 아깝습니다. 훨씬 중요한 것은 판별 유니온으로 상태를 설계하는 것과 타입을 실제 데이터 구조에 맞게 정확히 쓰는 것입니다.

📌 요약

  • 객체 모양 정의는 둘 다 가능하고 서로 호환된다.
  • type만 가능: 유니온·튜플·원시 별명·타입 연산.
  • interface만 가능: 선언 병합(라이브러리 타입 확장에 필수).
  • 확장 충돌 시 interface는 오류, type은 조용히 never.
  • TypeScript는 구조적 타이핑 — 이름이 아니라 모양으로 호환을 판단한다.
  • 초과 속성 검사는 객체 리터럴을 직접 넘길 때만 작동하며 오타를 잡아 준다.
  • 판별 유니온으로 불가능한 상태를 만들 수 없게 설계한다.
