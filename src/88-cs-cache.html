캐시라는 하나의 아이디어

📦 한 문장 정의

느린 곳에서 가져온 것을, 다음에 또 쓸 것 같으니 빠른 곳에 두는 것.
CPU 캐시부터 CDN까지 전부 같은 아이디어입니다. 다른 건 "느린 곳"과 "빠른 곳"이 무엇이냐뿐입니다.

대략적인 자릿수 감각용 수치입니다. 기기마다 다릅니다.

이 표에서 읽어야 할 건 정확한 숫자가 아니라 자릿수 차이입니다. 네트워크는 메모리보다 백만 배 느립니다. 그래서 프론트엔드 성능에서 "네트워크 요청을 한 번 줄이는 것"이 압도적으로 큰 개선입니다.

왜 캐시가 통하는가 — 지역성

시간 지역성   방금 쓴 것은 곧 또 쓸 가능성이 높다
              → 방금 본 상품 페이지로 되돌아온다

공간 지역성   방금 쓴 것 '근처'를 쓸 가능성이 높다
              → 배열을 0번부터 순서대로 읽는다
              → CPU는 한 칸이 아니라 주변 한 줄을 통째로 캐시에 올린다
              → 배열 순회가 연결 리스트 순회보다 빠른 숨은 이유 (81·82장)

웹 요청이 지나는 캐시 계층

층설명
① 메모리 캐시탭이 살아 있는 동안. 가장 빠릅니다 (DevTools에 from memory cache)
② Service Worker코드로 직접 제어하는 캐시. 오프라인 지원의 핵심
③ 디스크 캐시(HTTP)Cache-Control 헤더에 따름. 브라우저 종료 후에도 유지
④ CDN 엣지 캐시사용자와 가까운 서버 (3장)
⑤ 서버 캐시Redis 등
⑥ 데이터베이스진짜 원본

위에서 찾으면(캐시 히트) 아래로 가지 않습니다. ①에서 끝나면 0ms, ⑥까지 가면 수백 ms입니다.

HTTP 캐시 — 헤더가 전부다

브라우저가 파일을 얼마나 오래 보관할지는 서버가 내려준 헤더가 정합니다.

지시어뜻
max-age=36003600초 동안은 서버에 묻지 않고 그냥 씁니다
no-cache저장은 하되, 쓰기 전에 매번 서버에 "바뀌었나요?" 물어봅니다
no-store저장 자체를 하지 않습니다
must-revalidate유효기간이 지나면 반드시 서버에 확인합니다
immutable유효기간 안에는 새로고침해도 재검증하지 않습니다
s-maxage=86400CDN 같은 공유 캐시에만 적용되는 max-age
private브라우저만 저장 가능. CDN은 저장 금지 (개인화된 응답)
public공유 캐시도 저장 가능
stale-while-revalidate=60만료 후 60초 동안은 일단 옛 응답을 주고 뒤에서 조용히 새로 받아 둡니다 (체감 속도가 크게 좋아집니다)

🚨 no-cache는 "캐시하지 마라"가 아닙니다

no-cache = 저장은 한다. 다만 쓰기 전에 매번 서버에 확인한다. 서버가 "안 바뀌었다(304)"고 하면 저장해 둔 걸 그대로 씁니다. 본문 전송이 없어 빠릅니다. no-store = 진짜로 아무 데도 저장하지 않는다. 매번 전부 새로 받습니다. 개인정보·결제 정보·인증 토큰이 담긴 응답에 씁니다. 이름 때문에 반대로 쓰는 경우가 정말 많습니다. "캐시 끄려고 no-cache 넣었는데 왜 옛날 게 나오죠?"의 원인이 이것입니다.

재검증 — ETag와 Last-Modified

"바뀌었나요?"를 묻는 방법 
첫 요청
  서버 ──▶ 200 OK
           ETag: "a1b2c3"
           Content-Length: 250000

두 번째 요청 (캐시가 만료됐을 때)
  브라우저 ──▶ If-None-Match: "a1b2c3"      ← "이 버전 갖고 있는데요"
  서버     ──▶ 304 Not Modified             ← 본문 없음! 헤더만 온다
                                              250KB 대신 수백 바이트

  바뀌었다면 ──▶ 200 OK + 새 본문 + 새 ETag

Last-Modified / If-Modified-Since 는 같은 일을 '시간'으로 한다.
ETag가 더 정확하다 (내용이 같으면 시간이 바뀌어도 304).

캐시 무효화 — 파일명 해싱

🧠 유명한 농담

"컴퓨터 과학에는 어려운 문제가 두 개 있다. 캐시 무효화와 이름 짓기다." — Phil Karlton
농담이지만 정확합니다. 얼마나 오래 캐시할 것인가와 바뀌었을 때 어떻게 바로 반영할 것인가는 서로 반대 방향이기 때문입니다.

프론트엔드는 이 문제를 아주 깔끔하게 풀었습니다. 파일 내용이 바뀌면 파일 이름을 바꾸는 것입니다.

번들러가 만드는 파일명 (47장) 
main-4f2a9c1b.js      ← 이름 안의 해시는 파일 내용에서 계산된다
main-8d3e5f70.js      ← 코드를 한 글자만 바꿔도 해시가 달라진다

즉, 같은 이름 = 같은 내용이 보장된다
→ 그러니 아주 오래 캐시해도 안전하다

권장 설정
  /assets/main-4f2a9c1b.js   Cache-Control: public, max-age=31536000, immutable
                             (1년 + 재검증도 하지 않음)

  /index.html                Cache-Control: no-cache
                             (항상 확인. 여기에 새 파일 이름이 적혀 있으므로)

동작: 배포하면 index.html이 새 해시 파일명을 가리킨다
      → 브라우저는 그 이름을 캐시에 갖고 있지 않다 → 새로 받는다
      → 안 바뀐 파일은 이름이 같으므로 캐시에서 즉시 꺼내 쓴다

🛠️ 현장 노트 — 이건 대부분 자동입니다

Vite·Next.js는 해시 파일명을 기본으로 만들고, Vercel·Netlify·Cloudflare Pages는 위 캐시 헤더를 알아서 설정합니다. 직접 손댈 일은 거의 없습니다.

직접 설정해야 하는 경우는 자체 서버(Nginx 등)에 올릴 때입니다. 이때 가장 흔한 사고가 index.html까지 1년 캐시로 걸어 버리는 것입니다. 새 배포가 사용자에게 영원히 도달하지 않습니다. 그리고 이미 그렇게 배포된 뒤에는 되돌릴 방법이 사실상 없습니다 — 브라우저가 서버에 묻질 않으니까요. 반드시 배포 전에 확인하세요.

CDN 캐시에서 주의할 것

1. 개인화된 응답을 캐시하면 남의 정보가 새어 나간다
   로그인 사용자 이름이 든 HTML을 CDN이 캐시하면
   다음 방문자에게 그 이름이 보인다. → Cache-Control: private 또는 no-store

2. Vary 헤더
   같은 URL이라도 요청 헤더에 따라 응답이 다르면 Vary로 알려야 한다
   Vary: Accept-Encoding        gzip/brotli 별로 따로 캐시
   Vary: Accept-Language        언어별로 따로 캐시
   → Vary 대상을 늘릴수록 캐시 적중률이 떨어진다. 꼭 필요한 것만.

3. 퍼지(purge) / 무효화
   급히 내려야 할 때 CDN 대시보드나 API로 캐시를 비운다
   전 세계 엣지에 반영되는 데 시간이 걸릴 수 있다

4. stale-while-revalidate 는 CDN에서 특히 강력하다
   사용자는 항상 즉시 응답을 받고, 갱신은 뒤에서 일어난다

앱 레벨 캐시

HTTP 캐시 외에 애플리케이션이 직접 관리하는 캐시도 있습니다.

TanStack Query (67장) 
useQuery({
  queryKey: ["user", id],
  queryFn: fetchUser,
  staleTime: 60_000,   // 60초 동안은 '신선함' — 다시 요청하지 않는다
  gcTime: 300_000      // 화면에서 안 쓰이게 된 뒤 5분 뒤 메모리에서 제거
});

🧩 staleTime과 gcTime은 다른 것입니다

staleTime = "이 데이터를 언제까지 믿을까". 이 시간 안에는 다시 요청하지 않습니다. 기본값이 0이라 설정하지 않으면 화면에 다시 들어올 때마다 요청이 나갑니다.
gcTime = "안 쓰게 된 데이터를 언제 버릴까". 메모리 정리 시점입니다(84장).
"왜 계속 요청이 나가지?"의 답은 대개 staleTime이고, "왜 뒤로 가기 했을 때 데이터가 없지?"의 답은 대개 gcTime입니다.

Network First네트워크를 먼저 시도하고, 실패하면 캐시최신성이 중요한 API. 오프라인 대비용
Stale While
Revalidate		캐시를 즉시 보여 주고, 동시에 네트워크로 갱신해 다음에 반영대부분의 화면에 맞는 균형점

주의 — Service Worker는 한 번 등록되면 계속 살아 있습니다. 잘못 등록하면 사용자가 옛 버전에 갇힐 수 있어 업데이트·해제 경로를 반드시 함께 설계해야 합니다.

🛠️ 현장 노트 — 캐시 디버깅 순서

  1. DevTools Network 패널의 Size 칼럼을 봅니다. (memory cache), (disk cache), (ServiceWorker)로 어디서 왔는지 바로 보입니다.
  2. "내 화면만 안 바뀌어요" → Network 패널의 Disable cache 체크 후 새로고침해 보세요. 그걸로 해결되면 캐시 문제입니다.
  3. 강력 새로고침(Cmd/Ctrl+Shift+R)은 HTTP 캐시를 무시하지만 Service Worker까지 지우지는 않습니다. Application → Service Workers에서 Unregister가 필요할 수 있습니다.
  4. 사용자에게 "캐시 지워 보세요"라고 안내해야 한다면 그건 설계 실패입니다. 파일명 해싱과 올바른 헤더로 애초에 그런 상황이 없게 만드는 것이 정답입니다.

📌 요약

  • 캐시는 느린 곳의 결과를 빠른 곳에 두는 것. CPU부터 CDN까지 원리가 같다.
  • 네트워크는 메모리보다 자릿수로 백만 배 느리다. 요청 하나를 없애는 게 가장 큰 개선이다.
  • no-cache는 "저장하되 매번 확인", no-store는 "저장 금지". 헷갈리면 안 된다.
  • 재검증은 ETag/If-None-Match로 하고, 안 바뀌었으면 304(본문 없음)가 온다.
  • 파일명 해싱 + 에셋 1년 immutable + index.html은 no-cache가 표준 조합이다.
  • index.html을 오래 캐시하면 새 배포가 영원히 도달하지 않는다.
  • CDN에는 개인화된 응답을 캐시하지 않도록 private·no-store를 쓴다.
  • 앱 레벨에서는 staleTime(믿는 기간)과 gcTime(버리는 시점)을 구분한다.
