왜 자료구조를 여러 개 배우나

자료구조는 데이터를 담는 그릇입니다. 그릇이 여러 개인 이유는 하나입니다. 어떤 작업을 빠르게 할지 그릇마다 다르기 때문입니다.

🏠 비유 — 책장과 사물함

책장에 책을 순서대로 꽂아 두면 "세 번째 책"은 즉시 꺼낼 수 있습니다. 대신 맨 앞에 한 권을 끼워 넣으려면 뒤의 책을 전부 한 칸씩 밀어야 합니다. 이것이 배열입니다.
이름표가 붙은 사물함이라면 "김철수 칸"을 곧장 열 수 있습니다. 순서는 상관없습니다. 이것이 해시 테이블, JavaScript의 객체와 Map입니다.

배열 — 나란히 붙여 놓은 상자

전통적인 배열은 메모리에 같은 크기의 칸이 빈틈없이 이어진 구조입니다. 그래서 arr[5000]을 찾을 때 앞에서부터 세지 않습니다. 시작 주소 + 5000 × 칸 크기를 계산하면 곧바로 그 자리입니다. 인덱스 접근이 즉시인 이유입니다.

배열의 메모리 배치 
주소  1000  1004  1008  1012  1016
     ┌────┬────┬────┬────┬────┐
     │ 10 │ 20 │ 30 │ 40 │ 50 │
     └────┴────┴────┴────┴────┘
index   0     1     2     3     4

arr[3] → 1000 + 3×4 = 1012 → 한 번에 도착 (즉시)

맨 앞에 5를 끼워 넣으려면?
     ┌────┬────┬────┬────┬────┬────┐
     │  5 │ 10 │ 20 │ 30 │ 40 │ 50 │
     └────┴────┴────┴────┴────┴────┘
            ↑ 기존 요소를 전부 한 칸씩 이동해야 한다

여기서 실무 결론이 나옵니다. 끝에 넣고 빼는 것(push/pop)은 싸고, 앞에 넣고 빼는 것(unshift/shift)은 비쌉니다. 데이터가 많아질수록 차이가 벌어집니다.

🧩 JavaScript 배열은 "진짜 배열"이 아닙니다

명세상 JS 배열은 특별한 객체입니다. 키가 "0", "1" 같은 문자열이고, 길이가 자동으로 늘어나며, 서로 다른 타입을 섞어 담을 수 있습니다. 그래도 대개는 빠릅니다. V8 같은 엔진이 "요소가 빈틈없이 채워진 배열"을 감지하면 내부적으로 진짜 연속 메모리로 최적화해 두기 때문입니다. 다만 구멍을 만들면 그 최적화가 풀립니다. delete arr[2]나 arr[10000] = 1처럼 중간을 비우면 엔진이 사전(딕셔너리) 모드로 내려가 훨씬 느려집니다. 요소를 지울 땐 delete가 아니라 splice나 filter를 쓰세요.

해시 테이블 — 객체가 빠른 이유

해시 함수는 임의의 키(문자열 등)를 고정된 범위의 숫자로 바꾸는 함수입니다. 그 숫자를 저장할 칸 번호로 쓰면, 키만 알면 계산 한 번으로 자리를 찾아갑니다.

해시 테이블의 원리 
"name" ──해시 함수──▶ 3        ┌───┐
                              0 │   │
"age"  ──해시 함수──▶ 7        1 │   │
                              2 │   │
찾을 때도 똑같이 계산한다      3 │ "홍길동"  ← "name"
→ 앞에서부터 뒤지지 않는다     …
→ 평균 '즉시' (O(1))          7 │ 30      ← "age"
                                └───┘

서로 다른 키가 같은 칸 번호로 계산되는 일을 해시 충돌이라 합니다. 실제 구현은 그 칸에 목록을 달아 두거나 다음 빈 칸을 찾는 식으로 해결합니다. 충돌이 심하면 느려지지만, 잘 만든 해시 함수에서는 드뭅니다. 그래서 해시 테이블 조회는 평균적으로 즉시, 최악의 경우 선형이라고 말합니다.

🛠️ 현장 노트 — "반복문 안의 find"를 의심하세요

React 목록 화면이 갑자기 버벅일 때 가장 흔한 원인입니다. items.map(item => ... other.find(...)) 형태를 발견하면 바깥에서 Map을 한 번 만들어 두고 get으로 바꾸세요. 데이터가 100개일 땐 티가 안 나다가, 5000개가 되는 순간 화면이 멈춥니다. find 안에 includes가 또 들어 있으면 상황은 더 나빠집니다.

Object vs Map

둘 다 "키 → 값" 저장소지만 성격이 다릅니다.

ObjectMap
키 타입문자열 · 심볼만무엇이든 (객체·숫자·함수도)
숫자 키"1" 문자열로 변환됨1과 "1"이 서로 다른 키
키 순서규칙이 있음 (아래 설명)항상 삽입한 순서
크기Object.keys(o).lengthmap.size
순회Object.entries() 등for…of로 바로
프로토타입toString 등이 딸려 옴없음 (깨끗함)
JSONJSON.stringify 바로 됨직접 변환 필요
용도고정된 구조의 레코드자주 넣고 빼는 사전

⚠️ 사용자 입력을 객체의 키로 쓸 때

사용자가 __proto__나 constructor를 키로 보내면 객체의 동작이 바뀌거나 검사 로직이 뚫릴 수 있습니다(프로토타입 오염, 78장). 키를 외부에서 받는 저장소는 Map이나 Object.create(null)을 쓰세요. Object.create(null)로 만든 객체는 프로토타입이 없어 toString 같은 게 딸려 오지 않습니다.

Set — 중복 없는 모음

Set은 값이 있는지만 빠르게 확인하는 자료구조입니다. 내부는 해시 테이블이라 has가 평균 즉시입니다. 배열의 includes는 앞에서부터 전부 확인합니다.

🛠️ 현장 노트 — 실무 선택 기준

  1. 구조가 고정된 데이터(API 응답 한 건, 컴포넌트 props) → 객체. JSON으로 바로 오가고 구조 분해가 편합니다.
  2. 키가 동적으로 계속 늘고 줄어드는 사전(id → 항목 조회표, 캐시) → Map.
  3. "있냐 없냐"만 묻는 것(선택된 ID 목록, 방문한 URL) → Set.
  4. 순서와 인덱스가 의미 있는 목록(화면에 그릴 리스트) → 배열. React 렌더링에는 결국 배열이 필요합니다.
  5. React state에 Map·Set을 담을 땐 새 인스턴스를 만들어 교체해야 리렌더링됩니다 (setSel(new Set(sel).add(id))). 기존 것을 add만 하면 참조가 같아 화면이 안 바뀝니다.

📌 요약

  • 자료구조 선택은 "무엇을 자주 할 것인가"로 정한다.
  • 배열은 인덱스 접근이 즉시, 앞쪽 삽입·삭제가 비싸다(unshift/shift).
  • delete arr[i]는 구멍을 만들어 엔진 최적화를 깬다. splice·filter를 쓴다.
  • 해시 테이블은 키를 숫자로 바꿔 자리를 계산한다. 평균 즉시 조회.
  • 반복문 안의 find/includes는 대표적 성능 함정. Map·Set으로 바꾼다.
  • 객체 키 순서에는 규칙이 있다: 정수형 키 오름차순 → 문자열 키 삽입순 → 심볼.
  • 키를 외부 입력에서 받으면 Map 또는 Object.create(null).
