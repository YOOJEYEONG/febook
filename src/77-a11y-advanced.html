🇰🇷 한국의 기준

11장에서 말했듯 「장애인차별금지법」에 따라 웹 접근성 제공 의무가 있고, 국내 기술 기준으로 KWCAG(한국형 웹 콘텐츠 접근성 지침)가 국가표준으로 제정되어 있습니다. KWCAG는 WCAG를 기반으로 하므로 WCAG AA를 목표로 하면 대체로 함께 충족됩니다. 공공기관 프로젝트에서는 접근성 인증이 요구되기도 합니다.

포커스 관리

🎯 SPA에서 가장 많이 깨지는 부분입니다

키보드 사용자에게 포커스는 커서입니다. 포커스를 잃으면 지금 어디 있는지 모르게 되고, 다시 Tab을 처음부터 눌러야 합니다.

상황해야 할 일
페이지 이동(68장)새 페이지의 제목이나 main으로 포커스 이동
모달 열기모달 안 첫 요소로 이동, 안에 가두기
모달 닫기열었던 버튼으로 되돌리기 ← 자주 빠뜨립니다
항목 삭제다음(또는 이전) 항목으로 이동. 안 하면 포커스가 body로 튑니다
새 콘텐츠 추가필요하면 그 콘텐츠로 이동하거나 aria-live로 알림
오류 발생첫 오류 필드로 이동(62장)
모달의 포커스 처리 
function Modal({ isOpen, onClose, children }) {
  const dialogRef = useRef(null);
  const previousFocus = useRef(null);

  useEffect(() => {
    if (!isOpen) return;

    previousFocus.current = document.activeElement;   // ① 현재 위치 기억
    dialogRef.current?.focus();                        // ② 모달로 이동

    return () => {
      previousFocus.current?.focus();                  // ③ 닫으면 되돌리기
    };
  }, [isOpen]);
}

✨ <dialog>를 쓰면 대부분 공짜입니다

40장에서 말했듯 <dialog>의 showModal()은 포커스 가두기·Esc 닫기·배경 비활성화를 브라우저가 처리합니다. 직접 구현하면 반드시 무언가를 빠뜨립니다.
직접 만들어야 한다면 Radix UI·React Aria 같은 접근성이 검증된 라이브러리를 쓰세요. "모달 하나쯤이야" 하고 만든 것이 키보드 사용자를 갇히게 만드는 일이 매우 흔합니다.

건너뛰기 링크 — 모든 사이트에 필요합니다 
<a href="#main" class="skip-link">본문으로 건너뛰기</a>
<nav>… 링크 30개 …</nav>
<main id="main" tabindex="-1">…</main>
.skip-link {
  position: absolute;
  left: -9999px;
}
.skip-link:focus {
  left: 8px; top: 8px;      /* 포커스를 받으면 나타납니다 */
  background: white; padding: 8px; z-index: 999;
}

키보드 사용자가 매 페이지마다 메뉴 30개를 Tab으로 지나가지 않아도 되게 합니다. 평소에는 보이지 않다가 Tab을 처음 누르면 나타납니다.

🙈 display: none으로 숨기면 안 됩니다

건너뛰기 링크나 스크린 리더 전용 텍스트를 display: none으로 숨기면 스크린 리더에서도 사라집니다(5장). 위처럼 화면 밖으로 밀어내는 방식을 써야 합니다. 이 패턴을 보통 .sr-only 또는 .visually-hidden 클래스로 만들어 둡니다.

동적 콘텐츠 알리기

// 검색 결과 개수처럼 '알면 좋은' 변화
<div aria-live="polite" aria-atomic="true">
  {results.length}개의 결과를 찾았습니다
</div>

// 오류처럼 '즉시 알아야 하는' 것
<div role="alert">저장에 실패했습니다</div>

// 로딩 중
<div aria-busy="true" aria-live="polite">불러오는 중…</div>

📢 live 영역은 미리 존재해야 합니다

// ❌ 요소 자체가 새로 생기면 읽히지 않을 수 있습니다
{error && <div role="alert">{error}</div>}

// ✅ 컨테이너는 항상 두고 내용만 바꿉니다
<div role="alert">{error}</div>

스크린 리더는 이미 감시 중이던 영역의 변화를 알립니다. 영역 자체가 새로 나타나면 놓칠 수 있습니다.
그리고 남용하지 마세요. 모든 변화를 알리면 끊임없이 떠드는 화면이 되어 오히려 못 씁니다.

📚 패턴은 외우지 말고 찾아보세요

W3C ARIA 저작 실무 가이드(APG)에 탭·아코디언·콤보박스·트리·모달 등 거의 모든 패턴의 필요한 ARIA 속성과 키보드 동작이 예제와 함께 정리되어 있습니다.
직접 만들기 전에 반드시 확인하세요. 화살표 키 동작, aria-* 조합 같은 것을 감으로 만들면 거의 항상 틀립니다.

직접 테스트하기

🧪 5분 점검

  1. Tab만으로 처음부터 끝까지 써 보기 — 가장 효율적입니다(11장)
  2. 브라우저 확대 200%로 보기 — 잘리거나 겹치는 곳이 있는가
  3. 이미지를 끄고 보기 — alt만으로 이해되는가
  4. 흑백으로 보기 — 색만으로 정보를 전달하는 곳이 있는가 (DevTools의 렌더링 패널에서 색각 이상 시뮬레이션 가능)
  5. 스크린 리더로 들어 보기

🛠️ 현장 노트 — 실무에서 통하는 접근

  1. 처음부터 챙기세요. 나중에 고치는 비용이 훨씬 큽니다. "출시 전에 접근성 점검"은 대개 실패합니다.
  2. 시맨틱 HTML이 80%입니다. 11장의 기본만 지켜도 대부분 해결됩니다. ARIA는 그다음입니다.
  3. 검증된 컴포넌트 라이브러리를 쓰세요. 모달·드롭다운·콤보박스를 직접 만드는 것은 생각보다 훨씬 어렵습니다.
  4. 린터를 켜세요. jsx-a11y가 작성 시점에 잡아 줍니다.
  5. 완벽할 필요 없습니다. 이번 주에 하나 고치는 것이 "언젠가 전부"보다 낫습니다.

접근성은 체크리스트가 아니라 사람에 관한 것입니다. "규정을 통과했는가"가 아니라 "실제로 쓸 수 있는가"를 물어야 합니다.

📌 요약

  • WCAG 네 원칙: 인식 가능·운용 가능·이해 가능·견고함. 실무 목표는 AA.
  • 포커스 관리가 SPA에서 가장 많이 깨진다. 모달은 닫을 때 원래 위치로 되돌린다.
  • <dialog>나 검증된 라이브러리를 쓰면 대부분 공짜로 해결된다.
  • 건너뛰기 링크는 화면 밖으로 밀어내 숨긴다. display: none은 안 된다.
  • aria-live 영역은 미리 존재해야 하고, 남용하면 오히려 방해가 된다.
  • UI 패턴은 ARIA APG에서 찾아본다. 감으로 만들면 틀린다.
  • 스크린 리더로 10분만 써 보면 가장 많이 배운다.
  • 자동 도구는 절반도 못 잡는다. 사람의 확인이 필요하다.
