🖥️ 서버 설정이 필요합니다

사용자가 example.com/about을 주소창에 직접 입력하면 브라우저는 서버에 그 경로를 요청합니다. 그런데 SPA에는 index.html 하나뿐이라 서버는 404를 반환합니다.
해결: 서버가 모든 경로에 index.html을 돌려주도록 설정합니다. 그러면 JS가 로드된 뒤 라우터가 주소를 보고 맞는 화면을 그립니다. Vercel·Netlify 같은 서비스는 대개 자동으로 처리하지만, 직접 서버를 운영한다면 반드시 설정해야 합니다. "새로고침하면 404"의 원인이 이것입니다.

React Router 기본

import { BrowserRouter, Routes, Route, Link, NavLink } from "react-router-dom";

function App() {
  return (
    <BrowserRouter>
      <nav>
        <Link to="/">홈</Link>
        <NavLink to="/about" className={({ isActive }) => isActive ? "active" : ""}>
          소개
        </NavLink>
      </nav>

      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/about" element={<About />} />
        <Route path="/products/:id" element={<ProductDetail />} />
        <Route path="*" element={<NotFound />} />
      </Routes>
    </BrowserRouter>
  );
}

🔗 <a href>가 아니라 <Link>

일반 <a>를 쓰면 페이지가 통째로 새로고침됩니다. SPA의 이점이 전부 사라지고 상태도 날아갑니다.
단, 외부 사이트로 나가는 링크는 <a>가 맞습니다.
<NavLink>는 현재 경로와 일치하면 활성 표시를 해 줍니다. 접근성을 위해 aria-current="page"도 자동으로 붙여 줍니다.

동적 세그먼트와 쿼리

// 경로: /products/:id
function ProductDetail() {
  const { id } = useParams();                       // "42" — 항상 문자열입니다
  const navigate = useNavigate();
  const [searchParams, setSearchParams] = useSearchParams();

  const tab = searchParams.get("tab") ?? "info";     // /products/42?tab=reviews

  const { data } = useQuery({
    queryKey: ["product", id],                       // 67장 — id를 키에 포함
    queryFn: () => fetchProduct(id)
  });

  return (
    <>
      <Tabs value={tab} onChange={(next) => setSearchParams({ tab: next })} />
      <button onClick={() => navigate(-1)}>뒤로</button>
      <button onClick={() => navigate("/cart")}>장바구니로</button>
      <button onClick={() => navigate("/login", { replace: true })}>
        로그인 (히스토리에 남기지 않음)
      </button>
    </>
  );
}

🔍 URL을 상태 저장소로 쓰세요 (65장)

검색어·필터·정렬·페이지·열린 탭은 URL 쿼리에 두는 것이 맞습니다.

  • 공유 가능 — 링크를 보내면 상대도 같은 화면을 봅니다
  • 새로고침해도 유지됩니다
  • 뒤로 가기가 자연스럽게 동작합니다
  • 북마크할 수 있습니다

useParams()의 값은 항상 문자열입니다. 숫자로 쓰려면 Number(id)로 변환하고, 사용자가 임의의 값을 넣을 수 있다는 점(/products/abc)도 처리해야 합니다.

중첩 라우트

<Routes>
  <Route path="/" element={<Layout />}>          {/* 공통 레이아웃 */}
    <Route index element={<Home />} />
    <Route path="products" element={<ProductLayout />}>
      <Route index element={<ProductList />} />
      <Route path=":id" element={<ProductDetail />} />
    </Route>
    <Route path="*" element={<NotFound />} />
  </Route>
</Routes>

// 부모 컴포넌트에서 자식이 그려질 자리를 지정합니다
function Layout() {
  return (
    <>
      <Header />
      <main><Outlet /></main>      {/* ← 자식 라우트가 여기 렌더링됩니다 */}
      <Footer />
    </>
  );
}

🎁 중첩 라우트의 진짜 이점

경로가 바뀌어도 공통 레이아웃은 다시 렌더링되지 않습니다. 헤더의 검색어 입력, 사이드바 스크롤 위치, 열린 메뉴 상태가 그대로 유지됩니다. 각 페이지가 헤더를 따로 그리면 이 모든 것이 매번 초기화됩니다.

코드 분할

import { lazy, Suspense } from "react";

// 34·47장의 동적 import가 여기서 쓰입니다
const AdminPage = lazy(() => import("./pages/AdminPage"));
const Editor = lazy(() => import("./pages/Editor"));

<Routes>
  <Route path="/" element={<Home />} />              {/* 즉시 로드 */}
  <Route path="/admin" element={
    <Suspense fallback={<PageSkeleton />}>
      <AdminPage />
    </Suspense>
  } />
</Routes>

📦 라우트가 가장 자연스러운 분할 지점입니다

사용자의 5%만 들어가는 관리자 페이지 코드를 나머지 95%에게 보낼 이유가 없습니다. 라우트 단위로 나누면 초기 번들이 크게 줄어듭니다.
다만 너무 잘게 나누면 화면을 넘길 때마다 로딩이 생겨 오히려 답답합니다. 큰 페이지 몇 개부터 시작하세요. 사용자가 이동할 것 같은 시점에 미리 불러오는(prefetch) 기법도 있습니다.

보호된 라우트

function RequireAuth({ children }) {
  const { user, isLoading } = useAuth();
  const location = useLocation();

  if (isLoading) return <Spinner />;      // ⭐ 확인 중에 로그인으로 보내면 안 됩니다
  if (!user) {
    // 로그인 후 원래 가려던 곳으로 돌려보내기 위해 위치를 넘깁니다
    return <Navigate to="/login" state={{ from: location }} replace />;
  }
  return children;
}

<Route path="/mypage" element={
  <RequireAuth><MyPage /></RequireAuth>
} />

🔓 프론트엔드 라우트 보호는 보안이 아닙니다

1장의 원칙 그대로입니다. 사용자는 JavaScript를 수정하거나 API를 직접 호출할 수 있습니다. 라우트 가드는 사용자 경험을 위한 것이지 접근 제어가 아닙니다.
실제 보호는 서버에서 합니다. API가 권한을 검사하지 않으면 관리자 페이지 화면을 못 보게 해도 데이터는 그대로 가져갈 수 있습니다(78장).

라우팅의 접근성

♿ 대부분의 SPA가 빠뜨리는 부분

전통적인 페이지 이동에서는 브라우저가 포커스를 문서 처음으로 옮기고 스크린 리더가 새 페이지 제목을 읽어 줍니다. SPA에서는 아무 일도 일어나지 않습니다. 스크린 리더 사용자는 화면이 바뀐 것조차 모릅니다.

function RouteAnnouncer({ title }) {
  const location = useLocation();
  const headingRef = useRef(null);

  useEffect(() => {
    document.title = `${title} | 내 서비스`;   // ① 문서 제목 갱신
    headingRef.current?.focus();               // ② 포커스를 새 콘텐츠로
    window.scrollTo(0, 0);                     // ③ 스크롤 맨 위로
  }, [location.pathname, title]);

  return <h1 ref={headingRef} tabIndex={-1}>{title}</h1>;
  //                          ↑ 스크립트로만 포커스 가능 (11장)
}

스크롤 위치도 직접 관리해야 합니다. 페이지를 이동했는데 스크롤이 중간에 남아 있는 것은 흔한 SPA 버그입니다. 반대로 뒤로 갈 때는 원래 위치로 복원하는 것이 좋습니다.

🛠️ 현장 노트

  1. 404 라우트를 반드시 만드세요. 없으면 오타 주소에서 빈 화면이 나옵니다.
  2. 로딩 중 판단을 서두르지 마세요. 인증 확인 중에 로그인 페이지로 보내면 새로고침할 때마다 로그인 화면이 번쩍입니다.
  3. 경로 문자열을 상수로 관리하세요. ROUTES.PRODUCT_DETAIL(id) 형태면 오타가 사라집니다.
  4. 이동 후 스크롤과 포커스를 처리하세요.
  5. 새로고침 404가 나면 서버의 폴백 설정을 확인하세요.

📌 요약

  • SPA 라우팅은 History API 위에 만들어져 있다(40장).
  • 서버가 모든 경로에 index.html을 주도록 설정해야 새로고침 404가 없다.
  • 내부 이동은 <Link>, 외부는 <a>.
  • useParams()는 항상 문자열을 준다.
  • 검색·필터·페이지는 URL 쿼리에 두어 공유·복원·뒤로 가기를 얻는다.
  • 중첩 라우트는 레이아웃과 그 상태를 유지시켜 준다.
  • 라우트는 코드 분할의 자연스러운 경계다.
  • 라우트 가드는 보안이 아니다. 서버가 권한을 검사해야 한다.
  • 이동 후 제목·포커스·스크롤을 직접 처리해야 접근성이 확보된다.
