이 챕터에서 배우는 것

  • 제네릭이 어떤 문제를 푸는지
  • 타입 매개변수와 제약(extends)
  • 실무에서 쓰는 제네릭 패턴
  • 제네릭을 쓰지 말아야 할 때

읽는 데 약 30분 · 사전 지식: 기본 타입·함수 타입(51장), interface와 type(52장)

문제 상황

지금까지는 타입을 정확히 하나로 정해 적었습니다. 그런데 어떤 함수는 무엇을 넣어도 같은 일을 합니다. "배열의 첫 요소를 꺼낸다"는 문자열 배열이든 숫자 배열이든 똑같이 동작합니다. 이런 함수에 타입을 붙이려 하면 곤란해집니다. 타입마다 함수를 따로 만들자니 끝이 없고, any로 퉁치자니 타입 정보가 사라집니다.

배열의 첫 요소를 반환하는 함수 
// 시도 1: 타입마다 따로 만들기 — 끝이 없습니다
function firstString(arr: string[]): string { return arr[0]; }
function firstNumber(arr: number[]): number { return arr[0]; }
function firstUser(arr: User[]): User { return arr[0]; }

// 시도 2: any — 타입 정보가 사라집니다
function firstAny(arr: any[]): any { return arr[0]; }
const item = firstAny(["a", "b"]);
item.toFixed(2);      // 오류가 안 납니다. 실행하면 터집니다

// ✅ 제네릭
function first<T>(arr: T[]): T {
  return arr[0];
}
const name2 = first(["a", "b"]);     // string 으로 추론
const num = first([1, 2, 3]);         // number 로 추론
// name2.toFixed(2);                  ❌ 즉시 오류

▶ Playground에 붙여 보세요. 맨 위에 type User = { name: string };을 추가하면 됩니다. item에 마우스를 올리면 any, name2에 올리면 string이 보입니다. 같은 일을 하는 함수인데 결과에 대해 아는 정보가 완전히 다릅니다. 함수 이름 뒤의 <T>가 이 차이를 만듭니다. T는 "지금은 정하지 않은 어떤 타입"을 가리키는 이름이고, first(["a", "b"])처럼 호출하는 순간 TypeScript가 인자를 보고 T를 string으로 채워 넣습니다.

📦 제네릭은 타입의 매개변수입니다

함수가 값을 나중에 받듯이, 제네릭은 타입을 나중에 받습니다. <T>는 "지금은 모르지만 쓸 때 정해질 타입"이라는 뜻입니다.
그리고 그 타입이 입력과 출력을 연결합니다. "들어온 배열의 요소 타입 = 나가는 값의 타입"이라는 관계를 표현하는 것이 제네릭의 본질입니다.

비유하자면 제네릭 함수는 빈칸이 있는 서식입니다. 택배 송장의 "내용물: ______" 칸처럼, 서식을 만들 때는 비워 두고 실제로 보낼 때 채웁니다. 한 번 "책"이라고 적으면 그 송장의 다른 칸(파손 주의 여부, 보험 품목)도 모두 "책"을 기준으로 맞춰집니다. T를 한 번 정하면 매개변수와 반환값에 쓰인 모든 T가 같은 타입으로 채워지는 것도 이와 같습니다.

🤔 자주 하는 오해 — 제네릭은 any의 다른 이름이다

오해 — <T>는 무엇이든 받을 수 있으니 결국 any와 같다. 사실 — 받는 범위는 비슷해 보여도 결과가 다릅니다. any는 들어온 타입을 잊어버리고, 제네릭은 기억했다가 반환값에 그대로 전달합니다. 그래서 first([1, 2])의 결과에 문자열 메서드를 쓰면 즉시 오류가 납니다. 또 제네릭은 실행 중에 무언가를 하는 기능이 아니라, 50장의 다른 타입처럼 빌드 후 사라집니다.

기본 문법

꺾쇠(<>)는 타입 매개변수를 선언하는 자리입니다. 함수 이름 뒤, interface·type·class 이름 뒤에 올 수 있습니다. 51장의 Array<number>도 이미 만들어진 제네릭 타입 Array에 number를 채워 넣은 것이었습니다.

// 함수
function identity<T>(value: T): T { return value; }

// 호출 — 대개 추론에 맡깁니다
identity("hello");           // T = string 으로 추론
identity<string>("hello");   // 명시할 수도 있습니다

// 타입 매개변수 여러 개
function pair<K, V>(key: K, value: V): [K, V] {
  return [key, value];
}
pair("age", 20);             // [string, number]

// 인터페이스·타입에도
interface Box<T> {
  value: T;
}
type Nullable<T> = T | null;

const box: Box<string> = { value: "hello" };
const maybeUser: Nullable<User> = null;

// 클래스에도
class Stack<T> {
  private items: T[] = [];
  push(item: T): void { this.items.push(item); }
  pop(): T | undefined { return this.items.pop(); }
}
const stack = new Stack<number>();

호출할 때 identity<string>("hello")처럼 직접 채울 수도 있지만, 대개는 인자에서 추론에 맡깁니다. 직접 채워야 하는 경우는 new Stack<number>()처럼 인자가 없어 단서가 없을 때입니다. Box<string>은 "내용물이 문자열인 상자", Nullable<User>는 "User이거나 null"입니다. 같은 틀(Box)을 내용물만 바꿔 여러 번 쓸 수 있다는 것이 핵심입니다.

🔤 이름 관례

  • T — Type (가장 흔함)
  • K, V — Key, Value
  • E — Element
  • R — Return

다만 의미가 있으면 풀어서 쓰는 편이 읽기 좋습니다. <TData, TError>처럼요. TanStack Query 같은 라이브러리가 이 방식을 씁니다.

제약 — extends

아무 타입이나 받을 수 있다는 것은 반대로 말하면 그 타입에 대해 아무것도 모른다는 뜻입니다. T가 숫자일 수도 있으니 .length를 쓸 수 없습니다. 이럴 때 extends로 "이런 모양을 가진 타입만 받겠다"고 조건을 겁니다. 놀이기구 입구의 "키 120cm 이상"과 같습니다. 누가 탈지는 모르지만 최소 조건은 보장됩니다.

// ❌ T가 무엇이든 될 수 있어 length를 쓸 수 없습니다
function logLengthBad<T>(value: T) {
  console.log(value.length);   // ❌ Property 'length' does not exist on type 'T'
}

// ✅ "length를 가진 것"으로 제한합니다
function logLength<T extends { length: number }>(value: T) {
  console.log(value.length);   // ✅
}
logLength("hello");        // ✅ 문자열에는 length가 있습니다
logLength([1, 2, 3]);      // ✅
logLength(42);             // ❌ 숫자에는 length가 없습니다

▶ Playground에 붙여 보세요. 첫 함수 안쪽과 마지막 줄 두 곳에서만 오류가 납니다. 여기서 extends는 클래스 상속(32장)과 같은 단어지만 뜻이 조금 다릅니다. "~에 들어맞는"으로 읽으면 됩니다. 52장의 구조적 타이핑 덕분에 length 속성만 있으면 문자열이든 배열이든 직접 만든 객체든 통과합니다.

다음 예제의 keyof T는 "T의 키 이름들의 유니온"입니다. { id, name, isAdmin }이라면 "id" | "name" | "isAdmin"이 됩니다(55장에서 자세히). T[K]는 "T에서 K 키의 값 타입"입니다. 처음 보면 어렵지만, 한 줄씩 마우스를 올려 결과를 확인하면 금방 익숙해집니다.

keyof 와 함께 — 매우 자주 쓰는 패턴 
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { id: 1, name: "홍길동", isAdmin: true };

const id = getProperty(user, "id");         // number
const userName = getProperty(user, "name"); // string
const admin = getProperty(user, "isAdmin"); // boolean
// getProperty(user, "age");                ❌ 없는 키는 자동 완성에도 안 나옵니다

🔑 이 예제가 제네릭의 힘을 가장 잘 보여 줍니다

getProperty(user, "id")가 number임을 아는 것이 핵심입니다. any였다면 아무것도 몰랐을 것이고, 오버로드로 하나하나 정의했다면 끝이 없었을 것입니다. 키에 따라 반환 타입이 달라지는 관계를 한 줄로 표현한 것입니다.

기본값

함수 매개변수에 기본값을 줄 수 있듯이 타입 매개변수에도 기본값을 줄 수 있습니다. <T = unknown>은 "아무것도 안 채우면 unknown으로 하라"는 뜻입니다. 쓰는 쪽이 매번 꺾쇠를 채우지 않아도 되어 편합니다.

interface ApiResponse<T = unknown> {
  data: T;
  message: string;
}

const a: ApiResponse = { data: "아무거나", message: "ok" };        // T = unknown
const b: ApiResponse<User[]> = { data: [], message: "ok" };        // T = User[]

기본값으로 any가 아니라 unknown을 쓴 것에 주목하세요. 내용물 타입을 지정하지 않고 쓰면 data는 확인 전에는 쓸 수 없는 값이 되어, "타입을 깜빡 안 채운" 실수가 조용히 검사를 끄는 일을 막습니다(50장의 any vs unknown).

실전 패턴

실무에서 직접 제네릭을 만드는 곳은 대체로 세 군데입니다. 서버 통신 함수, 배열을 가공하는 유틸리티, 그리고 여러 데이터에 재사용하는 React 컴포넌트입니다. 세 예제 모두 "쓰는 쪽이 넘긴 타입이 결과에 그대로 전달된다"는 같은 구조를 갖고 있습니다.

① API 클라이언트 
async function apiGet<T>(path: string): Promise<T> {
  const response = await fetch(path);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json() as Promise<T>;
}

const users = await apiGet<User[]>("/api/users");     // User[] 로 다뤄집니다
const post = await apiGet<Post>("/api/posts/1");

⚠️ 위 코드는 거짓말할 수 있습니다

as Promise<T>는 타입 단언(54장)으로, "내가 보증한다"는 선언일 뿐 실제로 검사하지 않습니다. 서버가 다른 형태를 보내도 통과합니다. 50장에서 말한 "타입은 런타임에 사라진다"는 원칙 그대로입니다.
안전하게 하려면 Zod 같은 라이브러리로 실제 값을 검증해야 합니다.

② 배열 유틸리티 
function groupBy<T, K extends string | number>(
  items: T[],
  getKey: (item: T) => K
): Record<K, T[]> {
  const result = {} as Record<K, T[]>;
  for (const item of items) {
    const key = getKey(item);
    (result[key] ??= []).push(item);
  }
  return result;
}

const byCategory = groupBy(products, p => p.category);
//    ↑ 반환 타입이 자동으로 맞춰집니다

groupBy는 타입 매개변수가 두 개입니다. T는 배열 요소, K는 묶는 기준 값이고, K에는 "문자열이나 숫자만"이라는 제약이 걸려 있습니다. 반환 타입 Record<K, T[]>는 "키가 K, 값이 T의 배열인 객체"로 55장의 유틸리티 타입입니다. ??=는 "값이 없으면 오른쪽 값을 넣는다"는 논리 할당 연산자입니다(26장). 이런 함수를 한 번 제네릭으로 만들어 두면 상품이든 회원이든 같은 함수로 묶을 수 있습니다.

③ React에서 (56장에서 자세히 — 지금은 훑어만 보세요) 
interface ListProps<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
  keyExtractor: (item: T) => string;
}

function List<T>({ items, renderItem, keyExtractor }: ListProps<T>) {
  return <ul>{items.map(item =>
    <li key={keyExtractor(item)}>{renderItem(item)}</li>
  )}</ul>;
}

// 사용할 때 item의 타입이 정확히 추론됩니다
<List
  items={users}
  keyExtractor={u => String(u.id)}
  renderItem={u => <span>{u.name}</span>}   // u는 User 로 추론
/>

React 문법은 8부에서 배우므로 지금은 흐름만 보세요. items에 회원 배열을 넘기면 T가 회원 타입으로 정해지고, 그 정보가 renderItem과 keyExtractor의 매개변수 u까지 전달됩니다. 그래서 u.를 입력하면 회원의 속성이 자동 완성됩니다. 같은 List에 상품 배열을 넘기면 이번에는 u가 상품이 됩니다. 컴포넌트 하나를 여러 데이터에 재사용하면서도 타입 안전성을 잃지 않는 것, 이것이 제네릭이 주는 이득입니다.

제네릭을 쓰지 말아야 할 때

제네릭을 막 배우면 모든 함수에 <T>를 붙이고 싶어집니다. 하지만 제네릭은 코드를 읽는 사람에게 "여기 두 곳이 서로 연결되어 있다"는 신호입니다. 연결이 없는데 붙이면 읽는 사람만 헷갈립니다. 판단 기준은 간단합니다. T가 두 번 이상 등장하는지 세어 보세요.

🚫 타입 매개변수가 한 번만 쓰이면 필요 없습니다

// ❌ T가 매개변수에만 쓰이고 반환과 연결되지 않습니다
function log<T>(value: T): void {
  console.log(value);
}

// ✅ 그냥 이렇게 쓰면 됩니다
function log(value: unknown): void {
  console.log(value);
}

제네릭의 목적은 "두 곳 이상을 연결하는 것"입니다. 매개변수와 반환값, 또는 여러 매개변수 사이의 관계를 표현할 때만 의미가 있습니다. 연결하는 것이 없으면 복잡도만 늘어납니다.

앞의 log와 달리 first<T>(arr: T[]): T는 T가 매개변수와 반환값에 두 번 나옵니다. 그래서 의미가 있습니다. pair<K, V>(key: K, value: V): [K, V]도 K와 V가 각각 두 번씩 나옵니다. 코드 리뷰에서 "이 제네릭이 꼭 필요한가요?"라는 질문을 받는다면, 이렇게 T가 등장하는 횟수를 세어 답하면 됩니다.

🛠️ 현장 노트 — 제네릭과 친해지는 법

  1. 먼저 구체적인 타입으로 짜세요. string[]용으로 만들고, 나중에 다른 타입도 필요해지면 그때 T로 바꿉니다. 처음부터 일반화하려 하면 방향을 잃습니다.
  2. 이미 쓰고 있습니다. Array<T>, Promise<T>, useState<T>, Map<K,V>가 전부 제네릭입니다.
  3. 제약을 걸어 좁히세요. <T>보다 <T extends { id: number }>가 훨씬 다루기 쉽습니다.
  4. 남의 코드를 읽는 것이 먼저입니다. 직접 제네릭 유틸리티를 만들 일은 생각보다 드뭅니다. 라이브러리 타입 정의를 읽고 이해하는 능력이 더 자주 필요합니다.

어렵게 느껴지는 것이 정상입니다. 개념은 단순하지만(타입을 나중에 받는다) 실제 코드는 복잡해 보입니다. 당장 다 이해하지 못해도 사용은 할 수 있습니다. 만드는 것은 나중 일입니다.

📌 요약

  • 제네릭은 타입의 매개변수다. 값이 아니라 타입을 나중에 받는다.
  • 핵심 목적은 입력과 출력의 타입 관계를 표현하는 것이다.
  • any는 타입을 버리지만 제네릭은 보존한다.
  • extends로 제약을 걸어야 그 타입의 속성을 쓸 수 있다.
  • <T, K extends keyof T> 패턴으로 키에 따라 달라지는 반환 타입을 표현한다.
  • as 단언은 검사하지 않는다. 외부 데이터는 런타임 검증이 필요하다.
  • 타입 매개변수가 한 곳에서만 쓰이면 제네릭이 필요 없다.
